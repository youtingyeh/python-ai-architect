@section 開場：幾百種模型，該選哪一個？
打開任何 AI 新聞，你會被一堆名字淹沒：GPT-4o、Claude、Gemini、Llama、Qwen、Mistral、Phi、DeepSeek……每隔幾週就有新模型宣稱「打敗了所有對手」、「在某某排行榜拿下第一」。

如果你要為公司或自己的專案挑一個模型，該怎麼選？最大的？最新的？排行榜第一名的？

**答案是：都不一定。**選模型就像買車：跑車最快，但不適合載貨；卡車能載貨，但停車很痛苦；機車在市區最靈活，但不能上高速公路。**沒有「最好的車」，只有「最適合你需求的車」。**

這一課對應 Microsoft《Generative AI for Beginners》第 02 課，我們要學一套**有系統的選模型方法**：
1. 模型有哪幾大類？各有什麼優缺點？
2. 為什麼排行榜第一名，不一定適合你？
3. 「速度」要怎麼衡量？為什麼有兩種不同的快？
4. 「成本」要怎麼算？為什麼最便宜的 API 可能最貴？
5. 資料隱私和法規，怎麼影響選擇？
6. 怎麼設計一場公平的模型比賽？

這一課的觀念不只適用於選 AI 模型，也適用於任何技術選型：**先定義你的需求和評分標準，再用你自己的資料去測試。**

@section 模型的三大家族
今天的大型語言模型，大致可以分成三類。

**第一類：閉源旗艦模型（透過 API 使用）。**
例如 OpenAI 的 GPT 系列、Anthropic 的 Claude 系列、Google 的 Gemini 系列。

「閉源」的意思是：你拿不到模型本身（那幾千億個參數），只能透過網路 API 送出問題、拿回答案，按使用量付費。

- **優點**：能力最強，特別是複雜推理、寫程式、多語言、跨領域的知識。你不需要自己買顯示卡、架伺服器，打開就能用。
- **缺點**：單價較高；資料要傳到別人的伺服器；你無法修改模型內部；供應商可能隨時調整價格或停用舊版本。

**第二類：開放權重模型（可以下載自己架）。**
例如 Meta 的 Llama、阿里巴巴的 Qwen、Mistral、DeepSeek。

「開放權重」（Open-Weight）的意思是：模型的參數檔案可以免費下載，放到你自己的伺服器上執行。（注意：這和「開源」不完全一樣，因為訓練資料和訓練程式通常沒有公開，授權條款也各有限制。）

- **優點**：資料完全不離開你的機房；可以針對自己的領域深度微調（後面的課程會教）；長期大量使用時可能比較便宜。
- **缺點**：要自己準備昂貴的顯示卡（一個 700 億參數的模型，需要好幾張高階顯示卡才跑得動）；要有工程師負責維護、更新、監控。

**第三類：小型語言模型（SLM，Small Language Model）。**
例如微軟的 Phi 系列、Google 的 Gemma、Llama 的 80 億參數版，以及雲端上的輕量版本如 GPT-4o-mini、Gemini Flash。

這是近年成長最快的一類。參數只有幾十億，甚至可以在筆電或手機上執行。

- **優點**：非常快、非常便宜。對於**簡單、明確**的任務（例如分類、格式轉換、擷取特定欄位、簡短摘要），經過適當的提示或微調，準確率可以追上大模型，而速度和成本只要大模型的十分之一到三十分之一。
- **缺點**：複雜推理、長篇寫作、冷門知識比較弱。

**一個重要觀念**：很多任務根本不需要最強的模型。用旗艦模型做簡單分類，就像開跑車去巷口買早餐。

@section 為什麼排行榜第一名，不一定適合你？
很多團隊選模型時，直接打開公開的**排行榜**（Leaderboard），挑第一名。常見的排行榜和測驗包括：
- **Chatbot Arena**（LMSYS）：讓網友匿名比較兩個模型的回答，投票選出比較好的，累積成排名。
- **MMLU**：涵蓋 57 個學科（數學、歷史、法律、醫學……）的大型選擇題考試。
- **HumanEval**：寫程式的測驗，檢查模型寫的程式能不能通過測試。

這些**基準測試**（Benchmark）很有參考價值，但實務經驗反覆證明：**排行榜的名次，和模型在「你的特定任務」上的表現，往往沒有直接關係。**原因有三個：

**原因一：考的東西不一樣。**
MMLU 考的是英文的高中、大學學科選擇題。但你的需求可能是：「從繁體中文的醫療收據中，準確擷取健保代碼和自費金額，輸出成固定格式的 JSON」。一個學科考滿分的模型，不一定擅長嚴格遵守格式、不一定熟悉台灣的用語和單據格式。

就像一個學測滿級分的學生，不一定是最好的會計師。

**原因二：考題可能外洩了（基準測試污染）。**
這些測驗的題目是公開的，網路上到處都是。模型訓練時用了整個網路的資料，很可能**無意間（或刻意）看過這些考題**。結果分數虛高，就像學生考前拿到了考古題的答案。一遇到沒見過的真實資料，表現就打回原形。

經濟學有一條「**古德哈特定律**」（Goodhart's Law）：「當一個指標變成目標時，它就不再是一個好的指標。」大家都在拚排行榜，排行榜就越來越不能反映真實能力。

**原因三：每個模型的「脾氣」不同。**
不同模型對提示詞的寫法敏感程度不同。有的模型喜歡用 XML 標籤分段、有的喜歡 Markdown 格式、有的需要給範例才表現好。排行榜用的是統一的提示詞，不一定是每個模型最擅長的寫法。

**正確用法**：排行榜適合做**第一輪初篩**，從幾百個模型中挑出 3 到 4 個候選。**最終決定，一定要用你自己的真實資料來測。**

@section 速度：兩種不同的「快」
評估模型速度時，不能只看「平均回應幾秒」。生成式 AI 的速度有**兩個完全不同的指標**：

**① 首字延遲（TTFT，Time To First Token）。**
從送出請求，到收到**第一個字**花了多久。

這段時間主要花在：網路來回，以及模型「**閱讀**」你的整段輸入。模型讀輸入時可以平行計算（第 15 課：所有位置同時算），這個階段叫做「**預填充**」（Prefill）。輸入越長，這段時間越久。例如塞了 5 萬個 Token 的參考文件，首字延遲可能從 0.3 秒拉長到 5 秒以上。

**② 生成速度（TPS，Tokens Per Second）。**
開始輸出後，**每秒能產生幾個 Token**。

這時模型進入「**解碼**」（Decode）階段，必須一個字一個字生成（第 15 課：未來還沒發生）。每生成一個字，都要把整個模型（可能幾十 GB）從顯示卡記憶體搬到運算核心一次。所以速度主要受限於**記憶體搬運速度**，而不是計算速度。

**哪個比較重要？看你的產品。**

**情境 A：聊天介面（字會一個一個跳出來）。**
使用者對**首字延遲**非常敏感。只要 0.5 秒內畫面開始跳字，就算後面每秒只吐 25 個字（已經比人類閱讀速度快了），使用者也會覺得「秒回」。這種「邊產生邊顯示」的方式叫做**串流**（Streaming）。

**情境 B：後端批次處理（要等整份結果出來才能用）。**
例如要等模型產生完整的 JSON 才能解析、存進資料庫。這時重要的是**總時間**：

$$\text{總延遲} = \text{TTFT} + \frac{\text{輸出 Token 數}}{\text{TPS}}$$

**算一個例子**：TTFT = 0.5 秒、TPS = 50、輸出 500 個 Token。
總延遲 = 0.5 + 500 / 50 = 0.5 + 10 = **10.5 秒**。

可以看到，輸出長度是主要瓶頸。如果把輸出精簡到 100 個 Token（只輸出必要欄位），總延遲降到 0.5 + 2 = **2.5 秒**。所以「要求模型簡潔回答」是最有效的加速方法之一。

另外，評估速度時要看「**P95 延遲**」，意思是「95% 的請求在多少秒內完成」。平均值可能被少數很快的請求拉低，掩蓋了那些讓使用者等很久的慢請求。

@section 成本：最便宜的 API，可能最貴
**陷阱一：輸入和輸出的價格不一樣。**

幾乎所有 AI API 的**輸出 Token 單價，是輸入 Token 的 3 到 5 倍**。例如某模型：輸入每百萬 Token 2.5 美元，輸出每百萬 Token 10 美元。

為什麼輸出比較貴？原因就是上一段說的：輸入可以平行一次算完，顯示卡利用率高；輸出必須一個一個慢慢生成，顯示卡大部分時間在等記憶體搬資料，效率低，單位成本就高。

**實務意義**：要省錢，「要求模型回答簡潔、只輸出必要內容」往往比「刪減輸入的參考資料」更有效。

**陷阱二：只算 API 帳單，忘了算「人工修正」的成本。**

這是最常被忽略、也最重要的一點。用一個例子說明：

你要處理 **10,000 筆**客服退貨申請，讓 AI 判斷是否符合退貨條件。

**模型 A（輕量、便宜）**：
- API 費用：5 美元
- 準確率：82%，有 1,800 筆判斷錯誤
- 每筆錯誤需要客服人員花 3 分鐘重新審核，假設人工成本每筆 1 美元
- 人工成本：1,800 美元
- **總成本：1,805 美元**

**模型 B（旗艦、貴 10 倍）**：
- API 費用：50 美元
- 準確率：98%，只有 200 筆錯誤
- 人工成本：200 美元
- **總成本：250 美元**

API 貴了 10 倍的模型 B，總成本反而只有模型 A 的**七分之一**！

**真實的總成本**（TCO，Total Cost of Ownership，總體擁有成本）要把所有東西算進去：
- API 費用（或自建伺服器的顯示卡、電費、維護人力）；
- 錯誤造成的人工修正成本；
- 錯誤造成的商業損失（客戶不滿、賠償）。

當然，反過來也可能成立：如果任務很簡單、輕量模型準確率也有 99%，那選貴的就是浪費。**關鍵是用自己的資料實測準確率，再算總帳。**

@section 上下文長度與資料隱私：兩道硬門檻
除了準確率、速度、成本，還有兩個條件常常是「**一票否決**」的。

**門檻一：上下文長度，宣稱的不等於好用的。**

現在的模型紛紛宣稱支援 12.8 萬、20 萬、甚至 100 萬個 Token 的上下文視窗（第 13 課）。但「塞得進去」不等於「讀得懂」。

一篇有名的研究論文《Lost in the Middle》（迷失在中間）發現：當關鍵資訊藏在一篇超長文件的**中間**時，許多模型找到它的能力會明顯下降；放在開頭或結尾時則表現較好。就像人讀一本很厚的書，開頭和結尾記得清楚，中間容易模糊。

業界常用「**大海撈針**」（Needle In A Haystack）測試：在一大段無關文字中藏一句關鍵資訊，看模型能不能找到。

而且，每次請求都送 10 萬字，首字延遲和費用都會暴增上百倍。所以實務上，通常會搭配 **RAG**（只挑相關段落送給模型）和**提示詞快取**（Prompt Caching，重複的長前綴只計算一次、費用打折）來控制成本。

**門檻二：資料隱私與法規。**

金融、醫療、政府、半導體等產業，常受到嚴格的法規限制（例如歐盟的 GDPR 個資保護法、美國的 HIPAA 醫療隱私法），或公司的機密保護政策，禁止把客戶個資或核心技術傳到外部。

選模型時要確認三個層級：
1. **免費版或消費者版網頁介面**：你輸入的內容可能被供應商保留，並用來訓練未來的模型。**不要在這裡輸入機密資料。**
2. **企業版雲端 API**：例如 Azure OpenAI，或簽了「零資料留存」（Zero Data Retention）協議的企業方案。資料在處理後即刻刪除，不用於訓練。大多數企業應用可以接受。
3. **資料絕對不能離開公司機房**：有些法規或政策要求完全隔離（叫做地端部署，On-Premise）。這時所有雲端 API 都出局，只能選開放權重模型，部署在自己的伺服器上。

@section 怎麼辦一場公平的模型比賽？
有了上面的觀念，一套嚴謹的選型流程分成四步：

**第一步：先定規則，再比賽。**
在測試任何模型**之前**，先做兩件事：
- **收集黃金測試集**（Golden Test Set）：從真實業務中挑出 50 到 200 筆有代表性的案例，包括：
  - 一般常見的案例；
  - **邊界案例**（Edge Case）：格式奇怪的、資料不完整的、模稜兩可的；
  - 惡意或刁鑽的輸入。
  每筆都要準備好「正確答案」。
- **制定評分標準**（Rubric）：例如「JSON 格式正確得 1 分、金額完全正確得 2 分、沒有編造原文沒有的資訊得 2 分，滿分 5 分」。

為什麼要先定規則？因為如果先看到結果再定標準，很容易不自覺地偏向自己喜歡的模型。

**第二步：盲測。**
把同一批測試資料送給 3 到 4 個候選模型。把模型名稱遮起來，改叫 A、B、C，再請程式自動檢查（格式、精確答案）加上領域專家人工評分。專家不知道哪個是哪個，就不會因為品牌偏見而影響判斷。

記錄每個模型的：平均分數、P95 延遲、每千次呼叫的成本。整理成一張**評估矩陣**，依需求給各項加權（例如準確率 50%、成本 30%、速度 20%），算出總分。

**第三步：考慮混搭（模型路由）。**
最佳解常常不是「整個系統只用一個模型」，而是：
- 80% 的簡單問題交給又快又便宜的小模型；
- 20% 的複雜問題才轉給旗艦模型。
這叫做「**模型路由**」（Model Routing）。也可以先讓小模型試，信心不足時再升級給大模型，叫做「**階梯式呼叫**」（Cascading）。

**第四步：鎖定版本。**
上線時，程式裡要寫**帶日期的精確版本名稱**，例如 `gpt-4o-2024-08-06`，而不是 `gpt-4o-latest` 這種「最新版」別名。

為什麼？因為「最新版」背後的模型，供應商隨時可能更新。也許某天半夜它換了新版本，輸出格式稍微改變，你的程式解析就壞了，而你完全不知道發生了什麼。這叫做「**靜默迴歸**」（Silent Regression）。

鎖定版本後，每次要升級，先用黃金測試集重跑一次，確認沒有退步再切換。這叫做**迴歸測試**（Regression Test）。

@section 動動腦：幫這些團隊選模型
**情境一**：一家電商要把賣家寫的雜亂商品描述，轉成標準的 JSON 規格表（品牌、尺寸、顏色、材質）。每天 5 萬筆，資料不敏感。
→ 任務明確、量大、格式固定。**先試小模型**（例如 GPT-4o-mini 或 Gemini Flash），用 100 筆真實商品描述建立測試集。如果準確率夠高，成本只有旗艦的幾十分之一。

**情境二**：一家醫院要用 AI 摘要病歷，法規要求病患資料不能離開醫院。
→ 雲端 API 全部出局（即使有零資料留存協議，可能仍不符合院內規定）。選**開放權重模型**部署在院內伺服器，並且一定要有醫師審核摘要結果。

**情境三**：一家法律事務所要分析長達 300 頁的合約，找出潛在風險條款。
→ 需要強推理能力和長上下文。選**旗艦模型**，但要實測「條款藏在中間」時能不能找到。考慮先把合約切段、用 RAG 挑出相關段落，而不是整本塞進去。

**情境四**：主管看到某模型在英文排行榜第一名，決定直接上線處理中文客服，結果格式錯誤率 25%。哪裡做錯了？
→ 沒有用**自己的資料**測試。排行榜考的是英文通識，不代表中文客服的表現。應該先建立黃金測試集再比較。

@section 本課重點整理
- **沒有最好的模型，只有最適合的模型。**
- **三大家族**：閉源旗艦（最強但貴、資料外傳）、開放權重（可自架和微調、但要自己維護）、小型模型（快又便宜、適合簡單明確的任務）。
- **排行榜只能初篩**：考的東西不一樣、考題可能外洩、每個模型脾氣不同。最終要用自己的資料測。
- **兩種速度**：首字延遲（TTFT）決定聊天介面的體感；生成速度（TPS）和輸出長度決定批次處理的總時間。
- **輸出比輸入貴 3 到 5 倍**：精簡輸出最省錢、也最省時間。
- **總成本要算人工修正**：便宜但常出錯的模型，總成本可能更高。
- **兩道硬門檻**：上下文長度要實測（小心迷失在中間）；資料隱私決定能不能用雲端。
- **選型四步驟**：先定測試集和評分標準 → 盲測 → 考慮模型路由 → 鎖定版本並做迴歸測試。

@term 閉源模型
只能透過 API 使用、無法取得參數的模型，例如 GPT、Claude、Gemini。
@term 開放權重模型
參數可以下載並自行部署的模型（Open-Weight），例如 Llama、Qwen、Mistral。
@term SLM
小型語言模型（Small Language Model），參數較少、速度快、成本低，適合簡單明確的任務。
@term 基準測試
用標準化題目評量模型能力的測驗（Benchmark），例如 MMLU、HumanEval。
@term 基準測試污染
模型訓練時看過測驗題目，導致分數虛高的現象（Benchmark Contamination）。
@term 古德哈特定律
當一個指標變成追求的目標時，它就不再能準確反映原本要衡量的東西。
@term TTFT
首字延遲（Time To First Token）：從送出請求到收到第一個輸出 Token 的時間。
@term TPS
每秒生成的 Token 數（Tokens Per Second），衡量模型輸出速度。
@term 串流
模型邊產生邊傳送、使用者邊看到的輸出方式（Streaming），能大幅改善等待體感。
@term P95 延遲
95% 的請求能在這個時間內完成，比平均值更能反映使用者實際遇到的慢速情況。
@term TCO
總體擁有成本（Total Cost of Ownership）：把 API 費用、人力、錯誤修正等所有成本加總。
@term 黃金測試集
從真實業務挑出、附有正確答案的代表性測試案例（Golden Test Set），用來評估和比較模型。
@term 邊界案例
不常見、格式怪異或模稜兩可的輸入（Edge Case），最容易暴露系統的弱點。
@term 模型路由
依任務難度把請求分配給不同模型（Model Routing），簡單的給小模型、困難的給大模型。
@term 迴歸測試
修改或升級系統後重跑既有測試，確認原本正常的功能沒有退步（Regression Test）。
@term 地端部署
把系統部署在自己公司的機房，而不是雲端（On-Premise）。
