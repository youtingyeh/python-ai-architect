@section 開場：模型這麼多，怎麼挑？
打開開源模型的下載網站（例如 Hugging Face），你會看到成千上萬個模型，名字一個比一個長：`Mistral-7B-Instruct-v0.3`、`Mixtral-8x7B`、`Mistral-Small-24B`、`Codestral-22B`……而且每隔幾週就有新的冒出來。

怎麼判斷哪個適合你？名字裡的數字代表什麼？為什麼有的模型名字是「8x7B」？可以免費商用嗎？

這一課以法國的 AI 公司 **Mistral AI** 的模型家族為例，對應 Microsoft《Generative AI for Beginners》第 20 課「使用 Mistral 模型建構應用」。但我們真正要學的，是**任何模型都適用的選型方法**：
1. 兩種模型架構：**稠密模型**和**混合專家模型**（MoE）；
2. 為什麼 Mixtral 8x7B 的參數量不是 56B？
3. MoE 部署時最容易踩的陷阱：**算得快，但記憶體吃得兇**；
4. 授權條款：不是每個能下載的模型都能商用；
5. 中文能力和長文件能力要實測哪些地方；
6. 一套標準化的選型流程。

（註：模型的版本和授權條款更新很快，本課提到的具體型號和條款以撰寫時的資料為例。實際選用前，請一定查看最新的官方模型說明。）

@section 稠密模型：每個字都動用全部的腦
先回顧第 13 課的 Transformer：每一層有兩個主要部分：
- **注意力層**：讓每個字參考其他字；
- **前饋網路**（Feed-Forward Network，FFN）：對每個字做進一步的處理和轉換。在一般模型中，FFN 大約佔了三分之二的參數。

在傳統的「**稠密模型**」（Dense Model）中，不管輸入的是簡單的逗號「，」，還是複雜的數學方程式，每一個 Token 經過每一層時，都會**用到該層全部的參數**。

一個 70B 的稠密模型，每生成一個字，就要實實在在地做完 700 億個參數的計算。品質好，但每個字的計算量也很大。

**比喻：**一家醫院只有一位全科醫師，什麼病都找他。醫術很全面，但每個病人他都要從頭到尾仔細看，忙不過來。

常見的稠密模型有 Mistral-7B、Mistral-Small-24B、Llama 系列等。

@section 混合專家：每個字只找兩位專家
有沒有辦法讓模型「**知道很多**」（參數多），但「**算得很快**」（每次只用一部分參數）？

這就是「**混合專家模型**」（Mixture of Experts，**MoE**）的想法：
1. 把每一層的 FFN，從**一個**大網路，換成**好幾個**平行的小網路，叫做「**專家**」（Expert），例如 8 個；
2. 在前面放一個很小的「**路由器**」（Router），像醫院的掛號櫃台；
3. 每個 Token 進來時，路由器替它打分數，**只挑分數最高的 2 個專家**來處理，其他 6 個專家休息，不做計算。

**比喻：**醫院改成有 8 個專科（內科、外科、眼科……），掛號櫃台看了你的症狀，只把你轉給最相關的 2 位專科醫師。醫院整體的醫學知識很豐富（8 個專科），但你只需要 2 位醫師的時間。

**用公式表示：**對一個 Token 的向量 $x$，路由器算出每個專家的分數，挑出前 2 名，用 softmax（第 7 課）轉成權重 $G(x)_i$，輸出是兩位專家結果的加權總和：
$$y = \sum_{i \in \text{前 2 名}} G(x)_i \cdot E_i(x)$$

其中 $E_i(x)$ 是第 $i$ 位專家對 $x$ 的處理結果。

有趣的是：研究發現，專家們的分工通常**不是**照「主題」分的（不是一位專管數學、一位專管歷史），而比較像是依照語法或 Token 的類型分工。「專家」只是個比喻名稱。

@section 為什麼 8x7B 不是 56B？
**Mixtral 8x7B** 是 Mistral 最著名的 MoE 模型。名字的意思是「8 個專家，每個專家的規模大約來自一個 7B 模型」。

這裡有一個常被問到的細節：
- 它的**總參數量**是約 **46.7B**，而不是 $8 \times 7 = 56$B；
- 每個 Token 實際用到的「**活化參數**」（Active Parameters）是約 **12.9B**，而不是 $2 \times 7 = 14$B。

**為什麼？因為不是整個模型都複製 8 份！**

只有 FFN 被複製成 8 個專家。其他部分是**大家共用的**：
- 詞嵌入層（把 Token 轉成向量，第 24 課）；
- 輸出層（把向量轉回下一個字的機率）；
- **注意力層**（約佔一個 7B 模型的三分之一參數）；
- 正規化層等。

所以：
- **總參數** = 共用部分 + 8 × 一個專家 ≈ **46.7B**；
- **每個 Token 用到的參數** = 共用部分 + 2 × 一個專家 ≈ **12.9B**。

**比喻：**8 個專科醫師共用同一棟大樓、同一個掛號櫃台、同一套檢驗設備。醫院的總成本不是「8 間獨立醫院」，而是「1 棟大樓 + 8 位醫師」。

@section 最大的陷阱：算得像小模型，吃記憶體像大模型
理解了 MoE 的運作後，就能看穿部署時最常見的錯誤。

很多工程師看到「Mixtral 8x7B 每個 Token 只用 12.9B 參數，速度跟 13B 模型差不多」，就興沖沖地買了一張 24 GB 的顯示卡，結果一啟動就出現**記憶體不足**，程式當掉。

**原因：**雖然每個 Token 只叫醒 2 位專家，但路由器對**每一個** Token 都可能選**不同**的專家組合。下一個字可能需要專家 3 和 7，再下一個字可能需要專家 1 和 5。你無法預知，所以**全部 8 位專家都必須一直待在顯示卡記憶體裡**。

**算一算（用第 32 課的公式）：**
- **計算量和速度**：看活化參數 12.9B，相當於一個 13B 的稠密模型；
- **記憶體需求**：看總參數 46.7B：
  - FP16：$46.7 \times 2 \approx 93.4$ GB，需要至少兩張 80 GB 的高階伺服器顯示卡；
  - 就算量化成 INT4：$46.7 \times 0.55 \approx 25.7$ GB，**光權重就超過 24 GB**，再加上 KV 快取，單張 24 GB 顯示卡還是放不下，至少需要 32 到 48 GB。

**一句話記住 MoE：計算省，記憶體貴。**

**比喻：**醫院每次只需要 2 位醫師看診，但 8 位醫師都必須**全天候在醫院待命**，你得付 8 個人的辦公室租金。

**那 MoE 適合誰？**
- **適合**：記憶體充足、但希望每個字算得快、同時服務很多使用者的大型部署；
- **不太適合**：記憶體有限的單張顯示卡或邊緣裝置。這種情況下，一個能放得進記憶體的稠密模型（例如 24B 稠密模型）往往更實際。

@section 授權條款：能下載 ≠ 能商用
這是選型時最容易被忽略、後果卻最嚴重的一點。

很多人以為「開源模型」都可以隨便用。事實上，模型的**授權條款**差異很大。以 Mistral 的產品線為例（撰寫時的情況），大致分成三類：

**第一類：寬鬆的開源授權（例如 Apache-2.0）。**
可以自由下載、在自己的機器上部署、修改、微調，**也可以商業使用**。Mistral-7B、Mixtral 8x7B、Mixtral 8x22B 以及部分 Small 系列模型屬於這類。

**第二類：限制商用的授權。**
權重可以公開下載，但條款寫明**不能直接用在正式的商業服務**，只能做研究或測試。例如某些版本的程式碼專用模型 Codestral 採用 Mistral 的「非生產授權」。若要商用，必須購買 API 或另外簽約。

**第三類：只透過雲端提供的旗艦模型。**
例如 Mistral Large 系列，通常不提供權重下載（或另有條款），透過官方 API 或雲端平台（Azure、AWS、Google Cloud）按 Token 計費使用。

**原則：不能看到名字裡有「Mistral」就以為全部都是 Apache-2.0。**每個模型、甚至同一個模型的不同版本，都要**逐一**查看它的「**模型卡**」（Model Card）：一份說明模型用途、訓練資料、限制、授權條款的文件，通常放在下載頁面上。

選錯授權的後果，可能是產品上線後收到律師函。

@section 中文和長文件：一定要實測的兩件事
在台灣使用歐美公司開發的模型時，有兩個地方特別要實測。

**一、Tokenizer 對繁體中文的效率。**
回想第 14 課的 Tokenizer：它決定一段文字會被切成幾個 Token。Tokenizer 的「詞表」是用訓練資料建立的。

- 早期 Mistral 模型的詞表約 3.2 萬個，主要用英文、法文、德文、西班牙文建立。繁體中文字常常不在詞表裡，一個中文字可能被拆成 **2 到 3 個** Token。
- 後來的新模型改用約 13 萬個的大詞表（Mistral 稱為 Tekken），中日韓文字和程式碼的切分效率大幅改善。

**為什麼這很重要？**同一份中文合約：
- 消耗的 Token 數可能**多一倍以上**，API 費用跟著翻倍；
- 上下文視窗能裝的內容**少一半**；
- KV 快取（第 32 課）也大一倍；
- 生成速度變慢（因為每個字要生成好幾個 Token）。

而且，中文訓練資料不足的模型，常在長篇輸出中**夾雜簡體字或英文單字**。

**二、長文件的處理方式。**
早期的 Mistral-7B 為了省記憶體，用了「**滑動視窗注意力**」（Sliding Window Attention）：每個字只直接注意前面 4,096 個 Token 之內的內容，更遠的內容只能透過層層傳遞間接影響。

在「**大海撈針**」測試中（在很長的文件中藏一個特定數字，看模型找不找得到），超出視窗範圍的資訊找回率會明顯下降。後續版本則改為支援完整的長上下文，並內建工具呼叫（第 34 課）的格式。

**教訓：**模型名稱一樣，不同版本的能力可能差很多。要用**你的**中文資料、**你的**文件長度去實測。

@section 標準化選型流程
新模型每隔幾週就出現一個。成熟的團隊不會每次憑感覺換模型、重寫程式，而是把每個新模型當作一個「**候選**」，放進一張固定的**評估表**，跑完同一套流程。

**第一關：硬體和授權。**
記錄：
- 稠密還是 MoE？
- **總參數**（決定需要多少記憶體）和**活化參數**（決定速度）；
- 授權是否允許你的用途？

不符合的直接淘汰，不必浪費時間測試。

**第二關：中文和 Token 成本實測。**
- 拿同一份 2,000 字的台灣商業合約，看這個模型的 Tokenizer 切出幾個 Token。這直接決定成本和可用的上下文長度；
- 檢查輸出是否**嚴格維持繁體中文**，沒有簡體字混入。

**第三關：黃金測試集對決。**
在同一份內部測試集（例如 100 題，第 21 課）上，和**目前正在用的模型**正面比較：
- 各類題目的準確率；
- 工具呼叫的 JSON 格式正確率；
- P95 延遲（100 個請求中第 95 慢的那個要多久）；
- 每一萬次請求的總成本。

**只有在「品質和成本」的取捨上明顯更好**的候選，才進入下一步：**灰度發布**（先讓一小部分使用者使用，確認沒問題再逐步擴大）。

這套流程的好處是：不管明天出現什麼新模型，你都有一把**固定的尺**可以量它，而不是被網路上的排行榜和宣傳牽著走。

@section 走一遍：一家律師事務所的選型
用一個虛構的例子，把選型流程完整走一遍。

**背景：**一家律師事務所想用 AI 幫忙摘要中文合約，每天約 500 份，每份平均 8,000 字。合約內容**不能離開事務所**，所以必須自己部署。預算是兩張 48 GB 的顯示卡（共 96 GB）。

**候選名單：**
- 候選 A：一個 MoE 模型，總參數約 47B、活化參數約 13B，早期 3.2 萬詞表，Apache-2.0；
- 候選 B：一個 24B 稠密模型，13 萬大詞表，Apache-2.0；
- 候選 C：一個 22B 的程式碼專用模型，限制商用授權。

**第一關：硬體和授權。**
- C 的授權不允許商業服務，而且它是寫程式用的，不擅長合約摘要，**淘汰**。
- A 用 FP16 約 93 GB，兩張卡勉強放得下權重，但幾乎沒空間給 KV 快取；8,000 字的長合約、多份同時處理，一定不夠。改用 INT8 約 47 GB，可行。
- B 用 FP16 約 48 GB，剩下近一半空間給 KV 快取，可行。

**第二關：中文 Token 實測。**
拿一份 8,000 字的合約測試：
- A 的舊詞表切出約 16,000 個 Token（每字約 2 個）；
- B 的新詞表切出約 9,000 個 Token。

A 處理每份合約要多花約 78% 的 Token，KV 快取也大得多，速度也會慢。另外 A 的輸出偶爾出現簡體字。

**第三關：黃金測試集。**
用 100 份已經由律師人工摘要過的合約做比較：B 在「關鍵條款是否遺漏」和「繁體中文正確率」兩項都勝出。

**結論：**選 B。值得注意的是：A 的「每字計算量」其實比較小，單看規格表可能會以為它更快。但加上中文 Token 效率和記憶體的實際考量後，結論完全相反。這就是為什麼**一定要用自己的資料實測**。

@section 動動腦：選型練習
**題一**：Mixtral 8x7B 的總參數約 46.7B、活化參數約 12.9B。下列哪個說法正確？
(A) 只需要 13B 模型的記憶體　(B) 速度接近 13B 稠密模型，但記憶體需求接近 47B 模型
→ **(B)**。全部專家都必須常駐記憶體。

**題二**：一家公司只有一張 24 GB 顯示卡，要在 Mixtral 8x7B（INT4）和一個 24B 的稠密模型（INT4）之間選擇。哪個比較可行？
→ 24B 稠密模型 INT4 約 $24 \times 0.55 = 13.2$ GB，放得下還有空間給 KV 快取；Mixtral INT4 約 25.7 GB，放不下。選稠密模型。

**題三**：一個模型的 Tokenizer 把每個中文字平均切成 2.5 個 Token，另一個平均 1.2 個。處理同樣的中文文件，前者的 API 費用大約是後者的幾倍？
→ $2.5 / 1.2 \approx 2.1$ 倍。

**題四**：在網站上看到一個寫著「Mistral」的模型可以免費下載，可以直接用在公司的付費產品裡嗎？
→ 不一定。要先查看該模型版本的模型卡和授權條款，確認是否允許商業使用。

@section 常見問題 Q&A
**Q1：模型名字裡的 Instruct 是什麼意思？**
代表這個版本經過了指令微調（第 15 課的 SFT 和對齊），會聽從指令、適合對話。沒有 Instruct 的通常是「基礎模型」（Base），只會接續文字，不太會好好回答問題，比較適合拿來做進一步的微調。

**Q2：MoE 會越來越普遍嗎？**
近年許多大型模型都採用了 MoE 架構，因為它能用較少的計算量獲得更大的知識容量。但記憶體需求大的問題依然存在，所以在小型、邊緣部署的情境中，稠密模型仍然很常見。兩者會長期並存。

**Q3：排行榜上分數最高的模型，就是最好的選擇嗎？**
不一定。公開排行榜測的是通用能力，而且常用英文題目，有些題目可能已經洩漏到訓練資料中（第 21 課的資料污染）。最可靠的依據永遠是：**用你自己的任務、你自己的資料**跑出來的結果。

@section 本課重點整理
- **稠密模型**：每個 Token 用到全部參數，品質穩定但計算量大。
- **混合專家（MoE）**：每層有多個專家，路由器只挑前 2 名來計算。知識容量大、計算量小。
- **8x7B ≠ 56B**：只有 FFN 被複製成專家，注意力層和嵌入層共用。Mixtral 8x7B 總參數約 46.7B、活化參數約 12.9B。
- **MoE 的陷阱**：速度看活化參數，記憶體看總參數。所有專家都必須常駐記憶體。「計算省，記憶體貴。」
- **授權條款**：分為寬鬆開源、限制商用、雲端專屬。每個模型都要逐一查看模型卡。
- **中文實測**：Tokenizer 效率直接影響成本、上下文容量和速度；長文件能力也因版本而異。
- **標準化選型**：硬體與授權 → 中文與成本實測 → 黃金測試集對決 → 灰度發布。

@term 稠密模型
每個 Token 經過每一層時都會用到該層全部參數的模型（Dense Model）。
@term 混合專家模型
每層有多個專家網路，由路由器為每個 Token 挑選少數幾個來計算的模型（MoE）。
@term 專家
MoE 模型中平行存在的多個前饋網路之一（Expert）。
@term 路由器
MoE 模型中為每個 Token 評分並挑選要使用哪些專家的小網路（Router）。
@term 前饋網路
Transformer 每層中對每個 Token 做進一步轉換的部分（FFN），約佔三分之二參數。
@term 總參數
模型全部參數的數量，決定需要多少記憶體。
@term 活化參數
處理每個 Token 時實際參與計算的參數數量，決定計算量和速度（Active Parameters）。
@term 授權條款
規定模型能如何使用、修改、是否可商用的法律條件（License）。
@term Apache-2.0
一種寬鬆的開源授權，允許自由使用、修改與商業利用。
@term 模型卡
說明模型用途、訓練資料、限制與授權條款的文件（Model Card）。
@term 詞表
Tokenizer 能辨認的所有 Token 清單（Vocabulary），大小與涵蓋語言影響切分效率。
