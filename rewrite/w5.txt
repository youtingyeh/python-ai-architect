@section 開場：「真的最後一版_改2」
在沒有版本控制的年代，很多人是這樣備份的：
```
project_final
project_final_v2
project_真的最後一版
project_真的最後一版_改2_修好bug
```

這種做法有三個大問題：
1. **不知道改了什麼**：試了一個新的 AI 提示詞模板，把系統改壞了，但完全想不起過去三小時動了哪些檔案的哪幾行；
2. **回不去**：想要退回到「昨天還能正常運作的版本」，卻不確定是哪個資料夾；
3. **多人協作時互相覆蓋**：兩個人（或你和第 41 課的 AI 寫程式助手）同時修改同一個專案，後存檔的人蓋掉了前一個人的修改。

**Git** 就是解決這些問題的工具。它不只是「把程式上傳到 GitHub 的備份工具」，而是現代軟體開發的「**時光機和安全網**」：每一次修改都有紀錄、隨時能回到過去、多人可以平行工作再安全地合併。

第 41、42 課提到「讓 AI 在獨立分支上修改」「看 `git diff` 審查差異」「檢查修改範圍」，靠的都是 Git。這一課我們要學：
1. Git 的三個區域：工作目錄、暫存區、版本庫；
2. **快照**：Git 怎麼記錄歷史；
3. **分支**：平行宇宙一樣的開發方式；
4. 好的提交習慣：一次只做一件事；
5. 遇到**合併衝突**怎麼辦；
6. 最危險的錯誤：把密碼提交進去。

@section 三個區域：工作桌、待寄箱、檔案櫃
用 Git 管理的專案，檔案會在三個區域之間移動：

**一、工作目錄（Working Directory）：**你正在編輯的檔案，就像**工作桌**上攤開的文件。

**二、暫存區（Staging Area）：**你挑選出「準備記錄下來」的修改，像是**待寄出的信封**。你可以只挑一部分修改放進去。

**三、版本庫（Repository）：**已經正式記錄下來的歷史，像是**歸檔的檔案櫃**。存在專案裡一個隱藏的 `.git` 資料夾中。

**基本流程：**
```
git status              # 看看目前狀態：哪些檔案被修改了？
git add app.py          # 把 app.py 的修改放進暫存區
git commit -m "說明"     # 把暫存區的內容正式記錄成一個版本
```

**兩個重要的觀念：**
- `git add` **只是**放進暫存區，還沒記錄；
- `git commit` **只是**記錄在**你自己電腦上**的版本庫，**不會**自動上傳到 GitHub。要上傳，還需要 `git push`。

**看差異的兩個指令：**
- `git diff`：工作目錄 vs. 暫存區，也就是「**還沒 add** 的修改」；
- `git diff --staged`：暫存區 vs. 最新的版本，也就是「**即將被 commit** 的內容」。

**好習慣：**每次 commit 之前，先跑 `git status` 和 `git diff --staged`，確認要記錄的每一行都是你預期的，沒有夾帶測試用的垃圾或密碼。

@section 快照：Git 記錄的是「照片」
很多人以為 Git 記錄的是「每次改了哪幾行」。其實 Git 的核心是**快照**（Snapshot）：

每次 `git commit`，Git 會替暫存區裡**所有檔案的當前狀態**拍一張「照片」，並記錄：
- 這張照片的唯一編號（一串雜湊值，例如 `a2b1c3...`，第 33 課提過雜湊函式）；
- 上一張照片是哪一張（叫做「**父提交**」，Parent Commit）；
- 作者、時間、說明訊息。

**不會很佔空間嗎？**不會。沒有改變的檔案，新照片會直接**指向舊照片裡的同一份檔案**，不會重複儲存。

每一個這樣的記錄，叫做一個「**提交**」（Commit）。所有提交串起來，就是專案的完整歷史：
```
git log --oneline
```
可以列出所有提交。想看某個舊版本的內容、或比較兩個版本的差異，都可以隨時做到。

@section 分支：平行宇宙
**分支**（Branch）讓你可以從某個時間點「**分岔**」出去，在不影響主線的情況下自由實驗。

例如：主線（通常叫 `main`）是目前能正常運作的版本。你想試試新的登入功能：
```
git switch -c feature-auth      # 建立並切換到新分支
```
在 `feature-auth` 上隨便改、隨便 commit，`main` 完全不受影響。實驗成功，再**合併**（Merge）回主線；失敗了，直接丟掉這個分支就好。

**分支不是把整個資料夾複製一份。**
它只是一個「**書籤**」，指向某一個提交。建立分支幾乎是瞬間完成的，不佔額外空間。當你在分支上 commit，書籤就跟著往前移動到新的提交。

還有一個特別的書籤叫 **`HEAD`**，代表「**你現在在哪裡**」，通常指向你目前所在的分支。

**這和 AI 開發的關係：**
第 39、41 課說的「讓 AI 在獨立分支上修改」「把最佳版本存到 `agent/attempt-best` 分支」，就是利用分支的隔離能力：AI 怎麼改都不會污染主線，人類審查通過後才合併。

@section 好的提交：一次只做一件事
**糟糕的提交：**累積三天的修改，同時改了登入邏輯、修了畫面排版、順便調整了資料庫連線，然後：
```
git commit -m "update"
```

三天後發現新的資料庫連線設定讓正式系統當掉了，要退回。但這三件事被包在**同一個**提交裡，你**沒辦法只退回資料庫的部分**，要退就得連登入功能和排版修正一起退掉。

**好的做法：原子提交（Atomic Commit）。**
- **一個提交只做一件事**；
- 每個提交都能**獨立**通過測試；
- 提交訊息說清楚**為什麼**要改，例如：
```
fix(score): 新增成績前先檢查分數範圍
feat(auth): 加入登入失敗次數限制
```
（開頭的 `fix`、`feat` 是常見的慣例：`fix` 是修錯誤，`feat` 是新功能，`docs` 是改文件。）

這樣，任何一個修改出問題，都可以用 `git revert` **單獨撤銷**那一個提交，其他修改不受影響。

**比喻：**搬家時，每個箱子只裝一個房間的東西，並在外面寫清楚「廚房：碗盤」。要找東西或退回某一箱，一目了然。如果把所有東西混在一個超大箱子裡，寫「雜物」，要找什麼都得全部翻出來。

這也和第 41 課的「控制爆炸範圍」是同一個精神：**修改越小、越單純，越容易審查、測試和撤銷。**

@section 合併和衝突
**自動合併：**兩個分支從同一個點分出去，如果它們修改的是**不同的檔案**，或同一個檔案的**不同段落**，Git 可以自動把兩邊的修改合在一起。Git 會比較三個版本：兩個分支各自的最新版，以及它們的**共同祖先**，這叫做「**三方合併**」（Three-Way Merge）。

**衝突：**如果兩邊都改了**同一個檔案的同一行**，而且改得不一樣，Git **不會**自作主張猜要聽誰的。它會停下來，告訴你「**合併衝突**」（Merge Conflict），把決定權交給最了解業務意圖的人。

這和第 33 課「AI 不該自己做無法撤回的決定」的精神很像：**遇到真正的分歧，由人來判斷。**

@section 走一遍：解決一次合併衝突
**起點：**`README.md` 第一行是 `課程名稱：工程必修`。

**兩條分支：**
- `branch-a` 改成：`課程名稱：Python 工程必修`，並提交；
- `branch-b` 改成：`課程名稱：系統架構必修`，並提交。

**合併：**站在 `branch-b`，執行：
```
git merge branch-a
```
Git 回報：
```
CONFLICT (content): Merge conflict in README.md
```

**打開檔案，會看到：**
```
<<<<<<< HEAD
課程名稱：系統架構必修
=======
課程名稱：Python 工程必修
>>>>>>> branch-a
```
- `<<<<<<< HEAD` 到 `=======` 之間：**你目前所在分支**（branch-b）的版本；
- `=======` 到 `>>>>>>> branch-a`：**要合併進來的分支**（branch-a）的版本。

**解決步驟：**
1. **理解雙方的意圖**：一邊想強調 Python，一邊想強調系統架構。和團隊確認後，決定兩者都要；
2. **編輯成最終正確的內容**，並**刪除所有三行標記**：
```
課程名稱：Python 與系統架構必修
```
3. 告訴 Git 衝突已解決：`git add README.md`；
4. 完成合併：`git commit -m "merge: 合併 Python 與架構課程名稱"`。

這個合併提交有**兩個**父提交（分別來自兩個分支），歷史在這裡匯流。可以用 `git log --oneline --graph` 看到分岔又匯合的圖形。

**常見錯誤：忘了刪標記。**
沒刪乾淨 `<<<<<<<` 這些標記就提交了，程式一執行就出現語法錯誤。解完衝突後，最好搜尋一下檔案裡還有沒有殘留的標記，並重新跑一次測試。

@section 從自己的電腦到 GitHub：遠端協作
到目前為止，所有操作都在**你自己的電腦**上。要和別人合作，或把程式碼備份到雲端，就需要一個「**遠端版本庫**」（Remote Repository）。最常見的服務是 **GitHub**（還有 GitLab、Bitbucket 等）。

**四個和遠端相關的指令：**
- `git clone 網址`：把遠端的整個專案（包含完整歷史）**複製**到你的電腦，通常是第一次加入專案時使用；
- `git push`：把你本機的新提交**上傳**到遠端；
- `git pull`：把遠端的新提交**下載**下來，並合併進你目前的分支；
- `git fetch`：只下載、不合併，讓你先看看別人改了什麼。

遠端通常叫做 `origin`，所以常見的寫法是：
```
git push origin feature-auth
```
意思是「把 `feature-auth` 分支上傳到 origin」。

**Pull Request：團隊協作的標準流程。**
在團隊中，通常**不會**直接修改 `main` 分支。標準流程是：
1. 從 `main` 建立自己的分支，例如 `feature-auth`；
2. 在分支上修改、提交（保持原子提交）；
3. 把分支 push 到 GitHub；
4. 在 GitHub 上建立一個「**Pull Request**」（簡稱 PR，合併請求）：意思是「我改好了，請大家看看，同意的話把它合併進 main」；
5. 隊友在 PR 頁面上逐行看差異、留下意見（第 42 課的程式碼審查就發生在這裡）；
6. 同時，自動化流程（第 65 課的 GitHub Actions）會自動跑測試；
7. 審查通過、測試全綠，才合併進 `main`。

**比喻：**PR 像是交給主管的「**公文簽呈**」。你不能自己蓋章生效，要經過審核、會簽，全部通過才算數。這保證了 `main` 上的每一行程式碼，都至少被兩個人（或一個人加上自動測試）看過。

**一個好習慣：開始工作前先 pull。**
每天開始寫程式前，先 `git pull` 取得別人最新的修改，再建立自己的分支。這樣可以大幅減少之後合併時的衝突。

@section 最危險的錯誤：把密碼提交進去
**陷阱一：把機密和垃圾檔案提交進版本庫。**
- 機密：`.env` 檔、API 金鑰、資料庫密碼；
- 垃圾：Python 的 `__pycache__` 資料夾、JavaScript 的 `node_modules`、大型的資料檔。

**要特別記住：**一旦檔案被提交進 Git 的歷史，**就算你下一個提交把它刪掉**，任何能存取這個專案的人，只要查看前一個提交的快照，**仍然**能看到完整的密碼！因為快照是永久保存的。

**預防：在第一次 `git add` 之前，就建立 `.gitignore` 檔案**，列出不該被追蹤的檔案：
```
.env
__pycache__/
node_modules/
*.log
```
Git 會自動忽略這些檔案。

**萬一已經提交了密碼：**最重要的一步不是改 Git 歷史，而是**立刻到該服務的後台，撤銷那把金鑰，換一把新的**（叫做「**輪替**」，Rotate）。因為你無法確定有沒有人已經看過了。第 64 課會詳細談機密管理。

**陷阱二：工作目錄很亂時就合併。**
合併前，先用 `git status` 確認工作目錄是乾淨的（所有修改都已提交）。否則你自己未完成的修改和衝突會混在一起，很難收拾。

**陷阱三：亂用破壞性指令。**
- `git reset --hard`：丟棄所有未提交的修改，**無法復原**；
- `git push --force`：用你的版本**強制覆蓋**遠端的歷史，可能抹掉隊友的工作。

在完全理解後果之前，不要使用這些指令。

@section 動動腦：判斷看看
**題一**：`git add README.md` 的作用是什麼？
→ 把 README.md 目前的修改放進暫存區，作為下次 commit 的內容。還沒有正式記錄，也沒有上傳。

**題二**：已經 `git add app.py` 了，commit 之前想確認即將提交的內容，用什麼指令？
→ `git diff --staged`。

**題三**：合併時出現衝突，正確的處理流程是什麼？
→ 打開檔案，看懂雙方版本和意圖，編輯成正確內容並刪除所有衝突標記，再 `git add` 和 `git commit`。

**題四**：發現上週的提交裡有 API 金鑰，這週已經提交刪除了，安全嗎？
→ 不安全。舊快照裡仍然看得到。必須立刻到服務後台撤銷並更換那把金鑰。

@section 本課重點整理
- **Git 的價值**：記錄每次修改、隨時回到過去、多人平行開發再安全合併。
- **三個區域**：工作目錄（正在改）→ `git add` → 暫存區（準備提交）→ `git commit` → 版本庫（正式記錄，在本機）。上傳要 `git push`。
- **快照**：每次提交記錄所有檔案的狀態，沒改的檔案不重複儲存。
- **分支**：一個指向提交的書籤，建立幾乎不花成本；在分支上實驗不影響主線。
- **原子提交**：一次只做一件事、訊息說明原因，出問題時可以單獨撤銷。
- **合併衝突**：兩邊改了同一行時，Git 交給人判斷。看懂雙方意圖、編輯成正確內容、刪除標記、add、commit。
- **最危險的錯誤**：提交密碼。先設好 `.gitignore`；萬一提交了，立刻撤銷並更換金鑰。
