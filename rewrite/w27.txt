@section 開場：「當初為什麼要這樣做？」
在任何存活超過半年的專案裡，新加入的工程師最常問的問題是：
- 「當初為什麼不用微服務，而是把所有功能放在同一個 FastAPI 專案裡？」
- 「為什麼向量檢索用 PostgreSQL 的 pgvector，而不是另外架一套專用的向量資料庫？」
- 「為什麼登入用 Session，而不是現在很流行的 JWT？」

如果團隊**沒有留下紀錄**，答案往往是：「呃……好像是某某人決定的，他已經離職了。」

六個月後，連當初做決定的人自己都忘了**當時的預算限制和測試數據**。新主管一來，覺得「這個架構太老土」，下令全部重構。結果團隊把過去**已經踩過、已經排除的坑**，又重新踩了一遍。

**軟體架構沒有放諸四海皆準的完美答案。**每一個技術選擇背後都是**取捨**（Trade-off）：得到某些好處，同時放棄另一些東西。今天正確的選擇，換了規模、換了團隊、換了預算，可能就變成錯誤的選擇。

**架構決策紀錄**（Architecture Decision Record，簡稱 **ADR**）就是用來解決這個問題的。它是**一頁精簡的文件**，記錄：
- 當時面臨什麼**背景和限制**；
- 考慮過哪幾個**候選方案**；
- 最後**選了哪一個**、為什麼；
- 我們**願意承擔什麼代價**；
- 未來**什麼情況下**該重新評估。

這一課要學：
1. ADR 的五個段落；
2. 怎麼寫出有用（而不是空泛）的 ADR；
3. 三個常寫成 ADR 的經典取捨；
4. 完整寫一份 ADR；
5. 常見的錯誤。

@section ADR 長什麼樣子
ADR 通常是一個 Markdown 檔案，**放在程式碼的版本庫裡**，例如：
```
docs/adr/
  0001-use-modular-monolith.md
  0002-use-postgresql.md
  0003-use-server-side-session.md
  0004-use-pgvector-for-rag.md
```
為什麼放在版本庫，而不是公司的共用文件平台？
- 和程式碼**放在一起**，工程師找得到；
- 有**版本歷史**（第 52 課）；
- 可以在 **PR 中審查**：重大的架構變更，連同 ADR 一起提交，團隊一起討論。

**比喻：**ADR 像法院的**判決書**。不只寫「判決結果」，還寫了「案件事實、雙方主張、法官考量了哪些因素、為什麼這樣判」。日後有類似案件，或有人質疑這個判決時，都可以回頭查閱當時的完整推理。

@section 五個段落
由 Michael Nygard 提出的經典 ADR 格式，有五個段落：

**一、標題與狀態**
- 依序**編號**：`ADR-0004：RAG 向量檢索使用 pgvector`；
- 標明**狀態**：
  - `Proposed`（提議中）：還在討論；
  - `Accepted`（已採納）：正式生效；
  - `Deprecated`（已廢止）：不再適用；
  - `Superseded by ADR-0009`（已被取代）：有新的決策取代了它。

**重要的規則：ADR 不刪除、不改寫。**
架構改變時，**不是**去修改舊的 ADR-0004，而是**新增**一份 ADR-0009，並把 ADR-0004 的狀態改成「已被 ADR-0009 取代」。這樣就保留了**完整的演進歷史**：當初為什麼這樣選、後來因為什麼改變。

這和第 72 課的稽核紀錄是同樣的精神：歷史不應該被覆蓋。

**二、背景與限制（Context）**
客觀描述**當下的**情況：業務規模、團隊人數、預算、技術限制、要解決的具體問題。

**空泛的寫法：**「我們需要一個向量資料庫。」

**有用的寫法：**「目前團隊只有 2 名後端工程師，每月雲端預算 80 美元。課程教材的向量總數約 5 萬筆（每筆 1536 維），查詢的 P95 需要小於 150 毫秒（第 70 課的 SLO）。而且查詢時，必須同時依照學生的選課紀錄過濾權限（第 64 課），結果要即時正確。」

**這一段是 ADR 最重要的部分。**因為決策的「對錯」，完全取決於當時的背景。日後有人質疑時，第一個要問的是：「當時的背景，現在還成立嗎？」

**三、候選方案（Considered Options）**
至少列出 **2 到 3 個真正可行的方案**，公平地比較各自的優缺點。

**常見的錯誤：寫「稻草人」方案。**也就是故意列一個明顯很爛的選項，好讓自己想要的方案顯得很好。例如「方案 A：用 Excel 存向量」。這種比較沒有任何價值。

「**維持現狀**」常常是一個合理的候選方案，值得認真評估。

**四、決定（Decision）**
清楚寫出選了哪一個，並且**把理由扣回背景中的限制**。

**空泛的理由：**「因為 pgvector 比較好、比較熱門。」

**有用的理由：**「選擇 pgvector，因為：5 萬筆向量遠在它能良好處理的範圍內；可以和選課表在**同一個查詢**中做權限過濾，不需要在兩個資料庫之間同步權限；不需要額外的主機，符合 80 美元的預算；2 人團隊不必多維護一套系統。」

**五、後果與重新評估條件（Consequences）**
誠實寫出：
- **正面效益**：我們得到了什麼；
- **負面代價**：我們**放棄了**什麼、要承擔什麼風險；
- **重新評估的觸發條件**：當哪個**量化指標**超過門檻時，就該重新討論這個決策。

例如：「當向量數量超過 500 萬筆，或查詢 P95 超過 300 毫秒時，重新評估是否改用專用的向量資料庫。」

**這一段讓 ADR 不會變成「教條」。**它明確說明「這個決定在什麼條件下成立」，條件改變時，大家就知道該重新討論了，而不是「因為 ADR 這樣寫，所以永遠不能改」。

@section 三個經典的取捨
以下是軟體和 AI 系統中，最常需要寫成 ADR 的三種決策。

**取捨一：模組化單體 vs. 微服務**
- **微服務**：把系統拆成很多個獨立部署的小服務，每個有自己的資料庫；
- **模組化單體**：所有功能在**同一個**應用程式中部署，但程式碼內部有清楚的模組邊界。

很多小團隊一開始就拆成 8 個微服務，結果立刻要面對：
- 跨服務的交易：原本一個資料庫交易（第 58 課）就能搞定的事，現在要協調好幾個服務；
- 網路延遲：原本是函式呼叫，現在每次都要經過網路；
- 8 套 CI/CD（第 69 課）、8 套監控（第 66 課）、8 套部署設定。

這些額外的負擔，被稱為「**維運稅**」。

對 2 到 5 人的小團隊，「模組化單體」通常是更好的起點：共用一個資料庫，享有完整的交易保障，迭代快速。代價是所有模組在同一個程式中，需要紀律來維持模組邊界，避免程式碼互相糾纏。等團隊和規模真的大到需要時，再把邊界清楚的模組拆出去。

**比喻：**剛創業的小公司，不需要一開始就把每個部門分到不同的大樓。大家在同一層辦公室，但分區坐好、職責清楚。等公司真的長大了，再讓某些部門搬出去。

**取捨二：pgvector vs. 專用向量資料庫**
- 百萬筆以下的向量，而且需要和關聯式資料（例如權限表）一起查詢時，pgvector 可以省去兩個資料庫之間的同步問題和額外的主機成本；
- 代價是：在數千萬到上億筆的超大規模下，它的水平擴充能力不如專用的向量資料庫。

**取捨三：雲端 LLM API vs. 自己部署開源模型**
- 初期流量低時，按 token 計費的雲端 API（第 16、18 課），成本遠低於 24 小時租用 GPU；
- 當每日 token 用量超過**損益平衡點**，或者有法規要求資料不能離開某個地區時，自己部署開源模型（第 32、37 課）可能更划算或成為必要。

**共同點：**這三個取捨的答案，**都取決於規模、團隊和限制**。沒有永遠的正解，只有「在這個背景下的合理選擇」。這就是為什麼背景段落那麼重要。

@section 走一遍：寫一份完整的 ADR
```
# ADR-0003：登入機制採用伺服器端 Session 加 HttpOnly Cookie

## 狀態
已採納（2026-09-15）

## 背景
- 平台需要支援「帳號疑似被盜或違規時，管理員按下停權後，
  1 秒內撤銷該帳號所有存取權」（安全需求 NFR-SEC-03）。
- 目前只有瀏覽器前端，沒有手機 App 或第三方呼叫者。
- 後端已有 PostgreSQL 與 Redis，不需新增基礎設施。

## 候選方案
A. 無狀態 JWT，有效期 7 天，存在前端 localStorage。
   + 每次請求不必查資料庫
   - 過期前無法立即撤銷
   - localStorage 可被 XSS 讀取
B. 伺服器端 Session，session_id 存在 HttpOnly + Secure +
   SameSite=Lax 的 Cookie，Session 紀錄存在 Redis。
   + 刪除紀錄即可立即撤銷
   + 前端 JavaScript 讀不到 Cookie
   - 每次請求需查詢一次 Redis
C. 短效 JWT（15 分鐘）加長效 Refresh Token。
   + 撤銷延遲最多 15 分鐘
   - 實作較複雜，仍無法滿足 1 秒內撤銷

## 決定
採用方案 B。它是唯一能滿足「1 秒內撤銷」需求的方案，
且所需的 Redis 已存在，2 人團隊不需額外維運。

## 後果
正面：
- 停權立即生效；XSS 無法竊取登入憑證。
負面：
- 每次 API 請求多一次 Redis 查詢（實測約 1 毫秒）。
- Redis 故障時所有使用者無法登入，需確保 Redis 的可用性。
- 需另外處理 CSRF 防護（SameSite 加上重要操作的 CSRF Token）。
重新評估條件：
- 若未來開放手機 App、命令列工具或第三方服務呼叫 API，
  另行新增範圍受限的存取 token 機制，並撰寫新的 ADR。
```

注意這份 ADR 的特點：
- 背景**引用了具體的需求編號**（第 70 課）；
- 每個方案都有**優點和缺點**，連被淘汰的方案也公平描述；
- 決定的理由**直接對應**背景中的限制；
- 負面代價寫得很**誠實**，包括「Redis 掛了大家都不能登入」這種不好看的事實；
- 重新評估條件**很具體**。

一年後，團隊決定推出手機 App，有人說「我們應該改用 JWT」。打開 ADR-0003，大家馬上看到：「喔，當初就預見了這個情況，而且建議的做法是**新增**一套給 App 用的 token 機制，而不是推翻整個 Session 設計。」討論可以直接從這裡開始，而不是從頭吵一遍。

@section 常見錯誤
**錯誤一：只有結論，沒有數據和代價。**
「我們決定用微服務，因為它比較有擴充性。」這種 ADR 等於沒寫。擴充性要擴充到多大？代價是什麼？在什麼情況下這個判斷會不成立？

**錯誤二：事後補寫，美化決策。**
決策做完半年後才補寫，往往會把當時的猶豫和風險都略過，寫成一份「英明決策」的宣傳文。ADR 應該在**做決定的當下**撰寫，忠實記錄當時的不確定性。

**錯誤三：什麼都寫成 ADR。**
「變數要用駝峰式還是底線式命名」不需要 ADR，那是程式碼風格規範。ADR 是給「**影響深遠、難以回頭、團隊會反覆質疑**」的決策用的。判斷標準：如果這個決定錯了，要花很多時間和成本才能改回來嗎？是的話，就值得寫。

**錯誤四：改寫或刪除舊的 ADR。**
如上所述，要新增一份並標記舊的為「已被取代」。

**錯誤五：寫了就沒人看。**
ADR 要被**引用**才有價值：PR 描述中引用相關的 ADR；新人入職時閱讀所有已採納的 ADR；有人提出重大變更時，先查有沒有相關的 ADR。

@section 常見疑問
**問：ADR、需求文件、C4 架構圖，三者有什麼關係？**
答：它們回答不同的問題，彼此引用。**需求文件**（第 70 課）回答「**要做什麼、做到多好**」；**C4 架構圖**（第 71 課）回答「**系統現在長什麼樣子**」；**ADR** 回答「**為什麼長成這個樣子**」。一個典型的流程是：需求中出現「1 秒內撤銷權限」→ 撰寫 ADR-0003 比較登入方案 → 決定後更新 C4 容器圖，加上 Redis 存放 Session。看到圖上的 Redis，想知道為什麼要有它，就去查 ADR。

**問：ADR 由誰來寫？要誰同意？**
答：通常由**提出變更或負責研究的人**撰寫初稿，狀態設為「提議中」，發 PR 讓相關的人審查：會受影響的團隊、負責維運的人、資安負責人。討論的重點是：背景描述正確嗎？有沒有漏掉的方案？代價是否寫得誠實？達成共識後改為「已採納」並合併。重點不在於「誰有權拍板」，而在於**決策的推理過程攤在陽光下**，任何人都能檢視和質疑。

**問：小團隊、個人專案也需要 ADR 嗎？**
答：越小的團隊，越容易覺得「大家都知道為什麼」，但人的記憶比想像中短。即使是個人專案，三個月後的你也會問「我當初為什麼這樣做？」不需要寫得很長，五個段落各寫兩三行就有價值。**最重要的是背景和代價**，那是最容易被遺忘的部分。

**問：做決定時資訊不足怎麼辦？**
答：很常見。可以在背景中**明確寫出不確定的地方**，例如「目前不確定尖峰流量，估計在每秒 50 到 200 次之間」，並選擇一個**容易回頭**的方案，再把「實際流量超過 200」寫成重新評估條件。有時候正確的決定是「先做一個小實驗（例如兩個方案各做一個雛形並測量），一週後再決定」，這本身也可以記錄成 ADR。

**問：怎麼知道一個決策「難以回頭」？**
答：有人用「**單向門與雙向門**」來比喻。雙向門：走過去發現不對，可以走回來，例如換一個日誌套件。單向門：走過去就很難回頭，例如選定主要的資料庫、決定資料要存在哪個國家、對外公開 API 的格式。單向門的決策值得多花時間、寫成 ADR；雙向門的決策可以快速做、做錯再改。

@section AI 時代的 ADR
**ADR 是給 AI 程式助手的最佳背景資料。**
讓 AI 協助修改程式碼時（第 38 課的情境工程），如果把相關的 ADR 一起提供給它，AI 就知道「為什麼這裡要這樣設計」，比較不會提出違反既有架構決策的修改。例如 AI 看到 ADR-0003，就不會建議「把 Session 改成 JWT 存在 localStorage 會比較簡單」。

**AI 系統特有的決策，也該寫成 ADR：**
- 選用哪個模型、為什麼（第 18 課）；
- 用 RAG 還是微調（第 25、31 課）；
- 提示詞的關鍵設計原則；
- 評估的標準和門檻（第 29 課）。

這些決策和模型版本、成本、效果數據緊密相關，而模型更新換代非常快。寫下「當時用的是哪個版本、評估分數是多少」，下次模型更新時，就有明確的比較基準。

**也可以請 AI 協助撰寫草稿：**把會議討論的重點交給 AI，請它依 ADR 格式整理。但「背景數據」和「負面代價」一定要自己檢查：AI 容易寫出聽起來合理、但不符合你實際情況的內容。

@section 動動腦：判斷看看
**題一**：架構改變了，舊的 ADR 應該修改成新的內容嗎？
→ 不應該。新增一份 ADR，並把舊的標記為「已被取代」，保留完整演進歷史。

**題二**：「選用 pgvector，因為它比較熱門」是好的決策理由嗎？
→ 不是。理由應扣回背景中的具體限制，例如資料量、預算、團隊規模、權限過濾需求。

**題三**：為什麼 ADR 要寫「重新評估的觸發條件」？
→ 讓大家知道這個決定在什麼條件下成立；條件改變時就該重新討論，避免決策變成教條。

**題四**：「函式名稱要用底線式命名」需要寫成 ADR 嗎？
→ 不需要。那是程式碼風格規範；ADR 用於影響深遠、難以回頭的架構決策。

@section 本課重點整理
- **ADR** 記錄重大架構決策的背景、方案、決定與代價，回答「當初為什麼這樣做」。
- **放在版本庫**：和程式碼一起、有歷史、可審查。
- **五個段落**：標題與狀態、背景與限制、候選方案、決定、後果與重新評估條件。
- **背景最重要**：決策的對錯取決於當時的規模、團隊、預算與需求。
- **公平比較**：至少 2 到 3 個可行方案，不寫稻草人。
- **誠實寫代價**，並給出量化的重新評估條件。
- **不刪改舊 ADR**：新增並標記為已被取代。
- **經典取捨**：模組化單體 vs. 微服務、pgvector vs. 專用向量庫、雲端 API vs. 自架模型。
- **AI 時代**：ADR 是 AI 程式助手的重要背景資料；模型選擇等 AI 決策也該記錄。

@term ADR
記錄重大架構決策之背景、選項、決定與後果的文件（Architecture Decision Record）。
@term 取捨
選擇某方案獲得好處的同時，必須放棄或承擔的代價（Trade-off）。
@term 背景與限制
決策當下的業務規模、團隊、預算與技術限制（Context）。
@term 候選方案
決策時認真評估過的可行選項（Considered Options）。
@term 稻草人方案
故意列出明顯不可行的選項來襯托偏好方案的錯誤做法。
@term 已被取代
ADR 的狀態之一，表示已有新決策取代它（Superseded）。
@term 重新評估條件
當特定指標超過門檻時，應重新討論決策的條件（Re-evaluation Trigger）。
@term 模組化單體
所有功能在同一應用中部署，但內部有清楚模組邊界的架構（Modular Monolith）。
@term 微服務
將系統拆成多個獨立部署、各自擁有資料的小服務（Microservices）。
@term 維運稅
系統拆分後增加的部署、監控、協調等額外負擔（Operational Tax）。
@term 損益平衡點
兩種方案成本相等的用量臨界點（Break-even Point）。
