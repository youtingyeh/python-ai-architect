@section 開場：靠記憶力把關，遲早出事
一個人寫三百行的小腳本時，你可能記得每次改完程式都跑一下 pytest。

但當專案長大，有後端 API、前端頁面、資料庫結構、AI 提示詞的評估集，還有好幾位同事一起開發時，靠「**人的記憶力和自律**」來跑測試、部署，遲早會出大事：
- 有人趕時間，**忘了跑測試**，就把壞掉的程式碼合併進主分支；
- 有人在自己電腦上測試通過，因為他電腦裡剛好有某個**沒提交的檔案**或**舊版套件**，推上伺服器卻立刻崩潰；
- 部署步驟有十幾個，某次漏了一步。

**CI/CD** 的核心價值，是把「驗證」和「發布」從**容易出錯的人工步驟**，變成**由程式碼定義、自動執行**的流程：
- **CI**（Continuous Integration，持續整合）：每次推送程式碼，**自動**在乾淨的環境中檢查、測試；
- **CD**（Continuous Delivery / Deployment，持續交付 / 部署）：檢查通過後，**自動**打包，甚至自動部署上線。

只要任何一關失敗（**紅燈**），就立刻**擋下**合併和部署。

**比喻：**工廠的**自動化品質檢驗線**。每一件產品出廠前，都必須自動通過尺寸、重量、功能的檢驗站。任何一站不合格，產品就被擋在線上，不會被裝箱出貨。而不是靠某位老師傅「憑感覺看一眼」。

這一課以 **GitHub Actions** 為例，學：
1. 流水線的五個核心要素；
2. 檢查的順序：越快的越先跑；
3. 一個實際攔下 bug 的例子；
4. 「綠燈」到底代表什麼，不代表什麼；
5. CI 本身的資安陷阱。

@section 流水線長什麼樣子
GitHub Actions 用一個 YAML 檔（放在 `.github/workflows/` 資料夾）描述自動化流程：
```
name: CI
on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install -r requirements.txt
      - run: ruff check .
      - run: mypy .
      - run: pytest

  deploy:
    needs: validate
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - run: echo "部署到正式環境"
```
這份檔案就叫做「**流水線**」（Pipeline 或 Workflow）。它本身也是程式碼，放在版本控制裡，修改流程也要經過審查。

@section 五個核心要素
**一、觸發條件（`on`）：什麼時候啟動？**
- `push` 到 main：程式碼合併進主分支時；
- `pull_request`：有人開 PR（第 52 課）時。

PR 觸發特別重要：程式碼在**合併進主分支之前**就先被檢查，壞掉的東西根本進不了主幹。

**二、乾淨的執行環境（`runs-on`）：每次都從零開始。**
每個工作（Job）都在一台**全新的**虛擬機上執行，裡面什麼都沒有：沒有你電腦上的暫存檔，沒有你忘記自己裝過的套件。

所以 CI 會**依照鎖定檔**（例如 `requirements.txt` 裡寫死的版本）從零安裝套件。在你電腦上能跑、CI 上卻跑不起來？那通常代表**你的專案少寫了某個相依套件**，CI 幫你抓到了。這和第 67 課 Docker 的精神一樣。

**比喻：**考試時，每位考生拿到的都是**全新的考卷**，不能帶自己的筆記。這樣才能確認你真的會，而不是剛好帶了小抄。

**三、失敗即停止：看結束碼。**
第 51 課學過：程式結束時會回傳一個**結束碼**（Exit Code），0 代表成功，非 0 代表失敗。

CI 的每一個步驟都看結束碼。pytest 只要有任何一個測試失敗，就回傳 1，這一步就失敗，**整個工作立刻停止**，後面的步驟不會執行。

**四、工作之間的依賴（`needs`）：沒過關就不部署。**
`deploy` 設了 `needs: validate`：只有 `validate` **成功**，`deploy` 才會執行。驗證亮紅燈，部署就**絕對不會發生**。

`if: github.ref == 'refs/heads/main'`：只有主分支才部署，PR 只做驗證。

**五、最小權限（`permissions`）。**
在最上層宣告 `contents: read`：預設只能**讀取**程式碼。只有真正需要發布的工作，才額外給予需要的權限。這是第 28 課最小權限原則在 CI 中的應用。

@section 檢查的順序：越快的越先跑
CI 的價值之一是「**快速回饋**」：越早知道錯了，越好修。所以檢查要依速度排序：

**第一關（幾秒鐘）：靜態檢查。**
不用執行程式，只「讀」程式碼就能發現的問題：
- **Linter**（程式碼檢查工具，例如 `ruff`）：語法錯誤、沒用到的變數、常見的壞寫法；
- **型別檢查**（`mypy`、TypeScript 的 `tsc`，第 62 課）：型別對不上；
- **秘密掃描**（`gitleaks`，第 68 課）：程式碼裡有沒有金鑰。

連語法都錯了，幾秒鐘就該報錯，不需要浪費幾分鐘去啟動資料庫跑測試。

**第二關（幾十秒到幾分鐘）：測試。**
- 單元測試；
- 整合測試：GitHub Actions 可以用 `services` 啟動一個**測試專用的 PostgreSQL** 容器（第 61、63 課）；
- AI 應用還可以在這裡跑**黃金評估集**（第 29 課），確認提示詞的修改沒有讓回答品質退步。

**第三關（只在主分支、前兩關都通過後）：打包與部署。**
- 打包成**不可變的產物**，例如 Docker 映像檔。「**測試過的那一份，就是上線的那一份**」；
- 先部署到**預備環境**（第 68 課），跑「**煙霧測試**」（Smoke Test）：最基本的檢查，例如健康檢查端點 `/healthz` 有沒有回傳 200；
- 確認沒問題，才切換到正式環境。

**「煙霧測試」**這個名字來自硬體業：新電路板第一次通電時，先看看有沒有冒煙。沒冒煙，再做詳細測試。

@section 走一遍：CI 攔下了一個 bug
某位工程師修改權限檢查函式時，不小心把：
```
if user.role == "admin":
```
寫成了：
```
if user.role != "admin":
```
他沒在自己電腦上跑測試，直接開了一個 PR。

GitHub Actions 自動啟動 `validate`：
1. 下載程式碼，建立乾淨的 Python 3.12 環境；
2. `ruff check .`：**通過**。語法完全合法，Linter 看不出邏輯錯誤；
3. `pytest`：第 65 課寫的測試 `test_student_cannot_delete_course` 發現，學生竟然收到 **200** 而不是 **403**。斷言失敗，pytest 回傳結束碼 1；
4. PR 被標示為紅燈 ✕。因為 `deploy` 設了 `needs: validate`，部署被**自動跳過**。

正式環境**毫髮無傷**。工程師看著 CI 日誌裡失敗的行號，修好條件，再推一次。CI 轉成綠燈 ✓，這才安全合併。

**注意第 2 步：**Linter 抓不到邏輯錯誤，型別檢查也抓不到（`==` 和 `!=` 型別都對）。**只有測試能抓到「行為錯了」**。CI 只是執行者，真正的守門員是你寫的那些測試。

**分支保護：**在 GitHub 的設定中，可以把主分支設定為「**必須 CI 通過才能合併**」。這樣連管理員也沒辦法跳過紅燈直接合併。

@section 綠燈代表什麼，不代表什麼
**綠燈只代表一件事：「目前寫進流水線的那些檢查，都通過了。」**

它**不代表**：
- **系統沒有 bug**：沒寫測試的情境，CI 當然抓不到；
- **部署出問題可以輕鬆回復**：這一點特別重要。

**資料庫結構變更的陷阱：**
假設新版本包含一個資料庫變更：刪除某個欄位（`DROP COLUMN`）。部署後發現問題，你把程式碼 `git revert` 回舊版。但是，**被刪掉的欄位和裡面的資料不會回來**。程式碼可以回復，資料不行。

**解法：「先擴充、再收斂」**（Expand and Contract）。以「把 `name` 欄位拆成 `first_name` 和 `last_name`」為例：
1. **擴充**：先**新增**新欄位，舊欄位保留。新舊程式都能運作；
2. **過渡**：程式同時寫入新舊欄位，把舊資料搬到新欄位；
3. **收斂**：確認所有程式都只用新欄位、穩定運作一段時間後，**最後**才刪除舊欄位。

每一步都可以安全回退。

**比喻：**搬家時，不會先把舊房子拆了再去找新房子。而是先租好新房子、慢慢搬過去、確定住得習慣了，才退掉舊房子。

@section CI 本身的資安陷阱
**陷阱一：`|| true` 製造假綠燈。**
```
- run: pytest || true
```
`|| true` 的意思是「如果前面失敗，就執行 `true`」，而 `true` 永遠成功。結果**測試全部失敗，結束碼仍然是 0**，CI 永遠亮綠燈，把壞掉的程式碼一路推上正式環境。

有人加這個是因為「某個測試不穩定，先讓它過」。正確做法是修好那個不穩定的測試（第 65 課），或明確地暫時跳過**那一個**，而不是關掉整個測試的把關。

**陷阱二：外部 PR 偷走秘密。**
開源專案會收到陌生人的 PR。如果 CI 設定不當（例如使用 `pull_request_target` 觸發器，又直接執行了 PR 裡的程式碼），攻擊者就能在 PR 中放一段惡意腳本，在你的 CI 裡執行，**偷走部署用的秘密金鑰**。

原則：**未經審查的外部程式碼，不能在擁有秘密的環境中執行。**GitHub 預設對外部 Fork 的 PR 不提供秘密，不要為了方便而繞過這個保護。

**陷阱三：第三方 Action 的供應鏈風險。**
`uses: someone/some-action@v1` 是在使用別人寫的程式。如果那個專案被入侵，標籤 `v1` 被指向惡意版本，你的 CI 就會執行惡意程式。重要的專案可以把第三方 Action 鎖定到**特定的提交雜湊值**，而不是可以被移動的版本標籤。這和第 67 課「不要用 latest」是同一個道理。

@section 常見疑問
**問：持續交付和持續部署有什麼不同？**
答：差在最後一步有沒有人按按鈕。**持續交付**（Delivery）：每次通過檢查，都自動產出一份「**隨時可以上線**」的版本，但上線與否由人決定，按一下按鈕即可。**持續部署**（Deployment）：連那個按鈕都省了，通過檢查就自動上線。後者需要非常完善的測試和監控，以及能快速回退的能力。大多數團隊從持續交付開始。

**問：CI 跑太久怎麼辦？**
答：常見的加速方法有：**快取**套件安裝結果（不用每次重新下載）；把互不相依的檢查**並行**執行（Linter 和單元測試可以同時跑）；只在相關檔案改動時才跑某些昂貴的檢查（例如只改了文件，就不跑端對端測試）。目標是讓開發者在**十分鐘內**得到結果。CI 超過半小時，大家就會開始想辦法繞過它。

**問：部署後才發現問題，怎麼最快止血？**
答：先**回退**到上一個正常的版本，再慢慢查原因。這就是為什麼要保留「不可變產物」：上一版的映像檔還在，重新部署它只要幾分鐘。更進階的做法是「**金絲雀部署**」（Canary）：新版本先只給 5% 的使用者，觀察錯誤率和延遲（第 66 課的指標），沒問題再逐步擴大到 100%。名字來自早期礦工帶金絲雀下礦坑偵測毒氣：先讓一小部分承擔風險。

**問：AI 提示詞的修改也要經過 CI 嗎？**
答：要。提示詞改一個字，模型的行為就可能大幅改變（第 20、29 課）。把提示詞放進版本控制，修改時自動跑黃金評估集，分數低於門檻就擋下，和程式碼的測試是同樣的道理。**提示詞也是程式碼。**

@section 實作：需要資料庫的測試怎麼在 CI 上跑
很多測試需要真的資料庫（第 65 課的整合測試）。GitHub Actions 可以在工作執行時，順便啟動一個 PostgreSQL 容器（第 67 課），測試結束後自動丟掉：
```yaml
name: ci
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_PASSWORD: test
          POSTGRES_DB: school_test
        ports: ["5432:5432"]
        options: >-
          --health-cmd "pg_isready -U postgres"
          --health-interval 5s
          --health-retries 10
    env:
      DATABASE_URL: postgresql://postgres:test@localhost:5432/school_test
      OPENAI_API_KEY: sk-fake-for-tests
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip
      - run: pip install -r requirements.txt
      - run: ruff check .
      - run: pytest -q
```
幾個值得注意的地方：
- **`services` 區塊**啟動了一個乾淨的資料庫。每次執行都是全新的，測試之間不會互相汙染；
- **`health-cmd`** 讓 CI 等資料庫真的準備好了才開始跑測試，避免「資料庫還沒開好，測試就連不上」這種時好時壞的失敗；
- **這裡的密碼是假的，可以直接寫在檔案裡**，因為這個資料庫只存在幾分鐘、只有測試資料。真正的秘密（例如部署用的金鑰）才要放在 GitHub 的 Secrets 裡（第 68 課）；
- **LLM 金鑰是假的**：CI 上的測試應該用假的 LLM 回應（第 65 課的替身），不要真的呼叫外部 API。否則測試會變慢、會花錢，也會因為外部服務不穩而時好時壞；
- **`cache: pip`** 會快取下載過的套件，讓下一次執行快上不少。

@section 和 AI 一起做：讓 CI 驗收 AI 的修改
CI 是你和 AI 合作時**最可靠的守門員**。不管程式碼是你寫的、同事寫的，還是 AI 寫的，都必須通過同一套自動檢查才能合併。這讓你不必完全信任任何一方。

**請 AI 寫工作流程設定**
```
請為 Python 專案寫一個 GitHub Actions 工作流程：
- 在 push 和 pull request 時執行
- 步驟：安裝依賴 → ruff 檢查 → mypy 型別檢查 → pytest
- 權限設為最小（contents: read）
- 任何一步失敗就停止
```

**怎麼檢查**
- 確認 `permissions` 有明確設定，而不是使用預設的寬鬆權限；
- 確認第三方 Action 有指定版本（例如 `actions/checkout@v4`）；
- 檢查有沒有把秘密印在日誌裡的步驟；
- 故意推一個會讓測試失敗的修改，確認 CI 真的會擋下來。

**讓 AI 讀懂 CI 失敗的原因**
CI 失敗時，把錯誤日誌貼給 AI，請它找出原因，是非常有效率的做法。但要小心一種情況：AI 為了讓 CI 通過，可能會建議「跳過這個測試」或「降低檢查標準」。這是在拆除守門員，而不是修正問題。

**一個好的規則**
在團隊裡約定：**修改 CI 設定本身的 PR，一定要有人親自審查**，不能只靠自動檢查通過就合併。因為 CI 設定就是檢查的規則，改規則的人不能同時是被檢查的人。

@section 動動腦：判斷看看
**題一**：`deploy` 工作設了 `needs: validate`，如果 pytest 有一個測試失敗，會發生什麼事？
→ validate 失敗，deploy 不會執行，壞掉的程式碼不會上線。

**題二**：`pytest || true` 有什麼問題？
→ 測試失敗時結束碼仍是 0，CI 永遠綠燈，失去把關作用。

**題三**：CI 全部綠燈，部署後發現問題，`git revert` 回舊版就能恢復一切嗎？
→ 不一定。程式碼可以回復，但已執行的破壞性資料庫變更（如刪除欄位）不會自動復原；資料庫變更應採先擴充、再收斂的策略。

**題四**：為什麼 Linter 和型別檢查要排在測試之前？
→ 它們只需幾秒，能最快回報基本錯誤，不必浪費時間啟動資料庫跑測試。

@section 本課重點整理
- **CI/CD**：把驗證和發布變成自動化的品質閘門，不再依賴人的記憶。
- **五個要素**：觸發條件（PR 時就檢查）、乾淨環境（依鎖定檔從零安裝）、看結束碼失敗即停、`needs` 阻斷部署、最小權限。
- **檢查順序**：靜態檢查（秒級）→ 測試（分鐘級）→ 打包、預備環境、煙霧測試、正式部署。
- **真正的守門員是測試**：Linter 和型別檢查抓不到邏輯錯誤。
- **分支保護**：主分支必須 CI 通過才能合併。
- **綠燈的意義有限**：只代表寫了的檢查都通過；資料庫變更要用先擴充、再收斂。
- **CI 資安**：不用 `|| true`、外部 PR 不能接觸秘密、第三方 Action 注意供應鏈風險。

@term CI
每次提交程式碼時，自動在乾淨環境中建置與測試（Continuous Integration，持續整合）。
@term CD
驗證通過後，自動打包並交付或部署（Continuous Delivery / Deployment）。
@term GitHub Actions
GitHub 內建的自動化流水線服務。
@term 流水線
定義自動化檢查與部署步驟的流程（Pipeline / Workflow）。
@term 品質閘門
不通過就無法進入下一階段的自動檢查關卡（Quality Gate）。
@term 結束碼
程式結束時回傳的數字，0 代表成功、非 0 代表失敗（Exit Code）。
@term Linter
不執行程式、只讀程式碼就找出問題的檢查工具。
@term 煙霧測試
部署後最基本的健康檢查，確認系統能正常啟動（Smoke Test）。
@term 分支保護
規定主分支必須通過檢查才能合併的設定（Branch Protection）。
@term 不可變產物
建置後不再修改、測試與上線使用同一份的打包結果（Immutable Artifact）。
@term 先擴充再收斂
資料庫變更先新增、過渡、最後才刪除舊結構，以保持可回退（Expand and Contract）。
@term 供應鏈風險
使用的第三方套件或工具被入侵，導致自己的系統受害（Supply Chain Risk）。
