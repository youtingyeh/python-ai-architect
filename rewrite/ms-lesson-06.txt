@section 開場：教學範例的一行程式，和真實產品差多遠？
在教學範例中，呼叫 AI 產生文字只需要一行程式：

```
response = client.chat.completions.create(model="gpt-4o-mini", messages=[...])
```

跑一次、印出結果，看起來很順利。但如果你把這一行直接放進給上千人使用的產品裡，很快就會遇到各種狀況：
- 某天下午，AI 服務忙不過來，回傳「請求太多」的錯誤，你的網站整個卡住；
- 使用者不小心按了送出，傳來一個空白訊息，你白白付了錢讓 AI 回答「請問您需要什麼？」；
- 你要求 AI 回傳 JSON，它卻在前面加了一句「好的，以下是您要的資料：」，程式解析失敗、整個崩潰；
- 某次 AI 回應花了 40 秒，使用者早就關掉網頁了，你還在等。

這一課對應 Microsoft《Generative AI for Beginners》第 06 課「建立文字生成應用」。我們的重點不是「怎麼呼叫 API」（那只要一行），而是「**怎麼讓這一行在真實世界中穩定、安全、省錢地運作**」。

**為什麼 AI API 特別需要小心？**和一般的網站功能（例如從資料庫讀取一筆會員資料，通常幾毫秒完成、幾乎不花錢）相比，AI API 有三個特別的性質：
1. **慢，而且快慢不定**：同樣的請求，可能 2 秒完成，也可能 25 秒。
2. **按量計費，而且有使用上限**：每個 Token 都要錢，每分鐘能送的請求數也有限制。
3. **輸出不保證正確**：格式可能出錯，內容可能有幻覺。

所以我們要建立一條完整的「防護流程」。這一課會一步一步介紹五個關卡。

@section 一次 AI 請求的五道關卡
一個正式產品中的 AI 呼叫，應該經過五道關卡：

**關卡一：送出前先檢查輸入。**
在花任何錢之前，先擋掉明顯無效的輸入（空白、太短、太長）。

**關卡二：設定時間和長度的上限。**
告訴系統「最多等幾秒」、「最多產生幾個 Token」，避免無止境地等待或花費。

**關卡三：遇到暫時性錯誤，聰明地重試。**
服務忙碌時，等一下再試；但不要無腦地狂試，也不要對「永遠不會成功」的錯誤重試。

**關卡四：檢查回應的格式和內容。**
確認 AI 回傳的資料真的符合規格，才能交給後續的程式使用。

**關卡五：失敗時優雅地處理，並記錄一切。**
所有方法都失敗時，給使用者一個清楚的回應，而不是讓整個網站當掉；同時記錄發生了什麼事，方便日後分析。

這就像寄送重要包裹：寄出前檢查地址是否完整（關卡一）、設定最晚送達時間（關卡二）、遇到塞車就改時間再送而不是一直按喇叭（關卡三）、收到時檢查內容物是否正確（關卡四）、送不到時通知寄件人並留下紀錄（關卡五）。

@section 關卡一：別為無效的請求付錢
很多初學者寫後端時，直接把使用者傳來的文字塞進提示詞，送給 AI。這會造成兩個問題：

**問題一：空白輸入也要付錢。**
使用者不小心按了送出，傳來一個只有空白的訊息。AI 仍然會讀取你的系統提示詞（可能有幾百個 Token），然後認真地回答「請問您需要我摘要什麼內容呢？」。錢花了，產生的還是一筆沒用的資料。

**問題二：超長輸入會爆預算。**
有人（可能是惡意的，也可能只是不小心）一次貼上 50 萬字的檔案。單次請求就可能超過模型的上下文上限而失敗，或者花掉好幾美元。

**解法：在本地先檢查。**
「本地」是指在你自己的伺服器上，不需要呼叫任何外部服務。這種檢查**幾乎不花錢、只要幾微秒**。

```
cleaned = text.strip()          # 去掉前後空白
if len(cleaned) < 5:
    return 錯誤("內容太短")      # HTTP 400
if len(cleaned) > 8000:
    return 錯誤("內容太長")
```

`strip()` 會去掉字串前後的空白、換行等看不見的字元。如果去掉後長度是 0 或很短，直接拒絕。

**HTTP 狀態碼是什麼？**網頁伺服器回應時，會附上一個三位數的代碼，表示結果：
- **2xx**（例如 200）：成功。
- **4xx**：**客戶端**的錯誤，也就是「你送來的東西有問題」。例如 400（請求格式錯誤）、401（沒有登入或金鑰錯誤）、403（沒有權限）、404（找不到）、429（請求太多）。
- **5xx**：**伺服器端**的錯誤，也就是「我這邊出問題了」。例如 500（內部錯誤）、502（上游沒回應正確）、503（暫時無法服務）、504（上游逾時）。

如果想更精準地控制長度，可以用第 13 課介紹的 `tiktoken` 在本地計算 Token 數，而不只是算字數。

@section 關卡二：設定逾時和長度上限
**逾時（Timeout）：最多等多久？**
網路請求可能因為各種原因卡住。如果不設逾時，你的程式可能永遠在等。設定一個合理的上限，例如 30 秒，超過就放棄並進入錯誤處理。

逾時通常分成兩種：
- **連線逾時**：多久內要和對方伺服器建立連線（通常設短一點，例如 5 秒）。
- **讀取逾時**：連上後多久內要收到回應（AI 生成較慢，可以設長一點，例如 30 到 60 秒）。

**max_tokens：最多產生多少？**
第 17 課提過，一定要設定輸出長度的上限。原因之一是：模型偶爾會陷入**重複迴圈**（「很重要很重要很重要……」），如果沒有上限，它會一直產生到上下文的最大長度，浪費大量的錢和時間。

**temperature：任務需要多少創意？**
資料擷取、格式轉換這類需要穩定結果的任務，溫度設為 0 或 0.1（第 17 課）。

@section 關卡三：聰明地重試
雲端 AI 服務通常有兩種使用上限：
- **RPM**（Requests Per Minute）：每分鐘最多幾個請求。
- **TPM**（Tokens Per Minute）：每分鐘最多幾個 Token。

流量突然暴增時（例如行銷活動），超過上限的請求會收到 **HTTP 429**「請求太多」的回應，通常還會附帶一個 `Retry-After` 標頭，告訴你「幾秒後再試」。伺服器太忙時，也可能回傳 **503**「暫時無法服務」。

**錯誤的做法：立刻、不停地重試。**
```
while True:
    try: return call_ai()
    except: pass    # 失敗就馬上再試
```

想像有 100 個使用者同時遇到 429 錯誤，每個都立刻重試、再失敗、再重試……所有請求在同一瞬間湧向已經過載的伺服器，讓它更加癱瘓。這叫做「**驚群效應**」（Thundering Herd），就像停電後恢復供電的瞬間，所有電器同時啟動，又把電路燒壞了。

**正確的做法：指數退避加上隨機抖動。**

**指數退避**（Exponential Backoff）：每次失敗後，等待時間**加倍**：第一次等 1 秒、第二次等 2 秒、第三次等 4 秒……給伺服器喘息的空間。

**隨機抖動**（Jitter）：在等待時間上加一點隨機變化。這樣 100 個使用者就不會在同一秒重試，而是分散開來。

**上限**：設定最多重試幾次（通常 3 次）和最長等待時間（例如 16 秒）。不能無止境地重試。

公式：
$$t_{\text{等待}} = \min(T_{\text{上限}},\ b \times 2^r) \times \text{隨機}(0.5, 1.0)$$

（b 是基本等待時間，例如 1 秒；r 是第幾次重試，從 0 開始。）

**算一次**：b = 1 秒、上限 16 秒。
- 第 1 次重試（r = 0）：$1 \times 2^0 = 1$ 秒，乘上隨機數，實際等 0.5 到 1 秒。
- 第 2 次（r = 1）：$1 \times 2 = 2$ 秒，實際 1 到 2 秒。
- 第 3 次（r = 2）：$1 \times 4 = 4$ 秒，實際 2 到 4 秒。
- 3 次都失敗，就放棄，進入關卡五。

如果回應有 `Retry-After` 標頭，優先照它的建議等待。

**最重要的一點：分清楚哪些錯誤值得重試。**

**可以重試**（暫時性的問題，等一下可能就好了）：
- 網路逾時
- 429 請求太多
- 500、502、503、504 伺服器暫時故障

**不要重試**（重試一百次也一樣會失敗）：
- 400 請求格式錯誤、超過上下文長度 → 要改的是你的請求
- 401、403 金鑰無效或沒有權限 → 要改的是金鑰設定
- 內容安全過濾攔截 → 要改的是輸入內容

對這些錯誤重試，只是白白浪費時間和資源。應該立刻停止，回報明確的錯誤訊息。

@section 關卡四：「我有叫它回傳 JSON」不等於「它一定會回傳 JSON」
新手最常寫的一行危險程式：

```
data = json.loads(ai_response)   # 把 AI 的回應解析成 JSON
```

沒有任何錯誤處理，理由是「我已經在提示詞裡寫了『請只回傳 JSON』」。

**但提示詞只是「建議」，不是「保證」。**回想第 17 課：模型只是在產生機率最高的文字。實際上線後，你會遇到這四種讓解析失敗的情況：

**① 多了前後文。**
```
好的！以下是您要的資料：
```json
{"score": 85}
```
希望對您有幫助！
```
模型很習慣用 Markdown 的程式碼區塊包住 JSON，還加上禮貌的前言後語。

**② 內部格式錯誤。**
字串裡出現沒有正確處理的雙引號或換行符號，讓 JSON 的結構斷掉。

**③ 被截斷。**
輸出達到 max_tokens 上限，JSON 寫到一半就停了：`{"summary": "這份報告指出...`。

**④ 格式正確，但內容不對。**
JSON 語法完全合法，但欄位名稱拼錯（要 `action_items` 卻寫成 `actions`）、型別錯誤（要數字 85 卻給字串「八十五分」）、數值超出範圍（分數要 1 到 5，卻給了 7）。

**兩層保障：**

**第一層：使用模型原生的「結構化輸出」功能。**
OpenAI、Azure 等新版 API 提供了 **Structured Outputs**（結構化輸出）功能：你提供一份 JSON Schema（描述資料結構的規格），模型在生成時，系統會**強制**每一個 Token 都必須符合這個結構。這叫做「**受限解碼**」（Constrained Decoding）：在第 17 課的「從機率表中挑字」那一步，把不符合格式的選項直接排除。這樣產生的 JSON 在**語法上**一定合法。

**第二層：後端一定要再驗證一次。**
即使用了結構化輸出，還是要在你的程式中檢查**內容**是否合理。因為格式合法，不代表數值合理、內容正確。

@section 用 Pydantic 定義資料合約
Python 有一個非常流行的套件叫 **Pydantic**，專門用來定義和檢查資料格式。你可以把它想成一份「**資料合約**」：清楚寫明每個欄位叫什麼、是什麼型別、有什麼限制，不符合合約的資料一律拒收。

**例子：從產品評論中擷取情緒分析結果。**
```
from pydantic import BaseModel, Field
from typing import Literal

class ReviewAnalysis(BaseModel):
    sentiment: Literal["positive", "neutral", "negative"]
    confidence: float = Field(ge=0.0, le=1.0)
    key_issues: list[str]
```

這份合約規定：
- `sentiment`（情緒）只能是 positive、neutral、negative 三個值之一（`Literal` 表示「只能是這幾個字面值」）；
- `confidence`（信心）是 0 到 1 之間的小數（`ge` 是大於等於，`le` 是小於等於）；
- `key_issues`（主要問題）是一串文字。

如果 AI 回傳：
```
{"sentiment": "good", "confidence": 1.5, "key_issues": []}
```
Pydantic 會立刻報錯，明確指出：「sentiment 的值 good 不在允許清單中」、「confidence 的值 1.5 超過上限 1.0」。這樣錯誤的資料就不會寫進資料庫、不會讓網頁上的圖表顯示錯誤。

**驗證失敗怎麼辦？兩種策略：**

**策略一：請 AI 修正一次。**
把錯誤訊息（例如「sentiment 必須是 positive、neutral、negative 之一」）連同 AI 剛才的錯誤輸出，再送一次給 AI，請它修正。這適合**不急**的批次處理任務。但最多修一次，避免無止境的來回。

**策略二：直接優雅降級。**
對於使用者在線上等待的即時功能，修正一次會讓等待時間加倍。所以常見做法是直接回傳一個明確的狀態，例如：
```
{"status": "SCHEMA_VALIDATION_FAILED", "raw_text": "（AI 的原始輸出）"}
```
保留原始文字供人工檢查，前端則顯示「目前無法分析，請稍後再試」或切換到備用流程。

@section 關卡五：記錄一切，掌握成本
一個沒有監控的 AI 服務，就像沒有儀表板的飛機：你不知道油還剩多少、飛得多快、哪裡出了問題。

**每次呼叫結束時（不管成功或失敗），都應該自動記錄：**
- `request_id`：這次請求的唯一編號，串起前端、後端、AI 服務的所有紀錄。使用者回報問題時，用這個編號就能找到完整經過。
- `model_version`：用的是哪個模型的**精確版本**（第 18 課：鎖定版本）。
- `prompt_tokens`、`completion_tokens`：輸入和輸出各用了幾個 Token。
- `estimated_cost_usd`：估算這次花了多少錢。
- `latency_ms`：花了幾毫秒。
- `retry_count`：重試了幾次。
- `outcome_status`：最終結果，例如 SUCCESS（成功）、RATE_LIMITED（被限流）、TIMEOUT（逾時）、VALIDATION_ERROR（格式驗證失敗）。

這叫做「**可觀測性**」（Observability）：讓系統的內部狀態可以從外部被看見和理解。

**算一筆帳，看看為什麼這很重要。**
假設模型價格：輸入每百萬 Token 0.15 美元，輸出每百萬 Token 0.60 美元。
平均每次請求：1,200 個輸入 Token、300 個輸出 Token。

單次成本：
$$\frac{1200 \times 0.15 + 300 \times 0.60}{1{,}000{,}000} = \frac{180 + 180}{1{,}000{,}000} = 0.00036 \text{ 美元}$$

很便宜。但如果沒有重試上限，10% 的失敗請求每次都盲目重試 10 次：
- 正常的 90% 請求：每次 1 單位成本，共 0.9 單位
- 失敗的 10% 請求：每次 11 單位成本（原本 1 次 + 重試 10 次），共 1.1 單位

**10% 的失敗流量，花掉的錢比 90% 正常流量還多！**有了 `retry_count` 的紀錄，你才能發現這種問題，並設定第 16 課的成本斷路器。

@section 把五道關卡串起來
用一段簡化的程式，看看五道關卡怎麼組合在一起：

```
def analyze_review(text):
    # 關卡一：本地檢查
    cleaned = text.strip()
    if not (5 <= len(cleaned) <= 8000):
        return {"status": "INVALID_INPUT"}

    for attempt in range(3):          # 關卡三：最多 3 次
        try:
            # 關卡二：逾時和長度上限
            resp = call_ai(cleaned, timeout=30, max_tokens=300, temperature=0)
            # 關卡四：格式驗證
            result = ReviewAnalysis.model_validate_json(resp.text)
            log(status="SUCCESS", retries=attempt, usage=resp.usage)
            return {"status": "OK", "data": result}
        except 暫時性錯誤:
            wait(backoff_with_jitter(attempt))
        except ValidationError:
            log(status="VALIDATION_ERROR")
            return {"status": "SCHEMA_VALIDATION_FAILED"}
        except 永久性錯誤 as e:
            log(status="FATAL", error=e)
            return {"status": "ERROR", "message": str(e)}

    # 關卡五：重試用完，優雅降級
    log(status="RETRY_EXHAUSTED")
    return {"status": "SERVICE_BUSY"}
```

每一種失敗，都有一個**明確、穩定**的狀態代碼回傳，前端可以根據代碼顯示對應的訊息，而不是讓使用者看到一堆看不懂的錯誤訊息，或整個頁面當掉。

實務上，不用自己從頭寫重試邏輯。Python 的 **tenacity** 套件、OpenAI 官方 SDK 內建的 `max_retries` 參數，都已經實作了指數退避。但你仍然需要理解原理，才能正確設定和判斷哪些錯誤該重試。

@section 動動腦：找出問題
**情境一**：某工程師的重試邏輯是：「任何錯誤都重試，最多 10 次，每次間隔 0.1 秒。」有什麼問題？
→ 三個問題：(1) 400、401 這類永久性錯誤不該重試；(2) 間隔太短且固定，沒有指數退避，會造成驚群效應；(3) 10 次太多，失敗時浪費大量時間和金錢。應改為只對暫時性錯誤重試、最多 3 次、指數退避加抖動。

**情境二**：提示詞已經寫「只回傳包含 score（1 到 5 的整數）的 JSON」，所以程式直接 `json.loads` 然後存進資料庫。可能出什麼事？
→ AI 可能加上前言後語、用程式碼區塊包起來、輸出被截斷、或給出 score: 7 這種超出範圍的值。前三種會讓程式崩潰，第四種會把錯誤資料存進資料庫。應該用結構化輸出加上 Pydantic 驗證。

**情境三**：一個公開的摘要 API，沒有檢查輸入就直接送給 AI。有人寫了一個程式，每秒送 100 個空白請求。會發生什麼？
→ 每個空白請求都會消耗系統提示詞的 Token、佔用每分鐘的請求額度，讓正常使用者被限流，而且帳單持續增加。本地檢查可以在零成本的情況下擋掉這些請求。

@section 本課重點整理
- **AI API 三特性**：慢且不穩定、按量計費有上限、輸出不保證正確。教學範例的一行程式，上線前要加上完整的防護。
- **關卡一：本地檢查**：空白、太短、太長的輸入直接拒絕，零成本。
- **關卡二：設上限**：連線和讀取逾時、max_tokens、適當的溫度。
- **關卡三：聰明重試**：只對暫時性錯誤（逾時、429、5xx）重試，最多 3 次，指數退避加隨機抖動，避免驚群效應。400、401、403 不要重試。
- **關卡四：驗證輸出**：提示詞不保證格式。用結構化輸出（受限解碼）確保語法正確，再用 Pydantic 檢查內容。
- **關卡五：降級和記錄**：失敗時回傳明確的狀態代碼；記錄 Token 用量、成本、延遲、重試次數、結果，才能發現問題和控制成本。

@term 逾時
等待回應的時間上限（Timeout），超過就放棄並進入錯誤處理。
@term HTTP 狀態碼
伺服器回應時附帶的三位數代碼，2xx 成功、4xx 客戶端錯誤、5xx 伺服器端錯誤。
@term RPM
每分鐘請求數上限（Requests Per Minute）。
@term TPM
每分鐘 Token 數上限（Tokens Per Minute）。
@term 驚群效應
大量請求在同一瞬間同時重試，讓已經過載的服務更加癱瘓的現象（Thundering Herd）。
@term 指數退避
每次失敗後等待時間加倍的重試策略（Exponential Backoff）。
@term 隨機抖動
在等待時間中加入隨機變化，讓重試分散開來（Jitter）。
@term 結構化輸出
讓模型生成時強制符合指定 JSON 結構的 API 功能（Structured Outputs）。
@term 受限解碼
生成時只允許符合格式規則的 Token 被選中的技術（Constrained Decoding）。
@term JSON Schema
描述 JSON 資料結構（欄位名稱、型別、限制）的標準規格格式。
@term Pydantic
Python 套件，用類別定義資料格式，自動檢查資料是否符合規格。
@term 可觀測性
透過紀錄、指標和追蹤，讓系統內部狀態能從外部被看見和理解的能力（Observability）。
