@section 開場：程式不住在綠色的播放鍵裡
很多人學 Python 時，都是在 VS Code 之類的編輯器裡按一下綠色的「執行」按鈕。久了會以為程式「住在」那個按鈕裡。

等到要把程式放上雲端伺服器、裝進 Docker 容器（第 63 課），或交給自動化流程（第 65 課）執行時，面對一個沒有滑鼠、只有黑底白字的**終端機**（Terminal），常常一頭霧水：
- 為什麼在編輯器裡讀得到的 `open("data.json")`，換個地方執行就說找不到檔案？
- 背景跑的 AI 訓練程式把伺服器記憶體吃光了，要怎麼找到它、安全地停掉它？
- 為什麼不能把 AI 服務的 API 金鑰直接寫在程式碼裡？

要回答這些問題，需要理解作業系統的一個核心概念：**行程**（Process）。這一課以 **Linux** 為主（絕大多數伺服器都用它，Mac 的終端機也非常相似）。我們要學：
1. 按下 Enter 之後，到底發生了什麼事？
2. 行程有哪些「隨身物品」：編號、工作目錄、環境變數、三條資料管道；
3. 相對路徑的陷阱；
4. 怎麼優雅地停止程式，而不是直接拔插頭；
5. 環境變數：把設定和程式碼分開。

@section 終端機和 Shell
**終端機**是一個讓你**用文字下指令**的視窗。在終端機裡負責「聽懂」你指令的程式，叫做 **Shell**（殼層），常見的有 bash 和 zsh。

幾個最常用的指令：
- `pwd`：顯示我現在在哪個資料夾（print working directory）；
- `ls`：列出這個資料夾裡有什麼檔案；
- `cd 資料夾`：切換到某個資料夾；
- `python3 app.py`：用 Python 執行 `app.py`。

**比喻：**Shell 像一位櫃台接待員。你說「幫我跑 app.py」，他會去找負責的人（Python），安排好工作環境，然後讓它開始工作。

@section 按下 Enter 之後的四個步驟
當你輸入 `python3 app.py` 並按下 Enter，背後依序發生了四件事：

**第一步：找到 `python3` 在哪裡。**
Shell 怎麼知道 `python3` 這個程式放在硬碟的哪裡？它會去看一個叫 **`PATH`** 的設定。`PATH` 是一串資料夾清單，例如：
```
/usr/local/bin:/usr/bin:/bin
```
Shell 依序在這些資料夾裡找名叫 `python3` 的程式，找到第一個就用它。

這也解釋了一個常見的問題：「為什麼我裝了某個工具，終端機卻說 `command not found`？」通常是因為那個工具所在的資料夾，不在 `PATH` 裡。

**第二步：建立一個新的行程。**
Shell 請作業系統的核心（**Kernel**）建立一個新的**行程**。作業系統會給它：
- 一個獨一無二的編號：**PID**（Process ID，行程編號）；
- 一塊**獨立的記憶體空間**，其他行程不能直接碰。

**第三步：行程繼承「隨身物品」。**
新行程會從 Shell（它的「父行程」）那裡繼承：
- **目前工作目錄**（CWD，Current Working Directory）：也就是你**下指令時所在的資料夾**；
- **環境變數**：一組「名稱 = 值」的設定，例如 `PATH`、`HOME`。在 Python 裡可以用 `os.environ` 讀取；
- **三條標準資料管道**（下一節說明）。

**第四步：執行，然後回報結果。**
Python 載入 `app.py` 開始執行。結束時，會交給作業系統一個整數，叫做「**結束狀態碼**」（Exit Code）：
- `0`：成功；
- 非 0（例如 `1`）：失敗。

自動化工具（例如第 65 課的 GitHub Actions）就是靠這個數字判斷「這一步有沒有成功」。測試失敗時，pytest 會回傳非 0，整條自動化流程就會停下來。

**比喻：**行程像一位被派去出差的員工。公司（作業系統）給他一個員工編號（PID）、一間獨立的辦公室（記憶體），他帶著出發地點（工作目錄）和一份公司規定（環境變數）去工作，回來時交一份報告：「順利完成」（0）或「出了問題」（非 0）。

**同一個程式執行兩次，就是兩個行程。**
在兩個終端機視窗各執行一次 `python3 app.py`，會得到兩個不同 PID 的行程，記憶體**完全分開**。一個行程修改了自己的變數，不會影響另一個。這在之後的網站伺服器擴充（第 73 課）中非常重要。

@section 三條資料管道：stdin、stdout、stderr
每個行程一啟動，就會打開三條標準的資料管道：
- **stdin**（標準輸入，編號 0）：程式讀取輸入的地方，預設是鍵盤。Python 的 `input()` 就是從這裡讀；
- **stdout**（標準輸出，編號 1）：程式正常輸出的地方，預設是螢幕。`print()` 就是寫到這裡；
- **stderr**（標準錯誤，編號 2）：程式輸出錯誤訊息的地方，預設也是螢幕。

**為什麼要分成兩條輸出？**
因為它們可以被**分開導向**不同的地方：
```
python3 app.py > result.txt 2> error.log
```
- `>`：把 stdout 存到 `result.txt`；
- `2>`：把 stderr 存到 `error.log`。

這樣，正常的結果和錯誤訊息就不會混在一起。

**一個常見的陷阱：輸出被「卡住」了。**
當 stdout 被導向檔案或 Docker 的日誌時，Python 為了效率，會先把輸出存在一個「**緩衝區**」裡，等累積到一定大小（例如 4KB）才一次寫出去。

結果，你的背景程式每秒 `print("heartbeat")`，日誌裡卻好幾分鐘都看不到任何東西，你以為程式卡死了，其實只是還沒寫出來。

**解法：**
- `print("heartbeat", flush=True)`：每次都立刻寫出去；
- 或執行時加上 `python3 -u app.py`（u = unbuffered，不緩衝）；
- 或使用 Python 的 `logging` 模組（第 62 課會學到）。

@section 相對路徑的陷阱
這是最常見的錯誤之一。

假設你的程式放在 `/opt/ai/app.py`，同一個資料夾裡有 `config.json`。程式裡寫：
```
open("config.json")
```

- 如果你先 `cd /opt/ai`，再執行 `python3 app.py`：**成功**；
- 如果你在家目錄 `/home/ubuntu` 執行 `python3 /opt/ai/app.py`：**找不到檔案**！

**為什麼？**因為 `"config.json"` 是一個「**相對路徑**」，它是相對於**目前工作目錄**（你下指令時所在的地方），而**不是**相對於 `app.py` 所在的資料夾。

**解法：用程式檔案自己的位置來組路徑。**
```
from pathlib import Path
BASE_DIR = Path(__file__).resolve().parent
config_path = BASE_DIR / "config.json"
```
- `__file__`：目前這個程式檔案的路徑；
- `.resolve().parent`：轉成完整路徑，再取它所在的資料夾。

這樣無論從哪裡執行，都能找到正確的檔案。

**比喻：**你跟朋友說「在我左手邊第二間店」。如果朋友站在不同的位置，就會找錯地方。要說「在捷運站出口左手邊第二間」，以一個固定的地標為準。

@section 停止程式：先禮後兵
程式跑起來了，要怎麼停止它？首先，要找到它的 PID：
```
ps aux | grep worker.py
```
- `ps aux`：列出所有正在執行的行程；
- `|`（管線）：把前一個指令的輸出，交給下一個指令當輸入；
- `grep worker.py`：只留下包含 `worker.py` 的那幾行。

找到 PID 之後，用 `kill` 指令發送「**訊號**」（Signal）給它。最重要的三種訊號：

**SIGINT（中斷，編號 2）：**在終端機按 **Ctrl+C** 時發送。意思是「請停下來」。

**SIGTERM（終止，編號 15）：**`kill <PID>` 預設發送的訊號。意思是「**請準備結束**」。

收到這兩種訊號時，程式**有機會做收尾工作**：把寫到一半的資料存好、撤銷未完成的資料庫交易、關閉連線，然後才結束。這叫做「**優雅關閉**」（Graceful Shutdown）。

**SIGKILL（強制終止，編號 9）：**`kill -9 <PID>`。作業系統**直接拔掉**這個行程，程式**完全沒有**任何收尾的機會。

可能的後果：
- 檔案寫到一半，損壞了（第 46 課的原子寫入就是為了防這個）；
- 資料庫的鎖沒有釋放，其他程式卡住；
- 正在處理的任務消失，不知道做到哪裡了。

**原則：永遠先用 Ctrl+C 或 `kill <PID>`，給程式幾秒鐘收尾。真的停不下來，才用 `kill -9`。**

**比喻：**SIGTERM 像是對員工說「今天下班前把手上的工作存檔，然後回家」；SIGKILL 像是直接拉掉辦公室的總電源。

另外要小心：**只停止你自己啟動的程式**。在伺服器上亂殺不認識的 PID，可能會停掉資料庫或系統的關鍵服務。

@section 走一遍：部署一個背景工作程式
假設在 Linux 伺服器上，要執行一個持續監聽任務的 AI 工作程式 `worker.py`。在家目錄 `/home/ubuntu` 執行：
```
APP_MODE=prod WORKER_BATCH=16 python3 /opt/ai/worker.py
```

**推演：**
1. Shell 替**這一次**指令臨時加上兩個環境變數：`APP_MODE=prod`、`WORKER_BATCH=16`；
2. Python 行程啟動。`os.getpid()` 得到 PID **48210**；`os.getcwd()` 得到 **`/home/ubuntu`**（注意：不是 `/opt/ai`！）；
3. 程式每秒執行 `print("heartbeat", flush=True)`，日誌中即時出現心跳訊息；
4. 五分鐘後要更新版本。在另一個終端機執行 `ps aux | grep worker.py`，確認 PID 是 48210，然後 `kill 48210`（發送 SIGTERM）；
5. `worker.py` 裡事先寫好的訊號處理程式收到通知，把手上正在處理的第 16 筆任務存檔完成，印出 `Graceful shutdown complete`，以結束狀態碼 **0** 乾淨退出。

@section 環境變數：同一份程式，不同的設定
同一份程式，在你的筆電上（開發環境）和在雲端伺服器上（正式環境），常常需要**不同的設定**：資料庫位址不同、連接埠不同、是否開啟除錯模式不同。

**錯誤做法：**在程式碼裡寫死，每次部署前手動改。很容易忘記改，或改錯。

**正確做法：**從環境變數讀取：
```
import os
mode = os.getenv("APP_MODE", "dev")    # 沒設定時，預設是 "dev"
```
這是業界著名的「**十二要素應用**」（Twelve-Factor App）原則之一：**設定要和程式碼分開**。同一份程式碼，不用修改，就能在不同環境執行。

**設定環境變數的兩種方式：**
- **只對這一次指令有效**：`APP_MODE=prod python3 app.py`。下一行再執行 `python3 app.py`，`APP_MODE` 就不見了；
- **對這個終端機視窗之後的所有指令有效**：`export APP_MODE=prod`。
- Windows PowerShell 的寫法不同：`$env:APP_MODE="prod"; python app.py`。

**環境變數的資安提醒：**
環境變數常用來放 API 金鑰、資料庫密碼這類「**機密**」（第 64 課會詳細談）。要注意：
1. **環境變數不是保險箱**：同一台機器上有足夠權限的程式都讀得到；
2. **絕對不要**把整個 `os.environ` 印到日誌裡，那等於把所有密碼都寫進日誌。只印出明確列出的、不敏感的設定，例如 `APP_MODE`；
3. 常用來存放環境變數的 `.env` 檔案，**絕對不能**提交到 Git（第 48 課）。

@section 動動腦：判斷看看
**題一**：輸入 `python3 app.py` 時，`PATH` 的作用是什麼？
→ 告訴 Shell 要依序去哪些資料夾尋找 `python3` 這個程式。

**題二**：在兩個終端機各執行一次 `python3 app.py`，它們的 PID 和記憶體是什麼關係？
→ 兩個不同的行程，PID 不同，記憶體完全獨立，互不影響。

**題三**：為什麼停止程式時，要先用 Ctrl+C 或 `kill <PID>`，而不是直接 `kill -9`？
→ 前兩者讓程式有機會收尾（存檔、撤銷交易、關閉連線）；`kill -9` 直接強制終止，可能留下損壞的檔案或卡住的鎖。

**題四**：程式在 `/opt/ai/` 資料夾，寫了 `open("data.json")`，從 `/home/ubuntu` 執行時找不到檔案。怎麼修正？
→ 改用 `Path(__file__).resolve().parent / "data.json"`，以程式檔案的位置為基準。

@section 常見問題 Q&A
**Q1：我用的是 Windows，也要學 Linux 嗎？**
要。幾乎所有雲端伺服器、Docker 容器、自動化測試環境都是 Linux。好消息是：Windows 可以安裝 **WSL**（Windows Subsystem for Linux），在 Windows 裡直接開一個真正的 Linux 終端機。Mac 的終端機本身就和 Linux 非常相似，這一課的指令大多可以直接用。

**Q2：程式跑到一半，終端機視窗被關掉了，程式還會繼續嗎？**
通常**不會**。關閉終端機時，作業系統會通知它啟動的行程一起結束。要讓程式在背景長期執行，正式環境會交給專門的管理工具，例如 systemd（Linux 內建的服務管理員）或 Docker（第 63 課），它們會在程式當掉時自動重新啟動，也會統一收集日誌。

**Q3：怎麼看哪個程式吃掉最多記憶體？**
用 `top` 或更好看的 `htop` 指令，可以即時看到每個行程使用多少 CPU 和記憶體，按記憶體排序就能找到元凶。找到 PID 後，再依照本課的方式，先用 `kill` 請它優雅結束。

**Q4：結束狀態碼在 Python 裡要怎麼設定？**
程式正常跑完，預設就是 0。遇到無法處理的錯誤而當掉時，Python 會自動回傳 1。也可以主動呼叫 `sys.exit(2)` 這類寫法，回傳特定的數字，讓呼叫它的自動化工具知道是哪一種失敗。

@section 本課重點整理
- **行程**：每次執行程式，作業系統就建立一個行程，有自己的 PID 和獨立記憶體。
- **啟動四步驟**：Shell 依 `PATH` 找程式 → 作業系統建立行程 → 繼承工作目錄和環境變數 → 執行並回傳結束狀態碼（0 成功、非 0 失敗）。
- **三條管道**：stdin、stdout、stderr。輸出被導向時會緩衝，用 `flush=True` 或 `-u` 立即寫出。
- **相對路徑**：相對於下指令的位置，不是程式檔案的位置。用 `Path(__file__)` 組路徑。
- **停止程式**：先 SIGINT（Ctrl+C）或 SIGTERM（`kill`），讓程式優雅關閉；最後手段才用 SIGKILL（`kill -9`）。
- **環境變數**：設定和程式碼分開，用 `os.getenv("KEY", "預設值")` 讀取。不要把整個環境變數印進日誌，`.env` 不能提交到 Git。
