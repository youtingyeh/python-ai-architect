@section 開場：永遠不要相信從網路進來的資料
上一課，我們的 API 可以查詢和刪除學生了。接下來要做「**新增**」和「**修改**」。這時候會面對一個全新的挑戰：**別人傳進來的資料**。

如果把新增學生的路由寫成：
```
@app.post("/students")
def create_student(data: dict):
    ...
```
`dict` 代表「隨便什麼字典都接受」。呼叫的人可能傳來：
- 缺少名字：`{"age": 19}`；
- 年齡是負數：`{"name": "Bob", "age": -99}`；
- 年齡是文字：`{"name": "Bob", "age": "十八歲"}`；
- 甚至**惡意**多塞欄位：`{"name": "Evil", "id": 1, "role": "admin"}`。

最後一種特別危險。如果後端把這個字典直接存進資料庫，一般使用者就能**自己把自己升級成管理員**，或蓋掉別人的資料（覆寫 1 號學生）。這種漏洞叫做「**批量賦值**」（Mass Assignment），是真實世界中常見的資安事故。

**鐵律：永遠不要相信任何從網路邊界外進來的資料。**不管是網頁、手機 App，還是 AI 代理（第 33 課）送來的工具呼叫參數，都一樣。

這一課要學怎麼用 **Pydantic** 替 API 建立「**資料契約**」（Schema）：在髒資料進入業務邏輯和資料庫**之前**，就在門口把它擋下來。我們要學：
1. Pydantic 模型是什麼、怎麼運作；
2. 三個重要的設定：嚴格模式、禁止多餘欄位、去除空白；
3. 為什麼新增、修改、讀取要用**三個不同**的模型；
4. PATCH 的大陷阱：「沒傳」和「傳了空值」不一樣；
5. 怎麼讀懂 422 錯誤；
6. Schema 不能取代什麼。

@section Pydantic：資料的入境審查
**Pydantic** 是 FastAPI 背後負責驗證資料的套件。你用類別（第 49 課）的寫法，描述「**資料應該長什麼樣子**」：
```
from pydantic import BaseModel, Field, ConfigDict

class StudentCreate(BaseModel):
    model_config = ConfigDict(strict=True, extra="forbid",
                              str_strip_whitespace=True)
    name: str = Field(min_length=1, max_length=100)
    age: int = Field(ge=0, le=120)
```
- `name: str`：名字必須是文字；
- `Field(min_length=1, max_length=100)`：長度 1 到 100 個字；
- `age: int` 搭配 `Field(ge=0, le=120)`：年齡是整數，大於等於（ge, greater or equal）0、小於等於（le, less or equal）120。

在路由中使用：
```
@app.post("/students", status_code=201)
def create_student(data: StudentCreate):
    ...
```

**運作方式：**每個請求進來時，FastAPI 會拿收到的 JSON，試著建立一個 `StudentCreate`。
- **全部符合** → 建立成功，你的函式拿到一個乾淨、型別正確的 `data`，可以直接用 `data.name`、`data.age`；
- **有任何不符合** → **你的函式根本不會被執行**，FastAPI 直接回傳 `422`，並詳細說明哪裡錯了。

**比喻：**Pydantic 像機場的**入境審查**。護照不對、簽證過期、行李有違禁品，在入境大廳就被攔下，根本進不了市區（你的業務邏輯）。進得來的，都是審查過的。

這也呼應第 45 課的「契約優先」：先把資料長什麼樣子定義清楚，再寫業務邏輯。

@section 三個重要的設定
上面的 `ConfigDict` 有三個設定，各自擋住一種問題。

**設定一：`strict=True`（嚴格模式）——不要自作聰明地轉換。**
Pydantic 預設是「**寬鬆模式**」：為了方便，它會**自動轉換**型別。例如收到 `"age": "18"`（文字），它會幫你轉成整數 18。

這在處理網頁表單時很方便，但在嚴格的 API 中可能藏著問題：呼叫的程式明明傳錯了型別，卻沒有被告知，錯誤被默默掩蓋了。開啟嚴格模式後，`"18"` 會被**拒絕**，要求對方傳正確的整數 `18`。

（第 48 課的布林值陷阱也會在嚴格模式下被擋住：`true` 不會被當成整數 1。）

**設定二：`extra="forbid"`（禁止多餘欄位）——擋住偷塞的欄位。**
Pydantic 預設會**默默忽略**模型中沒定義的欄位。`extra="forbid"` 則是：**只要出現任何沒定義的欄位，就拒絕**。

好處有兩個：
- 擋住惡意的 `"role": "admin"`；
- 擋住**拼錯的欄位名**。例如前端工程師把 `age` 拼成 `agee`，如果被默默忽略，年齡就沒被設定，卻沒有任何錯誤提示，很難發現。

**設定三：`str_strip_whitespace=True`——去掉頭尾空白再檢查。**
一個陷阱：`"   "`（三個空白）的長度是 3，會**通過** `min_length=1` 的檢查！結果系統裡出現一個名字是空白的學生。

開啟這個設定後，Pydantic 會先把頭尾空白去掉，`"   "` 變成 `""`，長度 0，被擋下。`" Alice "` 則被整理成 `"Alice"`。

@section 三個模型：新增、修改、讀取各一個
這是專業 API 設計最重要的觀念之一：**不要偷懶只寫一個模型通吃所有路由。**新增、修改、讀取的需求完全不同。

**一、新增模型 `StudentCreate`：**
只包含**允許使用者填寫**的欄位：`name`、`age`。

**絕對不包含** `id`、`role`、`created_at`（建立時間）這類應該由**伺服器或資料庫產生**的欄位。學號由系統分配，角色由管理員設定，時間由伺服器記錄。使用者不能自己決定。

**二、修改模型 `StudentUpdate`（給 PATCH 用）：**
```
class StudentUpdate(BaseModel):
    model_config = ConfigDict(strict=True, extra="forbid")
    name: str | None = Field(default=None, min_length=1, max_length=100)
    age: int | None = Field(default=None, ge=0, le=120)
```
所有欄位都是**選填**的（`| None = None`），因為 PATCH 是「**部分修改**」（第 53 課），使用者可能只想改年齡。

**三、讀取模型 `StudentRead`（回應用）：**
```
class StudentRead(BaseModel):
    id: int
    name: str
    age: int
```
在路由上指定 `response_model=StudentRead`，FastAPI 就**只會**回傳這幾個欄位。

這有一個重要的安全作用：假設資料庫裡的學生資料還有 `password_hash`（密碼雜湊，第 63 課）或 `internal_notes`（內部備註），即使你的函式不小心回傳了整筆資料，`response_model` 也會把它們**過濾掉**，不會外洩。

**比喻：**像銀行的三種表單。「開戶申請書」只讓你填姓名、地址（不能自己填帳號和信用額度）；「資料變更單」每格都可以留空，只填要改的；「對帳單」只顯示該給你看的資訊，不會印出銀行內部的風險評分。

@section PATCH 的大陷阱：「沒傳」不等於「傳了空值」
這是 PATCH 最常見、後果也很嚴重的錯誤。

假設 1 號學生原本是 `{"name": "Alice", "age": 19}`。客戶端想把年齡改成 21，送來：
```
PATCH /students/1
{"age": 21}
```

Pydantic 建立 `StudentUpdate` 時，沒傳的 `name` 會被設成預設值 `None`。

**錯誤的寫法：**
```
updates = data.model_dump()     # {"name": None, "age": 21}
student.update(updates)
```
結果：Alice 的名字被**洗成 `None`**！使用者明明只想改年齡。

**正確的寫法：**
```
updates = data.model_dump(exclude_unset=True)   # {"age": 21}
```
`exclude_unset=True` 的意思是：「**只包含客戶端真的有傳的欄位**」。沒傳的 `name` 不會出現，原本的名字保持不變。

**兩種情況要能分清楚：**
- 客戶端**沒傳** `name`：代表「名字不要動」；
- 客戶端**明確傳了** `{"name": null}`：代表「我想把名字設成空的」。這是否允許，要看業務規則（以學生名字來說，應該不允許，所以要在驗證中擋下）。

**比喻：**資料變更單上，「**這格沒填**」代表不要改；「**這格寫了『刪除』**」才代表要清空。不能因為某格沒填，就把原本的資料擦掉。

@section 走一遍：四次請求
`StudentCreate` 開啟了嚴格模式、禁止多餘欄位、去除空白。

**請求一：正常。**
`POST /students`，`{"name": " Alice ", "age": 19}`
→ 去除空白得到 `"Alice"`，驗證通過；伺服器分配 `id = 1`；回傳 **201**，`{"id": 1, "name": "Alice", "age": 19}`。

**請求二：型別不對。**
`{"name": "Bob", "age": "19"}`
→ 嚴格模式不自動轉換，回傳 **422**。

**請求三：偷塞欄位。**
`{"name": "Bob", "age": 20, "role": "admin"}`
→ `extra="forbid"`，回傳 **422**，指出 `role` 是不允許的欄位。

**請求四：找不到 vs. 格式錯誤。**
- `PATCH /students/999`，`{"age": 21}`：格式正確，驗證通過，進入函式後發現沒有 999 號學生 → **404**；
- `PATCH /students/1`，`{"age": -5}`：格式就不合規則，**還沒進入函式**就被擋下 → **422**。

順序很重要：**先驗證格式（422），再檢查資源是否存在（404）。**

@section 讀懂 422 錯誤
請求二的回應長這樣：
```
{
  "detail": [
    {
      "type": "int_type",
      "loc": ["body", "age"],
      "msg": "Input should be a valid integer",
      "input": "19"
    }
  ]
}
```
- `loc`（location）：**錯在哪裡**。`["body", "age"]` 表示請求主體中的 `age` 欄位；
- `type`：**錯誤類型**。`int_type` 表示應該是整數；
- `msg`：給人看的說明；
- `input`：你實際傳了什麼。

`detail` 是一個**清單**：如果有多個欄位錯誤，會**一次全部列出**，而不是一次只告訴你一個，讓你改了又錯、錯了又改。前端（第 61 課）可以根據 `loc`，把錯誤訊息顯示在對應的表單欄位旁邊。

**三個容易混淆的錯誤碼：**
- **400 Bad Request**：連 JSON 本身都壞了，例如少了一個大括號，根本解析不了；
- **422 Unprocessable Entity**：JSON 格式正確，但**內容**不符合規則（型別錯、範圍錯、多了欄位）；
- **404 Not Found**：格式和內容都對，但要操作的資源不存在。

@section Schema 不是萬能的
通過了 Pydantic 驗證，代表「**這包資料的形狀、型別、範圍都合規**」。但它**不知道**以下這些事：

**一、權限：這個人能不能做這件事？**
學生 A 送來一個格式完美的 `PATCH /students/2`，想修改學生 B 的資料。Schema 完全看不出問題。要擋住這種越權行為（第 46 課的 IDOR），需要**權限檢查**（第 64 課）。

**二、資料庫的整體狀況：會不會和別人衝突？**
Schema 只看**這一筆**請求。它不知道「這個 email 是不是 1 毫秒前剛被另一個請求註冊走了」。這種需要看整體資料的規則（例如「email 不能重複」），要靠**資料庫的約束**（第 52、53 課）。

**三、不要把資料庫的模型直接當成 API 的 Schema。**
有些人為了省事，直接用資料庫的資料表結構當作 API 的輸入和輸出。結果資料庫一加了內部欄位（例如 `hashed_password`），API 就**自動**把它外洩出去，或允許外部修改它。

**原則：Schema 是第一道防線，不是唯一的防線。**這就是第 28、43 課的縱深防禦。

@section 常見疑問
**問：驗證寫在前端（網頁表單）不就好了？**
答：前端驗證是為了**使用者體驗**：打錯字當場提示，不必等伺服器回應。但前端程式在使用者的電腦上，任何人都能打開瀏覽器開發者工具改掉它，或乾脆用 curl（第 53 課）繞過網頁直接呼叫 API。**後端驗證才是真正的安全邊界**，前端驗證只是貼心提醒。

**問：嚴格模式會不會太不方便？**
答：看情境。機器對機器的 JSON API，對方是程式，傳對型別是基本要求，用嚴格模式能及早抓出錯誤。如果是處理網頁表單或網址參數（它們本質上都是文字），可以針對個別欄位放寬。重點是**有意識地選擇**，而不是不知道預設會自動轉型。

**問：巢狀資料怎麼驗證？**
答：模型可以包模型。例如學生有地址：
```
class Address(BaseModel):
    city: str
    zip_code: str = Field(pattern=r"^\d{3,5}$")

class StudentCreate(BaseModel):
    name: str
    address: Address
```
錯誤時 `loc` 會變成 `["body", "address", "zip_code"]`，一路指到最深的那一層。

**問：AI 的結構化輸出也能用嗎？**
答：可以，而且很推薦。第 22 課要求模型輸出 JSON，第 26 課的工具呼叫參數，都可以丟進 Pydantic 模型驗證。模型偶爾會漏欄位、型別錯、多塞東西，用同一套入境審查擋下，再決定要重試還是回報錯誤。**模型的輸出也是「外來資料」。**

@section 動動腦：判斷看看
**題一**：所有路由都加上了嚴格的 Pydantic Schema，還需要權限檢查和資料庫約束嗎？
→ 需要。Schema 只檢查資料的形狀、型別和範圍，不知道呼叫者有沒有權限，也無法防止並行寫入時的重複衝突。

**題二**：客戶端 A 送 `{"age": 21}`，客戶端 B 送 `{"name": null, "age": 21}`，後端該怎麼看待？
→ A 沒傳名字，代表名字不變（用 `exclude_unset=True` 取得有傳的欄位）；B 明確要求把名字設為空值，是否允許依業務規則決定。

**題三**：為什麼 `StudentCreate` 不應該包含 `id` 和 `role`？
→ 防止批量賦值：使用者不能自己指定編號或升級角色，這些應由伺服器依規則產生。

**題四**：`"   "` 會通過 `min_length=1` 嗎？怎麼防？
→ 會（長度 3）。開啟 `str_strip_whitespace=True`，先去除空白再檢查。

@section 本課重點整理
- **鐵律**：永遠不要相信從網路邊界外進來的資料，包括 AI 代理的工具參數。
- **批量賦值**：直接把收到的字典存進資料庫，會讓使用者偷塞 `role`、`id` 等欄位。
- **Pydantic**：定義資料應有的樣子；不符合時，函式不會執行，直接回傳 422。
- **三個設定**：`strict=True`（不自動轉型）、`extra="forbid"`（禁止多餘欄位）、`str_strip_whitespace=True`（去除空白後再檢查）。
- **三個模型**：Create（只含使用者可填欄位）、Update（全部選填）、Read（搭配 `response_model`，過濾敏感欄位）。
- **PATCH 陷阱**：用 `model_dump(exclude_unset=True)`，區分「沒傳」和「傳了 null」。
- **422 的結構**：`loc` 指出位置、`type` 指出類型，一次列出所有錯誤。400 是 JSON 壞了，422 是內容不合規，404 是資源不存在。
- **Schema 不是萬能**：仍需權限檢查和資料庫約束；不要拿資料庫模型直接當 API Schema。

@term 資料契約
規定資料必須包含哪些欄位、型別與範圍的約定（Schema）。
@term Pydantic
用類別寫法定義資料結構，並自動驗證與轉換資料的 Python 套件。
@term 批量賦值
直接把使用者傳來的所有欄位寫入資料，導致使用者能偷改不該改的欄位（Mass Assignment）。
@term 嚴格模式
不自動轉換型別、型別不符就拒絕的驗證模式（Strict Mode）。
@term 寬鬆模式
會自動嘗試轉換型別（如把 "18" 轉成 18）的驗證模式（Lax Mode）。
@term Field
Pydantic 中用來設定欄位長度、數值範圍等限制的函式。
@term 讀寫模型分離
新增、修改、讀取各自使用不同的資料模型，避免權限與資料外洩問題。
@term response_model
FastAPI 中指定回應格式的設定，會過濾掉模型未定義的欄位。
@term exclude_unset
model_dump 的選項，只輸出客戶端實際有傳的欄位。
@term 422 Unprocessable Entity
JSON 格式正確但內容不符合驗證規則時回傳的狀態碼。
@term loc
422 錯誤中指出錯誤發生位置的欄位，例如 ["body", "age"]。
@term 資料庫約束
在資料庫層級強制執行的規則，例如欄位不可重複（Constraint）。
