@section 開場：一台變四台，為什麼反而壞了？
服務在一台機器上（1 台 FastAPI 加 1 台 PostgreSQL）穩定運作時，程式可以默默假設：「**這台機器的記憶體和硬碟，就是全世界。**」

使用者變多了十倍；或者為了避免「一台壞掉就全站停擺」，你在前面放了一台「**負載平衡器**」，後面部署了 **4 台** FastAPI。

結果，原本在單機上從來不會出錯的程式，**全面崩潰**：
- 使用者在第 A 台**登入成功**（登入狀態存在 A 的 Python 字典 `SESSIONS = {}` 裡）。下一秒他點「我的課程」，負載平衡器把請求分給了第 B 台。B 的記憶體裡沒有這筆登入紀錄，**直接把剛登入的使用者踢回登入頁**；
- 學生上傳的作業 PDF 存在 A 的本機資料夾 `/app/uploads/`。老師下載時被分到 C 台，得到 **404 找不到檔案**。

這一課要學「**擴充**」（Scaling）：系統要服務更多使用者時，有哪些選擇、會遇到哪些新問題：
1. **垂直擴充**與**水平擴充**；
2. **無狀態**的應用程式設計；
3. **負載平衡器**和健康檢查；
4. 資料庫的**讀寫分離**與**複製延遲**；
5. 一個容易被忽略的計算：**連線池總數**。

@section 兩種擴充：換大車，還是多加幾台車？
**垂直擴充（Scale Up）：把機器換成更強的。**
把伺服器從 2 核心、4GB 記憶體，升級成 16 核心、64GB 記憶體。

- **優點**：**一行程式都不用改**，沒有任何分散式系統的麻煩；
- **缺點**：
  - 有上限：單台機器能買到的規格有極限，而且越高階越貴（價格通常不是線性增加）；
  - 依然是「**單點故障**」（Single Point of Failure，SPOF）：這台機器壞了、或升級需要重開機，**全站停擺**。

**水平擴充（Scale Out）：增加更多台機器，一起分擔工作。**
在負載平衡器後面，從 1 台增加到 N 台。

- **優點**：
  - 理論上可以一直加；
  - 一台壞了，其他台繼續服務（**高可用性**）；
  - 可以一台一台輪流更新，**不必停機**（稱為「**滾動更新**」）；
- **缺點**：前提是程式必須設計成「**無狀態**」，否則就會出現開場的那些問題。

**比喻：**搬家公司接到的工作量變大了。
- 垂直擴充：把小貨車換成大卡車。簡單，但再大的卡車也有極限，而且卡車拋錨，整個工作就停了；
- 水平擴充：多派幾台貨車一起搬。可以一直增加，一台拋錨其他台照常工作，但前提是**每個司機都能處理任何一箱貨**，而不是「這箱只有老王知道要送去哪裡」。

**實務建議：先垂直，再水平。**
垂直擴充簡單又便宜（在一定範圍內）。很多系統升級一次機器規格就能撐很久。但即使流量不大，為了**避免單點故障**，正式環境通常也至少部署 2 台，這就需要無狀態設計。

@section 無狀態：任何一台都能處理任何請求
**無狀態**（Stateless）的意思是：**應用程式本身不保存任何「跨請求」的資料。**每一個請求所需要的資訊，要嘛在請求本身裡，要嘛在**所有機器共用**的外部儲存裡。

**因為負載平衡器可能把同一個使用者的連續兩個請求，送到不同的機器。**

**哪些東西不能存在本機？要搬到哪裡？**
- **登入 Session** → 搬到共用的 **Redis** 或資料庫（第 63 課）；
- **速率限制的計數器**（第 63 課的登入限速）→ 搬到 Redis。否則每台機器各算各的，攻擊者的嘗試被分散到 4 台，每台都以為只有 1/4 的次數；
- **使用者上傳的檔案** → 搬到共用的**物件儲存**（例如 S3）；
- **背景任務** → 搬到共用的**佇列**（第 76 課）；
- **快取** → 搬到共用的 Redis（第 75 課），或接受每台各有自己的本機快取（但要知道它們可能不一致）。

**應用程式變成「可以隨時丟棄、隨時複製」的工人。**任何一台被關掉，都不會遺失任何資料；需要更多處理能力時，直接多開幾台。

**比喻：**銀行的櫃台。客戶的帳戶資料存在**銀行的中央系統**，不是存在某位櫃員的抽屜裡。所以你今天找 3 號櫃台，明天找 7 號櫃台，都能辦理業務。某位櫃員請假，也不影響任何客戶。

第 67 課的容器「可寫層隨容器消失」，也是在提醒同一件事：容器本身應該是無狀態的。

**一個常見的偷懶做法：「黏滯會話」（Sticky Session）。**
設定負載平衡器，讓同一個使用者**永遠被送到同一台機器**，這樣把狀態存在本機好像就沒問題了。

**但這只是掩蓋問題：**那台機器一重啟、或因為縮減規模被關掉，上面所有使用者的狀態**依然瞬間消失**。而且負載會不平均：某台機器剛好黏了很多重度使用者，就會特別忙。真正的解法是把狀態搬出去。

@section 負載平衡器與健康檢查
**負載平衡器**（Load Balancer）站在所有應用程式機器的前面，負責把進來的請求**分配**給後面的機器。

最簡單的分配方式是「**輪流**」（Round Robin）：第 1 個請求給 A、第 2 個給 B、第 3 個給 C……也有「分給目前最閒的那台」等更聰明的方式。

**健康檢查：不要把請求送給生病的機器。**
負載平衡器會**定期**呼叫每台機器的健康檢查端點，例如 `/healthz`：
- 回傳 200：健康，繼續分配請求；
- 回傳 503 或沒有回應：不健康，**暫時不再分配請求給它**，把流量轉給其他健康的機器。

健康檢查常分成兩種：
- **存活檢查**（Liveness）：程式還活著嗎？
- **就緒檢查**（Readiness）：程式準備好處理請求了嗎？例如資料庫連得上嗎？剛啟動、還在載入設定時，雖然活著，但還沒準備好。

**比喻：**餐廳領檯員帶客人入座前，會看一下哪一區的服務生有空。如果某位服務生正在處理打翻的飲料，就先別帶客人去他那一區。

**優雅關機（Graceful Shutdown）：**
部署新版本時，舊的機器會收到 SIGTERM 訊號（第 51 課）。正確的做法是：
1. **停止接受**新的請求（健康檢查開始回傳「未就緒」，負載平衡器就不再送新請求過來）；
2. **把正在處理的請求做完**；
3. 然後才結束。

這樣使用者完全感覺不到正在更新版本。如果收到訊號就立刻結束，正在處理中的請求就會中斷，使用者看到錯誤。

@section 資料庫：最後的瓶頸
應用程式可以輕鬆開到 10 台，但它們**最後都連到同一個 PostgreSQL**。應用層無狀態了，狀態都集中到資料庫，資料庫就成了最後的瓶頸。

**讀寫分離：一主多從。**
大部分系統是「**讀多寫少**」的（第 75 課）。可以設定：
- **一台主資料庫**（Primary）：負責**所有的寫入**（INSERT、UPDATE、DELETE）；
- **多台唯讀副本**（Read Replica）：主資料庫的資料會**自動複製**過來，負責**大量的讀取**。

**比喻：**一間圖書館只有一位館員能**登錄新書**（主資料庫），但有好幾個**閱覽室**（副本），每間都有一套藏書的複本，讀者可以分散到各閱覽室去看書。

**但有一個陷阱：複製延遲（Replication Lag）。**
資料從主資料庫複製到副本，需要一點時間，通常幾毫秒，忙碌時可能到幾秒。

**情境：**
1. 學生提交作業（寫入主資料庫）；
2. 頁面立刻重新整理，查詢「我的提交狀態」（從副本讀取）；
3. 副本還沒收到剛才的資料。學生看到：「**您尚未提交作業**」。

學生以為沒交成功，又交了一次，或者驚慌地寫信給老師。

這種情況違反了「**讀己之所寫**」（Read Your Own Writes）：使用者應該能看到自己剛剛做的修改。

**解法：依資料的時效需求決定從哪裡讀。**
- **對時效敏感的**：使用者**剛修改過**的資料（例如提交作業後的狀態頁），從**主資料庫**讀取；
- **可以容忍幾秒延遲的**：公開的課程搜尋、排行榜，從**副本**讀取。

**比喻：**你剛把新書交給館員登錄，馬上跑去閱覽室找，當然找不到，因為複本還沒送過去。想確認自己剛交的書，應該直接問登錄的館員。

@section 一個容易被忽略的計算：連線池總數
這是水平擴充時**最常出事**的地方之一。

**背景知識：**PostgreSQL 能同時接受的連線數有上限，預設是 `max_connections = 100`。每個應用程式為了效率，會維持一個「**連線池**」：預先開好一些連線重複使用，而不是每個請求都重新連線。

**單機時代：**FastAPI 的連線池設定為一般 20 條、尖峰最多 30 條。只有一個程式，完全沒問題。

**水平擴充之後：**
- 4 台 API 容器，每台跑 2 個程式（Uvicorn 的 worker）= 8 個程式；
- 加上 2 個背景工作程式（第 76 課）；
- 總共 **10 個程式**，每個的連線池最多 30 條；
- 尖峰時最多：$10 \times 30 = 300$ 條連線。

**但 PostgreSQL 只能接受 100 條！**尖峰一到，全站報錯：
```
FATAL: sorry, too many clients already
```
最諷刺的是：你為了**提升**處理能力而增加機器，結果反而讓系統**更容易崩潰**。

**解法：**
- **從總數反推**：先決定資料庫能給應用程式多少連線（例如 120 條中保留 20 條給管理和資料庫維護，剩 100 條），再除以總程式數，算出每個程式的上限；
- 例如總共 8 個程式，每個上限設為 12 條：$8 \times 12 = 96 < 100$，安全；
- 或在中間加一層「**連線池代理**」（例如 PgBouncer），讓很多應用程式共用少量的資料庫連線。

**記住：每次增加機器數量時，都要重新算一次連線池的總數。**

@section 走一遍：從單機到高可用
**第一步：找出瓶頸（第 58 課的量測精神）。**
壓力測試發現：單台 2 核心的 API 主機，在每秒 120 次請求時 CPU 就滿了。另外它曾因為本機硬碟塞滿，停機 20 分鐘。程式碼裡把登入狀態放在 Python 全域字典 `ACTIVE_USERS = {}`。

**第二步：無狀態化。**
- 移除所有存放狀態的全域字典；
- 登入 Session 搬到 Redis；
- 作業附件改存物件儲存；
- 背景任務改用持久化佇列。

**第三步：水平擴充，並重新計算連線池。**
- 負載平衡器後面部署 3 台 API 容器（每台 2 個 worker，共 6 個）；
- 2 個背景工作程式；總共 8 個程式；
- PostgreSQL 的 `max_connections` 設為 120，保留 20 條給管理；
- 每個程式的連線池：一般 8 條、尖峰最多 12 條。$8 \times 12 = 96 < 100$。

**第四步：設定健康檢查與優雅關機。**
**第五步：讀取繁重的公開查詢，改從唯讀副本讀取；使用者剛修改過的資料，仍從主資料庫讀。**
**第六步：壓力測試驗證**，並確認任意關掉一台 API 容器時，使用者不會被登出、檔案不會消失。

@section 常見陷阱
**陷阱一：用黏滯會話掩蓋有狀態的程式碼。**機器一重啟，狀態照樣消失。

**陷阱二：忘了重算連線池總數。**加機器反而讓資料庫連線爆掉。

**陷阱三：忽略複製延遲。**使用者剛做的修改「消失了」，造成重複提交或客訴。

**陷阱四：以為加機器能解決一切。**
如果瓶頸在資料庫（例如沒建索引的慢查詢，第 58 課），增加再多台 API 也沒用，反而會讓更多請求同時壓在資料庫上。**先找出真正的瓶頸，再決定擴充哪一層。**

**陷阱五：排程任務在每台機器上都跑一次。**
程式裡寫了「每天凌晨 3 點寄出成績摘要」。部署 4 台之後，每台都在 3 點執行一次，學生收到 **4 封**一樣的信。排程任務要集中由一個地方觸發，或透過第 76 課的佇列加上冪等設計來處理。

@section AI 應用的擴充
AI 應用有一些特別的考量：
- **LLM 服務商的速率限制**：你的 API 可以擴充到 10 台，但如果它們共用同一個 LLM API 金鑰，每分鐘可用的 token 數量是**固定的**。擴充 API 伺服器不會讓 LLM 變快，反而可能更快撞到上限（429 錯誤）。需要在系統層級統一控制呼叫速率，或透過佇列（第 76 課）排隊；
- **自己部署的模型**：模型推論需要 GPU，GPU 機器昂貴且啟動慢（要載入好幾 GB 的模型），不能像一般 API 容器那樣隨意增減。常見做法是把模型推論獨立成一個服務，和一般的 API 分開擴充；
- **長時間的串流回應**：LLM 串流回應可能持續幾十秒，負載平衡器的逾時設定要夠長，優雅關機時也要等這些長請求完成。

@section 常見疑問
**問：機器要開幾台，一定要人工決定嗎？**
答：雲端平台大多支援「**自動擴充**」（Autoscaling）：設定規則，讓系統依負載自動增減機器數量。例如「CPU 平均使用率超過 70% 就加一台，低於 30% 就減一台，最少 2 台、最多 10 台」。對背景工作程式（第 76 課），更好的指標常常是「**佇列中等待的工作數量**」：工作越積越多，就多開幾個背景程式。

但要注意兩件事。第一，**新機器啟動需要時間**（拉取映像檔、啟動程式、通過健康檢查），流量突然暴增時，自動擴充可能來不及。如果你知道尖峰何時到來（例如作業截止前，第 70 課），可以**提前**擴充。第二，**別忘了第 77 課的連線池總數**：最多 10 台時，資料庫撐得住嗎？「最多幾台」這個上限，正是為了保護後端的資料庫。

**問：Serverless（無伺服器）是什麼？**
答：一種把「管理機器」完全交給雲端平台的方式：你只上傳函式，平台在有請求時自動執行，沒請求時不收費（或收很少）。它天生就是無狀態、自動擴充的。缺點是「**冷啟動**」：一段時間沒被呼叫後，第一個請求要等平台準備執行環境，可能多花幾百毫秒到幾秒；而且長時間執行的工作（例如很長的 LLM 串流）可能受到執行時間的限制。適合流量起伏很大、或很零散的工作。

**問：資料庫的寫入也撐不住了怎麼辦？**
答：讀寫分離只能分擔**讀取**。寫入真的成為瓶頸時，先檢查：是不是有沒必要的寫入？能不能批次寫入？能不能把一部分寫入放進佇列慢慢處理？真的還不夠時，才考慮「**分片**」（Sharding）：把資料依某個規則（例如依學校）分散到好幾個資料庫。分片非常複雜：跨分片的查詢和交易都變得困難。**絕大多數系統一輩子都不需要分片**，一台調校良好的 PostgreSQL 能撐的量，往往超出你的想像。這正是第 74 課 ADR 中「重新評估條件」該寫清楚的事。

**問：靜態檔案（圖片、CSS、JavaScript）也要經過我的 API 伺服器嗎？**
答：最好不要。把它們放在物件儲存或 CDN（第 75 課），讓使用者直接從那裡下載。你的 API 伺服器只處理真正需要運算的請求，能服務的使用者數量會大幅增加。

@section 動動腦：判斷看看
**題一**：多台 API 機器時，使用者登入後一直被登出，最可能的原因是什麼？
→ 登入狀態存在單台機器的記憶體中，請求被分到其他機器時找不到；應將 Session 移到共用的 Redis 或資料庫。

**題二**：10 個應用程式各有最多 30 條連線，資料庫上限 100 條，會發生什麼事？
→ 尖峰時可能需要 300 條連線，超過上限導致大量連線錯誤；應依總程式數反推每個連線池的上限，或使用連線池代理。

**題三**：學生提交作業後立刻刷新頁面，卻顯示「尚未提交」，可能原因是什麼？
→ 寫入主資料庫後，從尚未同步的唯讀副本讀取（複製延遲）；剛修改的資料應從主資料庫讀取。

**題四**：用黏滯會話把使用者固定在同一台機器上，能取代無狀態設計嗎？
→ 不能。那台機器重啟或被移除時，狀態仍會遺失，且負載可能不均。

@section 本課重點整理
- **垂直擴充**換更強的機器，簡單但有上限且是單點故障；**水平擴充**增加機器，需要無狀態設計。
- **無狀態**：Session、計數器、上傳檔案、背景任務、快取都移到共用的外部儲存。
- **黏滯會話**只是掩蓋問題。
- **負載平衡器**分配請求；**健康檢查**避開故障機器；**優雅關機**讓更新不中斷使用者。
- **讀寫分離**：寫入主資料庫、讀取分散到副本；注意**複製延遲**，剛修改的資料從主資料庫讀。
- **連線池總數** = 程式數 × 每個連線池上限，必須小於資料庫上限；每次增加機器都要重算。
- **先找瓶頸再擴充**；排程任務不能每台都跑一次。
- **AI 擴充**：LLM 速率限制是共用的上限；GPU 推論服務獨立擴充；串流請求注意逾時與關機。

@term 擴充
提升系統處理能力以服務更多使用者（Scaling）。
@term 垂直擴充
把單台機器升級為更高規格（Scale Up）。
@term 水平擴充
增加更多台機器分擔工作（Scale Out）。
@term 單點故障
某個元件故障就會導致整個系統停擺（Single Point of Failure，SPOF）。
@term 高可用性
系統在部分元件故障時仍能持續提供服務（High Availability）。
@term 無狀態
應用程式不在本機保存跨請求的資料，任何機器都能處理任何請求（Stateless）。
@term 負載平衡器
把請求分配給多台後端機器的元件（Load Balancer）。
@term 黏滯會話
讓同一使用者固定被送到同一台機器的設定（Sticky Session）。
@term 健康檢查端點
供負載平衡器確認機器是否正常的網址，如 /healthz。
@term 優雅關機
停止接收新請求、完成進行中的請求後才結束程式（Graceful Shutdown）。
@term 滾動更新
逐台替換機器版本，使服務不中斷（Rolling Update）。
@term 唯讀副本
自動從主資料庫複製資料、負責讀取的資料庫（Read Replica）。
@term 複製延遲
資料從主資料庫同步到副本所需的時間差（Replication Lag）。
@term 讀己之所寫
使用者能立即看到自己剛做的修改的一致性保證（Read Your Own Writes）。
@term 連線池
預先建立並重複使用資料庫連線的機制（Connection Pool）。
@term PgBouncer
讓多個應用程式共用少量 PostgreSQL 連線的連線池代理。
