@section 開場：你是誰？
到目前為止，我們的 API 完全「裸奔」：任何人只要知道網址，就能查看、修改、刪除任何學生的資料。

真實的產品必須知道「**現在發請求的人是誰**」，才能：
- 載入**他自己的**對話紀錄（而不是別人的）；
- 扣**他的** API 額度；
- 擋住沒登入的訪客。

這就是「**身分驗證**」（Authentication，簡稱 **AuthN**）的工作：確認「**你是誰**」。

下一課（第 64 課）的「**授權**」（Authorization，簡稱 **AuthZ**）則是：「確認你是誰之後，你**能做什麼**」。

**比喻：**進公司大樓。在大門口出示員工證，警衛確認「你是王小明」，這是**身分驗證**；進去之後，你的門禁卡能開哪些樓層、哪些會議室，這是**授權**。

登入系統也是駭客**攻擊最猛烈**的地方。最常見的慘劇是：密碼存放方式錯誤，資料庫外洩後，所有使用者的密碼在幾秒內被破解。而且很多人在不同網站用同一組密碼，於是連帶他們在其他網站的帳號也被盜。

這一課要學：
1. 密碼該怎麼存：**雜湊、加鹽、慢速演算法**；
2. 登入之後，伺服器怎麼「記得」你：**Session、Cookie、JWT** 的差別；
3. 完整的註冊、登入、存取、登出流程；
4. 五個經典漏洞。

@section 密碼不能怎麼存
**錯誤一：存明文。**
```
users
email          | password
alice@mail.com | ilovecats123
```
資料庫一外洩（或某個工程師偷看），所有密碼一覽無遺。

**錯誤二：可逆加密。**
用一把金鑰把密碼加密，需要時再解密。問題是：金鑰通常和資料庫放在同一個系統裡，駭客拿到資料庫，很可能也拿得到金鑰。而且**系統根本不需要知道原本的密碼**，為什麼要能解回來？

**正確的思路：雜湊（Hash）。**
**雜湊**是一種**單向**的數學運算：把任意輸入變成一串固定長度的「指紋」，而且**無法從指紋反推回原文**。
- `ilovecats123` → `a7f3c9...`（一長串看似亂碼的字）；
- 同樣的輸入，永遠得到同樣的指紋；
- 輸入改一個字，指紋就完全不同。

**登入時怎麼驗證？**不是把指紋解回密碼，而是把使用者這次輸入的密碼**再算一次指紋**，和資料庫存的指紋比對。一樣就代表密碼正確。

**比喻：**雜湊像把一頭豬做成香腸。你可以驗證「這條香腸是不是用那頭豬做的」（同樣的做法、同樣的豬，做出同樣的香腸），但不可能把香腸變回一頭豬。

@section 為什麼連 SHA-256 都不夠
SHA-256 是一種很有名、很安全的雜湊演算法，但它**不適合存密碼**。原因出乎意料：**它太快了。**

SHA-256 的設計目標是**極速**，用在檔案校驗、區塊鏈等地方。一張現代顯示卡每秒可以算**上百億次** SHA-256。

攻擊者拿到外洩的資料庫後，可以進行「**離線暴力破解**」：把所有可能的 8 位數密碼一個個算出指紋，和資料庫比對。速度這麼快，常見長度的密碼很快就會被試出來。

更糟的是「**彩虹表**」：攻擊者**事先**把幾十億個常見密碼的指紋全部算好，存成一張大表。拿到資料庫後直接查表，連算都不用算。

**解法一：加鹽（Salt）。**
替每個使用者產生一段**隨機的字串**，稱為「**鹽**」，和密碼混在一起再雜湊：
- Alice 的密碼 `12345678` + 鹽 `xK9q` → 指紋 A；
- Bob 的密碼也是 `12345678` + 鹽 `mP2w` → 指紋 B（和 A 完全不同）。

效果：
- 彩虹表失效了：事先算好的表沒有包含這些隨機鹽；
- 就算兩個人密碼相同，存起來也不一樣，攻擊者看不出來；
- 攻擊者必須**針對每個使用者**分別破解。

鹽不是秘密，它和指紋存在一起即可。它的作用是讓每個密碼都「獨一無二」。

**解法二：故意變慢。**
用**專門為密碼設計的慢速演算法**，首選 **Argon2id**（資安組織 OWASP 推薦），或成熟的 **bcrypt**、**scrypt**。

它們**故意**讓每次計算耗時約 0.1 到 0.3 秒，還要消耗大量記憶體（讓顯示卡難以大量並行）。
- 正常使用者登入：等 0.2 秒，**完全感覺不到**；
- 攻擊者想猜十億次：從幾秒鐘變成**幾百年**。

**比喻：**保險箱的密碼鎖，每轉一次都要等 0.2 秒。主人只轉一次，不在意；小偷想把所有組合試一遍，就得在那裡待上幾輩子。

Python 中使用 `argon2-cffi` 套件：
```
from argon2 import PasswordHasher
ph = PasswordHasher()

hashed = ph.hash("ilovecats123")
# $argon2id$v=19$m=65536,t=3,p=4$隨機鹽$指紋
ph.verify(hashed, "ilovecats123")   # 正確則通過，錯誤則拋出例外
```
注意那串結果：演算法名稱、參數（`m` 是記憶體、`t` 是迭代次數）、鹽、指紋**全部存在一個字串裡**，你只要存這一個欄位。

**鐵律：不要自己發明密碼學。**用成熟、經過審查的函式庫。

@section 登入之後：伺服器怎麼記得你
第 53 課說過，HTTP 是「**無狀態**」的：每個請求都是獨立的，伺服器不會記得上一個請求是誰發的。

使用者在 `POST /login` 驗證成功，下一秒呼叫 `GET /me`（查看我的資料），伺服器怎麼知道他剛才登入過？總不能每個請求都要求輸入一次密碼吧。

答案是：登入成功後，發給使用者一張「**憑證**」，之後每個請求都帶著它。這裡有三個常被混為一談的概念，它們其實**不在同一個層次**：

**Cookie：瀏覽器的「小口袋」（傳輸與儲存的機制）。**
伺服器在回應中說「請幫我存這個值」，瀏覽器就把它存起來，之後**每次**發請求給同一個網站時，**自動**帶上它。

**Session：「憑證放在伺服器」的架構。**
伺服器在自己的資料庫存一筆紀錄：「`session_id` = `Xy7k...`，屬於使用者 1，到期時間是明天」。只把那串 `session_id` 交給使用者（通常放在 Cookie 裡）。

**比喻：**Session 像寄物處的**號碼牌**。號碼牌本身沒有任何資訊，只是一個號碼；寄物處的本子上記著「7 號是王小明的包包」。

**JWT：「資訊寫在憑證上」的格式。**
JWT（JSON Web Token）是一串自帶資訊的字串，分三段：`標頭.內容.簽章`。內容可能是 `{"user_id": 1, "exp": 明天}`，簽章則保證內容沒被竄改。伺服器**不用查資料庫**，只要驗證簽章就知道你是誰。

**比喻：**JWT 像一張**有防偽浮水印的通行證**，上面直接寫著姓名和有效期限。警衛只要確認浮水印是真的，就放行，不用打電話回總部查。

所以「Cookie vs. JWT」不是二選一：JWT 也可以放在 Cookie 裡傳送。真正的選擇是：**憑證的資訊存在伺服器（Session），還是寫在憑證本身（JWT）？**

@section Session 與 JWT 的取捨
**Session 最大的優點：可以立即撤銷。**
使用者按下登出、改了密碼、帳號被管理員停權時，只要從伺服器的資料庫**刪除**那筆 session，那個號碼牌**下一毫秒就作廢了**。就算有人偷了號碼牌，也沒有用。

**JWT 的兩個致命陷阱：**

**陷阱一：JWT 的內容沒有加密，任何人都能看。**
一般的 JWT 內容只是經過 **Base64 編碼**，那只是換一種寫法，不是加密。把它貼到任何解碼工具，內容就一清二楚。簽章只保證「**沒被竄改**」，**不保證「別人看不到」**。所以絕對不要在 JWT 裡放密碼或敏感個資。

**比喻：**通行證上的浮水印防偽造，但通行證本身是**透明的**，誰拿到都能讀上面寫的字。

**陷阱二：純 JWT 在過期前無法撤銷。**
伺服器不查資料庫，那它就**不知道**這張通行證是否已經被「取消」了。使用者登出了，但如果 JWT 還沒到期，被偷走的那張照樣有效。要支援立即登出，還是得在伺服器維護一份「黑名單」，那就又回到需要查資料庫了。

**實務建議：**一般網站的登入，用「**伺服器端 Session + 安全設定的 Cookie**」通常是最簡單、最安全的選擇。JWT 適合的場景是服務之間互相呼叫、或需要跨多個網域的情況，而且通常搭配很短的有效期限。

@section 走一遍：完整的登入系統
**流程一：註冊（`POST /register`）。**
1. 檢查密碼長度（第 55 課的 Pydantic）；
2. `ph.hash(密碼)` 產生 Argon2id 雜湊；
3. 存進 `users.password_hash`；
4. **原始密碼用完立刻丟棄**，絕不寫進資料庫或日誌（第 66 課）。

**流程二：登入（`POST /login`）。**
1. 依 email 查詢使用者，用 `ph.verify()` 驗證密碼；
2. **失敗時**，不論是「帳號不存在」還是「密碼錯誤」，都回傳**一模一樣**的 `401` 和訊息「帳號或密碼錯誤」；
3. **成功時**，用密碼學安全的亂數產生 session_id：
```
import secrets
session_id = secrets.token_urlsafe(32)
```
4. 把 `session_id`、`user_id`、到期時間存進 `sessions` 表；
5. 回應中設定 Cookie：
```
Set-Cookie: session_id=...; HttpOnly; Secure; SameSite=Lax; Path=/
```

**流程三：存取私人資料（`GET /me`）。**
讀取 Cookie 中的 session_id → 查表確認存在、未撤銷、未過期 → 通過才回傳資料，否則 `401`。

**流程四：登出（`POST /logout`）。**
從資料庫**刪除**這筆 session，並請瀏覽器清除 Cookie。之後就算有人事先偷抄了那串 session_id，拿去呼叫 `GET /me` 也只會得到 `401`。

**Cookie 的三個安全標記：**
- **`HttpOnly`**：前端 JavaScript **讀不到**這個 Cookie。即使網站有 XSS 漏洞（第 61 課），惡意程式也偷不走登入憑證；
- **`Secure`**：只在 HTTPS 加密連線下傳送（第 53 課）；
- **`SameSite=Lax`**：其他網站發起的請求，大多不會自動帶上這個 Cookie，降低被偽造請求的風險。

@section 五個經典漏洞
**漏洞一：自己發明加密，或用快速雜湊存密碼。**
`hashlib.sha256(password)`：沒有鹽、太快。改用 Argon2id 或 bcrypt。

**漏洞二：帳號枚舉。**
登入失敗時誠實地說「找不到此 Email」或「密碼錯誤」，攻擊者就能拿一份 email 清單逐一試，**掃出哪些人在你的網站有帳號**。這份名單本身就有價值（例如用來發釣魚信）。

所以兩種失敗要回傳**相同的訊息**。更講究的做法：帳號不存在時，也假裝算一次雜湊，讓兩種情況的**回應時間**也一樣，避免攻擊者從快慢判斷。

**漏洞三：可預測的 session_id。**
用 `random.randint()` 或遞增的 1、2、3 當 session_id。一般的亂數是「偽隨機」，可以被推測；遞增數字更是直接猜下一號就好。攻擊者把 Cookie 改成別人的號碼，就**劫持**了別人的帳號。一定要用 `secrets` 模組（第 51 課提過它和 `random` 的差別）。

**漏洞四：Cookie 沒設 HttpOnly，或把憑證存在 localStorage。**
網站只要有一處 XSS 漏洞，惡意 JavaScript 就能讀出所有登入憑證寄給攻擊者。

**漏洞五：忽略 CSRF 和暴力破解。**
- **CSRF**（跨站請求偽造）：使用者登入了你的網站，又打開一個惡意網站，惡意網站偷偷發請求給你的網站，瀏覽器會**自動帶上 Cookie**。`SameSite` 能擋下大部分情況，重要操作再加 CSRF Token；
- **暴力破解**：攻擊者對同一個帳號不停嘗試密碼。要對 `/login` 做**限速**（例如同一帳號 5 次失敗就暫停 15 分鐘），並建議提供**兩步驟驗證**。

@section 常見疑問
**問：能不能乾脆不要自己做登入，用「以 Google 帳號登入」？**
答：很多時候這是更好的選擇。這類「**第三方登入**」通常基於 **OAuth 2.0 / OpenID Connect** 標準：密碼由 Google 保管，你的網站只收到一張「Google 證明這個人是 alice@gmail.com」的憑證。你就不必煩惱密碼雜湊、忘記密碼、暴力破解這些問題。代價是要正確實作跳轉與驗證流程，並依賴外部服務。不論哪種方式，**拿到身分之後**的 Session 管理和授權，仍然是你的責任。

**問：使用者忘記密碼怎麼辦？伺服器能把密碼寄給他嗎？**
答：**不能，也不該能。**伺服器只存雜湊，本來就不知道原密碼。如果某個網站能把你的舊密碼寄給你，代表它用明文或可逆方式存密碼，這是個警訊。正確做法是寄一個**一次性、短時間有效**（例如 15 分鐘）的重設連結，連結中的 token 同樣用 `secrets` 產生，使用一次後立刻作廢。

**問：密碼規則要多複雜？一定要大小寫加符號嗎？**
答：現代的建議（例如美國 NIST 的指引）反而是：**長度比複雜度重要**。要求至少 8 到 12 個字元、允許很長的密碼（包括空白，方便使用「一句話」當密碼），並拒絕已知外洩過的常見密碼（如 `password123`）。強迫每 90 天更換、硬性規定符號組合，常讓使用者改用更好猜的模式（`Password1!`、`Password2!`）。

**問：API 給其他程式呼叫時，也用 Cookie 嗎？**
答：通常不用。程式對程式的呼叫常使用 **API 金鑰**或短效的存取 token，放在 `Authorization` 標頭中傳送。金鑰的保管原則和第 16 課一樣：存在伺服器端或環境變數，不寫進程式碼、不放前端。

@section 動動腦：判斷看看
**題一**：為什麼不用 SHA-256 存密碼？
→ 它太快，攻擊者每秒能試上百億次；應使用 Argon2id 等慢速、加鹽的密碼專用演算法。

**題二**：兩位使用者都用密碼 `12345678`，用 Argon2id 存起來的結果一樣嗎？
→ 不一樣。每筆密碼都有獨立的隨機鹽。

**題三**：JWT 裡放使用者的手機號碼安全嗎？
→ 不安全。一般 JWT 的內容只是編碼而非加密，任何人都能解碼讀取。

**題四**：登入失敗時回傳「此 Email 尚未註冊」，有什麼問題？
→ 造成帳號枚舉，攻擊者能藉此掃出哪些 email 有帳號。

**題五**：使用者登出後，Session 和純 JWT 誰能讓被偷的憑證立即失效？
→ Session。刪除伺服器上的紀錄即可；純 JWT 在過期前無法單靠本身撤銷。

@section 本課重點整理
- **身分驗證（AuthN）**確認「你是誰」；**授權（AuthZ）**決定「你能做什麼」。
- **密碼**：不存明文、不用可逆加密；用雜湊比對。
- **快速雜湊不夠**：SHA-256 太快；要用 Argon2id / bcrypt，每筆加隨機鹽、故意變慢。
- **Cookie** 是瀏覽器自動帶上的儲存機制；**Session** 把憑證資訊存在伺服器；**JWT** 把資訊寫在帶簽章的憑證上。
- **Session 可立即撤銷**；**JWT 內容不加密**、過期前難以撤銷。
- **Cookie 安全標記**：`HttpOnly`、`Secure`、`SameSite`。
- **session_id** 一定用 `secrets` 產生。
- **五個漏洞**：快速雜湊、帳號枚舉、可預測 ID、憑證可被 JS 讀取、忽略 CSRF 與暴力破解。

@term 身分驗證
確認使用者「是誰」的過程（Authentication，AuthN）。
@term 授權
確認身分後，決定使用者「能做什麼」的過程（Authorization，AuthZ）。
@term 雜湊
把輸入轉成固定長度指紋、無法反推回原文的單向運算（Hash）。
@term 鹽
為每個密碼加上的隨機字串，讓相同密碼產生不同雜湊（Salt）。
@term 彩虹表
事先算好大量常見密碼雜湊值的對照表，用於快速破解（Rainbow Table）。
@term Argon2id
OWASP 推薦的慢速、耗記憶體密碼雜湊演算法。
@term bcrypt
成熟且廣泛使用的慢速密碼雜湊演算法。
@term 無狀態
每個請求獨立處理、伺服器不記得先前請求的特性（Stateless）。
@term Cookie
瀏覽器儲存並在之後請求中自動附帶的小段資料。
@term Session
登入狀態存於伺服器、只發給客戶端一個隨機 ID 的機制。
@term JWT
自帶資訊並附簽章的憑證格式，內容預設未加密（JSON Web Token）。
@term HttpOnly
Cookie 標記，禁止前端 JavaScript 讀取該 Cookie。
@term 帳號枚舉
攻擊者藉由不同錯誤訊息或回應時間，判斷哪些帳號存在（Account Enumeration）。
@term CSRF
誘使已登入的使用者瀏覽器，向目標網站送出非本意請求的攻擊（Cross-Site Request Forgery）。
@term 限速
限制一段時間內可嘗試的次數，以防暴力破解（Rate Limiting）。
