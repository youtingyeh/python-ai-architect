@section 開場：「我手動點過，好像可以」
這是工程團隊**最昂貴**的一句話。

手動測試有三個根本問題：
- **無法重複**：你今天點過，明天改了程式，還會再點一遍嗎？
- **無法全面**：你點了「準時繳交」，有點「剛好在截止那一秒繳交」嗎？
- **無法交接**：你知道要點哪些地方，下一位同事不知道。

一個假設的情境：評分模組為了支援「逾期扣分」改了公式，但沒有測試。三週後，有學生發現：**同樣的分數，晚交的人反而比準時交的人高**。團隊只好重新計算 412 筆成績、寄出更正通知、應付家長的詢問。

真正的成本不是改那一行程式碼，而是**信任的流失**和**人工善後**。

**自動化測試**的本質，是把「系統**應該**怎麼運作」寫成**可以執行的規格**，每次修改程式後都自動重新驗證一遍。

**AI 時代，測試更重要，而不是更不重要。**LLM 幾秒內就能生成上百行程式碼，但它不知道你的業務規則，也不會為結果負責。判斷「這段 AI 生成的程式是否符合需求」，唯一客觀的方法就是測試（第 46 課）。

這一課要學：
1. 好測試的結構和四個性質；
2. 三種測試：**單元**、**整合**、**端對端**；
3. **測試金字塔**：每種測試該寫多少；
4. **測試替身**：mock、stub、fake 的差別和陷阱；
5. **回歸測試**：修一個 bug，就永遠防住它。

@section 好測試的結構：準備、執行、斷言
第 50 課初步介紹過 pytest。幾乎每個測試都可以拆成三步，稱為 **AAA**：
```
def test_late_submission_gets_penalty():
    # Arrange（準備）
    deadline = datetime(2026, 11, 1, 23, 59)
    submitted = datetime(2026, 11, 2, 10, 0)

    # Act（執行）
    score = apply_late_penalty(90, deadline, submitted)

    # Assert（斷言）
    assert score == 80
```
- **Arrange**：準備測試資料和環境；
- **Act**：執行**一個**被測試的行為；
- **Assert**：檢查結果是否符合預期。

**比喻：**科學實驗。準備器材和樣本（Arrange）、進行實驗（Act）、記錄並比對結果（Assert）。

測試的名字也很重要：`test_late_submission_gets_penalty`（逾期繳交會被扣分）比 `test_1` 好太多了。測試失敗時，光看名字就知道哪條規則壞了。

@section 好測試的四個性質
**一、快速。**慢的測試沒人想跑。理想上，大部分測試在幾毫秒內完成。

**二、獨立。**測試之間**沒有先後順序的依賴**。測試 B 不能依賴測試 A 先建立的資料。否則單獨跑 B 會失敗，或者換個順序就失敗，讓人摸不著頭緒。

**三、可重複。**同一份程式碼，跑一百次結果都一樣。這需要控制所有「**不確定的來源**」：
- **時間**：不要在函式裡呼叫 `datetime.now()`，而是把時間當參數傳進去。否則「截止前」的測試，過了截止日就會失敗；
- **隨機**：固定亂數種子（第 10 課）；
- **網路**：用替身取代真實的外部服務（下面會講）；
- **檔案**：用 pytest 提供的暫存資料夾 `tmp_path`，測完自動清除。

時好時壞的測試，業界稱為「**不穩定測試**」（Flaky Test）。它比沒有測試更糟：大家會開始習慣性忽略失敗，真正的問題也跟著被忽略了。

**四、自我說明。**測試讀起來就像規格文件。新同事看測試，就能理解系統的規則。

**fixture：共用的準備工作。**
很多測試都需要「一個空的資料庫」或「一個已登入的使用者」。pytest 的 **fixture** 負責建立並在測試後清理這些共用資源：
```
@pytest.fixture
def db():
    conn = connect_test_db()
    yield conn          # 交給測試使用
    conn.rollback()     # 測試結束後清理
```
每個測試結束後**回滾**交易（第 58 課），下一個測試又是乾淨的資料庫，維持獨立性。

@section 三種測試：範圍不同，回答的問題也不同
**一、單元測試（Unit Test）：測一個小零件。**
驗證**單一函式或類別**的業務規則，**不碰**網路、資料庫、檔案。
- 例子：分數必須在 0 到 100 之間；逾期扣分的公式；權限判斷函式；
- 速度：每個**幾毫秒**；
- 回答的問題：「**這條規則本身**算得對嗎？」

**二、整合測試（Integration Test）：測零件之間的接合。**
驗證**兩個以上真實元件**一起運作，例如 API 加上資料庫。
- 例子：新增學生後，資料庫真的多了一筆；違反唯一約束時，API 回傳 409；
- 速度：每個**幾十到幾百毫秒**；
- 回答的問題：「**零件接在一起**能正常運作嗎？」

**三、端對端測試（E2E Test）：從使用者的角度測整個系統。**
用工具（例如 **Playwright**）**真的打開瀏覽器**，模擬使用者點擊、輸入、送出。
- 例子：學生登入 → 選課 → 繳交作業 → 看到「繳交成功」；
- 速度：每條流程**幾秒到幾十秒**；
- 回答的問題：「**使用者真正的操作流程**走得通嗎？」

**比喻：**造汽車。
- 單元測試：在工作台上單獨測試煞車片的摩擦係數；
- 整合測試：把煞車片裝上煞車系統，測踩下踏板後輪子會不會停；
- 端對端測試：找一位試車員，把整台車開上測試跑道。

三種都需要。只有單元測試，零件個個合格，組起來卻可能接不上；只有端對端測試，車子停不下來時，你不知道是哪個零件出了問題，而且每次測試都要開一趟跑道，又慢又貴。

**FastAPI 的 TestClient**（第 54 課）在同一個程式內直接呼叫 API，不經過真實網路，介於單元和整合測試之間。搭配 `app.dependency_overrides`，可以把資料庫連線或「目前登入的使用者」替換成測試用的版本。

@section 測試金字塔：每種該寫多少
**測試金字塔**（Mike Cohn 提出的比喻）建議：
- **底層**：大量快速的單元測試；
- **中層**：適量的整合測試；
- **頂層**：少量的端對端測試。

有人用「70% / 20% / 10%」當入門比例，但這只是起點。以後端 API 為主的專案，問題常出在元件接合處，整合測試的比重可以高一些。也有人提出以整合測試為主體的「**測試獎盃**」模型。

**比例不是重點，重點是每一層有明確的責任**，同一條規則不要在三層各測一次，否則規則一改，要改三個地方的測試。

**成本結構的感受（假設的數字）：**
- 120 個單元測試：約 0.8 秒；
- 25 個整合測試：約 6 秒；
- 3 條端對端：約 40 秒；
- 總計**不到 1 分鐘**，每次提交程式碼都跑得起。

如果同樣 148 條全部寫成端對端測試，可能要 20 分鐘以上。測試一慢，開發者就會開始**跳過不跑**，品質把關就形同虛設。

**端對端測試只留最核心的 3 到 5 條使用者流程**，其餘的規則下沉到更便宜的層級驗證。

@section 測試替身：mock、stub、fake
測試時，常需要用「**替身**」取代真實的元件。就像電影的特技替身，代替主角去做危險、昂貴或難以控制的事。

**Stub（樁）：回傳固定答案。**
```
def fake_llm(prompt): return "這是固定的摘要"
```
用來取代呼叫 LLM API：真實呼叫又慢、又花錢、每次答案還不一樣。

**Fake（假實作）：能真正運作的簡化版。**
例如用 Python 字典實作一個「記憶體版的資料庫」，能新增、能查詢，只是不持久。

**Mock（模擬物件）：記錄被怎麼呼叫，讓你驗證互動。**
例如驗證「註冊成功後，寄信函式**被呼叫了一次**，收件人是 alice@mail.com」。

**過度 mock 的陷阱：測試全綠，上線就壞。**
Mock 的行為是**你想像出來的**。如果你以為外部 API 回傳 `{"result": ...}`，但它實際回傳的是 `{"data": ...}`，你的 mock 照你的想像回傳，測試全部通過，上線後才發現對不上。

**經驗法則：**
- **自己擁有、便宜的元件**（資料庫、檔案）：盡量用真的，或用 fake；
- **昂貴、不可控的外部服務**（LLM API、付款、寄信）：用 stub 或 mock；
- 另外保留**少量**測試，定期對照真實服務，確認你的替身沒有和現實脫節。

**資料庫引擎也要注意：**用 SQLite 記憶體資料庫跑測試很快很方便，但它和 PostgreSQL 有行為差異。例如 SQLite **預設不檢查外鍵**，型別也比較寬鬆。如果正式環境用 PostgreSQL，那麼約束、交易這類關鍵測試，應該在 PostgreSQL 上跑（第 67 課的 Docker 可以輕鬆啟動一個測試用的 PostgreSQL）。

@section 回歸測試：修一個 bug，永遠防住它
回到第 64 課的缺陷：「**沒被指派的助教也能批改作業**」。標準的修正流程有五步：

**第一步：寫測試重現問題。**
```
def test_unassigned_ta_cannot_grade(client, db):
    res = client.patch("/submissions/1041/grade",
                       json={"score": 80}, headers=as_user("ta#8"))
    assert res.status_code == 403
    assert db.get_score(1041) is None   # 沒有副作用
```

**第二步：確認測試是紅燈。**
在**還沒修**的程式上跑，應該失敗：實際得到 200，分數也變成 80。

**這一步很重要。**如果還沒修就已經是綠燈，代表這條測試**根本沒測到問題**，可能斷言寫錯了，或測試資料不對。

**第三步：修正程式。**加上指派表檢查。

**第四步：確認綠燈。**這條測試通過，而且**整套測試**都要跑過，確認沒有改壞別的地方。

**第五步：把測試永久留著。**
這就是「**回歸測試**」（Regression Test）：保證這個 bug **永遠不會悄悄回來**。哪天有人重構程式，不小心拿掉了檢查，這條測試會立刻變紅。

**比喻：**修好一個漏水的地方後，在那裡裝一個漏水偵測器。

**擴大成矩陣：**
4 種角色 × 3 種狀態（本課程、其他課程、不存在的資源）= 12 條測試。用 pytest 的參數化寫法，不必複製貼上 12 次：
```
@pytest.mark.parametrize("user, expected", [
    ("student#3", 403),
    ("ta#7", 200),
    ("ta#8", 403),
    ("teacher#2", 200),
])
def test_grade_permission(client, user, expected):
    ...
```

@section AI 時代的測試習慣
**好習慣：先讓 AI 寫測試，你審查，再讓它寫實作。**
你審查的重點是：這些斷言**真的對應需求**嗎？邊界條件有沒有涵蓋？這呼應第 45 課的規格驅動開發。

**警訊：AI 同時產出實作和「恰好全部通過」的測試。**
它可能**把實作的錯誤行為，直接寫成了預期值**。例如實作把逾期扣分算錯了，測試卻斷言那個錯誤的數字。測試和實作一起錯，就永遠是綠燈。

**AI 與資料管線也適用：**資料清洗、特徵轉換、評估指標的計算都是純邏輯，最適合單元測試；「LLM API 逾時要重試三次」、「重試後仍失敗要回傳友善錯誤」這類行為，用 stub 模擬逾時，寫成整合測試。

@section 常見陷阱
**陷阱一：測試連到正式資料庫。**
一個環境變數設錯，測試就可能**清空真實使用者的資料**。防護做法：測試一啟動就檢查「環境是 test 且資料庫名稱包含 test」，否則立刻中止；CI 環境使用用完即丟的資料庫。

**陷阱二：迷信覆蓋率。**
「**程式碼覆蓋率** 90%」只代表 90% 的程式碼**被執行過**，不代表**被驗證過**。一個沒有任何斷言的測試，也能把覆蓋率拉高。比數字更有意義的問題是：關鍵規則有沒有**邊界測試**？每個修過的 bug 有沒有**回歸測試**？

**陷阱三：只測成功的路徑。**
第 64 課說過：授權系統的價值在於正確地**拒絕**。驗證、錯誤處理也一樣，失敗的情境往往比成功的情境更值得測。

**陷阱四：測試依賴執行順序或真實時間。**
這是不穩定測試的兩大主因。

@section 動動腦：判斷看看
**題一**：「分數必須介於 0 到 100」這條規則，該用哪種測試驗證？
→ 單元測試。它是純邏輯，不需要資料庫或網路，又快又精準。

**題二**：修 bug 前先寫的測試，一跑就是綠燈，代表什麼？
→ 測試沒有測到問題本身，需要檢查斷言或測試資料，不能拿它當回歸保護。

**題三**：所有外部服務都用 mock，測試全綠，上線卻出錯，可能原因是什麼？
→ mock 的行為與真實服務不一致；應保留少量對照真實服務的測試。

**題四**：覆蓋率 95%，代表系統品質很好嗎？
→ 不一定。覆蓋率只代表程式被執行過；要看關鍵規則是否有斷言、邊界與回歸測試。

@section 本課重點整理
- **自動化測試**是可執行的規格；AI 生成程式碼越多，越需要測試把關。
- **AAA 結構**：準備、執行、斷言；測試名稱要說明規則。
- **四個性質**：快速、獨立、可重複（控制時間、隨機、網路、檔案）、自我說明；避免不穩定測試。
- **三種測試**：單元（一個零件的規則）、整合（零件接合）、端對端（使用者流程）。
- **測試金字塔**：大量單元、適量整合、少量端對端；每層責任明確，總時間要短到每次都跑得起。
- **測試替身**：stub 回傳固定值、fake 是簡化實作、mock 驗證互動；過度 mock 會脫離現實。
- **回歸測試五步**：重現、確認紅燈、修正、確認綠燈、永久保留。
- **陷阱**：連到正式資料庫、迷信覆蓋率、只測成功路徑。

@term 自動化測試
用程式自動驗證系統行為是否符合預期，可重複執行（Automated Testing）。
@term AAA
測試的三步結構：準備、執行、斷言（Arrange, Act, Assert）。
@term 不穩定測試
同一份程式碼有時通過、有時失敗的測試（Flaky Test）。
@term fixture
pytest 中建立與清理共用測試資源的機制。
@term 單元測試
驗證單一函式或類別、不碰外部資源的測試（Unit Test）。
@term 整合測試
驗證多個真實元件協同運作的測試（Integration Test）。
@term 端對端測試
從使用者角度操作整個系統的測試（End-to-End Test，E2E）。
@term Playwright
自動操作瀏覽器、進行端對端測試的工具。
@term 測試金字塔
建議大量單元測試、適量整合測試、少量端對端測試的比例模型（Test Pyramid）。
@term 測試替身
在測試中代替真實元件的物件，如 stub、fake、mock（Test Double）。
@term mock
記錄被呼叫情形、可驗證互動的測試替身。
@term stub
回傳固定答案的測試替身。
@term 回歸測試
確保已修復的錯誤不會再次出現的測試（Regression Test）。
@term 程式碼覆蓋率
測試執行時被執行到的程式碼比例，不等於被驗證的比例（Code Coverage）。
@term 參數化測試
用同一個測試函式搭配多組輸入與預期結果（Parametrized Test）。
