@section 開場：「昨天下午三點，我按了按鈕，然後失敗了」
在自己的電腦上開發時，很多人習慣用 `print("到這裡了")` 找錯誤，用 `except Exception: pass` 讓錯誤「消失」。

系統上線、同時服務很多使用者，還串接了 LLM、向量資料庫、金流之後，這些習慣會讓除錯變成災難。

想像一位使用者回報：「**昨天下午三點，我按了『產生課程摘要』，畫面轉了十秒，然後顯示失敗。**」

你打開伺服器的輸出，看到的是**每秒幾百行交錯的文字**，來自幾十個同時進行的請求。哪幾行屬於這位使用者？完全分不出來。

更糟的情況是：程式到處用 `except: pass` 吞掉錯誤（第 49 課的大忌）。資料庫斷線、API 金鑰過期、硬碟寫滿，全都**無聲無息地被掩蓋**。系統表面上回傳 200 成功，實際上資料只寫了一半。

這一課要學怎麼讓系統「**可觀測**」（Observability）：出事時，你能看見發生了什麼。重點有：
1. **結構化日誌**：機器能讀、能搜尋的日誌；
2. **Request ID**：把同一個請求的所有紀錄串在一起；
3. **日誌等級**：區分「正常的拒絕」和「真正的故障」；
4. **對內詳細、對外安全**：錯誤訊息的兩張臉；
5. **敏感資訊遮罩**：密碼和金鑰絕不能進日誌。

@section 日誌是什麼：飛機的黑盒子
**日誌**（Log）是程式在執行過程中留下的**紀錄**：什麼時間、發生了什麼事、結果如何。

**比喻：**飛機的**黑盒子**。平常沒人去看它，但一旦出事，調查人員要靠它還原「最後那幾分鐘到底發生了什麼」。沒有黑盒子，只能靠猜。

**為什麼不用 print？**
- `print` 沒有**等級**：分不出是一般資訊還是嚴重錯誤；
- `print` 沒有**時間**和**來源**；
- `print` 無法統一**開關**或**導向**：上線時想關掉除錯訊息、或把錯誤送到告警系統，都做不到。

Python 內建的 `logging` 模組可以解決這些問題：
```
import logging
logger = logging.getLogger(__name__)

logger.info("學生資料已載入")
logger.warning("LLM 回應較慢")
logger.error("資料庫連線失敗")
```

@section 日誌等級：不是每件事都是警報
日誌有幾個**等級**，由輕到重：
- **DEBUG**：開發時的細節，上線後通常關閉；
- **INFO**：正常事件，例如「請求開始」、「使用者登入」；
- **WARNING**：不正常但系統還能處理，例如「LLM 回應超過 5 秒」、「重試第 2 次」；
- **ERROR**：某個操作失敗了，需要有人關注；
- **CRITICAL**：系統層級的嚴重問題，例如資料庫完全連不上。

**最重要的區分：預期內的拒絕 vs. 非預期的故障。**

**預期內的拒絕（4xx）：系統正常運作的一部分。**
使用者輸入格式錯誤（422）、權限不足（403）、找不到資源（404）、重複註冊（409）。這些是系統**正確地說「不」**，用 INFO 或 WARNING 記錄即可，**不需要**印出冗長的錯誤堆疊。

**外部依賴的暫時故障（502、503、504）：**
上游 LLM API 逾時、向量資料庫短暫斷線。記錄 WARNING 或 ERROR 並記下耗時，觸發有限次數的重試或降級回應（第 22 課）。

**系統內部的錯誤（500）：程式有 bug。**
`KeyError`、除以零、資料庫連線池耗盡。這些**絕不能**被吞掉，要讓它往上拋到「**全域例外處理器**」，記錄 ERROR 加上完整堆疊，並觸發告警。

**比喻：**醫院的分級。病人掛號時說錯名字（4xx），櫃台更正就好，不需要廣播；檢驗儀器暫時故障（503），先改用備用儀器並記錄下來；手術室停電（500），要立刻拉警報。

如果每個 422 都印出一大段 ERROR 和堆疊，日誌就會被**洗版**，真正的嚴重錯誤反而淹沒在噪音裡。這叫做「**告警疲勞**」：警報太多，大家就不看了。

@section 結構化日誌：讓機器也讀得懂
**傳統的文字日誌：**
```
User 42 failed to query DB after 3 retries
```
人看得懂，但要用程式統計「過去一小時有多少使用者查詢失敗」，就得寫複雜的文字比對，而且訊息格式稍有不同就漏掉。

**結構化日誌：每筆紀錄是固定欄位的 JSON。**
```
{
  "timestamp": "2026-11-27T10:15:11.150Z",
  "level": "ERROR",
  "event": "llm_upstream_timeout",
  "request_id": "req-7c31b2",
  "user_id": 108,
  "provider": "openai",
  "timeout_sec": 10.0,
  "attempt": 2
}
```
- `timestamp`：使用 **UTC** 國際標準時間，避免伺服器在不同時區時搞混；
- `event`：**穩定的事件名稱**，例如 `llm_upstream_timeout`。不要每次寫不一樣的句子，這樣才能精準搜尋和統計；
- 其他欄位：和這個事件相關的數值。

現在你可以輕鬆查詢：「過去一小時 `event = llm_upstream_timeout` 有幾筆？」「`latency_ms` 的平均是多少？」日誌從「一堆文字」變成了「**可以分析的資料**」。

**比喻：**傳統日誌像手寫的流水帳；結構化日誌像填寫固定格式的表單。流水帳讀起來自然，但要統計時，表單方便太多了。

@section Request ID：把同一個請求串起來
這是解決開場難題的關鍵。

**做法：**
1. 每個請求進來時，產生一個**唯一的編號**，例如 `req-7c31b2`（如果上游的閘道已經帶了 `X-Request-ID` 標頭，就沿用它）；
2. 這個請求執行期間，**所有**日誌都自動帶上這個編號；
3. 回應給使用者時，也附上這個編號。

在 FastAPI 中，可以用「**中介軟體**」（Middleware，每個請求進出都會經過的一層）來產生編號，再用 Python 的 `contextvars` 把它「綁定」在目前的請求上。這樣不管程式呼叫了多少層函式，每一行日誌都會自動帶上同一個 `request_id`，不用每個函式都手動傳參數。

**比喻：**醫院的**病歷號碼**。病人從掛號、看診、抽血、照 X 光到領藥，每一站的紀錄都標上同一個號碼。之後要追查，只要搜尋這個號碼，就能把散落在各科室的紀錄串成完整的就醫過程。

**走一遍：**
學生在上午 10:15 按下「生成本週重點」，畫面顯示：
```
AI 生成服務暫時忙碌（追蹤碼：req-7c31b2）
```
學生把追蹤碼回報給客服。工程師搜尋 `request_id = "req-7c31b2"`，立刻看到三筆紀錄：
```
10:15:01.010 INFO  request_started      path=/api/summarize user_id=108
10:15:01.145 INFO  rag_chunks_retrieved chunk_count=4 latency_ms=135
10:15:11.150 ERROR llm_upstream_timeout provider=openai timeout_sec=10 attempt=2
```
三十秒內就能判斷：資料庫和向量檢索都很健康（只花了 135 毫秒），問題出在**上游 LLM API 連續兩次超過 10 秒逾時**。不用猜，不用重現。

當系統拆成多個服務時，request_id 會跟著請求在服務之間傳遞，這叫做「**分散式追蹤**」（Distributed Tracing），概念完全相同。

@section 錯誤的兩張臉：對內詳細，對外安全
發生非預期的錯誤時，有兩個對象需要知道：

**對內（給工程師的日誌）：越詳細越好。**
完整的錯誤堆疊（Stack Trace）、當時的參數摘要。用 `logger.exception()` 會自動附上堆疊：
```
try:
    ...
except Exception:
    logger.exception("summarize_failed")
    raise
```

**對外（給使用者的回應）：穩定、安全、有用。**
```
{
  "error": {
    "code": "INTERNAL_ERROR",
    "message": "系統暫時無法處理請求，請附上追蹤碼聯繫客服",
    "request_id": "req-9f8a..."
  }
}
```
- **穩定的錯誤代碼**（`code`）：前端可以依此決定顯示什麼；
- **人話訊息**：使用者看得懂，知道下一步該怎麼做；
- **追蹤碼**：連結到內部的詳細日誌。

**絕對不能對外回傳的東西：**原始 SQL 語句、檔案路徑、環境變數、錯誤堆疊、資料庫主機位址。

**常見錯誤：`return {"error": str(e)}`。**
`str(e)` 是原始的例外訊息。資料庫出錯時，它可能包含**資料表名稱、欄位結構，甚至資料庫的內部 IP 和帳號**。這等於免費提供攻擊者一份系統地圖。

**比喻：**餐廳廚房起火。對內，主廚要知道是哪個爐子、什麼原因；對外，服務生只要跟客人說「廚房暫時出了點狀況，您的餐點會延遲，這是您的號碼牌」，而不是把廚房的配置圖交給客人。

**自訂領域例外：**
可以定義自己的例外類別（第 49 課），例如 `CourseFullError`（課程已額滿），在全域例外處理器中統一轉換成對應的狀態碼和錯誤格式。業務邏輯只要 `raise CourseFullError()`，不需要在每個地方處理 HTTP 細節。

@section 敏感資訊遮罩：日誌不能變成洩密管道
開發者常隨手寫：
```
logger.info("收到請求：%s", payload)
```
如果 `payload` 裡有使用者的密碼、`Authorization` 標頭裡的 token、API 金鑰、身分證字號……它們全都被**明文寫進日誌**。

日誌會被存在硬碟、傳到第三方日誌平台、被很多工程師查看、保存很久。**日誌外洩，等於資料外洩。**這也是第 63 課說「原始密碼絕不寫進日誌」的原因。

**做法：在日誌系統層級自動遮罩。**
設定一個過濾器，凡是欄位名稱是 `password`、`token`、`api_key`、`secret`、`authorization` 的，一律替換成 `"***REDACTED***"`。

**為什麼要在系統層級做？**因為靠每個工程師「記得不要印」一定會漏。和第 58 課的資料庫約束一樣：**重要的規則要由系統強制，而不是靠人記得。**

**AI 應用的特別提醒：**使用者的提示詞和 LLM 的回應可能包含個資或機密。要記錄時，考慮只記錄長度、摘要或雜湊值，而非全文；如果必須保存全文，要有明確的存取權限和保存期限。

@section 常見陷阱
**陷阱一：吞掉例外。**
```
try:
    data = load_courses()
except:
    return []
```
型別錯誤、拼錯變數名稱、記憶體不足，全都被當成「查無資料」。系統帶著錯誤繼續往下跑，最後可能寫壞資料庫，而且**沒有任何紀錄**。只捕捉**明確知道如何處理**的例外型別。

**陷阱二：把原始例外訊息回傳給前端。**如上所述，`str(e)` 會洩漏內部資訊。

**陷阱三：在迴圈裡狂印大物件。**
處理一萬筆嵌入向量時，把每個長度 1536 的浮點數陣列印進日誌。幾分鐘就塞爆硬碟，大量寫入還會拖慢整個 API。日誌要記**摘要**（筆數、耗時），不是**原始資料**。

**陷阱四：每個 4xx 都記成 ERROR 並印堆疊。**
日誌被洗版，真正的問題被淹沒。

@section 日誌之外：指標與告警
日誌記錄「**發生了什麼事**」，但要回答「**系統現在健康嗎？**」，還需要另外兩樣東西。

**指標（Metrics）：用數字描述系統狀態。**
例如每秒請求數、錯誤率、回應時間的中位數和第 95 百分位（p95，代表「最慢的那 5%」大概多慢）。指標通常畫成即時圖表，一眼就能看出趨勢。

為什麼看 p95 而不只看平均？假設 100 個請求裡，95 個花 0.1 秒、5 個花 10 秒，平均大約 0.6 秒，看起來還好；但那 5% 的使用者等了 10 秒，體驗非常糟。AI 應用的回應時間差異特別大，更要看 p95。

**告警（Alerting）：數字越線時通知人。**
例如「5 分鐘內錯誤率超過 5%」或「p95 回應時間超過 8 秒」就發通知給值班工程師。告警要設在「**使用者會感受到的症狀**」上，而不是每個小事件都響，否則又會造成告警疲勞。

**三者的關係：**告警告訴你「**出事了**」，指標告訴你「**大概哪裡、從什麼時候開始**」，日誌和 request_id 告訴你「**具體發生了什麼**」。

**AI 應用該追蹤的指標：**LLM 呼叫的延遲、逾時率、每次請求消耗的 token 數與費用、RAG 檢索的命中數。這和第 29 課的 LLMOps 監控是同一件事，只是現在你知道它在系統中的位置了。

@section 和 AI 一起做：用 AI 讀日誌
日誌常常又長又雜，人工閱讀很花時間。AI 很適合幫你**從大量日誌裡找出模式**：哪個錯誤最常出現？哪些錯誤總是一起發生？錯誤從什麼時間點開始增加？

**貼日誌之前，先遮蔽敏感資訊**
這是最重要的一步。日誌裡可能有學生姓名、電子郵件、IP 位址、Token。貼給 AI 之前，先用程式把它們替換掉：
```python
import re
def mask(line: str) -> str:
    line = re.sub(r"[\w.+-]+@[\w-]+\.[\w.]+", "<email>", line)
    line = re.sub(r"Bearer [A-Za-z0-9._-]+", "Bearer <token>", line)
    return line
```
如果日誌一開始就照本課的做法加上了遮罩，這一步會輕鬆很多。

**一段好的請求範例**
```
以下是事故期間 10 分鐘的結構化日誌（已遮蔽個資）。
請找出：
1. 第一個異常出現的時間點與 request_id
2. 出現最多次的錯誤類型及次數
3. 錯誤之間是否有因果關係（例如 A 錯誤後總是接著 B 錯誤）
請引用具體的日誌行作為證據，不要推測日誌裡沒有的內容。
```
要求 AI **引用具體日誌行**，可以避免它編造看似合理、但日誌裡根本沒有的原因。

**不要交給 AI 的事**
最終的事故原因判斷。AI 找到的是「相關性」，真正的根本原因，需要你用重現和測試來確認。

@section 動動腦：判斷看看
**題一**：使用者輸入的年齡格式錯誤（422），該用什麼等級記錄？要印堆疊嗎？
→ INFO 或 WARNING，不需要堆疊；這是系統正常的拒絕。

**題二**：`return {"error": str(e)}` 有什麼問題？
→ 原始例外訊息可能洩漏資料表結構、檔案路徑、內部主機等資訊；對外應回傳穩定的錯誤代碼、人話訊息與追蹤碼。

**題三**：為什麼要給每個請求一個 request_id，並回傳給使用者？
→ 讓所有相關日誌能用同一個編號串起來；使用者回報時提供追蹤碼，工程師就能精準找到那次請求的完整紀錄。

**題四**：如何確保密碼和 API 金鑰不會出現在日誌中？
→ 在日誌系統層級設定過濾器，自動遮罩敏感欄位，而不是依賴每個人記得。

@section 本課重點整理
- **日誌**是系統的黑盒子；用 `logging` 而不是 `print`。
- **日誌等級**：DEBUG、INFO、WARNING、ERROR、CRITICAL。
- **區分三類**：預期內的拒絕（4xx，INFO/WARNING）、外部暫時故障（5xx 閘道類，WARNING/ERROR 並重試）、內部 bug（500，ERROR 加堆疊並告警）。
- **結構化日誌**：固定欄位的 JSON、穩定的事件名稱、UTC 時間，方便搜尋與統計。
- **Request ID**：每個請求一個編號，貫穿所有日誌並回傳給使用者。
- **錯誤的兩張臉**：對內記錄完整堆疊；對外只給錯誤代碼、人話訊息與追蹤碼。
- **敏感資訊遮罩**：在系統層級自動遮蔽密碼、token、金鑰。
- **陷阱**：吞掉例外、回傳 `str(e)`、在迴圈中印大物件、把 4xx 當 ERROR。

@term 日誌
程式執行過程中留下的紀錄，用於事後追查（Log）。
@term 可觀測性
透過日誌、指標、追蹤等資料，了解系統內部狀態的能力（Observability）。
@term 日誌等級
依嚴重程度區分日誌，如 DEBUG、INFO、WARNING、ERROR、CRITICAL（Log Level）。
@term 結構化日誌
以固定欄位（通常是 JSON）輸出、方便機器搜尋與統計的日誌（Structured Logging）。
@term Request ID
每個請求的唯一編號，用來串起同一請求的所有日誌。
@term 中介軟體
每個請求進出時都會經過的處理層（Middleware）。
@term 分散式追蹤
在多個服務之間傳遞追蹤編號，還原請求完整路徑的技術（Distributed Tracing）。
@term 錯誤堆疊
例外發生時，依序列出呼叫路徑的詳細資訊（Stack Trace）。
@term 全域例外處理器
集中攔截未處理例外、統一記錄與回應的機制（Global Exception Handler）。
@term 告警疲勞
警報過多導致人們忽略警報的現象（Alert Fatigue）。
@term 敏感資訊遮罩
在日誌中自動隱藏密碼、金鑰、個資等欄位（Redaction）。
@term UTC
國際標準時間，日誌常用以避免時區混淆。
