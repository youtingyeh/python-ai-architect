@section 開場：真實世界不是純文字，而是圖片、表格、PDF 和聲音
到目前為止，除了第 34 課介紹過「用文字生成圖片」之外，我們學的大多數應用（聊天、RAG、函式呼叫）都只處理**純文字**。

但打開你每天工作的資料夾看看：
- 公司報表是一堆掃描成圖片的 **PDF 折線圖與合併儲存格表格**；
- 產線品管傳來的是一張**拍到電路板焊點異常的照片**；
- 客服進線的是一通帶點背景雜音、夾雜中英文的 **3 分鐘語音電話**。

如果一個 AI 只能看純文字，它對這個世界就是「又盲又聾」。當你把一份充滿圖表的 PDF 丟進傳統的文字擷取工具，出來的往往是一堆亂碼數字，表格欄位全錯位，這也是為什麼很多新手做企業 RAG（第 25 課）時，明明文件裡有答案，AI 卻死活答錯！

現代 AI 已經全面邁入 **多模態**（Multimodal）時代——同一個模型可以同時「看圖、讀表、聽聲音、開口說話」。這也是李宏毅老師 2025 秋季《生成式 AI 與機器學習導論》後半段的重點主題。

這一課要帶你零門檻看懂多模態 AI 的底層機制與工程實戰：
1. 圖片和聲音怎麼變成語言模型看得懂的 Token？
2. **視覺語言模型（VLM）**的三大核心零件：視覺編碼器、對齊投影器、語言主幹；
3. 圖片要花多少 Token？動手算解析度與計費成本；
4. **多模態 RAG**：PDF 滿是表格和圖表時，三種處理架構怎麼選？
5. **語音模型（Spoken LM）**：傳統「聽寫→思考→朗讀」串接 vs. 原生端到端語音模型；
6. 多模態應用的常見幻覺、安全風險（圖片裡藏提示注入！）與驗收要點。

@section 圖片和聲音怎麼「翻譯」成 Token？
回想第 13 課與第 15 課：Transformer 語言模型骨子裡只吃一樣東西——**一排向量（Embedding）**。文字是先被分詞器切成 Token，再查表換成向量。

那圖片和聲音沒有「字」，要怎麼送進同一個 Transformer 裡？答案出奇地統一：**把它們也切成一小塊一小塊，轉成一樣維度的向量！**

**一、圖片怎麼變 Token？（Patchify 與 ViT）**
一張 1024×1024 的照片有超過一百萬個像素，如果每個像素當一個 Token，注意力機制的計算量會瞬間爆炸（第 40 課）。

於是 **視覺 Transformer（ViT，Vision Transformer）** 用了一個超聰明的辦法：
1. **切小方格（Patch）**：像把一張拼圖切成一格格小方塊（例如每格 $14 \times 14$ 或 $16 \times 16$ 像素）；
2. **每格變一個向量**：把每個小方格裡的紅綠藍（RGB）像素壓扁成一排數字，透過線性轉換變成一個「**視覺 Token**」；
3. 加上位置資訊（哪一格在左上、哪一格在右下），就可以直接丟進 Transformer 算注意力！

**比喻：**你不會一個顏料點一個顏料點去讀一幅畫，而是像看馬賽克拼磚一樣，一塊一塊掃過去，先認出「這幾塊合起來是貓耳朵」，再把整張圖串起來理解。

**二、聲音怎麼變 Token？**
聲音是一條隨時間震動的波形（例如每秒取樣 16,000 次）。直接看波形太細碎了，通常會經過兩步：
1. **轉成聲譜圖（Spectrogram）**或經過**神經音訊編解碼器（Audio Codec）**：把每 20～40 毫秒的一小段聲音，壓縮成一個「**音訊 Token**」，裡面不只記錄了「講了什麼字」，還保留了語氣、停頓、情緒和背景音；
2. 把這些連續的音訊 Token 排成一列，就能跟文字 Token 一樣送進模型處理。

@section 視覺語言模型（VLM）的內部三件套
現在你把一張發票照片傳給 Gemini、Claude 或 GPT，問它「這張發票的總金額是多少？」，模型內部實際上由三個模組接力完成：

```
[輸入圖片] ──▶ ① 視覺編碼器 (Vision Encoder) ──▶ 視覺特徵向量
                                                      │
                                                      ▼
                                               ② 投影器 / 連接器 (Projector)
                                                      │ (轉成語言模型懂的向量空間)
                                                      ▼
[文字問題] ──▶ 文字嵌入 ──────────────────────▶ ③ 大型語言模型 (LLM) ──▶ [文字回答]
```

**零件一：視覺編碼器（眼睛）**
通常是一個已經看過數億張「圖片＋說明文字」配對（例如 CLIP 或 SigLIP 對比學習）的視覺模型。它的任務是把圖片轉成富含語意的視覺向量（認得出哪裡是數字、哪裡是折線、哪裡是人臉）。

**零件二：對齊投影器（翻譯官）**
視覺編碼器的輸出維度和語言模型的嵌入空間原本「語言不通」（就像法文詞典對不上中文詞典）。投影器通常只是一個輕量的神經網路層（MLP 或 Cross-Attention），專門負責把視覺向量**翻譯成跟文字 Token 完全相容的向量**。

**零件三：大型語言模型主幹（大腦）**
一旦圖片變成一串視覺 Token，LLM 就把它和你的文字問題拼成**同一條輸入序列**：
`[視覺 Token 1, 視覺 Token 2, ..., 視覺 Token 256, "這", "張", "發", "票", "總", "金", "額", "是", "多", "少", "？"]`

接下來完全照第 14、15 課的自注意力機制運作！當模型生成答案時，文字的 Query 會直接「回頭看」發票右下角那個視覺 Token，讀出裡面的金額。

**更進一步：原生多模態（Native Multimodal）**
早期 VLM 是「外掛眼睛」（先把別人訓好的視覺編碼器接在 LLM 上）；新一代旗艦模型越來越走向「從預訓練第一天起，就把文字、圖片、音訊、影片的 Token 混在同一個統一架構裡聯合訓練」，跨模態的細膩理解（例如看影片同時聽對白、讀密密麻麻的工程藍圖）因此大幅躍進。

@section 動手算帳單：一張圖片到底值多少個 Token？
新手最常低估多模態的成本與上下文消耗：「不就傳了一張圖片嗎，應該比長文章便宜吧？」**不一定！**

很多模型對圖片採用「**動態切塊**」（Dynamic Tiling / High-Res Detail Mode）：
- 如果你傳一張**低解析度縮圖**（例如 $512 \times 512$），可能只要 **85～258 個 Token**；
- 但如果你傳一張高解析度 A4 文件掃描圖（例如 $1500 \times 2000$ 像素）並開啟「高精細模式」，模型為了看清楚上面的小字，會把圖切成好幾個 $512 \times 512$ 的磁磚，外加一張全景縮圖！

**實際算一次（以常見的磁磚計費規則為例）：**
假設規則是：基礎縮圖 85 Token ＋ 每塊 $512 \times 512$ 磁磚 170 Token。
一張 $1500 \times 2000$ 的 A4 掃描圖：
- 寬度需要 $\lceil 1500 / 512 \rceil = 3$ 塊；
- 高度需要 $\lceil 2000 / 512 \rceil = 4$ 塊；
- 總共 $3 \times 4 = 12$ 塊磁磚（有些 API 會先縮放至短邊 768，變成 $2 \times 2 = 4$ 塊，這裡先算未縮放上限與縮放後版本）：
  - 若縮放成 4 塊磁磚：$85 + 4 \times 170 = 765$ Token；
  - 若保留高解析 12 塊磁磚：$85 + 12 \times 170 = 2{,}125$ Token！

**放大到整個企業專案看看：**
假設你要處理一份 **100 頁的財務年報 PDF**，每頁轉成高解析圖（約 1,500 Token）：
$$100 \text{ 頁} \times 1{,}500 \text{ Token/頁} = 150{,}000 \text{ Token}$$
這份 PDF 還沒問任何問題，光塞進上下文就吃掉了 **15 萬 Token**——不但預填充時間（TTFT，第 40 課）會拉長到十幾秒，而且如果裡面 95 頁跟問題無關，還會嚴重觸發第 38 課的「**中間迷失**」！

**成本控制黃金法則：**
- **看大意（分類、找有沒有貓）**：縮到低解析度（512px）就夠，省下 80% Token；
- **讀小字（發票、合約、密表）**：保留高解析度，但**先裁切或只送命中的那幾頁**，不要把整本 100 頁全塞進單次請求。

@section 多模態 RAG：當企業 PDF 滿是圖表和複雜表格怎麼辦？
實務上做企業知識庫問答，80% 的死角都在「**非純文字 PDF**」（雙欄排版、跨頁表格、折線圖、架構流程圖）。處理多模態文件目前有三種主流架構，各有取捨：

**架構一：傳統文字解析（OCR + 表格抽取 → 純文字 RAG）**
- **做法**：用文件解析工具把 PDF 轉成 Markdown 文字與表格，再照第 25 課切塊建向量索引。
- **優點**：成本最低、搜尋最快、純文字文件效果極佳。
- **痛點**：遇到折線圖、流程圖、沒有格線的財務報表，抽取結果容易支離破碎，圖中趨勢完全丟失。

**架構二：VLM 離線轉述（圖片摘要進索引，回答時看原圖）**
- **做法**：建索引時，先用 VLM 把每張圖表／複雜頁面生成一段「**詳細的結構化文字描述**」（包含圖表標題、座標軸、關鍵數值與結論），連同頁碼一起存進向量資料庫；使用者提問時，用文字描述找到最相關的 2～3 頁，再把那幾頁的**原始圖片**交給 VLM 精讀回答！
- **優點**：兼顧檢索速度與最終看圖精準度，是目前**企業落地性價比最高**的方案。
- **痛點**：建索引階段要花一筆一次性 VLM 轉述費，且摘要漏寫的細節可能檢索不到。

**架構三：原生視覺檢索（如 ColPali 頁面影像嵌入）**
- **做法**：徹底跳過 OCR 和排版解析！直接把 PDF 每一頁當作一張圖片，用多模態視覺嵌入模型算出「頁面級向量」存進向量庫；提問時直接用文字問題去比對哪一頁的畫面最相關，撈出 Top-3 頁面原圖送給 VLM 回答。
- **優點**：完全不怕複雜排版、印章、手寫字、流程圖，管線極簡。
- **痛點**：向量儲存空間較大（常為多向量表示），對超精確的單一料號／關鍵字比對不如 BM25 混合檢索（第 24 課），實務上常與關鍵字檢索搭配使用。

@section 語音模型（Spoken LM）：串接管線 vs. 端到端原生語音
除了「看」，「聽與說」是多模態的另一大支柱（李宏毅老師 2025 導論也特別獨立介紹了語音語言模型）。

目前打造語音 AI（例如 AI 電話客服、即時口譯、英語口說教練）有兩種截然不同的架構：

**模式一：三段式串接（Cascaded Pipeline：ASR → LLM → TTS）**
```
[使用者的聲音] ──▶ ① ASR (語音轉文字) ──▶ 純文字
                                             │
                                             ▼
                                        ② LLM (文字思考回答)
                                             │
                                             ▼
[AI 的聲音]    ◀── ③ TTS (文字轉語音) ◀── 純文字
```
- **延遲加總**：假設 ASR 0.5 秒 + LLM 首字 0.8 秒 + TTS 0.4 秒，再加上說話停頓偵測（VAD）0.6 秒，總延遲常落在 **2.0～3.0 秒**，聽起來會有點「慢半拍」。
- **資訊流失**：ASR 把聲音轉成純文字的那一刻，**語氣、嘆氣、反諷、笑聲、背景音全不見了**！你嘆口氣說「太棒了喔……」，純文字看起來像稱讚，LLM 就誤解了你的情緒。
- **優點**：每個模組可獨立替換、容易做文字紀錄稽核、容易接現有的文字 RAG 與安全護欄（第 19 課）。

**模式二：原生端到端語音模型（Native Speech-to-Speech / Spoken LM）**
```
[使用者的聲音] ──▶ 音訊編碼 ──▶ 統一多模態模型（直接聽音訊、直接生成音訊） ──▶ [AI 的聲音]
```
- **極低延遲**：跳過兩次文字中轉，回應延遲可壓到 **300～500 毫秒**，甚至支援「**隨時打斷**」（Barge-in），像跟真人講電話一樣自然。
- **保留副語言資訊**：模型直接「聽到」你的焦急、猶豫或咳嗽，也能用安慰、興奮或放慢語速的語調回應。
- **挑戰**：語音安全審查較難（不能只靠文字關鍵字過濾）、成本通常比純文字高，且複雜業務仍需要「邊說邊同步輸出文字紀錄與工具呼叫」。

**架構師選型口訣**：
- 需要**嚴格合規稽核、複雜知識庫查詢、低成本**（如企業語音紀錄摘要、標準查詢）→ 用 **ASR + LLM + TTS 串接**（搭配串流 TTS 也能把體感延遲壓到 1 秒內）。
- 需要**高度擬真互動、情緒感知、即時插話**（如語言家教、陪伴、高階語音助理）→ 用 **原生端到端語音模型**。

@section 多模態的專屬陷阱：視覺幻覺與「藏在圖裡的提示注入」
以為給 AI 看原圖就不會胡說八道？多模態有自己獨特的坑：

**陷阱一：看圖說故事（視覺語言先驗蓋過畫面事實）。**
語言模型背過太多常識。如果你給它看一張「有 6 根手指的手」或「改過數字的著名標誌」，模型的**語言先驗**常常太強，會忽略畫面細節、直接回答「5 根手指」！
- **對策**：要求模型先「**逐項描述畫面中實際看到的元素與座標／位置**」，再下結論；關鍵數值（如發票統編、醫療劑量）仍要加程式格式校驗或雙重 OCR 比對。

**陷阱二：細小文字與密集表格看錯行（對齊偏移）。**
當一張表格有 20 欄、字體很小，VLM 很容易把「第 7 列的金額」錯看成「第 8 列」。
- **對策**：確保圖片解析度足夠，必要時把大表切塊辨識，並用程式碼驗證「各明細加總是否等於總計」（確定性驗算，第 39 課！）。

**陷阱三：圖片裡藏著間接提示注入（Visual Prompt Injection）。**
第 28 課提過文字裡的間接注入，在多模態時代，攻擊者可以把惡意指令用**淡灰色微字、浮水印、或背景海報**印在圖片裡！人眼掃過去根本沒注意，VLM 卻讀得一清二楚，還可能照著呼叫工具。
- **對策**：完全沿用第 28 課的鐵律——**任何外部上傳的圖片、PDF、音訊，一律視為第 3 層不可信資料**；讀圖的 AI 不得直接擁有未經人工確認的高風險寫入工具！

@section 實戰案例推演：打造一套「差旅收據＋簡報圖表」多模態助理
把前面學到的零件組裝起來，看看一間中小企業怎麼做出穩定又省錢的多模態系統，而不是傻傻把整份檔案丟進最貴的模型：

**情境**：員工拍照上傳 10 張餐費與交通收據，加上一份 30 頁的專案結案 PDF 簡報（裡面有 12 頁折線圖與成本表格），希望系統自動核對「報銷總額是否符合簡報裡的預算上限」。

**錯誤做法（新手常見踩雷）：**
把 10 張 4K 原圖＋30 頁簡報高解析圖片**全部塞進一次 API 請求**，讓單一 VLM 一次算完並直接呼叫財務系統撥款。結果單次請求吃掉 60,000 Token、等了 25 秒、表格看錯兩行、而且如果某張收據旁邊被貼了惡意提示文字，系統甚至可能直接把款項匯錯！

**架構師的分層拆解設計：**
1. **前處理縮放與路由**：先把收據圖片裁切去黑邊、長邊壓到適合辨識文字的 1024px（省下 60% 視覺 Token）；30 頁簡報走「架構二」，只在入庫時用 VLM 替每頁圖表寫結構化索引。
2. **結構化擷取（逐張處理）**：每張收據獨立呼叫輕量 VLM，強制輸出嚴格 JSON（日期、統編、品項明細、小計、總額），並要求附註「是否模糊或反光（`needs_human_review`）」。
3. **確定性程式驗算（不讓 AI 做加減法！）**：用 Python 程式碼把 10 張收據的明細全部加總，確認每張收據的「品項加總 == 總額」、總報銷額與簡報預算頁（檢索出的 Top-2 頁原圖精讀）交叉比對。
4. **風險分級與人工覆核**：凡是畫面模糊、加總不合、金額超過門檻或偵測到異常文字指令的單據，一律標紅交給財務人員在畫面上對照原圖核對，絕不讓 AI 自動放款。

這套流程完美結合了 VLM 的「看懂能力」與傳統程式的「算準、守規矩」，成本降低 75% 以上，準確率反而從 82% 拉升到 99%！

@section 動動腦：算一算
**題一**：一張 $1024 \times 1024$ 的圖片，若某視覺編碼器以 $16 \times 16$ 像素為一個小方格（Patch），會切成幾個視覺 Token？
→ 寬 $\frac{1024}{16} = 64$ 格，高 $\frac{1024}{16} = 64$ 格，共 $64 \times 64 = 4{,}096$ 個 Patch（實務上許多 VLM 還會再用合併層把相鄰 $2 \times 2$ 格壓成 1 格，變成 $1{,}024$ 個視覺 Token 以節省計算量）。

**題二**：某公司有 500 份各 20 頁的產品型錄（共 10,000 頁），充滿規格表與爆炸圖。如果每次客戶提問都把相關產品的整份 20 頁高解析圖（每頁 1,200 Token）直接送進 VLM，單次輸入幾 Token？怎麼改比較省？
→ $20 \times 1{,}200 = 24{,}000$ Token/次。改用「架構二（VLM 離線頁級描述建索引 + 檢索 Top-3 頁原圖送 VLM）」，單次只需 $3 \times 1{,}200 = 3{,}600$ Token，省下 **85%** 輸入成本且更少雜訊！

**題三**：客服語音系統收到一通客訴電話，客戶冷笑著說「你們出貨真是準時到讓我感動呢」，為什麼傳統 ASR → LLM 常常判斷失誤？
→ 因為 ASR 轉成純文字後失去了「冷笑」和「反諷語調」，只剩字面上的「準時、感動」，LLM 容易誤判成正面評價；改用原生語音模型或在 ASR 旁加入語音情緒辨識可改善。

@section 常見問題 Q&A
**Q1：有了 VLM 之後，傳統 OCR（光學字元辨識）是不是已經被淘汰了？**
還沒！在「超高吞吐量、超低成本、格式極度固定」的純文字掃描場景（例如每分鐘掃 10,000 張標準表格），傳統輕量 OCR 還是便宜且快上幾十倍。但遇到**版面千奇百怪、需要結合圖表語意理解、手寫與印章交錯**的文件，VLM 明顯勝出。實務上常把兩者混合使用：OCR 先抽純文字做關鍵字索引，複雜頁面交給 VLM 精讀。

**Q2：影片（Video）理解又是怎麼做的？**
影片本質上就是「一連串圖片（每秒抽 1～2 幀畫面）＋音軌」。因為幀數一多 Token 會瞬間爆掉，系統通常會先做**關鍵幀取樣**（畫面有明顯變化才抽幀）加上視覺 Token 壓縮，再結合字幕或音軌一起輸入多模態模型。

@section 本課重點整理
- **統一成 Token**：圖片靠 Patchify（切小方格）變視覺 Token、聲音靠聲譜圖或 Audio Codec 變音訊 Token，才能和文字一起進入 Transformer。
- **VLM 三件套**：視覺編碼器（眼睛）＋對齊投影器（翻譯官）＋語言模型主幹（大腦）；新一代正走向端到端原生多模態。
- **解析度決定帳單**：高解析度圖片會觸發動態切塊，可能消耗上千 Token；分類用低解析、讀小字用高解析且只送命中頁。
- **多模態 RAG 三架構**：純文字抽取（便宜但失圖表）、VLM 離線描述＋檢索原圖（企業落地高 CP 值）、原生頁面視覺檢索（如 ColPali，免排版解析）。
- **語音兩架構**：ASR→LLM→TTS 串接易稽核、便宜但失語氣且延遲高；原生端到端 Spoken LM 延遲低、懂語氣且可打斷。
- **安全與驗收**：防範語言先驗蓋過畫面、數值對齊用程式交叉驗算，並把外部圖片／音訊同樣視為可能藏有提示注入的不可信輸入。

@term 多模態
單一 AI 模型能同時處理並關聯文字、影像、音訊、影片等兩種以上資料型態的能力（Multimodal）。
@term 視覺語言模型
能同時輸入圖片與文字並進行視覺理解、讀表與問答的模型（VLM，Vision-Language Model）。
@term 視覺 Transformer
把圖片切成固定大小的小方格（Patch）並當作 Token 序列輸入 Transformer 處理的架構（ViT）。
@term 動態切塊
VLM 面對高解析度圖片時，將原圖裁成多張固定尺寸小塊並附一張全域縮圖輸入的機制，以看清小字但會增加 Token 數。
@term 多模態 RAG
針對含圖表、複雜表格與掃描影像的知識庫，結合視覺檢索或 VLM 轉述與原圖精讀的檢索增強生成架構。
@term 語音語言模型
能直接理解語音輸入（含語氣與副語言）並直接生成語音回應的多模態模型（Spoken LM）。
@term ASR
自動語音辨識：把人類語音轉換成文字的技術（Automatic Speech Recognition）。
@term TTS
文字轉語音：把文字合成為自然人聲輸出的技術（Text-to-Speech）。
@term 視覺提示注入
把惡意文字指令藏在圖片、浮水印或掃描文件裡，誘騙 VLM 執行未授權行為的間接攻擊手法。
