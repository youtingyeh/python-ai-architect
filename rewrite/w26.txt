@section 開場：API 是團隊之間的合約
當系統由前端工程師、後端工程師、手機 App 團隊，甚至好幾個 AI 程式助手**分工合作**時，**API** 就是把所有人連接在一起的骨幹。

如果沒有先設計好一致的規則，讓每個人邊寫邊隨意命名，很快就會出現這種混亂：
- 有的路由叫 `POST /getCourses`，有的叫 `GET /course_list`；
- 刪除學生竟然用 `GET /deleteStudent?id=5`；
- 有的成功時回傳 `{"data": [...]}`，有的回傳 `{"result": "ok"}`；
- 發生錯誤時，有的回傳 HTTP 200 加上 `{"status": "fail"}`（第 49 課的反模式）。

前端工程師每串一個 API，都要先問「這個怎麼用？錯誤長什麼樣子？」

**AI 時代，API 更重要。**你的 API 不只給前端呼叫，也常常是 **AI 代理的工具**（第 26、33 課）。規則一致、描述清楚的 API，AI 才能正確使用。

這一課要學「**契約先行**」（Contract-First）的 API 設計：在寫程式之前，先定義清楚：
1. **資源命名**和 HTTP 方法的語意；
2. **冪等性**：重試不會造成重複扣款；
3. **樂觀鎖**：兩人同時修改時不會互相覆蓋；
4. **分頁**：列表不能一次撈出全部；
5. **統一的錯誤格式**。

**比喻：**蓋房子時，水電師傅和裝潢師傅可以**同時**施工，因為他們都照著同一份藍圖：插座在哪、水管在哪，事先都講好了。API 契約就是軟體團隊的藍圖，讓前端、後端、AI 代理能**平行開發**，不必互相等待、互相猜測。

@section 原則一：URL 是名詞，HTTP 方法是動詞
第 49、50 課學過 REST 的基本觀念，這裡整理成設計原則。

**URL 代表「資源」（名詞），而且有層級：**
```
/api/v1/courses                         所有課程
/api/v1/courses/101                     101 號課程
/api/v1/courses/101/assignments         101 號課程的所有作業
/api/v1/courses/101/assignments/9       101 號課程的 9 號作業
```
讀起來像資料夾路徑，一看就懂資源之間的關係。

**動作由 HTTP 方法表達（動詞）：**
- `GET`：讀取；
- `POST`：建立，或觸發一個動作；
- `PUT` / `PATCH`：整個替換 / 部分修改；
- `DELETE`：刪除。

所以是 `DELETE /students/5`，而不是 `GET /deleteStudent?id=5`。

**為什麼不能用 GET 做修改？**這不只是風格問題，而是**會出事**：
- 瀏覽器為了加速，可能會**預先載入**頁面上的連結；
- 搜尋引擎的爬蟲會**自動點擊**所有 GET 連結；
- 網路中間的代理伺服器，在逾時時可能**自動重試** GET。

HTTP 的約定是「**GET 是安全的、不會改變任何東西**」，所有這些工具都依賴這個約定。如果你用 GET 刪除資料，某天爬蟲掃過你的管理頁面，資料就被刪光了。

**URL 中的 `v1`：版本號。**
API 一旦發布，就有人在用。如果要做**不相容**的修改（例如改欄位名稱），不能直接改掉，否則所有現有的呼叫者都會壞掉。做法是推出 `v2`，讓舊版本並存一段時間，給大家時間遷移。

@section 原則二：冪等性——重試一百次，結果都一樣
**冪等**（Idempotent）的意思是：**同一個操作執行一次和執行很多次，系統最終的狀態都一樣。**
- `GET /courses/101`：讀幾次都一樣，什麼都沒改變 → 冪等；
- `PUT /courses/101`（把標題設成「Python 入門」）：設一次和設十次，結果都是「Python 入門」 → 冪等；
- `DELETE /courses/101`：刪一次之後就沒了，再刪也還是沒了 → 冪等；
- `POST /submissions`（繳交作業）：送一次建立一筆，送兩次就**建立兩筆** → **不冪等**！

**為什麼這很重要？因為網路會讓人重試。**
用戶端送出請求後，沒收到回應。它不知道是：
- 請求根本沒送到伺服器？
- 還是伺服器處理完了，只是**回應**在路上丟了？

最安全的做法是重試（第 22 課的重試機制）。但如果是「繳交作業並扣一點 AI 額度」這種**不冪等**的操作，重試就可能**重複扣款、重複建立**。

**解法：冪等鍵（Idempotency Key）。**
1. 用戶端在發送請求時，產生一個**唯一的編號**（例如 UUID），放在標頭 `Idempotency-Key` 裡；
2. 重試時，**使用同一個編號**；
3. 後端收到請求時，先查「這個編號處理過了嗎？」
   - 沒處理過：正常執行，並**記下**「這個編號的結果是什麼」；
   - 處理過了：**不再執行**，直接回傳上次記下的結果。

**比喻：**寄掛號信。每封信都有一個掛號號碼。郵局如果收到兩封號碼相同的信，就知道是同一封寄了兩次，只會投遞一次。

**走一遍：捷運上的繳交。**
學生在捷運上用手機按下「送出期末作業並申請 AI 語法檢查」。手機產生了 `Idempotency-Key: idem-550e8400`。

1. 後端收到請求，建立了 `submission_id: 701`，扣除 1 點 AI 額度，記下「idem-550e8400 → 201，submission 701」；
2. 正要把 `201 Created` 傳回手機時，捷運進了隧道，**斷訊**；
3. 手機沒收到回應，三秒後**用同一個冪等鍵**自動重送；
4. 後端查到 `idem-550e8400` 已經處理過，**不再扣點、不再新增**，直接回傳剛才記下的 `201` 和 `submission_id: 701`。

學生畫面順利顯示「繳交成功」，額度**只扣了 1 點**。

冪等鍵通常會和使用者綁在一起記錄（`user_id` + `idempotency_key`），並設定保存期限（例如 24 小時）。第 66 課提到的「學生連點兩下送出」，也能用同樣的機制處理；第 72 課的佇列重試，同樣需要冪等的設計。

@section 原則三：樂觀鎖——防止兩人互相覆蓋
**情境：**兩位助教同時打開同一份作業批改。
1. 助教 A 讀取作業，評語是空的；
2. 助教 B 也讀取同一份作業；
3. 助教 A 寫好評語「論證清楚」，存檔；
4. 助教 B 寫好評語「需補充例子」，存檔。

結果：**助教 A 的評語被無聲地蓋掉了**，而且沒有人知道。這就是第 54 課的「**遺失更新**」。

**解法：樂觀鎖（Optimistic Locking）。**
1. 每筆資料有一個**版本號**，例如 `version: 3`；
2. 讀取時，API 回傳目前的版本號；
3. 更新時，用戶端必須帶上「我讀到的是第 3 版」；
4. 後端更新時檢查：
```
UPDATE submissions
SET feedback = '需補充例子', version = version + 1
WHERE id = 701 AND version = 3;
```
5. 如果有人已經先改過（版本變成 4 了），這句 SQL 影響 0 筆資料，API 回傳 **`409 Conflict`**（衝突），告訴助教 B：「這份作業在你打開之後已經被別人修改過，請重新載入。」

**為什麼叫「樂觀」？**因為它**假設衝突很少發生**，所以平常不鎖住資料，只在存檔的那一刻檢查。相對的，第 54 課的 `SELECT ... FOR UPDATE` 是「**悲觀鎖**」：一開始就鎖住，別人只能等。

**比喻：**共用文件的「版本衝突」提示。你打開文件時是第 3 版，存檔時系統發現已經有人存成第 4 版，就會提醒你「有人在你之後修改過，請先合併」，而不是直接把對方的修改蓋掉。這和第 48 課 Git 的合併衝突是同一個道理。

HTTP 也有標準的做法：用 `ETag` 回應標頭代表版本，更新時用 `If-Match` 標頭帶回來，不符合時回傳 `412 Precondition Failed`。

@section 原則四：分頁——列表一定要有上限
**任何回傳列表的 API，都絕對不能一次撈出整張表。**

想像 `GET /submissions` 沒有分頁，資料表有 50 萬筆。一個請求就讓後端把 50 萬筆全部載入記憶體、轉成好幾百 MB 的 JSON。幾個請求同時進來，伺服器的記憶體就爆了（OOM，Out of Memory），整台當機。

更糟的是，攻擊者知道這件事後，只要**一直發這個請求**就能讓你的服務癱瘓。

**規則：**
- 預設每頁筆數，例如 20；
- **強制上限**，例如最多 100。用戶端傳 `?limit=999999999`，後端也只回傳 100 筆。

**兩種分頁方式：**

**一、Offset 分頁：「跳過前 N 筆，取 M 筆」**
```
GET /submissions?limit=20&offset=40
```
對應 SQL：`LIMIT 20 OFFSET 40`。

優點：簡單，可以直接跳到第 50 頁。
缺點：
- **越後面越慢**：`OFFSET 500000` 時，資料庫仍要先數過前 50 萬筆再丟掉；
- **翻頁時可能重複或漏看**：你在看第 2 頁時，有人新增了一筆資料，所有資料往後擠一格，翻到第 3 頁時，第 2 頁最後一筆又出現了一次。

**二、游標分頁（Cursor）：「從某一筆之後，取 M 筆」**
```
GET /submissions?limit=20&after_id=1042
```
對應 SQL：
```
SELECT * FROM submissions
WHERE id > 1042
ORDER BY id
LIMIT 20;
```
利用索引（第 54 課）**直接跳到** 1042 的位置，不管翻到第幾頁，速度都一樣快。新增資料也不會讓翻頁錯位。

缺點：不能直接跳到「第 50 頁」，只能一頁一頁往下。

**比喻：**Offset 像讀書時說「從頭數 400 頁開始讀」，每次都要從第一頁數起；游標像在書裡夾了**書籤**，下次直接翻到書籤的位置繼續讀。

**選擇：**資料量大、會持續新增（例如動態消息、AI 對話紀錄、日誌）用游標分頁；資料量小、需要跳頁的管理後台可以用 Offset。

@section 原則五：統一的錯誤格式
不管是 400、401、403、404、409、422 還是 500，**全站所有 API 都回傳一模一樣的錯誤結構**：
```
{
  "error": {
    "code": "SUBMISSION_VERSION_CONFLICT",
    "message": "這份作業已被其他人修改，請重新載入後再試",
    "details": [],
    "request_id": "req-7c31b2"
  }
}
```
- `code`：**穩定的、機器可讀的**錯誤代碼。前端依此決定行為，不要依賴 `message` 的文字（文字可能會改、會翻譯）；
- `message`：給人看的說明；
- `details`：欄位層級的細節，例如第 51 課 422 錯誤中，哪個欄位錯了；
- `request_id`：對應第 62 課的追蹤碼。

**好處：前端只需要寫一套錯誤處理邏輯**，就能處理所有 API 的所有錯誤。

業界有一個標準格式叫「**Problem Details**」（RFC 9457），可以直接採用，不必自己發明。

**狀態碼要正確：**錯誤就回傳錯誤的狀態碼，不要用 200 包裝錯誤。否則監控系統（第 62 課）看到的錯誤率永遠是 0%，CDN 和快取甚至可能把錯誤回應當成正常頁面快取起來。

@section 契約先行：OpenAPI
這些規則要寫在哪裡？寫在一份機器可讀的 API 規格裡，最常用的格式是 **OpenAPI**。

第 50 課提過，FastAPI 會從程式碼**自動產生** OpenAPI 規格（`/docs` 頁面就是用它渲染的）。「契約先行」則是反過來：**先寫規格，經過前後端和相關人員審查同意後，再寫實作**。

有了這份契約：
- 前端可以用它產生假資料（Mock Server），**不必等後端寫完**就能開發；
- 前端可以自動產生 TypeScript 型別（第 58 課）；
- AI 代理可以讀取規格，知道有哪些工具、參數是什麼（第 26 課）；
- CI 可以自動檢查實作是否符合規格（第 65 課）。

這就是第 41 課規格驅動開發在 API 上的應用。

@section 延伸：REST 以外的選擇、限流與批次
**REST、GraphQL、gRPC 怎麼選？**
這一課講的是 REST 風格，它最常見，也最容易用瀏覽器和 curl 測試。但你可能會聽到另外兩種：
- **GraphQL**：只有一個端點，由前端在請求裡**描述自己要哪些欄位**，伺服器就只回傳那些欄位。好處是前端不會拿到太多或太少的資料；代價是伺服器端比較複雜，快取（第 71 課）也比較難做。適合前端畫面多變、資料關聯很複雜的產品；
- **gRPC**：用二進位格式傳輸，速度快、型別嚴格，常用在**後端服務彼此之間**的呼叫。瀏覽器不能直接用，所以很少給前端呼叫。

對一個學習平台這種規模的專案，REST 幾乎總是最好的起點。真的有特殊需求時，再寫一份 ADR（第 70 課）說明為什麼要換。

**限流：429 與 Retry-After**
有人（或有 bug 的程式）每秒送來上千個請求怎麼辦？API 應該設定「**限流**」（Rate Limiting）：例如每位使用者每分鐘最多 60 次請求。超過時回應：
```
HTTP/1.1 429 Too Many Requests
Retry-After: 30
```
意思是「請求太多了，30 秒後再試」。這對呼叫 LLM 的端點特別重要：每次呼叫都要花錢，限流同時保護了你的伺服器和你的帳單。寫**客戶端**時也要尊重這個規則：收到 429 就照 `Retry-After` 等待，不要立刻重試。

**批次操作：一次處理很多筆**
老師想一次幫 40 位學生打分數，前端如果送 40 個請求，又慢又浪費。可以設計一個批次端點：
```
POST /assignments/42/grades:batch
{
  "grades": [
    {"student_id": 1, "score": 88},
    {"student_id": 2, "score": 92}
  ]
}
```
設計時要先想清楚一件事：**其中一筆失敗時怎麼辦？** 是全部取消（用第 54 課的交易），還是成功的照常寫入、失敗的逐筆回報？兩種都合理，但一定要在 API 文件裡寫清楚，讓呼叫者知道該怎麼處理。

@section 動動腦：判斷看看
**題一**：`GET /deleteStudent?id=5` 有什麼問題？
→ 用 GET 改變狀態，瀏覽器預載、爬蟲、代理重試都可能誤觸刪除；應使用 `DELETE /students/5`。

**題二**：POST 繳交作業時網路逾時，用戶端重試，怎麼避免建立兩份作業？
→ 用冪等鍵：同一次操作的重試帶相同的 `Idempotency-Key`，後端發現已處理過就直接回傳先前的結果。

**題三**：兩位助教同時批改同一份作業，怎麼避免後存檔的人覆蓋前一位？
→ 樂觀鎖：更新時帶上讀取時的版本號，版本不符就回傳 409 衝突，請使用者重新載入。

**題四**：資料量很大、持續新增的列表，該用哪種分頁？
→ 游標分頁：利用索引直接定位，速度穩定，也不會因新增資料而重複或漏看。

@section 本課重點整理
- **契約先行**：先定義 API 規格（OpenAPI），讓前端、後端、AI 代理平行開發。
- **命名**：URL 是有層級的名詞資源，HTTP 方法是動詞；絕不用 GET 修改資料；用版本號處理不相容的變更。
- **冪等性**：GET、PUT、DELETE 天生冪等，POST 不是；用冪等鍵讓重試安全。
- **樂觀鎖**：版本號加條件更新，衝突時回傳 409，防止遺失更新。
- **分頁**：所有列表強制上限；Offset 簡單但深頁慢且可能錯位，游標分頁穩定快速。
- **統一錯誤格式**：穩定的錯誤代碼、人話訊息、細節、追蹤碼；狀態碼要正確，不用 200 包錯誤。

@term API 契約
事先約定的 API 路徑、輸入輸出格式與錯誤規則（API Contract）。
@term 契約先行
先撰寫並審查 API 規格，再進行實作的開發方式（Contract-First）。
@term 冪等
同一操作執行一次或多次，系統最終狀態相同的特性（Idempotent）。
@term 冪等鍵
用戶端為一次操作產生的唯一編號，讓伺服器辨識並略過重複請求（Idempotency Key）。
@term 樂觀鎖
不預先鎖定資料，在更新時以版本號檢查是否被他人修改（Optimistic Locking）。
@term 悲觀鎖
讀取時就鎖住資料，讓其他人等待的並行控制方式（Pessimistic Locking）。
@term 409 Conflict
請求與資源目前狀態衝突時回傳的狀態碼。
@term ETag
代表資源版本的 HTTP 回應標頭，可搭配 If-Match 做條件更新。
@term 分頁
將大量資料分成多頁回傳的機制（Pagination）。
@term Offset 分頁
以跳過筆數加取用筆數進行分頁，深頁效能差。
@term 游標分頁
以上一頁最後一筆的位置為起點繼續取資料的分頁方式（Cursor Pagination）。
@term Problem Details
標準化的 HTTP API 錯誤回應格式（RFC 9457）。
@term OpenAPI
描述 HTTP API 路徑、參數與回應格式的機器可讀規格標準。
@term API 版本
在不破壞現有呼叫者的前提下推出不相容變更的機制，如 /v1、/v2。
