@section 開場：網址背後發生了什麼事？
你每天都在用網址：打開網頁、用手機 App、呼叫 AI 服務。前面很多課提到的「呼叫 API」，例如第 22 課呼叫文字生成 API、第 26 課的函式呼叫，底層全都是透過一套叫做 **HTTP** 的網路規則在溝通。

如果把網址當成黑盒子，遇到錯誤時就會像無頭蒼蠅一樣亂改程式：
- 看到 `Connection refused`（連線被拒），明明是**伺服器根本沒啟動**，卻花兩小時去改 JSON 欄位；
- 明明是**權限不足**，伺服器卻回報「500 伺服器錯誤」，讓監控系統半夜狂發警報。

這一課要拆解「從輸入網址到收到回應」的整個過程。理解之後，遇到網路問題，你就能**一層一層**找出問題在哪裡。我們要學：
1. 一個請求要經過的四層：**DNS、TCP、TLS、HTTP**；
2. HTTP 訊息長什麼樣子：方法、標頭、主體；
3. 五個常用的 HTTP 方法，各代表什麼意思；
4. 狀態碼：200、404、500 這些數字在說什麼；
5. 用 `curl` 動手除錯；
6. 最常見的錯誤：用「200 成功」包裝所有錯誤。

@section 四層旅程：從網址到伺服器
當你輸入 `https://api.example.com/v1/students` 並按下 Enter，背後依序經過四層：

**第一層：DNS——查電話簿。**
電腦之間溝通靠的是 **IP 位址**（一串數字，例如 `93.184.216.34`），不是英文名字。所以第一步要把 `api.example.com` 這個「**網域名稱**」，轉換成 IP 位址。

負責這件事的系統叫 **DNS**（Domain Name System，網域名稱系統）。電腦會先看自己的快取，沒有的話再去問 DNS 伺服器。

**比喻：**DNS 就像手機的通訊錄。你只記得「媽媽」，手機幫你查出電話號碼再撥出去。

**第二層：TCP——建立連線。**
知道 IP 後，要和那台伺服器**建立一條可靠的連線**。最常用的是 **TCP** 協定，它會先「打招呼」確認雙方都準備好了，這個過程叫「**三向交握**」：
1. 用戶端：「你好，我想連線。」（SYN）
2. 伺服器：「好的，我準備好了，你呢？」（SYN-ACK）
3. 用戶端：「我也準備好了。」（ACK）

TCP 會確保資料**完整、依序**送達，掉了會重送。

每台伺服器上可能有很多服務，所以除了 IP，還需要一個「**連接埠**」（Port）號碼，指定要找哪個服務。例如網頁通常是 443（HTTPS）或 80（HTTP），本機開發時常用 8000。

**比喻：**IP 是大樓地址，Port 是樓層和房號。

（補充：最新的 HTTP/3 改用一種叫 QUIC 的協定，跑在 UDP 上，速度更快。所以「HTTP 一定走 TCP」已經不是絕對的。但觀念是一樣的：先建立傳輸通道。）

**第三層：TLS——加密和驗明正身。**
網址開頭是 `https://`（多了一個 s，代表 secure）時，連線建立後還要做 **TLS** 握手：
1. **驗證身分**：伺服器出示一張「**數位憑證**」，由公認的機構簽發，證明「我真的是 api.example.com」，而不是冒充的假網站；
2. **協商加密**：雙方商量出一把只有彼此知道的金鑰，之後所有傳輸的內容都加密。

這樣，就算中間有人攔截封包（例如在公共 Wi-Fi 上），也只看到一堆亂碼，看不到你的密碼或 API 金鑰。

**比喻：**像寄掛號信：先確認收件人身分證，再用只有雙方有鑰匙的保險箱寄送。

**第四層：HTTP——真正的對話。**
通道建好、也加密了，才開始真正的請求和回應。這就是下一節的主角。

**這四層的分層觀念，是網路除錯的關鍵。**每一層有不同的錯誤訊息：
- 找不到網域 → DNS 問題；
- 連線被拒或逾時 → TCP 層，伺服器沒啟動、Port 錯了、或被防火牆擋住；
- 憑證錯誤 → TLS 問題；
- 收到 4xx、5xx 狀態碼 → 已經到了 HTTP 層，前三層都沒問題。

@section HTTP 訊息長什麼樣子？
HTTP 是一問一答的格式：用戶端送出**請求**（Request），伺服器回傳**回應**（Response）。

**請求的結構：**
```
POST /students HTTP/1.1
Host: api.example.com
Content-Type: application/json
Authorization: Bearer abc123

{"name": "Alice"}
```
1. **請求行**：方法（`POST`）+ 路徑（`/students`）+ 版本；
2. **標頭**（Headers）：一行一個「名稱: 值」，是關於這個請求的**附加資訊**。例如：
   - `Content-Type: application/json`：主體是 JSON 格式；
   - `Authorization`：身分憑證（第 63 課）；
3. **一個空行**：分隔標頭和主體；
4. **主體**（Body）：真正要傳送的資料。

**回應的結構：**
```
HTTP/1.1 201 Created
Content-Type: application/json

{"id": 1, "name": "Alice"}
```
1. **狀態行**：版本 + **狀態碼**（`201`）+ 說明文字；
2. 標頭；
3. 空行；
4. 主體。

**比喻：**HTTP 訊息像一封信。請求行是「信件類型和收件部門」，標頭是「信封上的資訊」（寄件人、內容物類型、是否掛號），主體是「信的內容」。

@section 五個 HTTP 方法：動詞要用對
HTTP 方法就像句子的**動詞**，告訴伺服器「你想做什麼」：

**GET：讀取。**
例如 `GET /students/1`：查詢 1 號學生。
- **安全**（Safe）：不能改變伺服器上的任何資料；
- **冪等**（Idempotent，第 33 課）：做一次和做十次，結果一樣。

**POST：新增，或觸發一個動作。**
例如 `POST /students`：新增一位學生；或 `POST /chat`：請 AI 生成一段回答。
- **不冪等**：按兩次可能建立兩筆資料。這就是第 33 課與第 45 課「重複退款」問題的根源，需要冪等鍵保護。

**PUT：整筆替換。**
例如 `PUT /students/1`，附上完整的學生資料：用新的資料**完全取代**舊的。
- 冪等：送十次同樣的內容，結果都一樣。

**PATCH：部分修改。**
例如 `PATCH /students/1`，只附上 `{"name": "Alicia"}`：只改名字，其他欄位不動。

**DELETE：刪除。**
例如 `DELETE /students/1`。

**比喻：**PUT 像是把整份表格撕掉重填；PATCH 像是用修正液只改其中一格。

@section 狀態碼：伺服器的回覆摘要
狀態碼是三位數字，**第一個數字**代表大分類：

**2xx：成功。**
- `200 OK`：一般的成功；
- `201 Created`：新增成功（通常用在 POST）；
- `204 No Content`：成功，但沒有內容要回傳（常用在 DELETE）。

**3xx：請到別處。**
- `301`/`302`：網址搬家了，請改去新網址；
- `304 Not Modified`：你手上的快取還是最新的，不用重新下載（第 75 課）。

**4xx：用戶端（請求方）的問題。**
- `400 Bad Request`：請求格式錯誤，例如 JSON 寫壞了；
- `401 Unauthorized`：**不知道你是誰**。沒帶憑證，或憑證過期了。解法：重新登入；
- `403 Forbidden`：**知道你是誰，但你沒有權限**。重新登入也沒用；
- `404 Not Found`：找不到這個資源；
- `409 Conflict`：和目前狀態衝突，例如學號重複（第 49 課的 `DuplicateStudentError`）；
- `422 Unprocessable Entity`：格式正確，但內容不合規則，例如分數是 -10（第 55 課）；
- `429 Too Many Requests`：請求太頻繁，被限流了（第 22 課提過 AI 服務的限流）。

**5xx：伺服器端的問題。**
- `500 Internal Server Error`：伺服器的程式出了沒預料到的錯誤；
- `502`/`503`/`504`：伺服器背後依賴的其他服務沒回應、暫時無法使用或逾時（第 47 課的優雅降級就是處理這種情況）。

**一句話分辨：4xx 是「你的請求有問題」，5xx 是「我這邊出問題了」。**

**401 和 403 最容易搞混：**
- 401 像是門口警衛說：「請出示員工證。」
- 403 像是警衛看了你的員工證後說：「你是行銷部的，不能進財務室。」

@section 用 curl 動手除錯
`curl` 是一個在終端機發送 HTTP 請求的工具，是 API 除錯的好幫手。加上 `-i` 可以同時看到狀態行和標頭。

**場景一：連線被拒。**
```
curl -i -X POST http://127.0.0.1:8000/students \
  -H "Content-Type: application/json" \
  -d '{"name":"Alice"}'
```
（`127.0.0.1` 是「**這台電腦自己**」的特殊 IP，也叫 localhost。）

結果：
```
curl: (7) Failed to connect to 127.0.0.1 port 8000: Connection refused
```
分層判斷：**連 TCP 都沒建立起來**，根本還沒到 HTTP 和 JSON 的階段。原因幾乎一定是：本機的後端伺服器**忘了啟動**，或在別的 Port 上。改 JSON 一點用都沒有。

**場景二：成功。**
啟動伺服器（第 54 課會教）後再送一次：
```
HTTP/1.1 201 Created
Content-Type: application/json

{"id":1,"name":"Alice"}
```
四層全部通過，資料建立成功。

**場景三：權限不足。**
一位已登入的學生，嘗試 `DELETE /courses/101` 刪除老師的課程。伺服器確認他的身分有效，但角色不是老師或管理員，回傳：
```
HTTP/1.1 403 Forbidden
```
附上說明原因的 JSON。而**不是**回傳 200 或 500。

瀏覽器也有類似的工具：按 F12 打開「**開發人員工具**」，切到 **Network**（網路）分頁，就能看到網頁發出的每一個請求和回應的狀態碼、標頭、主體。

@section 最常見的錯誤：用 200 包裝一切
這是網站開發中惡名昭彰的錯誤做法：不管發生什麼事（查無資料、驗證失敗、資料庫斷線），HTTP 狀態碼**一律回傳 200 OK**，然後在主體裡寫：
```
{"success": false, "msg": "伺服器錯誤"}
```

**為什麼這很糟糕？**整個網路世界的自動化工具，都是看**狀態碼**判斷成功或失敗：
- 前端的 `fetch` 用 `response.ok` 判斷（第 61 課）；
- 負載平衡器（第 77 課）用它判斷伺服器是否健康；
- 監控系統（第 66 課）統計 5xx 的比例來發出警報；
- 第 22 課的重試邏輯，靠它判斷要不要重試（429、503 該重試；400、403 不該重試）。

全部回傳 200，這些工具都會以為一切正常。結果系統壞了三天，**沒有任何警報**。

**比喻：**像一個病人不管身體多不舒服，都跟醫生說「我很好」，只在小紙條上偷偷寫「其實很痛」。醫院的所有自動檢查系統都會判斷他健康。

**一個進階的安全考量：404 還是 403？**
使用者嘗試存取別人的私人專案 `/projects/9527`。照理應該回 403（你沒權限）。但這等於告訴對方「**9527 號專案確實存在**」。在需要隱藏資源是否存在的情況下（例如私人文件、醫療紀錄），有時會刻意統一回傳 404，讓攻擊者無法猜測哪些編號存在。

@section 常見疑問
**問：HTTP/1.1、HTTP/2、HTTP/3 有什麼不同？我需要在意嗎？**
答：它們傳的「內容」一樣：一樣的方法、網址、標頭、狀態碼、主體。不同的是「**怎麼在網路上搬運**」。
- **HTTP/1.1**：一條連線上，請求大致要一個接一個處理。網頁要載入 50 個小檔案時，前面一個慢了，後面的都得等；
- **HTTP/2**：一條連線上可以**同時**傳很多個請求，像一條多線道的公路；
- **HTTP/3**：改用一種叫 QUIC 的底層協定，在網路不穩（例如手機在移動中切換基地台）時表現更好。

對寫後端 API 的人來說，大多不用特別處理，瀏覽器和伺服器會自動協商使用哪一版。你寫的 FastAPI 程式完全一樣。

**問：為什麼有時候網址會自己跳到另一個網址？**
答：那是 **3xx 重新導向**。伺服器回應 `301 Moved Permanently`（永久搬家）或 `302 Found`（暫時去別處），並在 `Location` 標頭寫上新網址，瀏覽器就自動跳過去。最常見的例子：你輸入 `http://` 開頭的網址，伺服器把你導到 `https://` 的版本，確保連線是加密的。用 curl 測試時加上 `-L` 參數，curl 才會跟著重新導向走；不加的話，你只會看到那個 3xx 回應。

**問：一個請求的時間都花在哪裡？為什麼第一次比較慢？**
答：第一次連到一個網站時，要依序完成：DNS 查詢（問地址）、TCP 連線（三次握手）、TLS 握手（交換加密金鑰），**然後**才送出真正的 HTTP 請求。光是這些準備工作，跨國連線就可能花上幾百毫秒。之後的請求會快很多，因為：
- DNS 的結果被**快取**起來了；
- 連線被**保持開啟**（Keep-Alive）並重複使用，不必每次重新握手。

這就是為什麼第 56 課的資料庫連線、第 77 課的連線池，都強調「**重複使用連線**」：建立連線本身是很昂貴的。

**問：標頭的名稱有大小寫之分嗎？**
答：**沒有**。`Content-Type` 和 `content-type` 是同一個標頭。HTTP/2 甚至規定一律用小寫傳送。所以寫程式讀取標頭時，不要依賴大小寫；FastAPI 和大多數框架都已經幫你處理好了。

**問：請求的主體可以多大？**
答：HTTP 本身沒有規定上限，但每一層都可能有限制：反向代理（例如 Nginx 預設約 1MB）、應用框架、你自己的設定。上傳大檔案時常遇到的「413 Payload Too Large」就是撞到了這些限制。第 78 課會談到，**刻意設定上限**其實是一種保護：避免有人送來一個超大的請求塞爆伺服器。

@section 和 AI 一起做：除錯網路問題
網路問題最難的地方，是**不知道問題出在哪一層**：DNS、連線、TLS、HTTP，還是應用程式本身？AI 很適合陪你一層一層排查，但它需要真實的資料，而不是你的猜測。

**給 AI 真實的證據**
與其說「網站連不上」，不如貼上實際的輸出：
```
我用 curl -v https://api.example.com/health 得到以下輸出（完整貼上）：
...
預期應該回 200，實際卡住 30 秒後逾時。
請告訴我：問題大概出在哪一層（DNS / TCP / TLS / HTTP）？
接下來我應該執行什麼指令來確認？
```
`curl -v` 的輸出包含每一個階段的訊息，AI 可以從中判斷卡在哪一步。請它**建議下一步要收集什麼證據**，而不是直接猜答案，是除錯時最有效的合作方式。

**適合請 AI 做的事**
- 解釋一個陌生的狀態碼或標頭；
- 看一段請求和回應，指出哪裡不符合 HTTP 的語意（例如用 GET 修改資料）；
- 解釋瀏覽器開發者工具裡「Network」分頁的各個時間欄位。

**怎麼檢查**
- 貼上輸出之前，**先刪掉 Cookie、Authorization 標頭和金鑰**。這些是你的身分憑證，不應該出現在任何對話裡；
- AI 建議的修法，先在測試環境試，確認問題真的消失了。

**不要交給 AI 的事**
不要為了讓 AI 幫忙，就把正式環境的存取權限或憑證交出去。

@section 動動腦：判斷看看
**題一**：DNS、TCP、TLS、HTTP 各負責什麼？
→ DNS 把網域名稱查成 IP；TCP 建立可靠的連線；TLS 驗證伺服器身分並加密；HTTP 是真正的請求和回應。

**題二**：已登入的學生嘗試刪除老師的課程，應該回傳哪個狀態碼？
→ 403 Forbidden：已確認身分，但沒有權限。

**題三**：PUT 和 PATCH 有什麼不同？
→ PUT 用新的完整資料替換整筆資源；PATCH 只修改部分欄位。

**題四**：`curl` 回報 `Connection refused`，應該先檢查什麼？
→ 後端伺服器有沒有啟動、Port 是否正確。這是 TCP 層的問題，和 JSON 內容無關。

@section 本課重點整理
- **四層旅程**：DNS（查 IP）→ TCP（建立連線，搭配 Port）→ TLS（驗證身分、加密）→ HTTP（請求與回應）。除錯時一層一層檢查。
- **HTTP 訊息**：請求行或狀態行、標頭、空行、主體。`Content-Type` 宣告主體格式。
- **方法語意**：GET 讀取（安全、冪等）、POST 新增或觸發動作（不冪等）、PUT 整筆替換、PATCH 部分修改、DELETE 刪除。
- **狀態碼**：2xx 成功、3xx 轉址、4xx 用戶端問題、5xx 伺服器問題。401 是不知道你是誰，403 是知道但沒權限。
- **curl -i** 和瀏覽器開發人員工具的 Network 分頁，是 API 除錯的好幫手。
- **不要用 200 包裝錯誤**：會讓所有自動化工具和監控失效。

@term HTTP
網頁和 API 用來傳送請求與回應的通訊規則（HyperText Transfer Protocol）。
@term HTTPS
經過 TLS 加密與身分驗證的 HTTP。
@term IP 位址
網路上每台電腦的數字地址，例如 93.184.216.34。
@term DNS
把網域名稱轉換成 IP 位址的系統（Domain Name System）。
@term TCP
建立可靠連線、確保資料完整依序送達的傳輸協定。
@term 三向交握
TCP 建立連線前雙方互相確認的三個步驟（SYN、SYN-ACK、ACK）。
@term 連接埠
同一台電腦上區分不同服務的號碼，例如 443、8000（Port）。
@term TLS
驗證伺服器身分並加密傳輸內容的安全協定。
@term 數位憑證
由公認機構簽發、證明網站身分的電子文件（Certificate）。
@term localhost
代表「這台電腦自己」的名稱，IP 為 127.0.0.1。
@term 標頭
HTTP 訊息中描述附加資訊的欄位，例如 Content-Type（Headers）。
@term 主體
HTTP 訊息中真正要傳送的資料內容（Body）。
@term HTTP 方法
表示請求意圖的動詞，例如 GET、POST、PUT、PATCH、DELETE。
@term 狀態碼
伺服器回應中表示處理結果的三位數字，例如 200、404、500。
@term curl
在終端機發送 HTTP 請求的工具，常用於 API 除錯。
@term 開發人員工具
瀏覽器內建的除錯工具，按 F12 開啟，可查看網路請求（DevTools）。
