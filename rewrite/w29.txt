@section 開場：按下按鈕，等 25 秒
學生在網頁上按下「繳交作業」。如果後端在**同一個請求**裡依序做完這四件事：
1. 把作業寫進 PostgreSQL（0.01 秒）；
2. 呼叫外部 Email 服務，寄確認信給學生和老師（2 秒，偶爾逾時）；
3. 把 30 頁的 PDF 切塊，呼叫嵌入 API 建立索引（8 秒）；
4. 呼叫 LLM 產生 AI 初評報告（15 秒）。

學生按下按鈕後，要看著畫面轉圈**整整 25 秒**。

更糟的是：如果第 24 秒時，Email 服務剛好出了一點小問題，整個請求就失敗，回傳 500。學生根本不知道：**作業到底交成功了沒有？**要不要再交一次？再交會不會變成兩份？

**原則：**任何「**耗時超過幾百毫秒**」、「**依賴不穩定的外部服務**」（Email、LLM、第三方通知），或「**不需要立刻拿到結果**」的工作，都應該從使用者的請求中**拆出來**，放進「**工作佇列**」（Job Queue），交給獨立的「**背景工作程式**」（Background Worker）慢慢處理。

**比喻：**餐廳點餐。服務生不會站在你桌邊，等廚房把菜做完才離開。他把**點菜單交給廚房**，告訴你「點好了，餐點準備中」，就去服務下一桌。廚房按照點菜單的順序一張張做。點菜單就是**佇列**，廚師就是**背景工作程式**。

這一課要學：
1. 202 Accepted：「收到了，處理中」；
2. 為什麼記憶體裡的背景任務不可靠；
3. **交易發件箱**：確保「存了資料就一定會發出工作」；
4. **至少一次送達**與**冪等消費**；
5. **重試退避**與**死信佇列**。

@section 202 Accepted：誠實地說「處理中」
把耗時的工作放進佇列後，API 應該**立刻回應**，但要誠實：
```
HTTP/1.1 202 Accepted
{
  "submission_id": 88,
  "job_id": "job-88-notify",
  "status": "PENDING",
  "status_url": "/api/jobs/job-88-notify"
}
```
- **202 Accepted** 的意思是：「**請求已經收到並排入處理，但還沒完成。**」
- 附上一個 `job_id` 和查詢狀態的網址，讓前端可以查詢進度。

工作的狀態會依序變化：
```
PENDING（等待中）→ PROCESSING（處理中）→ SUCCEEDED（成功）或 FAILED（失敗）
```
前端可以每隔幾秒查詢一次狀態（稱為「**輪詢**」），或者由伺服器主動推播通知。這也是第 61 課「載入中」狀態的延伸。

**不要做的事：**工作還沒完成，就回傳 200 說「確認信已寄出」。那是在說謊，一旦寄信失敗，使用者會被誤導。

學生在 **0.02 秒內**就看到「作業已收件，確認信與 AI 分析處理中」，而不是等 25 秒。作業的保存（最重要的事）已經確實完成，其他的事慢慢來。

@section 記憶體裡的背景任務，一重啟就消失
FastAPI 有一個內建的 `BackgroundTasks` 功能，可以在回應送出後，在背景執行一個函式。看起來很方便，但它有一個致命的限制：

**它只存在於目前這個程式的記憶體裡。**

如果在任務執行完之前：
- 部署了新版本，容器被替換（第 67 課）；
- 記憶體不足，程式被系統強制關閉（第 51 課的 SIGKILL）；
- 伺服器當機或斷電；

記憶體裡**還沒做完的任務就永久消失了**，而且**沒有任何紀錄**可以追查。學生的確認信永遠不會寄出，AI 初評永遠不會產生，也沒有人知道。

**比喻：**服務生把點菜內容**記在腦子裡**，而不是寫在單子上。他一下班（重啟），那些還沒交給廚房的點菜就全部忘了。

**正式環境的重要工作，必須存在「持久化」的地方：**
- PostgreSQL 的一張 `jobs` 表；
- 或專門的訊息佇列系統，例如 Redis Streams、RabbitMQ、雲端的 SQS。

這樣即使程式重啟，工作仍然在那裡，等待被處理。

`BackgroundTasks` 適合的是「**丟了也無所謂**」的小事，例如更新一個不重要的統計數字。

@section 交易發件箱：存了資料，就一定會發出工作
即使用了持久化的佇列，還有一個隱藏的陷阱。

**看似合理的寫法：**
```
db.insert_submission(...)
db.commit()              # 第一步：作業存進資料庫
redis.push_job(...)      # 第二步：工作放進佇列
```
如果在第一步**成功**之後、第二步**執行之前**，程式剛好當機或網路斷了，會發生什麼事？

**作業已經交了，但工作永遠不會被放進佇列。**確認信不會寄、AI 初評不會產生。這是一個「幽靈狀態」：資料庫說作業存在，但所有後續處理都沒發生。

**反過來的順序也有問題：**
```
redis.push_job(...)      # 先放工作
db.commit()              # 再存作業
```
背景程式動作很快，拿到工作後立刻去資料庫查作業 88，但此時資料庫的交易**還沒提交**，查不到，工作失敗。或者更糟：交易最後失敗回滾了，作業根本不存在，但工作已經發出去了。

**問題的本質：**資料庫和佇列是**兩個不同的系統**，沒辦法放在同一個交易裡（第 58 課的原子性只在同一個資料庫內有效）。

**解法：交易發件箱（Transactional Outbox）。**
**把「要發出的工作」也存進同一個資料庫，在同一個交易中寫入。**
```
BEGIN;
INSERT INTO submissions (id, ...) VALUES (88, ...);
INSERT INTO outbox_jobs (job_id, type, payload, status)
VALUES ('job-88-notify', 'SEND_SUBMISSION_EMAIL',
        '{"submission_id": 88}', 'PENDING');
COMMIT;
```
因為是**同一個交易**，原子性保證：
- 要嘛作業和工作**都**存進去了；
- 要嘛**都**沒存進去。

不可能出現「作業存了，工作沒存」的幽靈狀態。之後，背景程式再從 `outbox_jobs` 表中取出待處理的工作來執行。

**比喻：**公司寄重要公文。不是「先在系統登記公文，再另外記得去郵局寄」（中間可能忘記），而是登記公文的**同時**，就在同一張表單上填好「待寄送」。收發室每天去看表單上所有「待寄送」的項目，一件件寄出。

**背景程式怎麼取工作？**
多個背景程式同時執行時，要避免兩個人搶到同一個工作。PostgreSQL 有一個好用的寫法：
```
SELECT * FROM outbox_jobs
WHERE status = 'PENDING' AND next_run_at <= now()
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;
```
- `FOR UPDATE`：鎖住這一筆（第 58 課）；
- `SKIP LOCKED`：**跳過**已經被別人鎖住的。所以每個背景程式都會拿到**不同的**工作，不會互相等待。

@section 至少一次送達：同一個工作可能被執行兩次
這是使用佇列時**最需要記住**的觀念。

背景程式取出一個工作，執行到一半（例如信已經寄出了），但在回報「完成」之前當機了。佇列看到這個工作**沒有被確認完成**，過一段時間後，就會**再把它派給另一個背景程式**。

結果：**同一封信被寄了兩次。**

幾乎所有佇列系統都是這樣設計的，叫做「**至少一次送達**」（At-Least-Once Delivery）：保證工作**一定會**被處理，但**可能**被處理不只一次。

為什麼不設計成「剛好一次」？因為在分散式系統中，要做到「剛好一次」極其困難：處理者當機的那一刻，系統無法確定它到底做完了沒有。與其冒著「工作遺失」的風險，不如選擇「寧可重複，不可遺漏」。

**所以，背景程式必須是「冪等」的。**（第 73 課學過冪等性。）

**做法：**
- 執行前先檢查：「這個工作做過了嗎？」例如檢查 `outbox_jobs` 中該工作的狀態，或檢查「作業 88 的確認信寄過了嗎」；
- 呼叫外部服務時，**帶上冪等鍵**。例如呼叫 Email 服務時帶上 `"email-sub-88"`，Email 服務商收到相同的鍵兩次，只會寄出一次。

**比喻：**收發室在寄出公文後，會在登記簿上**打勾**。如果有人又拿同一份公文來說「這要寄」，收發室先查登記簿，看到已經打勾，就知道寄過了，不會重複寄。

@section 重試：退避加抖動
外部服務失敗是常態：Email 服務商暫時忙碌（503）、LLM 逾時、網路瞬斷。背景程式要**重試**，但重試的方式很重要。

**錯誤的做法：失敗了立刻重試，不停重試。**
外部服務本來就已經過載了，你還用最快的速度一直打它。所有客戶端都這樣做的話，服務**永遠恢復不了**。

**正確的做法：指數退避（Exponential Backoff）加抖動（Jitter）。**
- 第 1 次失敗：等 2 秒；
- 第 2 次失敗：等 4 秒；
- 第 3 次失敗：等 8 秒；
- 第 4 次失敗：等 16 秒……

每次等待時間**加倍**，給外部服務喘息的空間。再加上一點**隨機時間**（第 75 課的抖動），避免所有失敗的工作在同一個時間點一起重試。這和第 22 課呼叫 LLM API 時的重試策略相同。

**比喻：**打電話給忙線中的客服。聰明的做法是等一下再打，如果還是忙線，就等久一點再打。而不是一掛斷就馬上重撥，連撥一百次。

**不是所有錯誤都該重試：**
- **暫時性錯誤**（503 服務忙碌、逾時、網路斷線）：重試**可能會成功**，應該重試；
- **永久性錯誤**（400 Email 格式錯誤、401 金鑰無效）：重試一萬次**也不會成功**，應該立刻標記為失敗，通知人來處理。

對永久性錯誤盲目重試，只會浪費資源，還可能因為短時間大量失敗請求，被外部服務封鎖。

@section 死信佇列：處理不了的工作，不能卡住整條線
有些工作**永遠不會成功**。例如資料格式損壞，背景程式每次處理都會出錯。這種工作被稱為「**毒藥訊息**」（Poison Message）。

如果讓它無限重試，它會一直占用背景程式的時間，甚至**卡住整個佇列**，後面正常的工作都排不到。

**解法：設定最大重試次數，超過就移到「死信佇列」（Dead-Letter Queue，DLQ）。**
- 例如重試 5 次仍然失敗，狀態改為 `DEAD_LETTER`；
- 記錄最後一次的錯誤原因；
- **發出告警**（第 66 課），讓工程師來看；
- 修好問題後，工程師可以**手動重新執行**（Replay）這些工作。

**比喻：**郵局的「**無法投遞郵件**」處理區。地址寫錯、查無此人的信，試著投遞幾次後，就移到專門的區域，由人工處理。而不是讓郵差每天背著這封信出門，永遠在找那個不存在的地址。

**死信佇列需要有人看。**如果它默默地累積了幾千筆工作卻沒人知道，那就和第 66 課的「吞掉錯誤」沒有兩樣。

@section 走一遍：繳交作業的完整流程
**第一階段：API（約 15 毫秒）**
在**同一個交易**中：
- 寫入 `submissions`（id = 88）；
- 寫入 `outbox_jobs`（`job-88-notify`，寄確認信）；
- 寫入 `outbox_jobs`（`job-88-ai-review`，AI 初評）。

提交成功後，立刻回傳 **202 Accepted** 和 job_id。學生在 0.02 秒內看到「作業已收件，處理中」。

**第二階段：背景程式處理寄信**
1. 用 `FOR UPDATE SKIP LOCKED` 取出 `job-88-notify`，狀態改為 `PROCESSING`；
2. 第一次呼叫 Email 服務時**逾時**；
3. 嘗試次數改為 1，設定 `next_run_at = 現在 + 4 秒`（指數退避），狀態改回 `PENDING`；
4. 4 秒後再次取出，帶著冪等鍵 `"email-sub-88"` 呼叫 Email 服務，**成功**；
5. 狀態改為 `SUCCEEDED`，記錄完成時間。

即使第一次逾時時，Email 服務其實已經收到請求並寄出了信，第二次呼叫時也會因為冪等鍵相同而**自動去重**。學生**只會收到一封**確認信。

**第三階段：AI 初評**
同樣的方式處理。如果 LLM 服務連續失敗 5 次，工作進入死信佇列並發出告警；同時依照第 70 課的降級需求，教師端顯示「AI 建議暫時無法產生」，教師可以直接手動批改，**不會被卡住**。

@section 常見陷阱
**陷阱一：先發佇列訊息、後提交交易。**
背景程式太快，去查資料時交易還沒提交，查不到而失敗。用交易發件箱，或確保交易提交後才發布訊息。

**陷阱二：對永久性錯誤盲目重試。**400、401 這類錯誤重試沒用，要立即失敗並通知。

**陷阱三：背景程式不是冪等的。**至少一次送達代表一定會遇到重複執行，重複寄信、重複扣款只是時間問題。

**陷阱四：沒有監控佇列。**
佇列長度持續增加，代表背景程式**處理不完**，工作越積越多。要監控：佇列中有多少等待的工作？最老的工作等了多久？死信佇列有多少筆？這些都是第 66 課指標和告警的重要項目。

**陷阱五：在工作內容中放太多資料。**
把整份 30 頁的 PDF 內容塞進佇列的工作裡。佇列會變得很大很慢。工作內容應該只放「**去哪裡找資料**」（例如 `submission_id: 88`），由背景程式自己去資料庫或物件儲存讀取。

@section 和 AI 一起做：AI 任務很適合放進佇列
LLM 呼叫是最適合放進佇列的工作之一：它很慢（數秒到數十秒）、可能失敗、而且花錢。本課學到的佇列設計，正是處理 AI 任務的標準做法。

**AI 任務的佇列設計要點**
- **重試要有上限**：LLM 服務暫時過載時重試是合理的，但無限重試會讓費用失控。設定最大重試次數，失敗的任務送進死信佇列（Dead Letter Queue）等待人工處理；
- **注意限流**：LLM 服務商通常有每分鐘請求數的限制。背景工作程式開太多，反而會一直收到 429 錯誤。工作程式的數量要配合服務商的額度；
- **記錄每次呼叫的成本**：在任務結果裡記下使用的 token 數量，才能監控費用；
- **讓使用者知道進度**：作文送出後，畫面顯示「AI 評語產生中」，完成後再通知，而不是讓使用者盯著轉圈圈。

**AI Agent 本身就是一連串的任務**
更複雜的 AI 應用，會讓 Agent 執行多個步驟：查資料、寫草稿、自我檢查、修改。每個步驟都可能失敗。把每一步設計成獨立的佇列任務，並記錄中間結果，Agent 失敗時就能從中斷的地方繼續，而不必從頭重來。這和第 39 課 Agent Harness 的想法一致：AI 負責思考，外部的系統負責記錄、驗證和復原。

**請 AI 審查你的工作程式**
```
請檢查這個背景工作程式：
如果 LLM 呼叫成功了，但寫入資料庫之前程式當掉，重新執行時會發生什麼事？
會不會重複扣費？會不會產生兩份評語？
```

@section 動動腦：判斷看看
**題一**：耗時的 AI 分析排入佇列後，API 應該回傳什麼狀態碼？
→ 202 Accepted，並附上 job_id 和狀態查詢方式；不應回傳表示已完成的 200。

**題二**：先 `db.commit()` 再 `redis.push()`，有什麼風險？
→ 提交後、推送前若當機，資料已存但工作永遠不會產生；應使用交易發件箱，在同一交易中寫入資料與待辦工作。

**題三**：為什麼背景程式必須設計成冪等？
→ 佇列通常保證至少一次送達，同一工作可能被執行多次；不冪等就會重複寄信或扣款。

**題四**：某個工作因為資料損壞每次都失敗，該怎麼處理？
→ 設定最大重試次數，超過後移入死信佇列、記錄錯誤並告警，修正後再手動重新執行。

@section 本課重點整理
- **耗時、依賴外部服務、不需立即結果**的工作，從請求中拆出，放進佇列由背景程式處理。
- **202 Accepted**：誠實表示「已收到、處理中」，附上 job_id 與狀態查詢。
- **記憶體中的背景任務**在重啟時會遺失；重要工作要存在持久化的佇列。
- **交易發件箱**：資料與待辦工作在同一交易中寫入，避免幽靈狀態。
- **SKIP LOCKED**：多個背景程式各取不同工作，不互相等待。
- **至少一次送達**：工作可能重複執行，背景程式必須冪等，呼叫外部服務帶冪等鍵。
- **重試**：指數退避加抖動；永久性錯誤不重試。
- **死信佇列**：超過重試上限的工作移出主線、告警、修正後重新執行。
- **監控**佇列長度、最老工作的等待時間、死信數量。

@term 工作佇列
存放待處理工作、由背景程式依序取出執行的機制（Job Queue）。
@term 背景工作程式
在使用者請求之外，獨立處理佇列中工作的程式（Background Worker）。
@term 202 Accepted
表示請求已受理、正在處理但尚未完成的狀態碼。
@term 輪詢
用戶端定期查詢工作狀態的方式（Polling）。
@term 持久化
資料存在不會因程式重啟而消失的地方（Persistence）。
@term 交易發件箱
在同一資料庫交易中寫入業務資料與待發出工作，確保兩者一致（Transactional Outbox）。
@term SKIP LOCKED
查詢時跳過已被其他交易鎖住的資料列，讓多個工作程式並行取件。
@term 至少一次送達
保證工作一定會被處理，但可能被處理不只一次（At-Least-Once Delivery）。
@term 冪等消費
同一工作被處理多次也只產生一次效果的設計（Idempotent Consumer）。
@term 指數退避
每次重試的等待時間依倍數增加（Exponential Backoff）。
@term 暫時性錯誤
重試後可能成功的錯誤，如逾時、服務忙碌（Transient Error）。
@term 毒藥訊息
因資料問題而每次處理都會失敗的工作（Poison Message）。
@term 死信佇列
存放超過重試上限仍失敗之工作的地方，等待人工處理（Dead-Letter Queue）。
