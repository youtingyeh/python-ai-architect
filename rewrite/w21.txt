@section 開場：五秒鐘被盜刷的金鑰
我們的程式需要連接很多外部資源，每一個都需要「鑰匙」：
- 資料庫的帳號密碼；
- 登入系統的簽章密鑰（第 59 課）；
- LLM 的 API 金鑰（第 16 課）；
- 雲端儲存的存取憑證。

新手最常犯、也最致命的錯誤，是為了方便直接寫在程式碼裡：
```
api_key = "sk-proj-xxxxxxxx"
db_url = "postgresql://admin:secret123@prod-db.example.com/app"
```
然後 `git add .`、`git push`，推上 GitHub。

網路上有無數自動化程式**全天候**掃描 GitHub 的公開提交，專門尋找這種金鑰。往往在推上去**短短幾秒到幾分鐘內**，外洩的 AI 金鑰就被拿去盜用，帳單暴增數千美元；或者正式資料庫被直接連進去，資料被洗劫一空。

**「十二要素應用」**（The Twelve-Factor App，一份廣為流傳的雲端應用設計原則）的第三條說：**設定要存放在環境中，和程式碼嚴格分離。**同一份程式碼，**一個字都不用改**，只要注入不同的環境變數，就能安全地在開發、預備、正式環境執行。

這一課要學：
1. 什麼是「設定」，什麼是「秘密」；
2. 啟動時就驗證設定：**快速失敗**；
3. `.env`、`.gitignore`、`.env.example` 的鐵三角；
4. 前端環境變數的真相；
5. 三種環境的隔離；
6. 金鑰外洩後的**正確處置順序**。

@section 設定和秘密：什麼該從程式碼裡拿出來
**設定**（Config）：在不同環境中**會不一樣**的值。
- 資料庫位址（開發用本機，正式用雲端）；
- 日誌等級（開發用 DEBUG，正式用 INFO）；
- 外部服務的網址。

**秘密**（Secret）：設定中**特別敏感**的那一部分。外洩就會造成損失。
- 密碼、API 金鑰、簽章密鑰、憑證。

兩者都不該寫死在程式碼裡，但秘密需要**更嚴格**的保護。

**怎麼判斷？**問自己：「如果這個專案**明天開源**，公開在網路上，會不會有問題？」會的話，它就不該在程式碼裡。

**怎麼傳進程式？環境變數。**
第 47 課學過環境變數：作業系統提供給程式的「外部設定」。
```
import os
DATABASE_URL = os.environ["DATABASE_URL"]
```
程式碼裡只寫「去拿 `DATABASE_URL`」，實際的值由執行環境提供。

**比喻：**程式碼像一台**通用的提款機**，設計圖可以公開；而秘密像每個人的**提款卡和密碼**，在使用的那一刻才插入，絕不會刻在機器上。

@section 快速失敗：啟動時就檢查設定
**錯誤的做法：用到時才發現少了。**
程式啟動時沒有檢查，等到半夜某個使用者觸發了寄信功能，才發現 `SMTP_PASSWORD` 沒設定，噴出錯誤。

**正確的做法：啟動的那一刻，一次檢查所有設定。**
用 Pydantic（第 51 課）的設定類別：
```
from pydantic import Field, SecretStr
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    database_url: str
    jwt_secret: SecretStr = Field(min_length=32)
    openai_api_key: SecretStr
    log_level: str = "INFO"

settings = Settings()   # 缺少或不合格就立刻報錯，拒絕啟動
```
- 沒有預設值的欄位就是**必填**；
- `jwt_secret` 至少 32 個字元。有人隨手填了 `"secret"`，程式**拒絕啟動**；
- `SecretStr`：印出來時會顯示 `**********`，避免不小心寫進日誌（第 62 課）。

這叫「**快速失敗**」（Fail Fast）：問題越早暴露，越容易修，影響越小。部署時發現設定錯誤，比半夜被使用者發現好太多了。

**比喻：**飛機起飛前的檢查清單。機長在跑道上逐項確認，任何一項不合格就**不起飛**。而不是飛到半空中才發現油沒加滿。

**危險的預設值：**
```
db_url = os.getenv("DB_URL", "postgresql://admin:pw@prod-db/app")
```
如果沒設定 `DB_URL`，就**預設連到正式資料庫**！某天有人在本機跑測試，忘了設定環境變數，測試就直接連上正式資料庫，可能把真實資料清空（第 61 課的陷阱一）。

**原則：秘密和關鍵設定不給預設值。沒設定就報錯，而不是猜一個。**

@section 鐵三角：.env、.gitignore、.env.example
在本機開發時，每次都手動設定一堆環境變數很麻煩。常見的做法是寫一個 `.env` 檔：
```
DATABASE_URL=postgresql://app:devpass@localhost:5432/app
OPENAI_API_KEY=sk-dev-xxxx
```
程式啟動時自動讀取（Pydantic 的 BaseSettings 就支援）。

**但 `.env` 裡有真正的秘密，絕對不能進版本控制。**所以需要三樣東西搭配：

**一、`.env`：真正的秘密，只存在自己的電腦。**

**二、`.gitignore` 裡加上 `.env`：**在建立專案的**第一天**就加。讓 Git 永遠忽略這個檔案（第 48 課）。

**三、`.env.example`：不含真實秘密的範本，要提交到版本庫。**
```
DATABASE_URL=postgresql://user:password@localhost:5432/app
OPENAI_API_KEY=sk-your-key-here
LOG_LEVEL=INFO
```
新同事 clone 專案後，複製一份改名成 `.env`，填入自己的值即可。這份範本同時也是**文件**：告訴大家這個專案需要哪些設定。

**一個重要的陷阱：`.gitignore` 只對「還沒被追蹤」的檔案有效。**
如果 `.env` **之前已經被 commit 過**，之後才加進 `.gitignore`，Git **仍然會繼續追蹤它**，而且舊的提交紀錄裡，秘密依然完整存在。要先用 `git rm --cached .env` 停止追蹤，而那些已經進入歷史的秘密，請參考下面的外洩處置流程。

@section 前端環境變數的真相
在 React、Vite、Next.js 等前端工具中，也有「環境變數」，例如 `VITE_API_KEY` 或 `NEXT_PUBLIC_...`。

**很多人以為放在環境變數裡就安全了，這是錯的。**

前端的環境變數會在**建置時被直接寫進** JavaScript 檔案中。這些檔案會被**完整下載**到每一位使用者的瀏覽器。任何人按 F12 打開開發者工具，搜尋一下就能找到。

**原則：任何會計費、有管理權限的金鑰，絕對不能放在前端，只能放在後端。**前端要用 LLM，就呼叫你自己的後端，由後端帶著金鑰去呼叫 LLM（第 16 課的代理架構）。第 57 課也強調過同一件事。

**比喻：**前端程式碼像寄到每個顧客家的**型錄**。你不會把金庫密碼印在型錄上，即使印在很小的字裡。

@section 三種環境：開發、預備、正式
**開發環境（Development）：你的電腦。**
- 用本機 Docker 的資料庫（第 63 課）；
- 用**測試用的** API 金鑰，並在服務商後台設定**很低的每月額度上限**（例如 5 美元）。就算電腦中毒、金鑰外洩，損失也有限。

**預備環境（Staging）：正式上線前的彩排。**
- 架構和正式環境**一模一樣**，用來演練資料庫結構變更、整合測試新版本；
- 使用**獨立的**資料庫和金鑰；
- 資料用**去識別化**或**合成**的測試資料。**嚴禁**直接把正式環境的真實客戶個資複製過來。

**正式環境（Production）：真正服務使用者的地方。**
- 秘密存放在雲端的「**秘密管理服務**」（Secret Manager，例如 AWS Secrets Manager、GCP Secret Manager、GitHub Actions 的 Encrypted Secrets）；
- 部署或容器啟動時才**動態注入**；
- 工程師日常**不直接經手**正式環境的明文金鑰；
- 定期**輪替**（換新）金鑰。

**為什麼每個環境要用不同的金鑰？**
- **追蹤**：分得清是誰在消耗額度；
- **隔離**：測試程式寫出無限迴圈，把 API 的速率限制打爆（HTTP 429），如果和正式環境共用同一把金鑰，**真實使用者也會同時全部斷線**；
- **爆炸半徑**：開發環境的金鑰外洩，不會波及正式資料。

**比喻：**一家餐廳有試菜廚房和正式廚房。試菜廚房可以實驗新菜色、可以失敗，但用的食材帳戶和正式廚房分開，試菜失敗不會把正式營業的食材用光。

@section 金鑰外洩了，怎麼辦？
一個真實會發生的情境：實習生在除錯時，把正式環境的 `OPENAI_API_KEY` 和 `DATABASE_URL` 寫進 `config.py`，推上了 GitHub。五分鐘後他發現了，趕緊把那兩行刪掉，改成讀環境變數，再推一個新的提交。他鬆了一口氣，以為沒事了。

兩小時後，公司收到帳單暴增的警報。

**為什麼？**Git 會保存**完整的歷史**（第 48 課）。任何人執行 `git log -p`，就能看到上一個提交裡被刪掉的那兩行。**刪除只是新增一個「刪除」的紀錄，舊的內容一直都在。**

**正確的處置順序：**

**第一分鐘：止血——撤銷金鑰。**
立刻登入 OpenAI 後台，**刪除**外洩的金鑰；修改資料庫密碼，切斷可疑的連線。這一步讓外洩的金鑰**立即失效**，不管有多少人已經拿到，都沒用了。

**第五分鐘：換新。**
產生新的金鑰，寫進秘密管理服務，重新啟動正式環境。

**第十五分鐘：調查與善後。**
- 調閱外洩期間的 API 和資料庫存取日誌，確認有沒有資料被竊取；
- 清理 Git 歷史（例如用 `git filter-repo` 工具）；
- 加上「**秘密掃描**」工具（例如 gitleaks），在每次提交前自動檢查，擋住含有金鑰樣式的程式碼。

**關鍵觀念：撤銷金鑰永遠是第一步，清理歷史是最後一步。**很多人第一個反應是「快把歷史刪掉」，但金鑰可能早就被爬蟲複製走了。清歷史救不回已經外洩的東西，**只有讓金鑰失效才能真正止血**。

**比喻：**家裡鑰匙掉了。第一件事是**換鎖**，而不是到處去找掉在哪裡。找到了也不知道有沒有被人複製過。

@section 常見陷阱
**陷阱一：以為後來加進 `.gitignore` 就安全了。**已經被追蹤過的檔案不受影響，歷史裡的秘密也還在。

**陷阱二：在錯誤訊息裡印出秘密。**
```
raise ValueError(f"金鑰格式錯誤：{api_key}")
```
這會把金鑰寫進錯誤監控平台和日誌。錯誤訊息只說「哪個設定有問題」，不要印出它的值。

**陷阱三：多個環境共用同一把金鑰或同一個資料庫。**無法追蹤、無法隔離，測試的意外會波及正式環境。

**陷阱四：把秘密寫進 Dockerfile 或容器映像檔。**第 63 課說過，`ENV API_KEY=...` 會永久留在映像檔的層裡。

**陷阱五：把秘密貼進聊天或 AI 工具。**為了除錯，把含有金鑰的設定檔整段貼給同事或 AI 助手，等於把秘密交給了第三方。貼之前先遮罩。

@section 常見疑問
**問：環境變數就一定安全嗎？**
答：比寫在程式碼裡好得多，但不是萬無一失。同一台機器上的其他程式、錯誤回報工具、`ps` 之類的指令，有時能看到環境變數；把整個環境印出來除錯（`print(os.environ)`）更是常見的外洩管道。所以正式環境的高敏感秘密，最好用秘密管理服務，並限制**誰能讀取**、記錄**誰讀取過**。環境變數是「把秘密和程式碼分開」的基本做法，不是保險箱本身。

**問：秘密管理服務比 .env 好在哪裡？**
答：至少有四點。第一，**集中管理**：秘密存在一個地方，不會散落在每位工程師的電腦裡。第二，**存取控制**：可以設定只有正式環境的服務能讀取正式金鑰，工程師本人不行。第三，**稽核紀錄**：誰、什麼時候讀取或修改過，都有紀錄。第四，**輪替方便**：換金鑰時只改一個地方，服務重新讀取就生效。

**問：金鑰多久要輪替一次？**
答：沒有統一答案，看風險而定。外洩或懷疑外洩時**立刻**輪替；有人離職、職務調整時，輪替他接觸過的金鑰；平常則定期輪替（例如每 90 天）。輪替要能**不停機**：先讓新舊兩把金鑰同時有效，所有服務換成新的之後，再撤銷舊的。如果輪替一次要全公司加班，代表流程需要自動化。

**問：AI 代理（第 33 課）要呼叫工具時，金鑰怎麼給？**
答：**不要把金鑰放進提示詞。**提示詞會被記錄、可能被提示注入（第 28 課）誘導模型洩漏出來。正確做法是：模型只決定「要呼叫哪個工具、帶什麼參數」，真正執行工具的是你的後端程式，由**後端**帶上金鑰去呼叫外部服務。模型從頭到尾都看不到金鑰。這也是第 26 課函式呼叫架構的安全優勢。

**問：測試時需要真的金鑰嗎？**
答：大多數不需要。單元測試和整合測試用 stub 取代外部服務（第 61 課），根本不必帶金鑰。少數需要真實呼叫的測試，在 CI 中用專門的測試金鑰，存在 CI 平台的加密秘密中，並設定低額度上限（第 65 課）。

@section 動動腦：判斷看看
**題一**：金鑰被推上 GitHub，馬上又推一個刪除它的提交，安全了嗎？
→ 不安全。舊提交仍在歷史中可被查看；第一步必須立刻撤銷並更換金鑰。

**題二**：`os.getenv("DB_URL", "正式資料庫連線字串")` 有什麼風險？
→ 沒設定時會默默連到正式資料庫，本機測試可能誤刪正式資料；關鍵設定不應給預設值，缺少就應報錯。

**題三**：把 OpenAI 金鑰放在前端的 `VITE_OPENAI_KEY`，安全嗎？
→ 不安全。前端環境變數會被打包進 JavaScript，任何使用者都看得到；金鑰只能放後端。

**題四**：開發、測試、正式環境共用同一把 LLM 金鑰，有什麼問題？
→ 無法區分用量；測試出錯打爆速率限制時，正式使用者也會受影響；外洩時影響範圍最大。

@section 本課重點整理
- **設定與程式碼分離**：同一份程式碼靠環境變數適應不同環境（十二要素應用）。
- **判斷標準**：專案明天開源會不會出事？會的話就不該寫在程式碼裡。
- **快速失敗**：啟動時用 Pydantic Settings 一次驗證所有設定；秘密用 `SecretStr`；關鍵設定不給預設值。
- **鐵三角**：`.env` 存秘密、`.gitignore` 第一天就排除它、`.env.example` 當範本與文件。
- **前端環境變數會被公開**：有權限的金鑰只能放後端。
- **三種環境**：開發、預備、正式各用獨立的金鑰與資料；正式環境用秘密管理服務注入。
- **外洩處置**：先撤銷與更換金鑰，再調查，最後清理歷史並加上秘密掃描。
