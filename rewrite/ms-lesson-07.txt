@section 開場：聊天機器人真的「記得」你說過的話嗎？
你跟 ChatGPT 聊了十幾句，在第 1 句說「我叫小明」，到了第 15 句問「我叫什麼名字？」，它答得出來。看起來它好像有記憶。

**真相可能讓你驚訝：AI 模型本身完全不記得任何事。**

每一次你送出訊息，對模型來說都是一次全新的、獨立的請求。它之所以「記得」你叫小明，是因為聊天程式在背後偷偷做了一件事：**每次都把之前所有的對話紀錄，連同你的新訊息，一起重新送給模型。**

**一個比喻：失憶的翻譯員。**
想像你請一位翻譯員，但他每次開口前都會完全失憶。為了讓他翻得通順，你每次都必須把之前所有的對話紀錄遞給他看，他快速讀完後，才能接著翻下一句。對話越長，他要讀的紀錄就越多，花的時間和你付的錢也越多。到了某個程度，紀錄厚到他一次讀不完了，怎麼辦？

這一課對應 Microsoft《Generative AI for Beginners》第 07 課「建立聊天應用」，要解決的就是這個問題：
1. 為什麼 AI 的 API 是「沒有記憶」的？
2. 對話越長，成本為什麼會暴增？
3. 最簡單的「只保留最近幾句」為什麼會出大事？
4. 怎麼設計才能又省錢、又不會忘記重要的事？
5. 多個使用者同時聊天時，怎麼避免把 A 的秘密說給 B 聽？
6. 怎麼讓使用者掌控 AI 記住了什麼？

@section API 是「無狀態」的
在軟體工程中，「**狀態**」（State）指的是系統記住的資訊。「**無狀態**」（Stateless）的意思是：每一次請求都是獨立的，系統不會記得之前發生過什麼。

大多數 AI 聊天 API 都是無狀態的。當你在聊天程式中送出第 5 句話時，背後實際送給模型的是這樣一個陣列：

```
messages = [
  {"role": "system",    "content": "你是友善的助理。"},
  {"role": "user",      "content": "我叫小明。"},          # 第 1 輪
  {"role": "assistant", "content": "你好，小明！"},
  {"role": "user",      "content": "推薦一本書。"},         # 第 2 輪
  {"role": "assistant", "content": "推薦《原子習慣》。"},
  ...                                                     # 第 3、4 輪
  {"role": "user",      "content": "我叫什麼名字？"}         # 第 5 輪（新訊息）
]
```

模型讀了整份紀錄，才能回答「你叫小明」。

**這帶來一個關鍵的觀念：**
> 對話紀錄存在你的資料庫裡，**不代表**模型這一次就看得到。

每一輪對話，你的後端程式都必須扮演「**上下文編排者**」：決定這一次要把哪些內容放進 messages 送給模型。系統指令要放、重要的事要放、最近的對話要放……但不能什麼都放，因為空間和預算都有限。

（附註：有些新的 API 提供「由伺服器幫你保存對話」的功能，例如 OpenAI 的 Assistants 或 Responses API。但原理一樣，只是幫你保存和組裝的工作交給了服務商，你仍需要理解背後的取捨。）

@section 對話越長，成本暴增
如果每一輪都把新的對話接在後面，**永遠不刪**，會發生什麼事？

**算一算。**假設：
- 系統提示詞：400 個 Token（每次都要送）
- 每一輪對話（使用者提問＋AI 回答）：平均 300 個 Token

第 k 輪時，要送出的輸入 Token 數是：
$$\text{輸入}(k) = 400 + (k-1) \times 300$$

- 第 1 輪：400
- 第 2 輪：700
- 第 5 輪：1,600
- 第 10 輪：3,100
- 第 20 輪：6,100

**20 輪對話下來，總共付費的輸入 Token：**
$$\sum_{k=1}^{20} [400 + (k-1) \times 300] = 20 \times 400 + 300 \times \frac{19 \times 20}{2} = 8{,}000 + 57{,}000 = 65{,}000$$

注意：每一輪對話本身只有 300 個 Token，20 輪才 6,000 個。但你實際付了 **65,000** 個 Token 的錢，超過 10 倍！因為前面的對話被一次又一次地重複送出。

**數學上，這叫做「二次方成長」**：對話輪數變成 2 倍，總成本變成約 4 倍；輪數變成 10 倍，成本變成約 100 倍。

**除了錢，還有三個問題：**
1. **撞到上限**：遲早會超過模型的上下文視窗（第 13 課），請求直接失敗。
2. **越來越慢**：輸入越長，首字延遲（第 18 課的 TTFT）越久。
3. **迷失在中間**：對話太長，模型可能被中間的閒聊干擾，忽略了一開始設定的重要規則（第 18 課的 Lost in the Middle）。

**所以，聊天應用一定要設定「上下文預算」**：例如每次請求最多 4,000 個 Token，超過就要想辦法精簡。

@section 最簡單的方法：只保留最近幾句，以及它的災難
控制長度最簡單的方法是「**滑動視窗**」（Sliding Window）：永遠保留系統提示詞，然後只取**最近**幾輪對話，更早的全部丟掉。就像一扇只能看到最近 5 公尺的窗戶，隨著你往前走，後面的景色就看不到了。

程式只要一行：
```
messages = [system_prompt] + history[-6:]    # 只取最後 6 則訊息
```

這種「先進來的先丟掉」的方式叫做 **FIFO**（First In, First Out，先進先出），像排隊一樣。

**簡單、有效、成本固定。但可能出大事。**

**一個真實可能發生的災難：**
一個智慧食譜助理。

- **第 1 輪**：使用者說：「我對**花生和堅果嚴重過敏**，也不吃牛肉，請幫我設計一週菜單。」
- **第 2 到 6 輪**：討論早餐燕麥怎麼煮、雞胸肉怎麼醃、烤箱幾度、採買清單……
- **第 7 輪**：使用者問：「今晚想吃泰式料理，有什麼推薦？」

因為滑動視窗只保留最近 5 輪，**第 1 輪的過敏資訊已經被丟掉了**。模型完全不知道使用者過敏，熱情推薦了一道撒滿花生碎的泰式炒河粉。

這不只是體驗不好，而是可能危害健康的嚴重錯誤。

**同樣的問題會發生在很多場景：**
- 旅遊規劃：一開始說「總預算 3 萬元」，聊久了就被忘記，推薦了 5 萬元的行程。
- 寫程式：一開始說「我們用 Python 3.9，不能用新語法」，後來寫出 3.12 才有的寫法。
- 客服：一開始確認了「客戶是企業方案」，後來卻用個人方案的規則回答。

**核心問題：「時間早」不等於「不重要」。**最早說的往往是最重要的前提條件。

@section 更好的設計：分四層組裝上下文
業界常用的做法，是把每次送給模型的內容分成**四層**，各自管理：

**第一層：系統指令（永遠保留）。**
定義 AI 的角色、規則、安全限制、輸出格式。這是固定的，永遠不刪。

**第二層：釘選的重要資訊（永遠保留）。**
當使用者在對話中說出**長期有效**的限制或偏好時，後端把它**擷取出來**，存成結構化的資料：
```
{
  "allergies": ["花生", "堅果"],
  "diet": ["不吃牛肉"],
  "budget_max": 30000
}
```
每次呼叫模型時，都把這份資料放在系統指令下方。就像在冰箱門上**釘一張便利貼**，不管聊多久，它都在那裡。這叫做「**釘選限制**」（Pinned Constraints）。

怎麼擷取？可以用另一個小型的 AI 呼叫（第 21 課的任務拆解），專門負責從每輪對話中找出「需要長期記住的事」。

**第三層：舊對話的摘要（滾動更新）。**
當較早的對話即將被滑出視窗時，**不是直接刪掉，而是先摘要**。把它濃縮成 150 到 300 字的重點，例如：「使用者正在規劃一週健康菜單，已確定早餐為燕麥、午餐為雞胸肉沙拉，採買清單已完成。」

隨著對話繼續，這份摘要會**持續更新**（把新滑出的內容併進去），所以叫做「**滾動摘要**」（Rolling Summary）。

**第四層：最近幾輪的原文（滑動視窗）。**
保留最近 3 到 5 輪的完整對話。這是為了讓模型能理解「剛才那個」、「把它改短一點」這類指代最近內容的說法。

**組裝順序：**
```
[系統指令] + [釘選資訊] + [舊對話摘要] + [最近 3~5 輪原文] + [新訊息]
```

**效果：**
- 不管聊多久，每次送出的 Token 數都**大致固定**，不會無限成長；
- 重要的限制**永遠不會被忘記**；
- 較早的對話脈絡以摘要形式保留；
- 最近的對話保持完整，對話銜接自然。

回到食譜的例子：第 7 輪時，「花生堅果過敏」在第二層的釘選資訊中，模型一定看得到，就不會推薦泰式炒河粉了。

@section 多人同時使用：絕對不能把 A 的對話給 B
寫教學範例時，很多人會這樣存對話紀錄：

```
chat_history = []    # 一個全域變數，存所有對話

def chat(message):
    chat_history.append(message)
    return call_ai(chat_history)
```

自己一個人測試，完全正常。但**放到伺服器上讓多人同時使用**，就會出大事：

使用者 Alice 剛輸入了她的薪資和財務狀況。下一秒，使用者 Bob 登入，問：「幫我總結剛才的內容。」伺服器把**同一個** chat_history（裡面有 Alice 的資料）送給模型，模型就把 Alice 的財務狀況總結給 Bob 看了。

這叫做「**跨使用者資料洩漏**」，是非常嚴重的隱私事故。

**三條鐵律：**

**① 對話紀錄必須按「誰的、哪一次對話」分開存。**
不能用一個共用的變數。要存在資料庫（或 Redis 這類快速的記憶體資料庫）裡，用三個欄位組合來區分：
- `tenant_id`：哪個客戶公司（如果你的產品賣給多家公司，每家叫一個「**租戶**」，Tenant）
- `user_id`：哪個使用者
- `session_id`：哪一段對話（一個使用者可以有很多段對話）

**② 不能相信前端說「我是誰」。**
前端送來的請求可能寫著「我是 user_id 123，請給我 session 456 的紀錄」。但前端的資料是可以被竄改的（第 16 課：前端什麼都藏不住）。

正確做法：從**已驗證的登入憑證**（例如登入時發的通行證）取得真正的使用者身分，然後檢查：「session 456 真的屬於這個使用者嗎？」不是的話就拒絕。

如果沒做這個檢查，攻擊者只要把網址中的 session 編號改一改，就能讀到別人的對話。這種漏洞叫做 **IDOR**（Insecure Direct Object Reference，不安全的直接物件參照），是網站最常見的安全漏洞之一。

**③ 快取和搜尋也要分開。**
如果系統有快取（暫存常用資料以加快速度）或後面課程會學到的向量搜尋，查詢時也一定要加上 user_id 的條件，確保只會找到這個使用者自己的資料。

@section 把控制權交給使用者
除了後端的設計，好的聊天產品還要讓使用者能**掌控** AI 記住了什麼。

**問題：上下文的慣性。**
模型很容易被前面的對話「帶著走」。如果對話一開始走偏了（例如 AI 誤解了你的需求，後面一直沿著錯誤的方向回答），或者你想換一個完全不同的話題（從討論 Python 換到寫季報），留在同一段對話裡，舊的內容會一直干擾新的回答，甚至讓 AI 硬把兩個不相關的話題扯在一起。

**解法一：明顯的「開新對話」按鈕。**
讓使用者隨時能開始一段乾淨的新對話。後端建立一個新的 session_id，舊的對話保留在歷史清單中，需要時還能查看。

**這也是給一般使用者的實用建議**：如果你發現 ChatGPT 或 Claude 一直鬼打牆、答非所問，**開一個新對話重新問**，往往比在原本的對話中一直糾正有效得多。

**解法二：透明的「記憶面板」。**
把系統目前釘選的重要資訊，直接顯示在畫面上，例如：

> 📌 已記住：花生堅果過敏、不吃牛肉、預算 500 元以內

並且讓使用者可以**點擊刪除或修改**。例如使用者後來說「我現在開始吃牛肉了」，但系統沒有正確更新，使用者可以自己把「不吃牛肉」刪掉。

這種「**把看不見的記憶變成看得見的**」設計，能消除很多「為什麼 AI 一直搞錯」的困惑。ChatGPT 和 Claude 的「記憶」功能，也都提供了讓使用者查看和刪除記憶內容的介面，就是這個道理。

@section 動動腦：算算看、想想看
**計算題**：系統提示詞 500 Token，每輪對話 200 Token。如果不做任何精簡，第 30 輪時這一次要送出多少 Token？30 輪總共付了多少輸入 Token？
- 第 30 輪：$500 + 29 \times 200 = 6{,}300$
- 總共：$30 \times 500 + 200 \times \frac{29 \times 30}{2} = 15{,}000 + 87{,}000 = 102{,}000$

如果改成四層設計，每次固定約 2,000 Token，30 輪總共約 $30 \times 2{,}000 = 60{,}000$，省了約四成，而且越聊省越多。

**情境題一**：旅遊規劃機器人，使用者第 1 輪說「總預算 3 萬」，第 15 輪時推薦了 5 萬的行程。可能原因和解法？
→ 滑動視窗把第 1 輪丟掉了。應該把「預算上限 3 萬」擷取為釘選資訊，每次都放進上下文。

**情境題二**：一個聊天網站，前端呼叫 `GET /chat/history?session_id=789` 取得對話紀錄，後端直接用 session_id 查資料庫回傳。有什麼漏洞？
→ IDOR 漏洞。任何人只要把 789 改成別的數字，就能讀到別人的對話。後端必須從登入憑證取得使用者身分，並確認 session 789 屬於這個使用者。

@section 常見問題
**Q：既然模型的上下文視窗已經有 100 萬 Token，還需要管理嗎？**
需要。視窗大只代表「塞得下」，不代表「便宜」、「快」或「讀得好」。每次送 100 萬 Token，費用和延遲都非常可觀，而且模型在超長內容中仍可能忽略中間的細節。好的上下文管理永遠有價值。

**Q：摘要會不會漏掉重要資訊？**
會，所以才需要釘選資訊這一層。摘要負責保留「脈絡」，釘選負責保證「關鍵限制」絕對不丟。兩者互補。

**Q：ChatGPT 的「記憶」功能是怎麼做的？**
原理和這一課的「釘選資訊」很像：系統會從對話中挑出值得長期記住的事（例如你的職業、偏好），存起來，之後的新對話中自動放進上下文。所以它能跨越不同的對話記住你。也因為如此，使用者能在設定中查看和刪除這些記憶。

@section 本課重點整理
- **AI API 是無狀態的**：模型本身不記得任何事。聊天程式每次都把歷史紀錄重新送出，模型才「記得」。
- **紀錄在資料庫 ≠ 模型看得到**：後端必須決定每次要放哪些內容進去。
- **成本二次方成長**：不精簡的話，對話輪數 10 倍，成本約 100 倍。還會撞上限、變慢、迷失在中間。
- **單純的滑動視窗很危險**：最早說的往往是最重要的限制（過敏、預算），會被丟掉。
- **四層設計**：系統指令 + 釘選重要資訊 + 舊對話滾動摘要 + 最近幾輪原文。成本固定，關鍵資訊不會遺失。
- **多人隔離**：不能用全域變數存對話。用租戶、使用者、對話編號分開存；從登入憑證確認身分，防止 IDOR。
- **使用者控制**：提供開新對話按鈕、顯示並允許編輯已記住的資訊。

@term 無狀態
每次請求都是獨立的，系統不記得之前發生過什麼（Stateless）。
@term 上下文編排
決定每次呼叫模型時，要放入哪些指令、記憶與對話內容的工作。
@term 二次方成長
數量變成 n 倍時，結果約變成 n² 倍的成長方式。
@term 滑動視窗
只保留最近一段內容、較舊的依序丟棄的做法（Sliding Window）。
@term FIFO
先進先出（First In, First Out）：最早進來的最先被移除，像排隊。
@term 釘選限制
從對話中擷取出長期有效的重要資訊，每次都固定放進上下文（Pinned Constraints）。
@term 滾動摘要
把即將被丟棄的舊對話濃縮成摘要，並隨對話進行持續更新（Rolling Summary）。
@term 租戶
多客戶系統中，每一個獨立的客戶（通常是一家公司）稱為一個租戶（Tenant）。
@term session
一段獨立的對話或工作階段，通常用一個編號（session_id）識別。
@term IDOR
不安全的直接物件參照：只要改網址或參數中的編號就能存取別人資料的漏洞。
@term Redis
一種把資料存在記憶體中的高速資料庫，常用於快取和工作階段資料。
@term 快取
把常用資料暫存在讀取更快的地方，以加速後續存取（Cache）。
