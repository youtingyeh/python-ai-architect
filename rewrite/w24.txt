@section 開場：一張什麼都有、卻什麼都看不懂的圖
回想你看過的系統架構圖。很多長這樣：一張圖裡同時畫了學生的小人圖示、React 前端、PostgreSQL、某個 Python 檔案裡的 `verify_password()` 函式、AWS 的負載平衡器，還有一堆箭頭，上面只寫著「資料」。

這種圖的問題是：**把不同層次的東西全部塞在一起**。
- 給老闆看：太瑣碎，看不出系統在做什麼；
- 給工程師看：又缺少關鍵資訊，看不出誰呼叫誰、用什麼協定、邊界在哪裡。

**C4 模型**（由 Simon Brown 提出）借用了「**地圖縮放**」的直覺，把架構圖分成四個層級，由遠到近：
1. **Level 1：系統脈絡圖**（System Context）：看整個城市；
2. **Level 2：容器圖**（Container）：走進一棟大樓，看有哪些樓層；
3. **Level 3：元件圖**（Component）：走進一層樓，看有哪些房間；
4. **Level 4：程式碼圖**（Code）：看房間裡的家具擺設。

**比喻：**用 Google 地圖。要知道台北在台灣的哪裡，你會縮小到全國；要找某家餐廳，你會放大到街道。**沒有人會用一張圖同時顯示整個台灣和每家餐廳的菜單。**每個縮放層級，只顯示那個層級該看的東西。

**好消息：大多數系統只需要畫好前兩層（C1 和 C2），**就能讓整個團隊對「系統邊界、技術分工、外部依賴」達成共識。這一課就專注在這兩層，並學：
1. C1：畫出系統邊界；
2. C2：每個方塊和箭頭要寫什麼；
3. C4 的「Container」和 Docker 容器的差別；
4. 什麼不該畫進去；
5. 為學習平台畫一套完整的 C1 和 C2。

@section 第一層：系統脈絡圖——你的系統在世界的哪裡
**系統脈絡圖**（System Context Diagram）是最「遠」的視角。它只回答三個問題：
- **我們要建構的系統是什麼？**畫在正中央，**只有一個大方塊**；
- **誰會使用它？**周圍畫出各種**人**（角色）；
- **它會和哪些外部系統互動？**周圍畫出**別人的系統**。

以學習平台為例：
```
     [學生]          [教師]
        \             /
         使用       使用
          \         /
     ┌─────────────────────┐
     │   Mini LMS 學習平台   │   ← 我們負責的系統
     └─────────────────────┘
          /          \
     呼叫 API      寄送通知
        /              \
[外部 LLM 服務]    [外部 Email 服務]
```

**這張圖最重要的價值：畫出「系統邊界」。**
邊界內是**我們團隊負責開發、維護、出事要負責**的東西；邊界外是**別人的系統**，我們只能使用、無法控制。

**為什麼邊界這麼重要？**
- **責任**：外部 LLM 服務掛了，不是我們能修的，但我們要設計「它掛了怎麼辦」（第 66 課的降級需求）；
- **安全**：資料**跨越邊界**的地方，就是需要特別防護的地方。第 75 課的威脅建模，就是從這些跨越邊界的箭頭開始分析的；
- **溝通**：這張圖連不懂技術的人都看得懂，適合放在專案文件的第一頁。

**比喻：**C1 像一張城市地圖，只標出「我們的工廠」在哪裡、原料從哪裡來、產品送到哪裡去。工廠內部怎麼運作，這張圖不管。

@section 第二層：容器圖——走進系統邊界
**容器圖**（Container Diagram）把 C1 正中央那個大方塊**放大**，看裡面由哪些部分組成。

**先釐清一個非常容易混淆的名詞：**
C4 模型的「**Container**」，意思是「**一個可以獨立部署、獨立執行的應用程式或資料儲存**」，例如：
- 瀏覽器裡的前端網頁應用；
- FastAPI 後端服務；
- 背景工作程式；
- PostgreSQL 資料庫；
- Redis 快取。

它**不等於** Docker 容器（第 63 課）！就算你的 FastAPI 和 PostgreSQL 直接跑在主機上、完全沒用 Docker，它們在 C4 的容器圖裡**仍然是兩個 Container**：一個是處理請求的應用程式，一個是保存資料的資料庫。

這個名字撞名很不幸，但記住：**C4 的 Container 是「邏輯上的執行單位」，Docker 容器是「一種部署技術」。**

**每個方塊必須寫三件事：**
1. **名稱**：例如「API 後端」；
2. **技術選型**：例如「Python / FastAPI」；
3. **一句話的職責**：例如「驗證身分與權限、處理課程資料、代理呼叫 LLM」。

**每條箭頭必須寫三件事：**
1. **方向**：誰**主動**呼叫誰；
2. **做什麼事**：例如「讀寫課程與權限資料」；
3. **協定或格式**：例如「HTTPS / JSON」、「TCP / SQL」。

**為什麼箭頭方向這麼重要？**
「A 呼叫 B」代表 **A 依賴 B**：B 掛了，A 就會出問題。箭頭方向告訴你**故障會怎麼傳播**，也告訴你**防火牆該開哪個方向的連線**。

只寫「傳資料」的雙向箭頭，等於什麼都沒說。

@section 走一遍：學習平台的 C2 容器圖
把學習平台的系統邊界放大，裡面有五個 Container：

**一、Web 前端（HTML / JavaScript，在瀏覽器執行）**
職責：提供課程瀏覽、作業繳交、AI 問答的介面（第 55～58 課）。

**二、API 後端（Python / FastAPI）**
職責：驗證身分（第 59 課）、檢查權限（第 60 課）、處理課程資料、組裝 RAG 上下文並呼叫外部 LLM（第 25 課）。

**三、背景工作程式（Python Worker）**
職責：處理耗時的工作，例如把上傳的講義切塊並產生嵌入向量（第 24 課）、寄送成績通知信（第 72 課會詳細介紹）。

**四、關聯式與向量資料庫（PostgreSQL + pgvector）**
職責：保存使用者、課程、作業等交易資料，以及講義的向量嵌入（第 52～54 課）。

**五、工作佇列與快取（Redis）**
職責：存放等待背景程式處理的工作，以及短期快取（第 71、72 課）。

**箭頭：**
```
學生 ──使用（HTTPS）──→ Web 前端
Web 前端 ──呼叫 REST API（HTTPS / JSON）──→ API 後端
API 後端 ──讀寫資料（TCP / SQL）──→ PostgreSQL
API 後端 ──放入工作（TCP）──→ Redis
背景工作程式 ──取出工作（TCP）──→ Redis
背景工作程式 ──讀寫資料（TCP / SQL）──→ PostgreSQL
API 後端 ──產生回答（HTTPS / JSON）──→ 外部 LLM 服務
背景工作程式 ──產生嵌入（HTTPS / JSON）──→ 外部 LLM 服務
背景工作程式 ──寄送通知（HTTPS）──→ 外部 Email 服務
```

**看這張圖，任何人都能一眼看出幾件重要的事：**
- 瀏覽器前端**絕對不會**直接連資料庫；
- 瀏覽器前端**絕對不會**直接呼叫外部 LLM。所有金鑰都收在後端（第 57、64 課）；
- 外部 LLM 服務掛了，受影響的是 API 後端和背景程式，所以這兩處都需要逾時、重試和降級的設計；
- 寄信是由背景程式處理，所以 Email 服務慢或掛了，**不會**拖慢使用者的操作。

**一張畫得好的 C2 圖，本身就在說明架構的關鍵決策。**

@section 不該畫進去的東西
保持每一層的「純粹」，是 C4 的精髓。

**不該出現在 C1、C2 的雜訊：**
- **函式和類別的名字**：例如 `verify_password()`。這是程式碼層級（C4 的 Level 4），而且程式一重構就過時了；
- **資料表的欄位細節**：那是 ER 圖的工作（第 53 課）；
- **部署細節**：例如「正式環境在某個雲端區域部署了 3 台主機，IP 是……」。這屬於另一種圖，叫「**部署圖**」（Deployment Diagram）。

**為什麼要分開？**
不同的圖**變化的頻率不同**，給**不同的讀者**看：
- C1：幾乎不變，給所有人看；
- C2：新增服務時才變，給工程師和架構師看；
- 部署圖：每次調整主機數量就變，給維運人員看；
- 程式碼：每天都在變，直接看程式碼就好。

把它們混在一張圖裡，這張圖就會**每天都過時**，最後沒人相信它、沒人維護它。

**比喻：**一本旅遊指南會分成「全國地圖」、「城市地圖」、「景點介紹」、「交通時刻表」。時刻表每個月都在變，你不會把它印在全國地圖上。

@section 第三層和第四層：需要時再畫
**C3：元件圖**（Component Diagram）把某一個 Container 再放大，看裡面的主要模組。例如 API 後端裡有「身分驗證模組」、「課程模組」、「RAG 模組」，以及它們之間的呼叫關係。

適合用在：某個 Container 特別複雜，或新同事需要了解它的內部結構時。

**C4：程式碼圖**（Code Diagram）是類別圖、函式關係等細節。通常**不需要手畫**，需要時用工具從程式碼自動產生即可。手畫的程式碼圖幾乎必然很快過時。

**原則：畫圖是為了溝通，不是為了畫圖而畫圖。**只畫能幫助團隊理解和決策的圖。

@section 常見陷阱
**陷阱一：把 C4 的 Container 當成 Docker 容器。**
如上所述，兩者無關。判斷標準是「它是不是一個可獨立部署和執行的單位」，而不是「它有沒有用 Docker」。

**陷阱二：箭頭沒有方向，或只寫「傳資料」。**
「A 同步呼叫 B」和「B 從佇列取出 A 放進去的工作」，在**故障如何傳播**、**防火牆規則**上完全不同：
- 同步呼叫：B 掛了，A 的請求會失敗或卡住；
- 透過佇列：B 掛了，工作會在佇列裡排隊等候，A 不受影響（第 72 課）。

箭頭必須標明**誰發起**和**用什麼協定**。

**陷阱三：邊界畫錯。**
- 把外部服務（例如 OpenAI、SendGrid）畫進自己的系統邊界內：彷彿它們是我們能控制的；
- 把自己維護的資料庫畫成外部系統：彷彿它出事不是我們的責任。

**系統邊界就是責任和控制權的邊界。**畫錯邊界，第 75 課做威脅建模時，就會漏掉「資料跨越信任邊界」的防護點。

**陷阱四：圖畫完就不管了。**
架構圖最常見的命運是：專案初期畫得很漂亮，半年後系統改了好幾次，圖卻沒人更新，最後**誤導**新同事。

解法：
- 只畫高層次、變化慢的圖（C1、C2）；
- 用「**圖即程式碼**」（Diagram as Code）的工具，例如 Mermaid 或 Structurizr，用文字描述架構、自動產生圖，並放進版本控制；
- 架構有重大變更時，**把更新架構圖列為完成條件之一**（呼應第 70 課的 ADR）。

@section 實作：用文字畫出 C1
「圖即程式碼」聽起來抽象，實際上很簡單。以 Mermaid 為例，下面這段文字就能產生學習平台的系統脈絡圖：
```
flowchart TB
    student["學生<br/>（人）"]
    teacher["教師<br/>（人）"]
    lms["Mini LMS 學習平台<br/>（我們的系統）"]
    llm["外部 LLM 服務<br/>（外部系統）"]
    mail["外部 Email 服務<br/>（外部系統）"]

    student -->|"瀏覽課程、繳交作業、AI 問答"| lms
    teacher -->|"開課、批改、發布成績"| lms
    lms -->|"產生回答與嵌入<br/>HTTPS / JSON"| llm
    lms -->|"寄送通知<br/>HTTPS"| mail
```
逐項說明：
- `flowchart TB`：由上（Top）往下（Bottom）排列的流程圖；
- 方括號裡是方塊的文字，`<br/>` 是換行；
- `-->|"..."|`：帶有說明文字的箭頭，箭頭方向就是呼叫方向。

很多文件平台（包括 GitHub）能直接把這段文字渲染成圖。它的好處是：
- **可以放進版本控制**：架構改了，修改紀錄一清二楚（第 48 課）；
- **可以在 PR 中審查**：新增一個服務時，順便改這段文字，審查者一起看；
- **不必找原始的繪圖檔**：不會發生「圖是某位已離職同事用某個軟體畫的，沒人能改」的狀況。

**一張好的 C1、C2 圖的自我檢查清單：**
- 每個方塊都有名稱、類型（人、我們的系統、外部系統），C2 還要有技術和職責；
- 每條箭頭都有方向、說明，C2 還要有協定；
- 有圖例或說明，讓第一次看的人知道顏色或形狀代表什麼；
- 一個不熟系統的人，看完能說出「資料從哪裡來、往哪裡去、哪些是我們負責的」。

**用 AI 協助畫圖：**你可以把需求描述（第 66 課）交給 AI，請它產生 Mermaid 草稿。但**邊界和箭頭方向要自己逐一確認**：AI 很容易把外部服務畫進邊界內，或把非同步的佇列畫成同步呼叫。架構圖是溝通的依據，錯了會誤導整個團隊。

@section AI 系統的 C4 圖要特別標註什麼
AI 應用有幾個特別值得在 C2 圖上看清楚的地方：
- **LLM 是外部系統還是自己部署的？**呼叫外部 API（例如 OpenAI）和自己部署開源模型（第 32、37 課），在成本、延遲、資料隱私上差異很大。自己部署的話，模型推論服務就是邊界內的一個 Container；
- **提示詞和使用者資料在哪裡跨出邊界？**每一條通往外部 LLM 的箭頭，都代表資料離開了你的控制範圍。哪些資料可以送出去？需要先去識別化嗎？
- **向量資料庫在哪裡？**它存的是由文件衍生的資料，同樣需要權限過濾（第 60 課的多租戶問題）；
- **哪些呼叫是同步、哪些走佇列？**LLM 呼叫很慢，放在使用者請求的同步路徑上，還是丟給背景程式，會大幅影響使用者體驗。

@section 動動腦：判斷看看
**題一**：FastAPI 直接跑在主機上、沒有用 Docker，它在 C4 容器圖裡還算一個 Container 嗎？
→ 算。C4 的 Container 指可獨立部署執行的單位，與是否使用 Docker 無關。

**題二**：C2 圖上的每條箭頭至少要標明哪些資訊？
→ 方向（誰主動呼叫誰）、做什麼事、使用的協定或資料格式。

**題三**：要在 C2 圖上標出「正式環境有 3 台主機與其 IP」，恰當嗎？
→ 不恰當。那屬於部署圖；C2 只描述邏輯上的執行單位與其通訊。

**題四**：把外部 LLM 服務畫進自己的系統邊界內，會有什麼問題？
→ 混淆責任與控制權，並可能在威脅建模時漏掉資料跨出信任邊界的防護。

@section 本課重點整理
- **C4 模型**：像地圖縮放，分為系統脈絡、容器、元件、程式碼四層；大多數系統畫好前兩層就夠。
- **C1 系統脈絡圖**：正中央一個方塊代表我們的系統，周圍是使用者與外部系統；核心價值是畫出系統邊界。
- **C2 容器圖**：系統內可獨立部署執行的單位；每個方塊寫名稱、技術、職責；每條箭頭寫方向、做什麼、協定。
- **C4 的 Container 不等於 Docker 容器。**
- **保持每層純粹**：函式名稱、資料表欄位、部署細節屬於其他圖。
- **陷阱**：混淆 Container、箭頭沒方向、邊界畫錯、圖畫完就不維護。
- **AI 系統**：標清楚 LLM 的位置、資料在哪裡跨出邊界、哪些呼叫同步或非同步。

@term C4 模型
以系統脈絡、容器、元件、程式碼四個縮放層級描述軟體架構的方法。
@term 系統脈絡圖
顯示目標系統、使用者與外部系統關係的最高層架構圖（System Context Diagram）。
@term 容器圖
顯示系統內部各可獨立部署執行單位及其通訊方式的架構圖（Container Diagram）。
@term C4 Container
可獨立部署與執行的應用程式或資料儲存，與 Docker 容器無關。
@term 系統邊界
區分自己負責維護的系統與外部系統的界線（System Boundary）。
@term 外部系統
不由本團隊開發維護、但與本系統互動的系統（External System）。
@term 元件圖
顯示單一容器內部主要模組與其關係的架構圖（Component Diagram）。
@term 部署圖
描述系統實際部署在哪些主機、網路與環境的圖（Deployment Diagram）。
@term 信任邊界
資料或控制權從一個信任範圍跨到另一個範圍的界線（Trust Boundary）。
@term 圖即程式碼
用文字描述架構並自動產生圖，以便版本控制與維護（Diagram as Code）。
@term Mermaid
用文字語法繪製流程圖、架構圖等的工具。
