@section 開場：從後端走到使用者面前
前面幾課，我們蓋好了後端：FastAPI 接收請求、Pydantic 驗證資料、PostgreSQL 保存資料。但使用者不會打開終端機用 curl 呼叫 API。他們需要一個**網頁**：輸入框、按鈕、表格。

接下來四課是前端基礎：
- 本課 **HTML**：網頁的**結構**（有哪些東西）；
- 第 60 課 **CSS**：網頁的**外觀**（長什麼樣子）；
- 第 61 課 **JavaScript**：網頁的**行為**（點了會怎樣）；
- 第 62 課 **TypeScript**：替 JavaScript 加上型別檢查。

**比喻：**蓋房子。HTML 是梁柱和隔間（哪裡是客廳、哪裡是門）；CSS 是油漆和裝潢；JavaScript 是水電和開關。

後端或 AI 工程師第一次寫網頁時，最常患上一種病，叫做「**div 狂熱症**」（Divitis）：整份網頁只用 `<div>` 和 `<span>` 兩種標籤。標題寫成 `<div class="big-text">`，按鈕寫成 `<div onclick="send()">`。

用滑鼠、眼睛正常的人看起來沒問題。但：
- 用鍵盤操作的人，按 Tab 鍵**跳不到**那個假按鈕；
- 視障者用的**螢幕閱讀器**不知道哪裡是標題、哪裡是按鈕；
- 自動化測試工具也看不懂頁面結構。

這一課要學「**語意化 HTML**」：用**正確意義的標籤**描述內容。好消息是，它幾乎不需要額外的工夫，就能免費得到瀏覽器內建的鍵盤操作、表單送出和無障礙支援。

@section HTML 是什麼：給內容貼上標籤
**HTML**（HyperText Markup Language，超文字標記語言）不是程式語言，而是**標記語言**：用「標籤」把內容包起來，告訴瀏覽器「這段是什麼」。
```
<h1>學生管理系統</h1>
<p>目前共有 3 位學生。</p>
<button>新增學生</button>
```
- `<h1>...</h1>`：這是**一級標題**；
- `<p>...</p>`：這是一個**段落**（paragraph）；
- `<button>...</button>`：這是一個**按鈕**。

大部分標籤成對出現：`<h1>` 開始，`</h1>` 結束。標籤還可以有「**屬性**」，提供額外資訊，例如 `<input type="number">` 的 `type` 屬性說明這是數字輸入框。

**比喻：**HTML 像給文件各部分貼上便利貼：「這是標題」、「這是清單」、「這是要填的欄位」。瀏覽器、搜尋引擎、螢幕閱讀器都會讀這些便利貼。

@section 兩棵樹：瀏覽器怎麼理解你的網頁
瀏覽器讀到 HTML 後，會在記憶體裡建出兩棵「樹」。

**一、DOM 樹**（Document Object Model，文件物件模型）：把所有標籤依照層層包含的關係組成一棵樹。CSS 用它決定外觀，JavaScript 用它找到元素、修改內容（第 61 課）。

**二、無障礙樹**（Accessibility Tree）：給**輔助科技**（例如螢幕閱讀器）看的簡化版本。每個節點記錄三件事：
- **角色**：這是按鈕？標題？輸入框？
- **名稱**：這個按鈕叫什麼？這個輸入框是填什麼的？
- **狀態**：是否被勾選？是否停用？

**語意化標籤決定了無障礙樹的內容。**用 `<button>`，無障礙樹就知道「這是按鈕」；用 `<div onclick>`，無障礙樹只看到「一段普通文字」。

**比喻：**螢幕閱讀器像一位幫視障者「唸網頁」的助理。如果網頁結構清楚，助理可以說：「這頁有一個主標題『學生管理系統』、一個表單有兩個欄位、一個表格有三欄。」如果全是 div，助理只能從頭到尾唸一堆沒有結構的文字。

**為什麼工程師要在乎？**除了「讓每個人都能用」這個理由本身就足夠重要之外，**自動化測試工具也是用無障礙樹找元素的**。例如測試程式寫「找到名稱是『新增學生』的按鈕，點下去」，這只在你用了真正的 `<button>` 時才找得到。

@section 頁面骨架：地標與標題階層
一個語意清楚的頁面骨架：
```
<!doctype html>
<html lang="zh-Hant">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>學生管理系統</title>
</head>
<body>
  <header>網站名稱、使用者選單</header>
  <nav>導覽連結</nav>
  <main>
    <h1>學生管理系統</h1>
    <section>
      <h2>新增學生</h2>
      ...
    </section>
    <section>
      <h2>學生清單</h2>
      ...
    </section>
  </main>
</body>
</html>
```
逐項說明：
- `<!doctype html>`：宣告這是現代 HTML 文件；
- `lang="zh-Hant"`：頁面語言是**繁體中文**。螢幕閱讀器會依此選擇正確的發音，瀏覽器也會選擇適合的字型；
- `<meta charset="utf-8">`：文字編碼用 UTF-8（第 13、46 課），避免中文變亂碼；
- `<meta name="viewport" ...>`：讓手機正確顯示寬度，而不是把桌面版網頁縮得很小；
- `<header>`、`<nav>`、`<main>`：頁面的「**地標**」（Landmarks）。螢幕閱讀器使用者可以直接跳到「主要內容」，不用每次都聽一遍導覽選單。`<main>` 一頁只能有一個。

**標題階層：照順序，不要跳號。**
`<h1>` 到 `<h6>` 代表標題的**層級**，不是字體大小。一頁通常一個 `<h1>`，底下是 `<h2>`，再底下是 `<h3>`。不要因為「`<h4>` 的字比較小比較好看」就從 `<h1>` 跳到 `<h4>`。字體大小交給 CSS 處理（第 60 課）。

**比喻：**標題階層像書的目錄：第一章、1.1 節、1.1.1 小節。你不會在第一章底下直接出現「1.1.1.1」。

@section 表單：前端和後端的資料契約
表單是使用者把資料傳給後端的入口。這一段是後端工程師**最該搞懂**的部分。
```
<form id="student-form">
  <label for="student-name">姓名</label>
  <input id="student-name" name="name" required maxlength="100">

  <label for="student-age">年齡</label>
  <input id="student-age" name="age" type="number"
         min="0" max="120" required>

  <button type="submit">新增學生</button>
  <p id="form-status" role="status" aria-live="polite"></p>
</form>
```

**`<label>`：每個輸入框都需要一個名字。**
`<label for="student-name">` 的 `for` 指向輸入框的 `id`，兩者就**綁定**在一起了。好處：
- 螢幕閱讀器聚焦到輸入框時，會唸出「姓名」；
- **點擊「姓名」兩個字，游標會自動跳進輸入框**。點擊範圍變大，對手機使用者特別友善。

**`id` 和 `name`：兩個常被搞混的屬性。**
- `id`：**頁面內**的唯一識別碼。給 `<label for>`、CSS、JavaScript 找元素用。同一頁不能有兩個相同的 `id`；
- `name`：表單**送出時**，這個欄位在資料中的「**鍵名**」。

`name="name"` 和 `name="age"` 送出後會變成 `{"name": "...", "age": "..."}`，**必須對上**後端 Pydantic 模型（第 55 課）的欄位名稱。

**這就是前後端的資料契約：**前端的 `name` 屬性、後端的 Schema 欄位，兩邊的名字必須一致。後端用了 `extra="forbid"`，前端拼錯一個字母就會收到 422。

**`role="status"` 和 `aria-live="polite"`：**
這一段先是空的，之後 JavaScript 會在裡面放「新增成功！」或錯誤訊息。這兩個屬性告訴螢幕閱讀器：「這裡的內容變化時，請（在使用者忙完手邊的事之後）唸出來。」否則視障使用者按了送出，根本不知道成功了沒有。

**ARIA** 是一組補充無障礙資訊的屬性。原則是：**能用原生標籤就用原生標籤，ARIA 是補充，不是替代。**

@section 按鈕：為什麼一定要用 button
**原生 `<button>` 免費送你的功能：**
- 自動排進鍵盤的 **Tab 順序**，按 Tab 就能聚焦到它；
- 按 **Enter** 或**空白鍵**就能觸發；
- 支援**停用**狀態（`disabled`），停用時不能點，畫面也會變灰；
- 放在 `<form>` 裡，使用者在任何輸入框打完字**直接按 Enter**，就會送出表單。

用 `<div onclick>` 假裝的按鈕，**以上全部都沒有**，你得自己用 JavaScript 一項一項補回來，而且很容易漏掉。

**一個常見地雷：表單裡的 `<button>` 預設就是送出按鈕。**
`<form>` 裡的 `<button>` 如果沒寫 `type`，預設是 `type="submit"`。所以表單裡如果有「清除」、「開啟說明」這類**不是送出**的按鈕，一定要寫 `type="button"`，否則一點就把表單送出去了。

@section 前端驗證 vs. 後端驗證
上面的輸入框有 `required`（必填）、`maxlength="100"`（最多 100 字）、`min="0" max="120"`（範圍）。按送出時，瀏覽器會自動檢查，不合規就跳出提示，**不送出請求**。

**它的價值是使用者體驗：**漏填欄位時立刻提示，不用等網路來回。

**但它絕對不能取代後端驗證。**任何人都可以：
- 按 F12 打開開發者工具，把 `required` 刪掉；
- 直接用 curl、Postman 或 Python 呼叫你的 API，**完全不經過網頁**。

第 55 課的鐵律在這裡再次出現：**後端必須假設每一個請求都可能是惡意的。**前端驗證是貼心的櫃台服務，後端驗證才是保全。

@section 表格：真正的資料才用 table
呈現學生清單這種「有欄有列」的資料，用 `<table>`：
```
<table>
  <caption>目前註冊學生清單</caption>
  <thead>
    <tr>
      <th scope="col">學號</th>
      <th scope="col">姓名</th>
      <th scope="col">年齡</th>
    </tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>Alice</td><td>18</td></tr>
    <tr><td>2</td><td>Bob</td><td>21</td></tr>
  </tbody>
</table>
```
- `<caption>`：表格的標題；
- `<thead>`、`<tbody>`：表頭和表身；
- `<th scope="col">`：宣告「這是**直欄**的標題」。螢幕閱讀器唸到「18」時，就知道要說「年齡：18」，而不是只唸一個孤零零的數字。

**兩個相反的錯誤：**
- 用 `<table>` 排版整個頁面（例如左邊選單、右邊內容）：這是 2000 年代的老做法，版面配置應該交給 CSS；
- 用一堆 `<div>` 假裝成表格：視覺上像表格，語意上卻什麼都不是。

**原則：HTML 負責「這是什麼」，CSS 負責「長什麼樣」。**

@section 驗收：把滑鼠拿開
寫完頁面後，做一個簡單但很有效的測試：**把滑鼠移開，只用鍵盤操作。**
1. 按 Tab：焦點應該依序停在「姓名輸入框」→「年齡輸入框」→「新增學生按鈕」；
2. 什麼都不填按 Enter：瀏覽器應該提示必填；
3. 年齡填 200 按 Enter：應該提示超出範圍；
4. 點擊「姓名」兩個字：游標應該跳進姓名輸入框。

任何一步失敗，通常就代表某個地方用了錯誤的標籤，或 `label` 沒綁好。

@section 常見錯誤
**錯誤一：只有 placeholder，沒有 label。**
`<input placeholder="請輸入姓名">` 的提示文字，在使用者**開始打字後就消失了**。填到一半忘了這格要填什麼？看不到了。螢幕閱讀器也無法穩定地把 placeholder 當成欄位名稱。

**錯誤二：label 和 input 沒綁定。**
「姓名」兩個字只是放在輸入框旁邊，但沒有 `for` 也沒有把輸入框包在 `<label>` 裡。視覺上看起來有關係，程式上卻毫無關聯。

**錯誤三：有 id 卻沒有 name。**
寫了 `id="name"` 卻忘了 `name="name"`。送出表單時，**沒有 `name` 的欄位會被瀏覽器直接忽略**，後端收到的資料是空的。這個錯誤很難發現，因為畫面上一切正常。

**錯誤四：重複的 id。**
同一頁兩個 `id="name"`，`<label for>` 和 JavaScript 都只會找到第一個。

@section 動動腦：判斷看看
**題一**：輸入框寫了 `id="student-name"` 但沒有 `name` 屬性，送出表單時會怎樣？
→ 這個欄位不會出現在送出的資料中，後端收不到姓名。

**題二**：表單裡有一個「清除」按鈕沒寫 `type`，點下去會發生什麼事？
→ 表單會被送出，因為表單內 `<button>` 預設是 `type="submit"`。應寫 `type="button"`。

**題三**：前端已經有 `required` 和 `max="120"`，後端還需要 Pydantic 驗證嗎？
→ 需要。前端驗證可被刪除或繞過，只能改善體驗，後端驗證才是安全邊界。

**題四**：為了讓標題字小一點，從 `<h1>` 直接跳到 `<h4>`，好嗎？
→ 不好。標題標籤代表層級，大小應由 CSS 控制。

@section 本課重點整理
- **前端三兄弟**：HTML 是結構、CSS 是外觀、JavaScript 是行為。
- **語意化 HTML**：用正確意義的標籤，免費得到鍵盤操作、表單送出與無障礙支援；避免 div 狂熱症。
- **兩棵樹**：DOM 樹給 CSS 與 JS 用；無障礙樹給螢幕閱讀器與測試工具用。
- **骨架**：`lang`、`charset`、`viewport`；`header`/`nav`/`main` 地標；標題不跳號。
- **表單契約**：`label for` 綁定 `id`；`name` 必須對上後端 Schema 欄位名。
- **按鈕**：用原生 `<button>`；表單內非送出按鈕要寫 `type="button"`。
- **前端驗證**改善體驗，**後端驗證**才是安全邊界。
- **表格**：真正的表格資料用 `<table>`、`<caption>`、`<th scope="col">`；排版交給 CSS。
- **驗收**：拿開滑鼠，只用鍵盤操作一遍。

@term HTML
用標籤描述網頁結構的標記語言（HyperText Markup Language）。
@term 語意化 HTML
使用符合內容意義的標籤（如 button、nav、table）撰寫網頁（Semantic HTML）。
@term div 狂熱症
整份網頁只用 div 和 span，失去語意結構的寫法（Divitis）。
@term DOM
瀏覽器把 HTML 解析成的樹狀結構，供 CSS 與 JavaScript 操作（Document Object Model）。
@term 無障礙樹
瀏覽器提供給輔助科技的結構，記錄元素的角色、名稱與狀態（Accessibility Tree）。
@term 螢幕閱讀器
把畫面內容唸出來、協助視障者使用電腦的輔助軟體（Screen Reader）。
@term 地標
header、nav、main 等標示頁面區塊的標籤，讓使用者快速跳轉（Landmarks）。
@term label
輸入框的名稱標籤，透過 for 屬性綁定輸入框的 id。
@term name 屬性
表單送出時，欄位在資料中的鍵名，須對應後端 Schema 欄位。
@term ARIA
補充無障礙資訊的一組 HTML 屬性，用來輔助而非取代原生標籤。
@term aria-live
讓內容變動時被螢幕閱讀器自動朗讀的屬性。
@term 無障礙
讓不同能力的使用者都能使用產品的設計原則（Accessibility，a11y）。
