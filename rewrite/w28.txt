@section 開場：同樣的問題，為什麼要算一千次？
想像兩個情境：
- 首頁的「熱門課程排行榜」，每秒被查詢 **500 次**。每次都要在 PostgreSQL 做一個複雜的統計查詢；
- 學生問 AI 助教的問題中，有一大堆是**一模一樣**的：「期中考範圍是什麼？」每次都要花 3 秒、付一次 LLM 的費用。

每次都老老實實地重新計算，資料庫的 CPU 很快衝到 100%，LLM 帳單也跟著爆表。

**快取**（Cache）的想法很直覺：**算過的結果先存起來，下次直接拿來用。**

**比喻：**你常用的資料，會放在書桌上，而不是每次都跑去地下室的檔案櫃翻找。書桌空間有限，只放最常用的；檔案櫃（資料庫）才是完整的正本。

快取用「**額外的空間**」和「**短暫的不一致**」，換取「**極快的讀取速度**」和「**大幅降低的後端負擔**」。

但電腦科學界有一句名言：
「**電腦科學只有兩件難事：快取失效，以及命名。**」

如果不經量測就盲目加上快取，或設計錯誤，後果可能是：
- 完全沒加速；
- 使用者修改了資料，畫面卻**一直顯示舊內容**；
- 最嚴重的：把**老師專屬的期中考解答**，快取起來**發給了學生**。

這一課要學：
1. 最常用的快取模式：**Cache-Aside**；
2. 什麼資料該快取、什麼不該；
3. **快取鍵**的設計與權限隔離；
4. 三種經典故障：**雪崩、擊穿、穿透**；
5. AI 應用中的快取。

@section Cache-Aside：先看書桌，沒有再去檔案櫃
**Cache-Aside**（旁路快取）是實務上最常用的模式。快取通常使用 **Redis**：一個把資料存在**記憶體**中的資料庫，讀取只要不到 1 毫秒。

**讀取流程：**
```
def get_course(course_id):
    key = f"course:v1:{course_id}:public"
    cached = redis.get(key)
    if cached is not None:              # 命中
        return json.loads(cached)
    course = db.query_course(course_id) # 未命中，查資料庫
    redis.set(key, json.dumps(course), ex=600)  # 存 10 分鐘
    return course
```
1. 先用一個「**鍵**」（key）去查快取；
2. **命中**（Cache Hit）：快取裡有，直接回傳。通常只要 1、2 毫秒；
3. **未命中**（Cache Miss）：快取裡沒有，就去查資料庫，把結果**存進快取**，再回傳；
4. 存的時候設定「**存活時間**」（TTL，Time To Live），例如 600 秒。時間到了，快取自動刪除。

**寫入流程：先改資料庫，再刪除快取。**
```
def update_course_title(course_id, title):
    db.update_course(course_id, title)
    redis.delete(f"course:v1:{course_id}:public")
```
老師修改了課程標題：
1. 先更新資料庫（正本，第 68 課的單一真相來源）；
2. **刪除**對應的快取。

下一次有人讀取時，會發生「未命中」，自然從資料庫載入最新的資料。

**為什麼是「刪除」快取，而不是「更新」快取？**
因為並行時會出錯。假設兩個請求幾乎同時修改同一門課：
1. 請求 A 把資料庫改成「Python 入門」；
2. 請求 B 把資料庫改成「Python 基礎」；
3. 請求 B 把快取更新成「Python 基礎」；
4. 請求 A（因為網路慢了一點）把快取更新成「Python 入門」。

結果：資料庫是「Python 基礎」，快取卻是「Python 入門」。而且在 TTL 到期之前，**所有人都看到錯的資料**。

「刪除」就沒有這個問題：不管誰先誰後，快取都只是被清空，下次讀取時從資料庫載入正確的值。

**比喻：**公告欄上的通知過時了，最安全的做法是**撕掉**，讓需要的人去查正式公文；而不是兩個人各自拿著新通知搶著貼，結果舊的蓋在新的上面。

@section 什麼該快取，什麼不該
**適合快取：**
- **讀多寫少**：例如讀寫比例 50 比 1 以上。課程目錄每天被看幾萬次，一學期才改幾次；
- **計算昂貴**：複雜的統計查詢、LLM 生成、嵌入向量的計算；
- **可以容忍短暫過時**：熱門排行榜晚幾分鐘更新，沒有人會在意。

**不適合快取（或需要極度小心）：**
- **帳戶餘額、扣款**：過時一秒就可能重複扣款；
- **即時的剩餘名額**：「還剩 1 個名額」是快取裡的舊資料，實際上已經額滿了，結果超收；
- **權限狀態**：管理員撤銷了某人的權限（第 60 課），但快取裡還是「有權限」，被停權的人在 TTL 到期前**仍然能操作**；
- **每次都不同、很少重複讀取的資料**：快取了也幾乎不會命中，白白浪費空間。

**判斷問題：**「如果使用者看到的是 5 分鐘前的舊資料，會出什麼事？」答案是「沒什麼」，就適合快取；答案是「會損失金錢或造成安全問題」，就不要快取，或用非常短的 TTL 並確保修改時立即刪除。

**用命中率衡量效果：**
**命中率** = 命中次數 ÷ 總查詢次數。

命中率 95% 代表 100 次查詢中只有 5 次需要碰資料庫，快取非常有效。命中率只有 10%，代表這個快取幾乎沒用，反而多了一層複雜度。**加了快取之後一定要量測命中率和延遲的變化**，這和第 54 課「效能不靠猜」是同樣的精神。

@section 快取鍵：決定回傳內容的每個因素都要放進去
**快取鍵**是快取中資料的「名字」。設計原則只有一條，但極其重要：

**所有會影響回傳結果的因素，都必須包含在快取鍵裡。**

**一個真實的教訓：**
某工程師發現 `GET /api/courses/101` 很慢，加上了快取，鍵設為 `"course_detail:101"`，TTL 10 分鐘。

問題是：這個 API 有一段邏輯：「如果呼叫者是這門課的授課教師，回傳的資料會**額外包含**尚未公布的期中考解答和全班不及格名單。」

- **上午 9:00**：授課老師打開課程頁面。快取未命中，後端查出**包含期中考解答**的完整資料，存進 `"course_detail:101"`；
- **上午 9:01**：一位學生打開同一門課。快取鍵 `"course_detail:101"` **命中**，後端直接回傳了快取裡的資料。

**學生看到了期中考解答。**

回傳內容取決於「呼叫者是誰」，但快取鍵裡**沒有**這個因素。

**兩種正確的修法：**
- **只快取公開的部分**：快取鍵 `"course_public:101"` 只存所有人都能看的課程資訊。教師專屬的資料**另外**依權限查詢，不放進共用快取；
- **把角色或使用者放進快取鍵**：例如 `"course_detail:101:role:teacher"` 和 `"course_detail:101:role:student"` 分開存。

**比喻：**餐廳的出餐檯。如果只標「3 號桌的餐」，但 3 號桌有素食者和非素食者，送錯就出事了。標籤必須包含**所有會讓餐點不同的資訊**：「3 號桌、素食」。

**這和第 60 課的授權、第 25 課 RAG 的權限過濾是同一個問題：**資料在任何地方被複製、被快取，權限的邊界都必須跟著一起走。

**快取鍵中的版本號：**
注意範例中的 `v1`。如果你修改了快取資料的格式（例如多加了一個欄位），把版本改成 `v2`，新程式就會讀取新的鍵，舊格式的快取自然被忽略，等 TTL 到期後消失。不必手動清空整個快取。

@section 三種經典故障
**故障一：快取雪崩（Cache Avalanche）——同時過期。**
系統啟動時，一次載入 10,000 門課程到快取，**全部**設定 TTL 為 3600 秒。

一小時後的**那一秒鐘**，10,000 個快取**同時過期**。所有請求一起變成「未命中」，一起衝向資料庫。資料庫瞬間被灌爆。

**解法：在 TTL 上加一點隨機時間**（稱為「抖動」，Jitter）：
```
ttl = 3600 + random.randint(0, 300)
```
過期時間被打散到 5 分鐘之內，資料庫的壓力就平均分攤了。

**比喻：**如果全公司的人都設定在同一秒下班打卡，打卡機前會大排長龍。錯開幾分鐘，就順暢了。

**故障二：快取擊穿（Cache Stampede）——熱門項目過期的瞬間。**
首頁的置頂公告，每秒被讀取 500 次。它的快取過期的那一瞬間，**500 個請求同時發現未命中**，於是同時跑去資料庫執行同一個昂貴的查詢。

這種現象又叫「**驚群效應**」（Thundering Herd）：一群受驚的動物同時往同一個方向衝。

**解法：只讓一個請求去查。**
用一把鎖：第一個發現未命中的請求取得鎖，去查資料庫並回填快取；其他 499 個請求**等它**，或者先拿稍微舊一點的資料。這叫「**單飛**」（Singleflight）。

**比喻：**辦公室的咖啡喝完了。如果每個人都自己跑去樓下買一大包，會買回來 20 包。正確的做法是：第一個發現的人去買，其他人等他回來。

**故障三：快取穿透（Cache Penetration）——查詢根本不存在的東西。**
攻擊者故意不斷查詢**不存在**的課程，例如 `course_id = -99999`。資料庫查不到，所以沒有東西可以存進快取，下一次又是未命中，又去查資料庫。快取完全被**穿透**了。

**解法：**
- **先驗證參數**（第 51 課）：課程編號不可能是負數，直接在入口擋下；
- **「查無資料」也快取起來**：存一個「不存在」的標記，TTL 設短一點（例如 30 秒）。這叫「**負快取**」（Negative Cache）。

@section AI 應用中的快取
快取在 AI 應用中特別有價值，因為 LLM 呼叫**又慢又貴**。

**一、嵌入向量的快取。**
同一段文字的嵌入向量（第 24 課），只要模型不變，**永遠是一樣的**。用「模型名稱 + 文字的雜湊值」當快取鍵，計算過的就不必再算。重建 RAG 索引時，沒改動的講義段落可以直接使用快取。

**二、完全相同問題的回答快取。**
「期中考範圍是什麼？」這種**一字不差**的常見問題，可以快取回答。但要注意：
- 快取鍵要包含**所有影響回答的因素**：問題文字、課程、使用者權限、提示詞版本、模型版本、檢索到的文件版本；
- 講義更新後（第 68 課），相關的回答快取要**一起作廢**，否則 AI 會繼續給出舊答案；
- 個人化的對話（含個人資訊、對話歷史）**不適合**共用快取。

**三、語意快取（Semantic Cache）。**
更進階的做法：「期中考考哪些？」和「期中考範圍是什麼？」文字不同但意思一樣。用嵌入向量的**相似度**判斷，相似度夠高就使用快取的回答。這能提高命中率，但也有風險：相似不等於相同，可能把不該共用的答案給錯人。門檻要謹慎設定，並用第 29 課的評估集驗證。

**四、模型服務商的提示詞快取。**
很多 LLM 服務提供「**提示詞快取**」：如果多個請求的開頭部分（例如很長的系統提示詞）相同，服務商會快取這部分的計算，降低費用和延遲。這和第 40 課的 KV 快取原理相關。設計提示詞時，**把固定不變的部分放在前面**，就能充分利用它。

@section 常見陷阱
**陷阱一：還沒優化就先加快取。**
連索引都沒建（第 54 課）、查詢寫得很糟，就先包一層快取。快取一過期或 Redis 一重啟，爛查詢照樣把資料庫拖垮。

**工程鐵律：先建正確的索引、優化查詢，量測後確認仍有瓶頸，再加快取。**快取是止痛藥，不是治療。

**陷阱二：忘記設定 TTL。**
沒有 TTL 的快取**永不過期**。只要某次修改時忘了刪除快取，錯誤的資料就會**永遠**留在那裡。TTL 是最後一道保險：就算其他機制都失效了，資料最多也只會過時 TTL 那麼久。

**陷阱三：快取鍵沒包含權限範圍。**如上面的期中考解答事件。

**陷阱四：把快取當成資料庫。**
Redis 的資料存在記憶體中，重新啟動或記憶體不足時，資料可能消失。**快取裡的東西必須隨時可以從正本重建**。重要的資料只存在快取裡，總有一天會遺失。

**陷阱五：快取一切。**
每多一層快取，就多一個「資料可能過時」的地方，除錯也更困難：「使用者看到的舊資料，是哪一層快取造成的？」只快取量測證明有需要的東西。

@section 快取不只在 Redis：瀏覽器與 CDN
這一課講的主要是伺服器端的快取。但一個請求從使用者到資料庫的路上，其實還有好幾層快取：

**一、瀏覽器快取。**
瀏覽器會把下載過的檔案（圖片、CSS、JavaScript）存在使用者的電腦裡。伺服器用 `Cache-Control` 回應標頭告訴瀏覽器可以存多久：
```
Cache-Control: public, max-age=31536000, immutable
```
意思是「任何人都可以快取、存一年、內容不會變」。適合加上版本號或雜湊值的靜態檔案，例如 `app.3f9a2c.js`：內容一改，檔名就跟著變，瀏覽器自然會下載新的。

**二、CDN（內容傳遞網路）。**
CDN 是分布在世界各地的快取伺服器。台灣的使用者從台灣附近的節點拿檔案，而不必每次都連到你在美國的主機。適合圖片、影片、靜態網頁等**所有人都一樣**的內容。

**三、最重要的安全提醒：個人資料絕不能被共用快取存起來。**
第 71 課期中考解答的教訓，在 CDN 和代理伺服器上一樣會發生，而且更難察覺。含有個人資料或權限相關內容的 API 回應，要明確告訴所有中間層「**不要存**」：
```
Cache-Control: private, no-store
```
- `private`：只有使用者自己的瀏覽器可以存，共用的 CDN 和代理伺服器不行；
- `no-store`：連瀏覽器都不要存（適合非常敏感的資料，例如成績、帳務）。

**四、應用程式內的本機記憶體快取。**
直接存在 Python 程式的記憶體裡，比 Redis 更快（不用經過網路）。但第 73 課說過：有多台機器時，每台的本機快取**各自獨立**，修改時很難同時清除每一台的快取。適合「很少變、過時也沒關係」的東西，例如設定檔、國家代碼清單，而且 TTL 要短。

**快取滿了怎麼辦？淘汰策略。**
快取的空間有限，滿了就要丟掉一些舊資料。最常見的策略是 **LRU**（Least Recently Used，最近最少使用）：**最久沒被用到的先丟**。就像書桌上的東西放不下時，你會先把最久沒碰過的那疊資料收回檔案櫃。Redis 可以設定記憶體上限和淘汰策略，讓它自動處理。

@section 動動腦：判斷看看
**題一**：老師修改了課程標題，快取應該更新成新標題，還是刪除？
→ 刪除。先更新資料庫再刪除快取，避免並行寫入時把舊值寫回快取。

**題二**：課程詳情 API 對教師會多回傳未公布的考題，快取鍵只用課程編號，會發生什麼事？
→ 教師的完整資料可能被快取並回傳給學生，造成資料外洩；鍵必須包含角色或只快取公開部分。

**題三**：一萬筆快取設定完全相同的 TTL，會有什麼風險？如何防範？
→ 同時過期造成快取雪崩，資料庫瞬間被灌爆；在 TTL 上加入隨機抖動。

**題四**：學生的剩餘選課名額適合快取 10 分鐘嗎？
→ 不適合。過時的名額會造成超收；需要即時正確的資料不應快取，或需極短 TTL 並在變動時立即作廢。

@section 本課重點整理
- **快取**用空間和短暫不一致換取速度；「快取失效」是電腦科學的難題之一。
- **Cache-Aside**：讀取時先查快取，未命中才查資料庫並回填；寫入時先改資料庫，再刪除快取。
- **TTL** 是最後一道保險，所有快取都要設。
- **適合快取**：讀多寫少、計算昂貴、可容忍短暫過時；**不適合**：金額、名額、權限狀態。
- **用命中率和延遲量測效果。**
- **快取鍵**必須包含所有影響結果的因素，特別是使用者權限；加上版本號方便升級格式。
- **三種故障**：雪崩（加抖動）、擊穿（單飛鎖）、穿透（驗證參數與負快取）。
- **AI 快取**：嵌入向量、相同問題的回答、語意快取、服務商的提示詞快取；講義更新時要一併作廢。
- **先優化再快取**；快取不是資料庫，必須能從正本重建。

@term 快取
把計算或查詢結果暫存在快速存取的地方，供後續重複使用（Cache）。
@term Redis
把資料存在記憶體中、常用於快取與佇列的高速資料庫。
@term Cache-Aside
讀取時先查快取、未命中再查資料庫並回填，寫入時更新資料庫後刪除快取的模式。
@term 命中
要找的資料在快取中，可直接回傳（Cache Hit）。
@term 未命中
要找的資料不在快取中，必須查詢正本（Cache Miss）。
@term TTL
快取資料的存活時間，到期後自動刪除（Time To Live）。
@term 命中率
快取命中次數占總查詢次數的比例（Hit Rate）。
@term 快取鍵
用來識別快取資料的名稱，須包含所有影響結果的因素（Cache Key）。
@term 快取雪崩
大量快取同時過期，請求一起衝向資料庫（Cache Avalanche）。
@term 抖動
在 TTL 等時間設定上加入隨機量，避免同時發生（Jitter）。
@term 快取擊穿
熱門快取過期瞬間，大量請求同時查詢資料庫（Cache Stampede）。
@term 驚群效應
大量請求或程序同時被觸發、搶奪同一資源的現象（Thundering Herd）。
@term 快取穿透
查詢不存在的資料，使每次請求都繞過快取打到資料庫（Cache Penetration）。
@term 負快取
將「查無資料」的結果也短暫快取，防止穿透（Negative Cache）。
@term 語意快取
以嵌入相似度判斷問題是否相同，重用先前回答的快取（Semantic Cache）。
