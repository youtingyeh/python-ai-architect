@section 開場：同一個模型，為什麼換個人跑就不準了？
小美是公司的資料科學家，她花了兩週訓練出一個預測機台異常的模型，驗證分數非常漂亮。她把模型存成一個檔案 `model.pt`，交給後端工程師阿哲，讓他放到公司系統上線。

上線第一天，系統瘋狂發出異常警報。明明機台一切正常，模型卻幾乎每一筆都說「異常」。

阿哲很困惑：「我就是照妳給的檔案載入的啊！」小美也很困惑：「我自己測的時候明明很準！」

兩週後，小美想重現當初的實驗結果，重新跑了一次同樣的訓練程式，卻發現分數跟報告上的不一樣。她甚至開始懷疑自己當初是不是記錯了。

這一課要解決的就是這種「**結果無法重現**」的問題。在一般的軟體開發中，同樣的程式碼通常就會得到同樣的結果；但在 AI 開發中，結果取決於很多看不見的東西：資料怎麼處理的、隨機數字怎麼抽的、模型在什麼模式下運作、用的是哪一版資料……少記一樣，結果就對不上。

**可重現性**（Reproducibility）是指：別人（或幾個月後的你自己）照著你的紀錄，能得到一樣的結果。這不只是學術上的好習慣，更是讓 AI 系統**能被信任、能被除錯、能安全上線**的基礎。

我們會依序學：
1. 為什麼只存模型權重遠遠不夠；
2. 最常見的上線事故：訓練與上線的處理方式不一致；
3. 怎麼控制隨機性；
4. 載入模型後一定要做的事；
5. 一份完整的「模型交付包」該包含什麼；
6. 怎麼記錄每一次實驗。

@section 只存權重，就像只給鑰匙不給鎖
在 PyTorch 裡，訓練完最常見的收尾是這一行：

```
torch.save(model.state_dict(), 'weights.pt')
```

`state_dict` 是「狀態字典」，裡面存的是模型所有的權重數字——就是那幾百萬個訓練好的旋鈕位置。很多人以為存了這個就等於存了模型。

李沐在《動手學深度學習》和實務上反覆強調：**權重檔只是模型最後一刻的一大堆數字，它本身並不是一個完整的預測系統。**

要讓這些數字真正派上用場，還需要很多「說明書」：

1. **前處理的方法和數字**：例如第 6 課的標準化，用的平均值 $\mu$ 和標準差 $\sigma$ 是多少？類別要怎麼轉成數字（例如「台北」= 0、「台中」= 1 的對照表，叫做**詞彙表**或 Vocabulary）？缺失的欄位要填什麼？
2. **模型的結構**：有幾層？每層多少神經元？用什麼激活函式？權重檔裡只有數字，沒有寫這些。載入時如果建錯結構，數字根本塞不進去，或塞進去意思全錯。
3. **用的是哪一版資料**：訓練集、驗證集是哪一份檔案？怎麼切的？
4. **用的是哪一版程式和工具**：程式碼是哪個版本？PyTorch 是哪一版？

只給權重檔，就像只給別人一把鑰匙，卻沒說這把鑰匙開哪一扇門、要往哪個方向轉。拿到的人只能用猜的，猜錯就出事。

@section 最常見的上線事故：訓練時和上線時「吃的東西不一樣」
在所有「離線測試很準、一上線就全錯」的事故中，排名第一的原因有個專門名稱：**訓練與服務不一致**（Training-Serving Skew）。「服務」（Serving）指的是模型上線後提供預測的階段。意思是：模型訓練時看到的資料，和上線時收到的資料，處理方式不一樣。

我們回到開場小美的故事，看看到底發生了什麼。

小美在 Jupyter Notebook（一種邊寫程式邊看結果的筆記本工具，資料科學家很常用）裡，有一格寫了這行手動標準化：

```
x_norm = (x - 10.0) / 2.0
```

意思是：原始溫度的平均是 10 度、標準差是 2 度，把每個溫度轉換成「比平均高幾個標準差」。然後她拿 `x_norm` 去訓練模型。最後只匯出了權重檔。

阿哲拿到的只有權重檔，**不知道還有這一行**。於是上線後，感測器傳來的原始溫度直接被送進模型。

**我們來算一下差多少。**現場傳來一個完全正常的溫度：14 度。
- 訓練時，模型應該看到：$\frac{14 - 10}{2} = +2.0$（比平均高 2 個標準差，有點偏高但還算正常）。
- 上線時，模型實際看到：**14.0**。

對模型來說，14.0 的意思是「比平均高 14 個標準差」，換算回原始溫度相當於 $10 + 14 \times 2 = 38$ 度——一個極端的高溫！所以模型理所當然地大喊「異常！」。每一筆都被放大了，難怪系統瘋狂報警。

模型本身一點錯都沒有，錯的是「餵給它的東西」。

**唯一的解法是一條鐵律：前處理的參數（平均值、標準差、詞彙表、決策門檻等等），是模型不可分割的一部分。**它們必須跟權重存在**同一個交付檔案**裡，或寫在**同一個程式類別**裡，一起儲存、一起載入、一起測試。不能散落在某個筆記本的某一格裡。

在 PyTorch 裡有一個好方法叫 `register_buffer`：把平均值和標準差「註冊」成模型內部的一部分。這些數字：
- **不會**被優化器當成要訓練的權重去修改；
- **會**自動跟著權重一起存進 `state_dict`、一起載入；
- 模型搬到顯示卡上時，也會自動一起搬過去。

這樣前處理就永遠不會和權重分家了。

@section 控制隨機性：四個「骰子」都要固定
小美的第二個問題是：同一份訓練程式，跑兩次結果不一樣。這是因為深度學習的訓練過程中，到處都在「擲骰子」：

1. **權重的初始值是隨機的**：模型開始訓練前，所有權重會被設成隨機的小數字（常見的方法有 Kaiming 初始化、Xavier 初始化，都是精心設計的隨機方式）。起點不同，最後走到的地方可能不同。
2. **資料洗牌順序是隨機的**：第 8 課的 `shuffle=True`，每一輪資料的順序都不一樣。
3. **Dropout 是隨機的**：第 9 課說的隨機關掉神經元。
4. **資料增廣是隨機的**：隨機翻轉、隨機裁切。

電腦裡的「隨機」其實是**偽隨機**：它是用一個起始數字，透過固定的公式產生一串看起來隨機的數字。這個起始數字叫做「**隨機種子**」（Random Seed）。只要種子一樣，產生出來的整串「隨機」數字就會一模一樣。就像同一副牌，用同一種方式洗，洗出來的順序每次都一樣。

所以，要讓實驗可以重現，就要把所有骰子的種子都固定住。通常會寫一個 `set_seed(seed)` 函式，一次設定：
- Python 內建的隨機：`random.seed(seed)`
- NumPy 的隨機：`np.random.seed(seed)`
- PyTorch 的隨機（一般處理器和顯示卡都要）：`torch.manual_seed(seed)`、`torch.cuda.manual_seed_all(seed)`

**但要知道一個重要的限制：**固定種子能讓你在**同一台電腦、同樣的環境**下重現結果，但**不保證**換一台電腦或換一張顯示卡也完全一樣。

為什麼？因為顯示卡為了算得飛快，會讓很多計算單元**同時**把數字加起來，誰先加完不一定。而電腦的小數加法有個怪特性：**加的順序不同，結果可能差一點點**。數學上 $(a + b) + c$ 一定等於 $a + (b + c)$，但在電腦的浮點數世界裡，因為每次加法都會四捨五入，這兩者可能在小數點後很多位有微小差異。這些微小差異經過幾萬步訓練累積，可能讓結果有可見的不同。

如果真的需要「每一個位元都一模一樣」的重現（例如某些嚴格的研究或稽核），PyTorch 提供了開關：`torch.use_deterministic_algorithms(True)` 和 `torch.backends.cudnn.deterministic = True`，強制使用固定順序的計算方式。代價是訓練會變慢。

實務上的態度是：**固定種子是基本功，一定要做；但比較兩個模型時，最好用幾個不同的種子各跑一次，看結果的平均和波動範圍。**如果模型 A 比 B 好 0.5%，但換個種子兩者的差距就會在 ±1% 之間跳動，那這 0.5% 就不算真的贏。

@section 載入之後，第一件事是切到「考試模式」
另一個讓人抓狂的狀況：重新載入模型後，**同一筆輸入連續預測兩次，結果竟然不一樣**，而且跟存檔前的分數也對不上。

最常見的原因：**載入權重後忘了呼叫 `model.eval()`**。

當你在推論程式裡建立一個新的模型物件、再把權重載入進去時，PyTorch 新建的模型**預設處於訓練模式**。第 8 課說過，有兩種零件在訓練模式下的行為不一樣：

- **Dropout**：還在隨機關掉神經元。所以同一筆輸入，每次預測都隨機跳動。
- **BatchNorm**：不會使用訓練時累積好、存在權重檔裡的長期平均和標準差，反而拿「這一批推論資料」重新算平均。如果一次只預測一筆資料，一筆資料的「標準差」是 0，甚至可能直接算出錯誤或報錯。

所以載入模型準備推論的**標準三步驟**是：

1. `model.load_state_dict(...)`：載入權重。
2. `model.eval()`：切到考試模式。
3. **用一筆固定的測試資料驗證**：拿存檔時就記錄好的一筆輸入和它的預期輸出，確認載入後算出來的結果一樣。程式上常用 `torch.allclose(原輸出, 新輸出)`，意思是「兩組數字在極小誤差範圍內相等」。

第 3 步非常重要。它把「我覺得應該沒問題」變成「我確認過沒問題」。

@section 一份完整的模型交付包，應該長什麼樣子
那麼，到底要存哪些東西，才算是一個「自給自足」的模型？好的做法是不要只存權重，而是存一個結構完整的「**交付包**」（Artifact Bundle）。至少包含六個部分：

**1. 格式版本（schema_version）**
例如 `'1.0'`。將來交付包格式升級時，載入程式可以先檢查版本，知道該怎麼讀。

**2. 模型設定（model_config）**
重建模型所需的所有結構資訊，例如「輸入 4 個特徵、隱藏層 16 個神經元、Dropout 0.2」。載入的人不用猜當初設了幾層。

**3. 前處理狀態（preprocess_state）**
從**訓練集**算出來的平均值、標準差、特徵名稱與順序等等。這正是小美漏掉的那個部分。

**4. 模型權重（model_state_dict）**
就是原本那一大堆數字。

**5. 決策規則（decision_policy）**
模型輸出機率之後怎麼做決定。例如第 7 課的決策門檻「0.35 以上算異常」，以及「0 代表正常、1 代表異常」的標籤對照表。門檻也是經過驗證集仔細挑選的，丟了它，模型的行為就變了。

**6. 冒煙測試資料（smoke_test_pair）**
一筆範例原始輸入，加上存檔當下算出來的預期輸出。「**冒煙測試**」（Smoke Test）這個名字來自電子工程：新電路板第一次通電，先看看會不會冒煙，不冒煙才做進一步測試。部署端載入交付包的那一刻，就自動拿這筆範例跑一次完整流程（原始輸入 → 前處理 → 模型 → 決策）；如果結果和存檔時差太多（例如超過 $10^{-6}$，也就是百萬分之一），就**拒絕啟動服務並發出警報**，而不是帶著錯誤上線。

如果小美當初交出的是這樣一個交付包，阿哲載入時，冒煙測試就會立刻失敗——因為他沒做前處理，算出來的結果會和預期差很多——事故在上線前就會被擋下來。

@section 實驗紀錄四大支柱：程式、資料、設定、結果
一個模型專案常常要跑上百次實驗。如果只是把檔案取名為 `model_v1.pt`、`model_v2_final.pt`、`model_v2_真的最終版_ok.pt`，兩天後就沒人記得哪一個是用哪一版資料、哪些設定訓練出來的。

在一般軟體開發中，只要用 **Git**（最常用的程式碼版本管理工具，可以記錄每一次修改）管好程式碼，就能重現結果。但在 AI 開發中：

> **結果 = 程式碼 + 資料版本 + 設定（含隨機種子）+ 執行環境**

少了任何一樣，都可能重現不出來。所以每一次訓練，都應該**自動**產生一份實驗紀錄（常用 JSON 格式，一種電腦和人都讀得懂的結構化文字），記錄四大支柱：

**① 程式碼版本**
目前的 Git 版本編號（叫做 commit SHA，一串像指紋一樣獨一無二的代碼），以及當時有沒有還沒存進版本紀錄的修改。還有 PyTorch 等工具的版本。

**② 資料版本**
訓練、驗證、測試資料檔案的「**雜湊值**」（Hash，例如 SHA-256），以及各有幾筆。雜湊值可以想成檔案的指紋：只要檔案內容改了一個字，指紋就完全不同。這樣就不怕底層的資料檔被人偷偷覆蓋掉——一比對指紋就知道。

**③ 設定**
所有超參數（學習率、批次大小、權重衰減、訓練輪數）和隨機種子。

**④ 結果與產出**
最佳驗證分數、是在第幾輪達到的（呼應第 9 課的早停），以及那一次產出的交付包檔案位置和它的雜湊值。

有了這份紀錄，任何一個模型，在任何時候，都能追溯到「它是用哪一份程式、哪一份資料、哪些設定訓練出來的」，並且照著重跑一次。業界有很多工具專門做這件事（例如 MLflow、Weights & Biases 等實驗追蹤平台），但即使只是自己寫一個 JSON 檔，也比什麼都不記好太多。

@section 跟著練一次：診斷三個重現失敗的案例
**案例 A：同事載入你的模型，對同一筆測試資料的預測和你的報告完全不同。**
→ 優先檢查兩件事：(1) 他的前處理是否和訓練時完全一樣（特別是有沒有用**訓練集**的平均值和標準差做標準化）；(2) 載入模型後有沒有呼叫 `model.eval()`。這兩個是最常見的元兇。如果交付包裡有冒煙測試資料，第一步就是跑它。

**案例 B：你自己重跑同一份訓練程式，驗證分數從 0.912 變成 0.897。**
→ 先確認有沒有固定所有隨機種子。如果固定了還是有差異，檢查是不是換了機器或顯示卡、PyTorch 版本是否不同，以及資料檔的雜湊值是否和實驗紀錄一致。如果都一樣，差異可能來自顯示卡的非確定性計算，需要時可以開啟確定性模式。

**案例 C：主管問「上個月那個表現最好的模型，是用哪一版資料訓練的？」你答不出來。**
→ 這是缺少實驗紀錄的典型後果。從現在開始，讓每次訓練自動產出記錄四大支柱的 JSON 檔。

**再想一題：**為什麼把平均值和標準差用 `register_buffer` 註冊在模型裡，比寫在 Notebook 的某一格裡安全？
→ 因為註冊後，它們會自動跟著權重一起存檔、一起載入、一起搬到顯示卡，而且不會被優化器誤當成權重去修改。前處理和權重從此不會分家。

@section 本課重點整理
- **可重現性**是 AI 系統能被信任、除錯和安全上線的基礎。結果 = 程式碼 + 資料版本 + 設定 + 環境。
- **只存權重不夠**：還要存前處理參數、模型結構、資料版本和程式版本。
- **訓練與服務不一致**是上線事故第一名：訓練時做了 $(x - 10) / 2$，上線時忘了做，14 度就會被當成 38 度。前處理參數必須和權重綁在一起（例如用 `register_buffer`）。
- **固定所有隨機種子**（Python、NumPy、PyTorch、顯示卡），但要知道跨硬體仍可能有微小差異；比較模型時最好跑多個種子。
- **載入三步驟**：載入權重 → `model.eval()` → 用固定範例驗證輸出一致。
- **交付包六件事**：格式版本、模型設定、前處理狀態、權重、決策規則、冒煙測試資料。
- **每次實驗自動記錄**程式、資料、設定、結果四大支柱。

恭喜你完成了「模型基礎與訓練」這個階段！你已經掌握了機器學習從資料、模型、訓練到評估、交付的完整流程。下一課開始，我們跟著 Andrej Karpathy 的腳步，親手拆開神經網路的內部：從零打造一個迷你的自動微分引擎。

@term 可重現性
別人或未來的自己照著紀錄，能得到一樣結果的能力（Reproducibility）。
@term 狀態字典
PyTorch 存放模型所有權重數字的字典（state_dict）。只有數字，沒有結構和前處理資訊。
@term 訓練與服務不一致
模型訓練時和上線時對資料的處理方式不同，導致上線後預測錯誤（Training-Serving Skew）。
@term 隨機種子
偽隨機數產生器的起始數字（Random Seed）。種子相同，產生的「隨機」序列就完全相同。
@term 詞彙表
把類別或文字對應成數字編號的對照表（Vocabulary），例如「台北」= 0。
@term 交付包
把模型權重連同前處理參數、結構設定、決策規則、測試資料一起打包的檔案（Artifact Bundle）。
@term 冒煙測試
最基本的快速檢查（Smoke Test），例如載入模型後跑一筆範例，確認輸出跟預期一樣。
@term 雜湊值
檔案內容的「指紋」（Hash），內容改了一個字指紋就完全不同，用來確認檔案沒被改過。
@term Git
最常用的程式碼版本管理工具，記錄每一次修改，可以隨時回到任何一個歷史版本。
@term Jupyter Notebook
資料科學家常用的互動式筆記本工具，可以一格一格執行程式、馬上看到結果。
@term 偽隨機
電腦用固定公式從種子算出、看起來隨機但其實可重現的數字序列。
@term 前處理
資料送進模型前的整理和轉換步驟，例如標準化、填補缺值、把類別轉成數字。
