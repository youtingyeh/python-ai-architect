@section 開場：AI 看到的不是「字」，而是「Token」
你可能聽過這樣的說法：「ChatGPT 的 API 按 Token 收費」、「這個模型的上下文長度是 128K Token」、「中文比英文更耗 Token」。Token 到底是什麼？

你也可能看過一個有名的笑話：問 AI「strawberry 這個字裡有幾個 r？」，早期的模型常常答錯，說「2 個」。一個能寫程式、能考律師執照的 AI，怎麼會連數字母都數錯？

答案就藏在這一課的主角：**分詞器**（Tokenizer）。

上一課我們用「字母」當作模型的最小單位。但真實的大型語言模型（LLM，Large Language Model）不是這樣做的。在文字進入模型之前，會先經過一道切割手續：把文字切成一塊一塊的小片段，每一塊叫做一個 **Token**（中文有時譯為「詞元」或「標記」），再把每塊換成一個編號。模型從頭到尾看到的，只是一串編號。

**Token 像什麼？**想像你在玩樂高。你可以用最小的 1×1 積木（字母）拼出任何東西，但要拼很久；你也可以用大型預製件（整個單字），拼得很快，但遇到沒有預製件的形狀就沒輒。Token 就是中間的折衷：常見的形狀有現成的大積木，罕見的形狀就用小積木拼。

這一課，我們跟著 Karpathy 的 Tokenizer 課程來理解：
1. 為什麼不用「字」或「單字」，而要用 Token？
2. 電腦怎麼儲存全世界的文字（UTF-8）？為什麼中文比較「貴」？
3. 最主流的切法 BPE 是怎麼運作的？
4. 為什麼 AI 數不出 strawberry 有幾個 r？

@section 為什麼不直接用「單字」或「字母」？
把文字切成單位，有兩個極端的選擇，各有致命缺點。

**極端一：以「完整單字」為單位。**

英文用空白切開，中文用斷詞工具切開。聽起來最自然，但問題很大：
- **詞彙表會爆炸。**人類語言加上人名、地名、品牌、程式變數名、錯字、各國語言……可能有幾百萬個不同的詞。模型的第一層（嵌入層，等一下會解釋）要為每個詞準備一組參數，會大到塞不進顯示卡。
- **遇到沒看過的詞就完蛋。**只要一個新詞（例如去年才出現的網路流行語、新產品名）不在詞彙表裡，模型只能把它當成一個「未知符號」`<UNK>`（unknown），等於失明。這叫做**詞彙表外問題**（Out-Of-Vocabulary，OOV）。

**極端二：以「單一字元」或「位元組」為單位。**

上一課就是用字母。好處是永遠不會遇到未知字（所有東西都能用最小單位拼出來）。但：
- **序列會變得超長。**同樣一段文章，切成字元會比切成單字長 4 到 10 倍。
- **長序列很貴。**後面幾課會學到，Transformer 的核心「注意力機制」要讓每個位置和其他所有位置比對，計算量和長度的**平方**成正比。長度變 5 倍，計算量就變 25 倍。
- **模型要浪費力氣在拼字上。**模型的前幾層得先花力氣學會「s-t-r-a-w 這幾個字母組在一起是一個詞」，而不是直接去理解意思。
- **上下文視窗**（Context Window，模型一次能讀進的最大長度）是固定的，序列越長，能塞進的實際內容就越少。

**解法：子詞（Subword）。**

現代所有主流 LLM 都採用折衷：**常見的詞保持完整，罕見的詞拆成常見的片段。**例如：
- "the"、"apple" 這種高頻詞 → 一個 Token。
- "unhappiness" → 可能拆成 "un" + "happiness"。
- 一個罕見的化學名詞 → 拆成好幾個常見片段。

這樣既不會遇到未知詞（最差也能拆到單一位元組），序列長度也不會暴增。這叫做「**子詞分詞**」（Subword Tokenization）。

@section 電腦怎麼存文字：Unicode 與 UTF-8
要理解現代分詞器，得先知道電腦怎麼儲存文字。電腦只懂數字，所以每個字都要有一個編號。

**Unicode：全世界文字的總編號表。**

Unicode 是一個國際標準，替地球上幾乎所有文字（英文、中文、阿拉伯文、表情符號……）都分配了一個獨一無二的編號，叫做**碼位**（Code Point）。例如：
- 英文字母 A 是 U+0041（十進位 65）
- 中文「智」是 U+667A
- 😀 是 U+1F600

目前 Unicode 收錄了超過 15 萬個字。

**UTF-8：把編號存進電腦的方式。**

光有編號還不夠，還要決定怎麼存。電腦儲存的基本單位是**位元組**（Byte），一個位元組可以表示 0 到 255 的整數。

**UTF-8** 是最流行的儲存格式（全世界超過 98% 的網頁使用它）。它是「**變長**」的：常用的字用少一點位元組，罕見的字用多一點：
- 英文字母、數字、標點：**1 個**位元組
- 帶重音的歐洲字母（é、ñ）：**2 個**位元組
- 常見基本多文種平面的漢字：**3 個**位元組；補充平面的漢字如「𠀀」是**4個**
- 表情符號：**4 個**位元組

**實際看看。**在 Python 裡：
- `list("AI".encode("utf-8"))` → `[65, 73]`，2 個數字。
- `list("人工智慧".encode("utf-8"))` → 12 個數字：`[228, 186, 186, 229, 183, 165, 230, 153, 186, 230, 133, 167]`。每個中文字佔 3 個。

**這跟 AI 有什麼關係？**現代分詞器（GPT-2、GPT-4、Llama 3 都是）都是從**位元組**出發。它們的最小單位就是這 256 種位元組，然後再往上合併。所以任何文字、任何語言、甚至亂碼，都能被表示，永遠不會有未知字。

**但這對中文不太公平。**如果分詞器主要用英文資料訓練，學到的合併規則大多是英文的，常見中文字的 3 個位元組可能沒被合併成一個 Token。結果：
- 一個中文字可能被拆成 2 到 3 個 Token。
- 同樣意思的一段話，中文的 Token 數可能是英文的 2 到 3 倍。
- 這直接代表：**API 費用更高、能塞進上下文視窗的內容更少、生成速度更慢**（模型一次生成一個 Token，一個字要生成 3 次）。

這就是為什麼新一代的模型（如 GPT-4o、Llama 3）都特別擴大了詞彙表，放進更多中文和其他語言的 Token，讓非英語使用者的成本降下來。

@section BPE：最主流的切法，其實是一種壓縮
**BPE**（Byte Pair Encoding，位元組對編碼）原本是 1994 年發明的**資料壓縮**方法，後來被拿來建立 Token 詞彙表，成為 GPT 系列的標準做法。

**核心想法簡單到不可思議：一直把「最常一起出現的兩個鄰居」黏成一個新單位。**

想像你在傳簡訊，發現自己老是打「哈哈」，就設定一個快捷鍵代表「哈哈」。後來發現「哈哈哈哈」也常出現，就再設一個快捷鍵代表「兩個哈哈」。BPE 就是自動化地做這件事。

**完整步驟：**
1. 從最基本的 256 個位元組開始，每個是一個 Token（編號 0 到 255）。
2. 掃過全部訓練文字，數一數「哪兩個 Token 最常相鄰出現」。
3. 把這一對合併成一個**新 Token**，給它新編號（從 256 開始）。
4. 把文字中所有這一對都換成新 Token。
5. 回到第 2 步，重複 K 次。

做完後，詞彙表從 256 個長到 256 + K 個，而文字的 Token 數量越來越少。

**手算一次（Karpathy 課程的經典例子）。**

字串："aaabdaaabac"，共 11 個字元。

**第一輪**：數相鄰配對。"aa" 出現最多次（aaab 裡有兩次、再一個 aaab 又兩次，共 4 次）。定義 **Z = aa**，把所有 aa 換掉：
→ "ZabdZabac"，長度 9。

**第二輪**：再數。"ab" 出現 2 次、"Za" 也 2 次，平手時選一個，假設選 **Y = ab**：
→ "ZYdZYac"，長度 7。

**第三輪**：再數。"ZY" 出現 2 次，定義 **X = ZY**（其實代表 "aaab"）：
→ "XdXac"，長度 5。

11 個字元，壓縮成 5 個 Token！而模型學到了三條合併規則：aa→Z、ab→Y、ZY→X。

**實際使用時。**分詞器只需要保存一份「**合併規則清單**」（merges），按學到的先後順序排列：
- **編碼**（文字 → Token）：先把文字轉成位元組，再**按照規則學到的先後順序**一條條套用合併。順序很重要，因為必須和訓練時的切法一致，模型才看得懂。
- **解碼**（Token → 文字）：把每個 Token 查表展開回位元組，再用 UTF-8 轉回文字。

**真實世界的 Token 長什麼樣？**以 GPT-4 的分詞器為例：
- "Hello world" → 2 個 Token："Hello" 和 " world"（注意空白黏在 world 前面）。
- "人工智慧" → 大約 3 到 4 個 Token（看分詞器版本）。
- 一個常見英文單字通常是 1 個 Token；平均而言，1 個 Token 約等於 4 個英文字母或 0.75 個英文單字。

你可以在 OpenAI 的線上工具 Tokenizer 頁面（platform.openai.com/tokenizer）親手輸入文字，看它怎麼被切開，非常有趣。

@section 詞彙表要多大？一場拉鋸戰
既然合併越多次，文字被壓得越短，為什麼不合併到 500 萬個 Token，讓每個常見片語都只佔 1 個？

這是一場**拉鋸戰**，因為詞彙表大小 V 直接決定模型兩端的大小：
- **輸入端：嵌入層**（Embedding）。模型要把每個 Token 編號換成一組數字向量（就像上一課「W 的第 x 列」），需要一張 V 列的大表。
- **輸出端：預測層**（LM Head）。每一步都要對 V 個 Token 各算一個分數，再做 Softmax，挑出下一個 Token。

**V 變大的好處：**
- 同樣的文字切出更少的 Token，上下文視窗能塞更多內容。
- 生成時要跑的步數更少，速度更快。

**V 變大的代價：**
- **模型變胖**：嵌入層和預測層的參數量跟 V 成正比。
- **每一步更慢**：每生成一個 Token，都要算 V 個分數。
- **冷門 Token 學不好**：詞彙表越大，排在尾巴的罕見 Token 在訓練時越少被看到，它們的向量訓練不足，模型對它們理解很差。
- **藏起內部結構**：一個 Token 太大塊，模型就看不到裡面的字母和字根。

**業界的選擇：**
- GPT-2：50,257 個 Token
- Llama 2：32,000 個
- GPT-4（cl100k_base）：約 10 萬個
- Llama 3：128,256 個
- GPT-4o（o200k_base）：約 20 萬個

趨勢是越來越大，主要是為了更好地支援多語言。目前 10 萬到 20 萬之間，是在「壓縮率」和「運算成本」之間的甜蜜點。

@section 揭密：為什麼 AI 數不出 strawberry 有幾個 r
現在可以回答開頭的謎題了。

**人看到的**：s-t-r-a-w-b-e-r-r-y，10 個字母，一眼就能數出 3 個 r。

**模型看到的**：這個常見單字在進入模型之前，早就被分詞器切成了像 ["str", "aw", "berry"] 這樣的幾個 Token，甚至只有一兩個 Token。每個 Token 在模型眼中只是**一個編號**，像是 #496、#675、#15717。

模型從來沒有「看到」字母。就像有人把整個字貼成一張貼紙給你，問你裡面有幾個 r，你得靠記憶去回想這個字的拼法，而不是直接看。除非訓練資料裡常有「strawberry 有三個 r」這種描述，模型很難答對。（新一代模型透過更多訓練和「先拼出來再數」的推理方式，已經能答對了。）

**同樣的原因造成的其他怪現象：**

**① 數學計算不穩。**數字 "123456" 可能被切成 ["123", "456"]，而 "12345" 被切成 ["12", "345"]。位數對不齊，模型就很難學會直式加法這種「個位對個位」的規則。所以 Llama 3 等新模型會在分詞前，先用規則強制把數字切成固定 1 到 3 位一組。

**② 程式碼縮排浪費。**早期 GPT-2 會把 Python 程式的四個空白縮排切成 4 個獨立 Token，白白浪費上下文。新的分詞器會把連續空白合併成一個。

**③ 結尾空白陷阱。**BPE 通常把空白和**後面**的詞黏在一起，例如 " world" 是一個 Token（前面帶空白）。如果你在提示詞結尾不小心多打一個空白，例如「網址為 http:// 」，那個孤零零的空白會被切成一個單獨的 Token。但在訓練資料中，「http:// 後面接一個單獨空白 Token」幾乎從來沒出現過。模型被推進一個它沒見過的情境（叫做**分布外**，Out-of-Distribution），生成品質就會莫名下降。

**④ 罕見 Token 的怪行為。**曾經有研究發現，某些在建立詞彙表時出現、但在模型訓練時幾乎沒出現的 Token（例如某個網路論壇的使用者名稱），會讓模型輸出完全莫名其妙的內容。這被戲稱為「**故障 Token**」（Glitch Token）。

這些例子告訴我們一件重要的事：**很多看起來是「AI 不夠聰明」的問題，其實是「AI 看世界的方式」造成的。**

@section 分詞器和模型是連體嬰
一個很重要的工程原則：**分詞器和模型必須配套使用，絕對不能混搭。**

為什麼？因為對模型來說，Token 編號 1532 本身沒有任何意義。它的意義，完全儲存在模型嵌入層「第 1532 列」的那一組數字裡，那是經過幾兆個 Token 訓練出來的。

如果你把 A 模型配上 B 模型的分詞器，原本 A 模型裡第 1532 列代表 " apple"，現在 B 分詞器把 "SELECT" 切成了 1532。模型收到的意思完全錯亂，輸出會是一堆胡言亂語。

就像一本密碼本：發信人和收信人必須用同一本，換了本子，訊息就變成亂碼。

**如果想幫一個模型增加中文詞彙怎麼辦？**例如一個開源模型的中文 Token 太少，想加入「晶圓代工」、「健保」這類詞。正確做法是：
1. **只能在詞彙表尾端新增**，絕對不能改動原有編號的對應。
2. **把嵌入層和預測層同步加長**，為新 Token 增加新的列。
3. **新列不要用隨機數字初始化**。比較好的方法是：先用舊分詞器把「晶圓代工」拆成舊的幾個片段，取這些片段向量的**平均值**當作新 Token 的起始值。這樣新詞一開始就有一個合理的意思，而不是一團亂數。
4. 再用含有這些新詞的資料**繼續訓練**一段時間，讓模型熟悉新詞。

**特殊 Token。**除了一般文字，分詞器還有一些特殊控制符號，例如 `<|endoftext|>`（文字結束）、`<|im_start|>`（對話中某人開始說話）。它們就像上一課的 `.`，用來告訴模型結構上的資訊：哪裡是使用者說的話、哪裡是 AI 的回答、哪裡該停下來。聊天模型能分辨「誰在說話」，靠的就是這些特殊 Token。

@section 動動腦：自己當一次分詞器
**題目一**：用 BPE 處理字串 "abababcab"。

第一輪：數相鄰配對。ab 出現 4 次（位置 1-2、3-4、5-6、8-9），ba 出現 2 次，bc 1 次，ca 1 次。最多的是 ab，定義 **P = ab**：
→ "PPPcP"，長度從 9 變 5。

第二輪：PP 出現 2 次，Pc 1 次，cP 1 次。定義 **Q = PP**：
→ "QPcP"，長度 4。

注意這裡有個小細節：「PPP」中 PP 重疊出現，合併時是從左到右，先合併前兩個，剩下一個 P。

**題目二**：你要用 API 處理 1,000 個中文字的客服對話。如果分詞器對中文很不友善，平均每字 2 個 Token，總共 2,000 Token；換成中文友善的分詞器，每字約 1 個 Token。差別在哪？
- 費用約減半；
- 能塞進上下文視窗的對話量約加倍；
- 生成回答的速度約快一倍。

這就是為什麼挑選模型時，「這個模型處理中文的 Token 效率」是一個實際的成本考量。

@section 動手試試：用 tiktoken 看 GPT 怎麼切字
OpenAI 開源了它的分詞器套件 **tiktoken**，只要幾行 Python 就能看到 GPT-4 怎麼切文字：

```
import tiktoken
enc = tiktoken.get_encoding("cl100k_base")
ids = enc.encode("我今天學了 Tokenizer")
print(ids)                       # 一串整數
print([enc.decode([i]) for i in ids])  # 每個 Token 對應的文字
```

建議你親手試幾件事，每一件都會讓你對 Token 更有感覺：
1. **中英比較**：分別編碼「我喜歡機器學習」和 "I like machine learning"，比較 Token 數量。
2. **空白的位置**：編碼 "hello world" 和 "hello  world"（兩個空白），看看空白黏在哪裡。
3. **數字的切法**：編碼 "12345678"，看看它被切成幾塊、每塊幾位數。
4. **換一個分詞器**：把 `cl100k_base` 換成 `o200k_base`（GPT-4o 用的），再編碼同一段中文，Token 數通常會明顯減少。

你會發現，有些中文 Token 解碼出來會是奇怪的符號，那是因為它只包含一個中文字 3 個位元組中的一部分，單獨解碼無法組成完整的字。這正是「從位元組出發」的分詞器的特徵。

@section 常見問題
**Q：1 個 Token 大概等於幾個中文字？**
沒有固定答案，取決於分詞器。較舊、偏英文的分詞器大約 1 個中文字 1.5 到 2 個 Token；新一代多語言分詞器可以接近 1 個字 1 個 Token，常見詞甚至 2 個字 1 個 Token。估算 API 費用時，最準的方法是用該模型的分詞器實際算一次。

**Q：分詞器是怎麼訓練的？跟模型一起訓練嗎？**
不是。分詞器是**先**用 BPE 在大量文字上單獨訓練好（只是數數和合併，不需要梯度），之後就固定不動。模型訓練時，所有資料都先經過這個固定的分詞器。這也是為什麼兩者必須配套。

**Q：中文有沒有不用 BPE 的做法？**
有。例如 Google 的 **SentencePiece** 工具，常搭配 BPE 或另一種叫 Unigram 的演算法，它不依賴空白切詞，對中文、日文這類沒有空白的語言特別友善。許多開源模型都使用它。

@section 本課重點整理
- **Token** 是模型看文字的最小單位。文字先被分詞器切成 Token，再換成編號，模型只看得到編號。
- **為什麼用子詞**：整個單字會讓詞彙表爆炸、遇到新詞就失明；單一字元會讓序列太長、計算量暴增。子詞取兩者折衷。
- **UTF-8**：ASCII英文字母1個位元組、常見漢字3個位元組，部分漢字4個位元組。分詞器若缺乏中文合併規則，中文會耗費更多 Token，費用更高、速度更慢。
- **BPE**：從 256 個位元組出發，反覆把最常相鄰的一對合併成新 Token。編碼時必須按學到的順序套用規則。
- **詞彙表大小是拉鋸**：大一點序列更短，但模型更胖、每步更慢、冷門 Token 學不好。目前主流在 10 萬到 20 萬之間。
- **很多 AI 的怪毛病來自分詞**：數不出字母、數學不穩、結尾空白陷阱。
- **分詞器和模型是連體嬰**：不能混搭。擴充詞彙要在尾端新增、新向量用舊片段平均初始化、再繼續訓練。

@term Tokenizer
分詞器：把文字切成 Token 並轉成編號，以及把編號轉回文字的工具。
@term Token
模型處理文字的最小單位，可能是一個字、一個詞或一個詞的片段。API 費用和上下文長度都用它計算。
@term LLM
大型語言模型（Large Language Model），用海量文字訓練、參數數十億以上的語言模型，例如 GPT、Claude、Llama。
@term OOV
詞彙表外問題（Out-Of-Vocabulary）：遇到詞彙表裡沒有的詞，模型無法處理。
@term 上下文視窗
模型一次能讀進的最大 Token 數（Context Window），超過的部分模型看不到。
@term 子詞分詞
常見詞保留完整、罕見詞拆成常見片段的切法（Subword Tokenization），現代 LLM 的標準做法。
@term Unicode
替全世界幾乎所有文字分配唯一編號的國際標準。
@term UTF-8
最流行的文字儲存格式，ASCII英文字母佔1個位元組，常見漢字佔3個，補充平面的漢字可佔4個；表情也可能由多個碼位組成。
@term 位元組
電腦儲存的基本單位（Byte），可表示 0 到 255 的整數。
@term BPE
位元組對編碼（Byte Pair Encoding）：反覆把最常相鄰的兩個單位合併成新 Token 的演算法。
@term 嵌入層
把每個 Token 編號換成一組數字向量的查找表（Embedding），是模型的第一層。
@term 分布外
輸入和模型訓練時看過的資料差很多（Out-of-Distribution），模型表現往往變差。
@term 特殊 Token
分詞器中代表結構資訊的控制符號，例如文字結束、對話角色開始等。
