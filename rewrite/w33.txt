@section 開場：所有東西都會壞
Amazon 前技術長 Werner Vogels 有一句著名的話：**「任何東西，隨時都可能壞掉。」**（Everything fails, all the time.）

- 資料庫的硬碟會損壞；
- 上游的 LLM API 可能在尖峰時段連續十分鐘回傳 503，或者回應時間飆到 40 秒；
- Email 服務會斷線；
- 甚至你自己部署的新版本，可能帶著一個只在正式環境才會觸發的 bug。

**初學者**寫程式時，默默假設：網路不會斷、外部 API 永遠在 0.1 秒內成功回應、備份腳本有在跑，資料就安全了。

**資深的架構師**在設計的第一天就會問：
- 「如果外部 AI 服務卡住 30 秒，我們的網站會不會**連看講義、交作業這些基本功能都一起卡死**？」
- 「如果資料庫的硬碟燒毀了，要花**幾分鐘**才能恢復服務？會**遺失多少**資料？」
- 「我們**真的實際還原過**那份備份嗎？」

這就是「**可靠性工程**」（Reliability Engineering）的核心。這是工程篇的最後一課，我們要學：
1. **逾時**：永遠不要無限等待；
2. **重試風暴**：重試可能讓情況更糟；
3. **斷路器**與**優雅降級**：外部服務壞了，核心功能照常運作；
4. **RPO 與 RTO**：備份的兩個關鍵指標，以及**還原演練**；
5. **可回退的部署**：新版本出問題時，能不能安全退回舊版？

**設計的目標不是「永遠不壞」（那不可能），而是「壞的時候，影響範圍小、恢復得快、資料不遺失」。**

@section 逾時：永遠不要無限等待
**任何跨網路的呼叫，都必須設定逾時（Timeout）。**包括：呼叫外部 HTTP API、連線資料庫、連線 Redis、呼叫 LLM。

很多函式庫的預設值是「**無限等待**」。這是一個隱藏的地雷。

**情境：**上游 LLM 服務卡住了，不回應也不報錯。你的程式沒設逾時，就一直等。
- 第 1 個請求卡住，占用了一個工人（第 54 課的 worker）；
- 第 2 個請求也卡住，又占用一個；
- 幾秒鐘內，**所有工人都卡在等待 LLM**；
- 現在連「看講義」、「交作業」這些**跟 LLM 完全無關**的請求，也沒有工人可以處理了。

整個網站癱瘓。一個**非核心**的外部服務出問題，拖垮了**整個系統**。這叫「**連鎖故障**」（Cascading Failure）。

**比喻：**一家銀行的所有櫃員，都在等同一位主管簽核某張單子，而那位主管去開會了。結果大廳排滿了只想存錢、提款的客人，卻沒有任何櫃員可以服務他們。如果規定「等主管超過 2 分鐘就先處理下一位客人」，問題就解決了。

**逾時要設多久？**依照服務的特性和第 70 課的 SLO：
- 資料庫查詢：通常幾秒；
- 一般外部 API：5 到 10 秒；
- LLM 生成：可能需要較長，但如果是在使用者的請求路徑上，要考慮使用者願意等多久。**真的很慢的工作，應該放進佇列**（第 76 課）。

@section 重試風暴：好心辦壞事
第 22、72 課學過重試。但重試是一把雙面刃。

**情境：**資料庫因為 CPU 100% 而回應變慢。前端逾時了，自動重試；API 逾時了，也自動重試。每一層都重試 3 次。

原本每秒 100 個請求，現在變成每秒 **幾百個**。資料庫本來就已經過載了，現在負擔更重，**永遠恢復不了**。這叫「**重試風暴**」（Retry Storm）。

更糟的是**多層重試會相乘**：前端重試 3 次 × API 重試 3 次 × 資料庫驅動重試 3 次 = 一個使用者的操作變成 **27 次**資料庫請求。

**比喻：**一條道路因為事故塞車。每個駕駛都不斷按喇叭、不斷變換車道試圖鑽過去，結果讓交通變得更糟，連救護車都進不去。

**重試的規則：**
- **只重試暫時性的錯誤**（逾時、503），不重試永久性的錯誤（400、401，第 76 課）；
- **只重試冪等的操作**（第 73 課），或帶著冪等鍵；
- **限制次數**：例如最多 2 次；
- **指數退避加抖動**：每次等更久，而且錯開時間；
- **只在一層重試**：避免多層相乘。通常在最接近外部服務的那一層重試即可。

@section 斷路器與優雅降級
**斷路器**（Circuit Breaker）的概念，來自家裡的電路斷路器：電流過大時自動「跳電」，保護整棟房子的電線不會燒起來。

軟體的斷路器運作方式：

**狀態一：閉合（Closed）——正常運作。**
請求正常送往外部服務，同時**記錄失敗率**。

**狀態二：斷開（Open）——停止呼叫。**
當失敗率超過門檻（例如最近 20 次呼叫中有 50% 失敗），斷路器「**跳開**」。在接下來的一段時間（例如 30 秒）內，**不再呼叫**這個外部服務，而是**立刻**回傳一個降級的結果。

為什麼？因為它幾乎肯定會失敗，與其讓每個請求都等 5 秒才逾時，不如**1 毫秒內就直接失敗**，把資源留給其他工作，也讓外部服務有時間恢復。

**狀態三：半開（Half-Open）——試探。**
30 秒後，允許**少量**請求試著呼叫外部服務。成功了，就回到閉合狀態；還是失敗，就再次斷開。

**優雅降級（Graceful Degradation）：壞了，但壞得有禮貌。**
斷路器斷開時，回傳什麼？不是一個錯誤畫面，而是一個**降級但仍然可用**的體驗：
- AI 摘要服務壞了 → 顯示「AI 即時摘要暫時維護中，您仍可正常閱讀原始講義」；
- 推薦課程的服務壞了 → 顯示熱門課程的固定清單；
- AI 批改壞了 → 教師可以手動批改（第 70 課的 FR-AI-02）。

**核心功能（看講義、交作業）完全不受影響。**

**比喻：**餐廳的咖啡機壞了。好的餐廳會說「抱歉，今天咖啡暫停供應，推薦您試試我們的茶」，照常營業；而不是因為咖啡機壞了，就整間餐廳關門。

**區分核心與非核心：**在設計時（第 70 課的需求階段）就要想清楚：哪些功能是「**壞了整個產品就沒意義**」的核心？哪些是「**壞了很可惜，但可以暫時沒有**」的附加功能？非核心的依賴，都應該能被降級。

@section 備份：RPO 和 RTO
**備份的兩個關鍵指標：**

**RPO（Recovery Point Objective，復原點目標）：最多能容忍遺失多少資料？**
用「時間」來衡量。
- 每天凌晨備份一次：如果晚上 11 點資料庫毀了，就會遺失當天將近 24 小時的資料。RPO 是 **24 小時**；
- 搭配 PostgreSQL 的 **WAL 持續歸檔**（第 58 課提過預寫式日誌）：把每一筆變更的日誌持續保存下來，可以還原到**任意時間點**（Point-in-Time Recovery），RPO 可以縮短到 **幾分鐘以內**。

**RTO（Recovery Time Objective，復原時間目標）：要多久才能恢復服務？**
從災難發生，到服務恢復正常，最多可以花多久。例如 RTO = 30 分鐘。

**比喻：**寫報告時的存檔習慣。
- RPO 是「**最後一次存檔是多久以前**」。每 5 分鐘自動存檔，電腦當機最多損失 5 分鐘的進度；
- RTO 是「**電腦當機後，多久能回到工作狀態**」。重新開機、打開檔案、找回進度，要花多少時間。

RPO 和 RTO 越短，成本越高。和第 70 課的 SLO 一樣，要依業務需求決定。期末成績的資料，RPO 可能要求幾分鐘；課程的瀏覽統計，丟一天也許無所謂。

**備份的基本原則：**
- **備份要和正本分開存放**：同一顆硬碟上的備份，硬碟壞了就一起沒了。至少要放在**不同的機器、不同的地點**；
- **備份要加密**，並且**解密的金鑰要另外妥善保存**；
- **要有多份、多個時間點**：如果只保留最新一份，而資料在三天前就已經被悄悄破壞了，最新的備份也是壞的；
- **要防止被刪除或竄改**：勒索軟體攻擊時，攻擊者常常**先刪除備份**再加密資料。

@section 鐵律：沒有測試過還原的備份，等於沒有備份
這是這一課**最重要的一句話**。

現實中，無數團隊在災難發生的那一天打開備份，才發現：
- 備份腳本好幾個月前就壞了，產生的全是 **0 位元組的空檔案**；
- 備份是加密的，但**解密金鑰找不到了**；
- 備份只包含了部分資料表；
- 還原需要 **12 小時**，遠超過所有人的預期；
- 沒有人知道還原的步驟，唯一知道的人已經離職。

**比喻：**消防演習。大樓有逃生梯，但如果從來沒演習過，真的失火時，大家可能發現逃生門被雜物堵住了、沒人知道集合點在哪裡。**備份是逃生梯，還原演練是消防演習。**

**還原演練怎麼做？**
1. 取出最新的備份檔；
2. **在一個全新、隔離的環境**中還原（**絕對不要在正式資料庫上測試還原**！一個指令打錯，正式資料就被覆蓋了）；
3. 驗證資料的完整性：核對重要資料表的筆數、最新一筆資料的時間；
4. **計時**：整個還原過程花了多久？符合 RTO 嗎？
5. 把步驟寫成「**操作手冊**」（Runbook），讓任何值班的人都能照著做。

**定期自動執行**，例如每個月一次。把它當成 CI 的一部分（第 69 課），失敗就告警。

@section 可回退的部署
新版本部署 3 分鐘後，監控發現錯誤率飆升（第 66 課）。第一個反應應該是：**立刻回退到上一個版本**（第 69 課的不可變產物讓這件事很容易），再慢慢查原因。

**但如果新版本同時修改了資料庫結構，回退可能會失敗。**

**情境：**新版本 v2 在部署時，把資料表的欄位 `name` 改名成 `full_name`。
- v2 出問題，你把程式回退到 v1；
- v1 的程式還在查詢 `SELECT name FROM users`；
- 但資料庫裡已經沒有 `name` 欄位了；
- **v1 也跟著崩潰。連回退都回不去。**

**解法：「先擴充、再收斂」**（Expand and Contract，第 69 課介紹過）。

**第一階段：擴充（新舊相容）。**
- 只**新增** `full_name` 欄位，**不刪除也不改名** `name`；
- v2 同時寫入兩個欄位，讀取時優先用新欄位；
- 這時候 v2 出問題，隨時可以回退到 v1：v1 用的 `name` 欄位還在，完全不受影響。

**第二階段：收斂。**
- 等 v2 穩定運作幾天，確認**不會再需要回退到 v1**；
- 在**下一次獨立的部署**中，才刪除舊的 `name` 欄位。

**原則：每一次部署，都要能安全地回退到上一個版本。**資料庫的破壞性變更，永遠和程式碼的變更**分開**，而且放在最後。

@section 走一遍：兩場演練
**演練一：外部 LLM 服務大規模故障。**
- **狀況**：上游 LLM 全球故障，所有請求超過 8 秒後回傳 503；
- **系統的反應**：
  1. API 設定了 5 秒逾時，最多重試 1 次（帶退避）；
  2. 30 秒內累積 5 次失敗，斷路器**斷開**；
  3. 學生點擊「提交作業並請 AI 檢查」：作業本體在 20 毫秒內**成功寫入**資料庫；AI 檢查部分由斷路器**立刻降級**，標記為「待服務恢復後補做」，放入佇列（第 76 課）；
  4. 前端清楚顯示：「您的作業已安全收件！AI 建議將在服務恢復後補發。」
- **結果**：核心的繳交功能**完全不受影響**。LLM 恢復後，斷路器經過半開狀態試探成功，回到閉合；佇列中待補做的 AI 檢查陸續完成。

**演練二：每月例行的備份還原驗證。**
1. 用 `pg_dump` 產生加密的備份檔；
2. 自動化腳本啟動一個**全新的隔離容器**（第 67 課）；
3. 用 `pg_restore` 還原；
4. 執行驗證：核對 users、courses、submissions 的筆數，以及最新一筆資料的時間；
5. **計時**：總共 4 分 12 秒，符合 RTO ≤ 30 分鐘的目標；
6. 結果寫入日誌，失敗則告警。

@section 常見陷阱
**陷阱一：無限等待。**沒設逾時，一個外部服務卡住就拖垮全站。

**陷阱二：無延遲、多層、無限次的重試。**讓過載的服務永遠無法恢復。

**陷阱三：在正式資料庫上測試還原。**一個指令打錯，正式資料就被覆蓋。

**陷阱四：備份和正本放在一起。**同一台機器、同一個雲端帳號，一起被毀。

**陷阱五：從不演練。**操作手冊過時了、步驟沒人會、金鑰找不到，都要到真正出事才發現。

**陷阱六：資料庫的破壞性變更和程式碼一起部署。**回退時舊程式找不到欄位而崩潰。

@section 工程篇的結語
回顧工程篇的 33 課，從一個 Python 函式（第 48 課），到一個能承受故障、能安全回退的完整系統。你會發現，越到後面，主題越少是「怎麼寫出能跑的程式」，越多是：
- **資料從哪裡來，能不能信任？**（驗證、注入、信任邊界）
- **出錯時會怎樣？**（錯誤處理、重試、降級、備份）
- **多人、多台機器、長時間之後，還正確嗎？**（交易、並行、快取一致性、ADR）
- **怎麼知道它是對的？**（測試、CI、監控、演練）

這也正是 AI 主線第 47 課「架構師」的視角：**AI 讓寫程式變得很快，但判斷「什麼是對的、哪裡會壞、壞了怎麼辦」，仍然是人的責任。**

@section 動動腦：判斷看看
**題一**：呼叫外部 LLM API 時沒有設定逾時，可能造成什麼後果？
→ 上游卡住時所有工人都在等待，連無關的功能也無法處理，造成整站連鎖故障。

**題二**：斷路器斷開時，系統應該怎麼回應使用者？
→ 立即回傳降級結果（例如提示 AI 功能暫停、核心功能照常），而不是讓每個請求等待逾時。

**題三**：每天凌晨備份一次，RPO 大約是多少？要縮短該怎麼做？
→ 約 24 小時；可搭配 WAL 持續歸檔實現時間點還原，將 RPO 縮短到數分鐘。

**題四**：新版本把欄位 `name` 改名為 `full_name` 並一起部署，出問題時回退會怎樣？
→ 舊版程式找不到 `name` 欄位而崩潰；應先新增欄位、新舊並存，穩定後再於獨立部署中刪除舊欄位。

**題五**：「我們每天都有自動備份，所以資料很安全」這句話缺了什麼？
→ 缺了定期在隔離環境實際還原並驗證；沒有測試過還原的備份，等於沒有備份。

@section 本課重點整理
- **所有東西都會壞**：目標是影響小、恢復快、資料不遺失。
- **逾時**：所有跨網路呼叫都要設定，避免連鎖故障。
- **重試風暴**：只重試暫時性錯誤與冪等操作、限制次數、退避加抖動、只在一層重試。
- **斷路器**：閉合、斷開、半開三種狀態；失敗率過高時立即降級，保護系統並讓下游恢復。
- **優雅降級**：區分核心與非核心功能，非核心壞了核心照常運作。
- **RPO** 是可容忍遺失多少資料，**RTO** 是多久恢復服務；依業務需求決定。
- **備份**要異地存放、加密、多個時間點、防刪除。
- **鐵律**：沒有測試過還原的備份等於沒有備份；在隔離環境定期演練並計時。
- **可回退的部署**：資料庫變更採先擴充、再收斂，每次部署都要能安全退回上一版。

@term 可靠性工程
設計系統使其在故障時影響小、恢復快、資料不遺失的工程實踐（Reliability Engineering）。
@term 逾時
等待回應的時間上限，超過即放棄（Timeout）。
@term 連鎖故障
一個元件的故障擴散，拖垮其他元件甚至整個系統（Cascading Failure）。
@term 重試風暴
大量請求在失敗後同時重試，使過載的服務更無法恢復（Retry Storm）。
@term 斷路器
外部服務失敗率過高時自動停止呼叫並立即降級的機制（Circuit Breaker）。
@term 半開
斷路器允許少量請求試探外部服務是否恢復的狀態（Half-Open）。
@term 優雅降級
部分功能故障時，以較陽春但仍可用的方式繼續提供服務（Graceful Degradation）。
@term RPO
災難時最多可容忍遺失多久的資料（Recovery Point Objective）。
@term RTO
災難發生到服務恢復所允許的最長時間（Recovery Time Objective）。
@term 時間點還原
利用持續歸檔的日誌，將資料庫還原到任意時間點（Point-in-Time Recovery）。
@term 還原演練
定期在隔離環境實際還原備份並驗證的程序（Restore Drill）。
@term 操作手冊
記錄故障處理或維運步驟、讓任何人都能照著執行的文件（Runbook）。
@term 回退
將系統恢復到上一個正常版本（Rollback）。
