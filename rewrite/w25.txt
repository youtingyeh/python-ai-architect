@section 開場：資料也有一生
初學資料庫時，我們關心的是「怎麼建表、怎麼 INSERT、怎麼 SELECT」。但當你負責一個真正營運的系統時，真正的挑戰在於資料的**一生**：它怎麼誕生、怎麼改變、最後怎麼退場。這叫做「**資料生命週期**」（Data Lifecycle）。

想像一個每天都會發生的情境：**一位學生在學期中申請刪除帳號。**

**做法 A：直接刪除，並且到處設了 `ON DELETE CASCADE`（第 53 課）。**
刪掉帳號的那一秒，連帶消失的還有：
- 他在小組專題中繳交的作業：**同組同學的成果跟著不見了**；
- 他在討論區的問答：其他人的回覆變成在回應一個不存在的問題；
- 選課人數統計、成績稽核紀錄、學費付款紀錄：**財務對帳對不起來**。

**做法 B：什麼都不刪。**
違反個資保護法規（例如歐盟的 GDPR、台灣的個資法），使用者有權要求刪除個人資料。

**AI 系統還有一個特有的問題：**老師把一份寫錯的舊講義換成新版，但 RAG 知識庫（第 25 課）裡**舊講義的向量還在**。AI 助教繼續拿已經作廢的內容回答學生的問題。

**資料架構**（Data Architecture）就是要從整體思考：
1. **誰擁有**這筆資料？哪裡是它的「正本」？
2. 它會經歷哪些**狀態**？
3. 更新時，要不要**保留歷史**？衍生的資料（例如向量索引）怎麼同步？
4. **刪除**時，該真刪、假刪，還是去除個人識別？
5. 各種資料要**保存多久**？

@section 支柱一：單一真相來源
**每一種資料，都必須有一個唯一的「正本」。**這叫做「**單一真相來源**」（Single Source of Truth）。

以學習平台的教材為例：
- **正本**：PostgreSQL 的 `course_documents` 表，存著講義的內容和狀態；
- **衍生資料**：向量資料庫裡的切塊嵌入（第 24 課）、快取（第 71 課）、搜尋索引。

衍生資料是**從正本計算出來的「副本」**，目的是加速讀取。它們**不是**正本。

**規則：修改時，先改正本，再更新（或作廢）衍生資料。絕不能只改其中一邊。**

只改了向量庫、沒改正本？下次重建索引時，修改就消失了。只改了正本、沒更新向量庫？AI 就繼續引用舊內容，這就是開場說的問題。

**比喻：**公司的**員工名冊正本**在人資部門。各部門可能有自己的通訊錄副本，方便查找。但有人離職時，必須先更新人資的正本，再通知各部門更新副本。如果各部門各改各的，很快就沒人知道哪份才是對的。

**判斷「誰是正本」的問題：**如果所有衍生資料都消失了，能不能從正本重建回來？能的話，關係就是對的。向量索引可以從講義重新計算；但講義不能從向量索引還原。所以講義是正本。

@section 支柱二：三種刪除方式
「刪除」不是只有一種。依照資料的性質，有三種做法。

**一、硬刪除（Hard Delete）：真的從資料庫移除。**
```
DELETE FROM drafts WHERE id = 7;
```
適用於：**沒有被其他紀錄參照、沒有保存價值**的資料。例如：
- 還沒送出的個人草稿；
- 過期的密碼重設 token（第 59 課）；
- 過期的暫存檔。

**二、軟刪除（Soft Delete）：標記為已刪除，但資料還在。**
```
UPDATE courses SET deleted_at = now() WHERE id = 101;
```
加一個 `deleted_at` 欄位（或 `status = 'archived'`）。資料還在資料庫裡，只是「**看不到**」了。

適用於：需要下架、但**仍被歷史紀錄參照**的資源。例如：一門課下架了，但修過這門課的學生成績單上，仍然要顯示課程名稱。

**關鍵：所有一般查詢都必須加上過濾條件：**
```
SELECT * FROM courses WHERE deleted_at IS NULL;
```
包括 RAG 檢索！向量搜尋也要排除已下架的文件。漏掉一處，被「刪除」的資料就會從那裡冒出來。

**比喻：**軟刪除像把書從圖書館的**開架區**移到**閉架書庫**。讀者在書架上找不到了，但館員在需要時還能調出來。

**三、去識別化（Anonymization）：抹除個人資料，保留紀錄的骨架。**
這是處理「**刪除帳號**」申請的常見做法：
```
UPDATE users SET
  email = 'deleted-user-8f9a@anonymized.invalid',
  real_name = NULL,
  avatar_url = NULL,
  status = 'deleted',
  deleted_at = now()
WHERE id = 42;
```
- 能識別出這個人的資訊（姓名、Email、照片、電話）被**抹除**；
- 主鍵 `id = 42` **保留**，所以他繳交過的作業、成績紀錄仍然完整，外鍵關係不會斷裂；
- 前端顯示名稱變成「**已註銷的使用者**」。

這樣**兼顧**了兩件事：使用者的隱私權，以及其他人的資料完整性（同組同學的專題、班級的成績統計）。

**比喻：**一份歷史合照中，有人要求不要被認出來。做法不是把整張照片燒掉（其他人的回憶也沒了），而是把他的臉**模糊處理**。

注意：去識別化要做得**徹底**。只刪了姓名，但保留了學號和生日，組合起來仍然可能認出是誰。哪些資料該處理，需要依法規和實際情況判斷。

@section 刪除策略和外鍵的搭配
第 53 課學過外鍵的刪除行為，現在可以把它和刪除策略對應起來：

**`ON DELETE RESTRICT`：核心業務紀錄的預設選擇。**
使用者或課程底下已經有作業、成績時，資料庫**直接拒絕**硬刪除。這會**強迫**應用程式走正規的軟刪除或去識別化流程，而不是一不小心就把一切抹除。

**資料庫約束在這裡扮演「安全網」：**就算某位工程師寫錯程式，試圖硬刪除一個有成績的學生，資料庫也會擋下來（第 52 課的「最後一道防線」）。

**`ON DELETE CASCADE`：只用於「主體消失，它就毫無意義」的附屬資料。**
例如刪除一篇尚未發布的草稿時，連帶刪除這篇草稿的標籤關聯。草稿都沒了，標籤關聯自然沒有存在的必要。

**`ON DELETE SET NULL`：保留紀錄，但切斷關聯。**
例如負責批改的助教帳號被移除時，已批改紀錄的 `graded_by` 欄位設為空值，**但分數本身不能消失**。

@section 支柱三：不可變的稽核紀錄
對於**重要**的修改，例如成績變更、權限調整、AI 批改的人工覆核，不能只用 `UPDATE` 把舊值蓋掉。

**問題情境：**期末時，某位學生的成績從 58 分變成 62 分（剛好及格）。是誰改的？什麼時候？為什麼？如果只有 `UPDATE`，舊值 58 就永遠消失了，沒人能回答這些問題。

**做法：在同一個交易中，同時寫入一筆稽核紀錄。**
```
BEGIN;
UPDATE grades SET score = 62 WHERE id = 501;
INSERT INTO audit_logs
  (actor_id, action, target_id, old_value, new_value, created_at)
VALUES
  (7, 'grade.update', 501, '58', '62', now());
COMMIT;
```
- 用**交易**包起來（第 54 課）：兩件事要嘛都成功、要嘛都不發生。不能成績改了，紀錄卻沒寫進去；
- `audit_logs` 是「**只增不改**」（Append-only）的表：只能新增，**不能修改、不能刪除**。可以透過資料庫權限設定，讓應用程式對這張表只有新增權限。

**比喻：**銀行存摺。你的餘額會變，但每一筆存入、提出都**逐行記錄**，而且已印上的紀錄不能塗改。有錯誤時，是**新增一筆更正**，而不是擦掉舊的那一行。

稽核紀錄和第 62 課的日誌不同：日誌是給工程師除錯用的，可以定期清除；稽核紀錄是**業務和法規上的證據**，通常要保存很多年，而且要防止竄改。

@section 支柱四：資料保存期限
**每一類資料，都要明確規定保留多久。**這叫做「**保存政策**」（Retention Policy）。

一個例子：
- 應用程式的除錯日誌：**30 天**；
- AI 對話的快取：**90 天**；
- 使用者上傳的暫存檔：**7 天**；
- 正式的學期成績與稽核紀錄：**7 年**（依教育或會計法規）。

**為什麼不全部永久保存？**
- **風險**：資料保存越久、越多，外洩時的損失就越大。**不存在的資料，不會外洩；**
- **法規**：很多個資法規要求「資料只能在必要期間內保存」；
- **成本**：儲存和備份都要錢，查詢也會變慢。

**為什麼不全部早早刪除？**
- 法規可能要求**最少保存**一段時間（例如財務紀錄）；
- 業務需要（例如學生畢業多年後申請成績單）。

保存政策要**自動執行**：例如每天跑一個排程工作，刪除超過期限的日誌。靠人記得「每個月去清一下」，一定會忘。

**AI 特別注意：**使用者和 AI 的對話紀錄常常包含很多個人資訊。要明確決定：保存多久？會不會拿來訓練或微調模型（第 31 課）？使用者知不知道？這也是第 19 課負責任 AI 的一部分。

@section 走一遍：兩個常出事的情境
**情境一：學生 #42 申請註銷帳號。**
在**同一個交易**中：
1. 撤銷他所有的登入 Session（第 59 課）；
2. **硬刪除**他還沒送出的作業草稿；
3. **去識別化** users 表中他的個人資料，標記為已刪除；
4. 寫入一筆稽核紀錄：「使用者 42 於某時申請刪除，已完成去識別化」。

結果：他過去已繳交的作業和成績**完整保留**，班級平均分數不受影響，同組同學的專題也還在；但畫面上顯示的是「已註銷的使用者」，沒有任何能認出他的資訊。

**情境二：老師更新了寫錯的講義。**
1. 舊講義標記為封存（軟刪除，`archived_at = now()`）；
2. 上傳新版講義；
3. 背景工作（第 72 課）**刪除舊講義對應的向量**，並為新講義產生向量；
4. RAG 檢索一律加上 `WHERE archived_at IS NULL` 的過濾條件。

雙重保險：就算背景工作延遲了幾分鐘還沒刪掉舊向量，檢索時的過濾條件也會擋住它。學生問 AI 助教時，**絕對不會**再拿到已作廢的舊內容。

這種「正本已刪、但衍生資料還留著」的向量，有人戲稱為「**殭屍向量**」。

@section 常見陷阱
**陷阱一：到處濫用 CASCADE。**
在 users 和 courses 底下一路設 CASCADE。某天管理員誤刪一個「測試帳號」，結果那其實是某位老師的帳號，他開的所有課、所有學生的作業和成績，**一秒鐘內全部消失**。

**陷阱二：用了軟刪除，卻忘了調整查詢和唯一約束。**
- **查詢**：某個報表、某個 API、某個 RAG 檢索忘了加 `deleted_at IS NULL`，被刪除的資料就從那裡冒出來；
- **唯一約束**：學生退選某門課（選課紀錄被軟刪除），之後想再次加選，卻被第 53 課的組合唯一約束擋下：「你已經選過了！」因為那筆軟刪除的紀錄還在。解法之一是 PostgreSQL 的「**部分索引**」：唯一約束只套用在 `deleted_at IS NULL` 的資料上。

**陷阱三：只刪了正本，忘了副本。**
使用者的資料刪了，但還留在：快取、搜尋索引、向量資料庫、日誌、備份、匯出到分析系統的檔案裡……個資刪除要**追蹤所有副本**。這也是為什麼「單一真相來源」和「知道有哪些衍生資料」這麼重要。

**陷阱四：稽核紀錄可以被修改。**
如果應用程式能 UPDATE 或 DELETE 稽核紀錄，那它就不是可信的證據。

@section 動動腦：判斷看看
**題一**：學生申請刪除帳號，但他有小組作業和成績紀錄，該怎麼處理？
→ 去識別化：抹除可識別個人的資料，保留主鍵與作業、成績紀錄，維持其他人資料的完整性。

**題二**：採用軟刪除後，最容易忘記的是什麼？
→ 所有查詢（包括報表與 RAG 檢索）都要加上排除已刪除資料的條件，唯一約束也要配合調整。

**題三**：老師更新講義後，AI 助教仍引用舊內容，最可能的原因是什麼？
→ 正本更新了，但向量索引（衍生資料）沒有同步刪除舊版，檢索時也沒有過濾封存的文件。

**題四**：為什麼成績修改要另外寫入只增不改的稽核紀錄？
→ UPDATE 會覆蓋舊值；稽核紀錄保留誰、何時、從什麼改成什麼，作為可追查、不可竄改的證據。

@section 本課重點整理
- **資料生命週期**：誕生、改變、退場都要設計，不只是建表和查詢。
- **單一真相來源**：每種資料有唯一正本；向量索引、快取是衍生資料；先改正本再同步副本。
- **三種刪除**：硬刪除（無參照的暫存資料）、軟刪除（下架但仍被參照）、去識別化（刪帳號時保留紀錄骨架）。
- **外鍵搭配**：核心紀錄用 RESTRICT 當安全網；CASCADE 只給純附屬資料；SET NULL 保留紀錄切斷關聯。
- **稽核紀錄**：與修改在同一交易寫入；只增不改，作為長期證據。
- **保存政策**：每類資料明訂保存期限並自動執行；不存在的資料不會外洩。
- **陷阱**：濫用 CASCADE、軟刪除忘了改查詢和唯一約束、只刪正本忘了副本、稽核紀錄可被修改。

@term 資料架構
從擁有權、生命週期、同步與保存等面向，整體規劃系統資料的設計（Data Architecture）。
@term 資料生命週期
資料從建立、修改、封存到刪除的完整歷程（Data Lifecycle）。
@term 單一真相來源
每種資料只有一個權威正本，其他皆為衍生副本（Single Source of Truth）。
@term 衍生資料
從正本計算而來、用於加速讀取的資料，如向量索引、快取（Derived Data）。
@term 硬刪除
真正從資料庫移除資料（Hard Delete）。
@term 軟刪除
以欄位標記資料為已刪除，資料仍保留在資料庫（Soft Delete）。
@term 去識別化
抹除能辨識個人的資訊，但保留紀錄結構（Anonymization）。
@term 稽核紀錄
記錄誰在何時做了什麼修改、只增不改的紀錄（Audit Log）。
@term 只增不改
資料只能新增、不能修改或刪除的特性（Append-only）。
@term 保存政策
規定各類資料保留期限與到期處理方式的規則（Retention Policy）。
@term 殭屍向量
正本已刪除或作廢，但仍殘留在向量索引中的嵌入資料。
@term 部分索引
只對符合條件的資料列建立的索引，如只對未刪除資料套用唯一約束（Partial Index）。
@term GDPR
歐盟的一般資料保護規則，賦予個人刪除個資等權利。
