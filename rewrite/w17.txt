@section 開場：登入了，然後呢？
上一課，系統終於知道「你是誰」了。但這只解決了一半。

想像這個情境：學生 A 登入後，打開自己的作業頁面，網址是：
```
GET /submissions/1041
```
他好奇地把 1041 改成 1042，按下 Enter。結果：**他看到了同學的作業和成績**。

系統只檢查了「你有沒有登入」，卻沒檢查「**這份作業是不是你的**」。這種漏洞叫做 **IDOR**（Insecure Direct Object Reference，不安全的直接物件參照），第 42 課的程式碼審查也提過它。

它有多常見？資安組織 OWASP 的 2021 年十大風險排行中，「**存取控制失效**」（Broken Access Control）高居**第一名**，報告指出受測的應用程式中，約 94% 被檢出某種形式的存取控制缺陷。

這類漏洞特別陰險：伺服器**不會當機**、**不會出現紅字**、功能**看起來完全正常**。所以常常上線很久之後才被發現。

**AI 系統讓問題更嚴重：**
- **RAG 跨租戶外洩**：多家公司共用一個知識庫系統，向量檢索（第 25 課）時忘了加上「只搜尋這家公司的文件」的條件，A 公司的機密文件就被塞進 B 公司使用者的提示詞裡，模型還會很有禮貌地引用它；
- **危險的管理功能**：重建索引、刪除向量庫、切換模型版本，被一般使用者呼叫到，影響是全站層級；
- **AI 生成的程式碼**通常只寫「能運作」的路徑，很少主動加上擁有權檢查。

這一課要學「**授權**」（Authorization）：
1. 授權決策的三個要素；
2. **RBAC**：用角色管理權限；
3. **垂直越權**與**水平越權**；
4. 401 和 403 的差別，以及 403 和 404 的取捨；
5. 用**權限矩陣**和**測試**把授權規則寫清楚。

@section 授權的三個要素：誰、做什麼、對誰
每一個授權決策，都在回答一個問題：
**「這個人（主體），能不能對這個東西（資源），做這件事（動作）？」**

- **主體**（Subject）：誰在做？例如 student#3；
- **動作**（Action）：做什麼？例如「讀取」、「批改」；
- **資源**（Resource）：對誰做？例如 submission#1041。

**比喻：**醫院的病歷系統。「王護理師（主體）能不能讀取（動作）李先生的病歷（資源）？」答案取決於：她是護理師（角色）、而且李先生是**她負責的病房**的病人（關係）。光是「她是護理師」還不夠，否則全院每個護理師都能看每個病人的病歷。

@section RBAC：用角色管理權限
最常見的授權模型是 **RBAC**（Role-Based Access Control，以角色為基礎的存取控制）。

它把關係拆成兩段：
- **使用者 → 角色**：Alice 是學生、王老師是教師；
- **角色 → 權限**：學生可以繳交作業、教師可以批改作業。

權限常用「`資源:動作`」的字串表示，例如 `submission:read`、`submission:grade`、`course:publish`。

**為什麼不直接在程式裡寫 `if role == "admin"`？**
因為這種判斷會**散落在程式碼各處**。哪天要新增「助教」角色，或調整某個角色的權限，你得翻遍整個專案，一定會漏掉某個地方。改用權限字串後，程式碼只問「這個人有沒有 `submission:grade` 權限」，至於哪些角色有這個權限，集中在**一張表**裡管理。

**權限矩陣：把規則寫成表格。**
迷你學習平台有 4 種角色、5 種操作：
```
               讀課程  繳作業  批改  發布成績  管理帳號
學生 student     ✓       ✓      ✕      ✕        ✕
助教 TA          ✓       ✕      ✓      ✕        ✕
教師 teacher     ✓       ✕      ✓      ✓        ✕
管理員 admin     ✓       ✕      ✕      ✕        ✓
```
4 × 5 = 20 個格子，每一格都是一個明確的「允許」或「拒絕」。再加上「課程 A 還是課程 B」這個維度，就需要 40 個以上的測試斷言才算完整覆蓋。

**授權規則如果沒有寫成表格和測試，就只存在於工程師的腦袋裡。而人腦，會在第三次需求變更時出錯。**

注意管理員那一列：管理員能管理帳號，但**不能批改作業**。「管理員什麼都能做」是常見的錯誤假設，「**最小權限原則**」（第 28 課）在這裡同樣適用。

@section 垂直越權與水平越權
只看角色還不夠。授權檢查分成兩種：

**垂直越權：低權限的人做了高權限的事。**
學生呼叫了只有管理員能用的「刪除帳號」API。RBAC 的角色檢查能擋住這種。

**比喻：**一般員工走進了董事長辦公室。

**水平越權：同樣角色的人，存取了別人的資料。**
學生 A 讀了學生 B 的作業。兩人**角色相同**，角色檢查會**通過**，但資料不是他的。這就是開場的 IDOR。

**比喻：**你住在 5 樓 3 號房，用你的鑰匙打開了 5 樓 4 號房。你確實是這棟大樓的住戶（角色對了），但那不是你的房間。

**完整的授權判斷公式：**
**身分有效 ∧ 角色擁有該權限 ∧ 與資源的關係成立**

（`∧` 是「而且」的意思，三個條件都要成立。）

前兩項擋垂直越權，第三項擋水平越權。**很多系統只做了前兩項。**

「關係」的例子：
- 學生只能看**自己的**作業（`submission.student_id == 目前使用者`）；
- 助教只能批改**被指派的課程**的作業；
- 教師只能發布**自己開的課**的成績。

@section 401 vs. 403：兩種不同的「不行」
**401 Unauthorized：我不知道你是誰。**
沒帶登入憑證，或憑證無效、過期了。前端看到 401，應該**導向登入頁**。

（名字雖然叫 Unauthorized，意思其實是「**未通過身分驗證**」，這是 HTTP 歷史留下的命名混亂。）

**403 Forbidden：我知道你是誰，但你不能做這件事。**
前端看到 403，應該顯示「**您沒有權限**」，重新登入也沒用。

如果兩種情況回傳同一個狀態碼，前端就無法判斷該做什麼：使用者明明登入了，卻一直被踢回登入頁。

**比喻：**401 像大樓警衛說「請出示證件」；403 像警衛看了證件後說「王先生，您好，但您的門禁沒有開放這一層」。

@section 403 還是 404？隱藏存在性
學生 B 想讀學生 A 的作業 1041。該回 403 還是 404？

**回 403**：「這份作業存在，但你不能看。」這**洩漏了一個資訊**：1041 號作業**存在**。攻擊者可以逐一嘗試編號，掃出哪些資源存在。

**回 404**：「找不到。」從攻擊者的角度，看不出是「不存在」還是「沒權限」，**隱藏了存在性**。代價是除錯比較困難：客服接到「我找不到作業」的回報時，不容易知道真正原因。

**折衷做法：**
- 結構公開的端點（例如大家都知道 `/admin` 存在）：回 403；
- 使用者私有的資源：回 404，同時在**伺服器端的稽核日誌**記下真正原因（「user=4 試圖讀取 1041，因不是擁有者被拒絕」），方便日後追查。

@section 實作原則：預設拒絕，把條件寫進查詢
**原則一：預設拒絕（Deny by Default）。**
權限表**沒有明確列出**的組合，一律**不允許**。授權函式出錯時（例如查資料庫失敗），也要走「拒絕」的路，而不是「放行」。這叫做「**故障時關閉**」（Fail Closed）。

**比喻：**門禁系統斷電時，門應該**鎖住**，而不是全部打開。（不過消防逃生門例外，那是另一種考量。）

**原則二：身分和角色只能來自伺服器。**
`user_id` 和 `role` **一律**從伺服器驗證過的 Session（第 59 課）取得。**絕對不要**從請求內容、網址參數，或像 `X-User-Role: admin` 這種自訂標頭讀取。那些都是使用者能隨意竄改的東西。

**原則三：把授權條件直接寫進 SQL 查詢。**
**容易漏掉的寫法：**
```
sub = db.get_submission(1041)          # 先查出來
if sub.student_id != current_user.id:  # 再判斷
    raise NotFound()
```
**更安全的寫法：**
```
SELECT * FROM submissions
WHERE id = %s AND student_id = %s
```
一次完成「取資料」和「檢查擁有權」。查不到就是 404，不會發生「先拿出來、忘了檢查」的情況。

**原則四：列表也要過濾。**
`GET /submissions/1041` 檢查了擁有權，但 `GET /submissions`（列出全部作業）忘了加 `WHERE student_id = ...`，一次就**洩漏所有人的資料**。

**AI 系統的對應：**RAG 檢索時，向量搜尋**一定要**帶上 `tenant_id`（租戶編號）或使用者權限的過濾條件。這正是第 25 課「權限要在檢索時過濾，而不是檢索後再過濾」的道理。

**原則五：權限變更要能即時生效。**
如果把角色寫在有效期 60 分鐘的 JWT 裡，被降權的使用者在最長 60 分鐘內仍然能用舊權限。敏感操作應該**重新查資料庫**確認當下的角色，這也是第 59 課偏好伺服器端 Session 的理由之一。

@section 走一遍：七個請求
迷你學習平台的資料：
- 課程 A 的教師是 teacher#2；課程 B 的教師是 teacher#9；
- ta#7 被指派到課程 A；ta#8 沒有；
- submission#1041 屬於 student#3，是課程 A 的作業。

**第一步：**沒登入，呼叫 `GET /submissions/1041` → **401**，資料庫完全沒被查詢。

**第二步：**student#4 呼叫同一網址 → 角色允許讀作業，但擁有權不符，查詢結果為空 → **404**，並寫入稽核日誌。

**第三步：**student#3 呼叫 → 是自己的作業 → **200**。

**第四步：**ta#8 呼叫 `PATCH /submissions/1041/grade`，內容 `{"score": 80}` → 他是助教（垂直通過），但沒被指派到課程 A（水平失敗）→ **拒絕**。

而且要額外確認：**資料庫的 score 欄位仍然是空的**。這個「沒有副作用」的檢查很重要。如果程式寫成「先寫入分數、再檢查權限、不通過才回 403」，只看狀態碼的測試會通過，但分數**已經被改掉了**。

**第五步：**ta#7 送出相同請求 → **200**，分數變成 80。

**第六步：**ta#7 送出 `{"score": 80, "role": "admin"}` → 第 51 課的 `extra="forbid"` 直接回 **422**。批量賦值被擋下，`role` 欄位根本不會被任何程式碼讀到。

**第七步：**teacher#9（課程 B 的老師）想發布課程 A 的成績 → **拒絕**（同角色、不同課程）；teacher#2 發布 → **成功**。

這七個步驟就是七個測試，其中**四個是「拒絕」案例**。一般人寫測試習慣只測「成功的路徑」，但授權系統的價值，恰恰在於它**正確地拒絕**。

@section 常見錯誤
**錯誤一：只在前端隱藏按鈕。**
學生的頁面上沒有「批改」按鈕，就以為學生不能批改。但攻擊者根本不用你的網頁，他直接用 curl 送請求（第 57 課也說過）。**前端隱藏按鈕是使用者體驗，不是安全措施。**

**錯誤二：只保護單筆，忘了列表、匯出、搜尋。**
資料可能從很多出口流出去：列表 API、CSV 匯出、搜尋結果、通知信件、AI 的回答。**每一個出口都要過濾。**

**錯誤三：只測成功案例。**
沒有「學生 B 讀不到學生 A 的作業」這條測試，哪天有人重構時不小心拿掉了擁有權檢查，所有測試照樣通過。

**錯誤四：相信客戶端送來的身分。**
從請求內容讀 `user_id`，攻擊者改一下數字就變成別人了。

@section 其他授權模型
RBAC 不是唯一的選擇：
- **ABAC**（以屬性為基礎）：用屬性寫規則，例如「同部門而且在上班時間內才能存取」。很有彈性，但規則難以窮舉測試；
- **ReBAC**（以關係為基礎）：依關係圖判斷，例如「是這份文件所在資料夾的編輯者」。適合 Google Docs 這類分享型產品；
- **ACL**（存取控制清單）：每個資源列一份名單，直觀但資源一多就難以管理。

RBAC 有個常見問題叫「**角色爆炸**」：為了「只能看課程 A 的助教」就新增一個角色，為了課程 B 又新增一個……角色多到管理不了。

對本教材的學習平台，建議用「**RBAC 加上資源關係檢查**」的混合式：角色處理「能做哪類事」，指派表和擁有者欄位處理「對哪些資料」。

@section 動動腦：判斷看看
**題一**：系統檢查了使用者已登入、角色是學生，就讓他讀取 `/submissions/{id}`，缺了什麼？
→ 缺了資源關係檢查（這份作業是否屬於他），會造成 IDOR 水平越權。

**題二**：沒登入和沒權限，分別該回什麼狀態碼？
→ 沒登入回 401（前端導向登入頁）；已登入但沒權限回 403（或對私有資源回 404 以隱藏存在性）。

**題三**：從請求標頭 `X-User-Role` 讀取角色，有什麼問題？
→ 使用者可以任意竄改；身分與角色只能來自伺服器驗證過的 Session。

**題四**：測試「助教批改未指派課程的作業會被拒絕」時，除了檢查狀態碼，還要檢查什麼？
→ 資料庫中的分數沒有被修改，確認拒絕時沒有產生副作用。

@section 本課重點整理
- **授權**回答「你能對哪個資源做什麼」；存取控制失效是 OWASP 第一名風險。
- **三個要素**：主體、動作、資源。
- **RBAC**：使用者 → 角色 → 權限；用權限字串與權限矩陣集中管理。
- **垂直越權**（低權限做高權限的事）vs. **水平越權**（同角色存取別人的資料，即 IDOR）。
- **完整判斷**：身分有效、角色有權限、與資源的關係成立，三者缺一不可。
- **401** 是不知道你是誰，**403** 是知道但不允許；私有資源可回 404 隱藏存在性，並寫稽核日誌。
- **實作原則**：預設拒絕、身分只來自伺服器、授權條件寫進查詢、列表與 RAG 檢索也要過濾。
- **測試**：大量的拒絕案例，並確認拒絕時沒有副作用。

@term 授權
確認身分後，決定使用者能對哪些資源做什麼事（Authorization）。
@term IDOR
只靠修改網址或參數中的編號，就能存取他人資料的漏洞（Insecure Direct Object Reference）。
@term 存取控制失效
系統未正確限制使用者能存取的功能或資料（Broken Access Control）。
@term RBAC
透過「使用者→角色→權限」管理存取權的模型（Role-Based Access Control）。
@term 權限矩陣
以角色為列、操作為欄，標示每格允許或拒絕的表格。
@term 垂直越權
低權限使用者執行了高權限才能做的操作。
@term 水平越權
同一角色的使用者存取了屬於他人的資料。
@term 403 Forbidden
已知使用者身分，但不允許執行該操作時的狀態碼。
@term 預設拒絕
未明確允許的操作一律拒絕的原則（Deny by Default）。
@term 故障時關閉
系統出錯時走向拒絕而非放行（Fail Closed）。
@term 稽核日誌
記錄誰在何時對什麼做了什麼、結果如何的紀錄（Audit Log）。
@term 多租戶
多個客戶共用同一套系統，但資料必須彼此隔離（Multi-tenancy）。
@term ABAC
依使用者、資源與環境屬性撰寫規則的授權模型（Attribute-Based Access Control）。
@term 角色爆炸
為了細微差異不斷新增角色，導致角色多到難以管理（Role Explosion）。
