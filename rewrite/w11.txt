@section 開場：10 筆資料時一切都很美好
在開發機上，你的資料表只有 10 筆測試資料，只有你一個人在點。任何寫得再隨便的 SQL，都能在 1 毫秒內跑完，也幾乎不可能遇到「寫到一半斷線」。

但系統上線後，資料表累積到 **100 萬筆**，每秒有 **200 個請求**同時湧入，兩個危機會一起爆發：

**危機一：效能懸崖。**某個「依名字找學生」的查詢，每次都得把 100 萬筆從頭翻到尾。一個請求還好，200 個請求同時來，資料庫的 CPU 瞬間衝到 100%，整個網站變得像在爬。

**危機二：寫到一半的髒資料。**轉帳分兩步：A 扣款、B 入帳。第一步成功了，第二步卻因為網路瞬斷或違反規則失敗了。結果：**錢憑空消失**。

這一課要學兩個解藥：
1. **索引**（Index）：讓查詢從「翻遍整本書」變成「查目錄」；
2. **交易**（Transaction）與 **ACID**：保證多個步驟「要嘛全部成功，要嘛全部沒發生」。

以及兩個重要的工程態度：
- 索引不是越多越好，它有代價；
- 效能不靠猜，要用 `EXPLAIN ANALYZE` **實際量測**。

@section 交易：同生共死的一組操作
第 52 課初步介紹過交易，這裡深入。

在 SQL 中，交易長這樣：
```
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```
- `BEGIN`：交易開始。之後的 SQL 會被打包成一組；
- `COMMIT`：全部成功，正式生效；
- 中途出錯時執行 `ROLLBACK`：**全部撤銷**，像什麼都沒發生過。

**比喻：**網購結帳。「扣款」、「扣庫存」、「建立訂單」三件事要嘛全部完成，要嘛全部沒發生。不能錢扣了、訂單卻沒建立；也不能訂單建立了、庫存卻沒扣，結果賣出不存在的商品。

在 Python 中，第 52 課的 `with psycopg.connect() as conn:` 區塊就是一個交易：正常結束自動 COMMIT，拋出例外自動 ROLLBACK。

@section ACID：交易的四個承諾
資料庫對交易做出四個承諾，取英文字首簡稱 **ACID**。

**A：原子性（Atomicity）——要嘛全有，要嘛全無。**
「原子」在古希臘文中是「不可分割」的意思。一個交易不可切開：不會只完成一半。PostgreSQL 靠「**預寫式日誌**」（WAL，Write-Ahead Log）做到：每個修改在真正寫入之前，先記錄在日誌裡，出事時可以依日誌撤銷或重做。

**C：一致性（Consistency）——交易前後都要符合規則。**
交易完成後，資料仍然滿足所有約束（主鍵、外鍵、CHECK）。

**但要特別注意：資料庫不會「猜」你的業務規則。**如果你沒在表上寫 `CHECK (balance >= 0)`，程式裡也沒檢查餘額，那把餘額扣成 `-500` 的交易，資料庫會**很誠實地成功提交**。一致性的前提是：**你有把規則告訴資料庫。**

**I：隔離性（Isolation）——同時進行的交易互不干擾。**
很多交易同時在跑，各自看到的資料應該像「一個接一個執行」一樣合理。隔離的程度可以調整，越嚴格越安全、但效能越差。

一個經典問題叫「**遺失更新**」（Lost Update）：兩個請求同時讀到餘額 100，各自扣 30 後寫回 70。結果扣了兩次，餘額卻只少了 30。重要的扣款操作，常用 `SELECT ... FOR UPDATE` **先鎖住**這一列，讓另一個請求排隊等候。

**D：持久性（Durability）——提交了就不會丟。**
`COMMIT` 一回傳成功，資料就已經寫進硬碟的日誌。即使下一秒伺服器斷電，重啟後資料仍在。

**比喻：**ACID 像銀行櫃台的四個保證：轉帳不會只做一半（A）、帳戶不會出現違規的負數（C，前提是銀行有訂這條規則）、兩個櫃員同時處理同一帳戶不會算錯（I）、收據給你之後帳就不會消失（D）。

@section 實驗一：看著交易回滾
`accounts` 表有 `CHECK (balance >= 0)`，帳戶 1 和帳戶 2 各有 100 元。我們故意做一個會失敗的轉帳：從帳戶 1 轉 150 元給帳戶 2。
```
BEGIN;
UPDATE accounts SET balance = balance + 150 WHERE id = 2;
-- 交易內看，帳戶 2 變成 250 了
UPDATE accounts SET balance = balance - 150 WHERE id = 1;
-- 帳戶 1 會變成 -50，違反 CHECK，報錯！
ROLLBACK;
```
執行 `SELECT id, balance FROM accounts;`：
```
id | balance
1  | 100
2  | 100
```
兩個帳戶都安全地維持 100 元。第一步「偷加」給帳戶 2 的 150 元被**乾淨地撤銷**了，沒有留下半套帳務。

**注意順序：**這裡故意先「加」後「扣」，就是要展示即使第一步已經成功，回滾也會一併撤銷它。

@section 索引：書的目錄
現在換第二個主題：查詢速度。

沒有索引時，資料庫要找 `name = 'Student_15000'`，只能**從第一筆看到最後一筆**，這叫「**循序掃描**」（Sequential Scan）。資料 100 筆時很快，100 萬筆時就很慢。

**索引**就像書後面的**索引頁**：想找「量子力學」這個詞，不用從第一頁翻到最後一頁，而是翻到索引頁，依注音或筆畫找到「量子力學：第 237 頁」，直接翻過去。

PostgreSQL 預設的索引結構叫 **B-Tree**（平衡樹）。不用深究細節，只要知道：
- 它把資料**排好順序**，並記錄每個值在哪裡；
- 找資料的步數從「全部 N 筆」變成大約「$\log N$ 步」。100 萬筆資料，循序掃描最多要看 100 萬筆，B-Tree 大約只要 20 步左右；
- 除了精確查找（`= 'Alice'`），也擅長範圍查找（`age BETWEEN 18 AND 25`）和排序（`ORDER BY`）。

建立索引：
```
CREATE INDEX students_name_idx ON students(name);
```
第 52 課提過：`PRIMARY KEY` 和 `UNIQUE` 會**自動**建立索引，不用另外建。

@section 索引的代價：為什麼不每個欄位都建？
知道索引能加速後，很多人的第一反應是：「那每個欄位都建索引就好啦！」

這是典型的工程取捨。**索引是用「額外的硬碟空間」和「更慢的寫入」換取「更快的讀取」。**

**代價一：空間。**每個索引都是一份額外的資料結構，要占用硬碟和記憶體。

**代價二：寫入變慢。**每次 `INSERT`、`DELETE`，或修改到有索引的欄位時，資料庫除了寫主表，還要**同步更新每一個索引**。一張表有 8 個索引，新增一筆資料就等於要寫 9 個地方。

**比喻：**一本書如果有「人名索引」、「地名索引」、「年代索引」、「主題索引」……查找非常方便。但每次出新版、增加一段內容，編輯就得把每一份索引都重新校對一遍。索引越多，改版越痛苦。

**原則：**
- 為**經常被查詢的條件**建索引（`WHERE`、`JOIN`、`ORDER BY` 常用到的欄位）；
- **寫入很頻繁、很少查詢**的表（例如日誌表），索引要少；
- 不要憑感覺建，要**量測**。

@section EXPLAIN ANALYZE：效能不靠猜
還有一個反直覺的事實：**有建索引，不代表查詢一定會用它；用了索引，也不代表一定比較快。**

PostgreSQL 有一個「**查詢最佳化器**」，會根據表的大小和資料分佈，估算哪種方式最快。例如：表只有 20 筆資料（全部塞在硬碟上的一小塊），直接整個讀完，反而比「先查索引、再跳去讀資料」更快。這時最佳化器會**選擇不用索引**，這是正確的決定。

所以判斷索引有沒有用，**不能用猜的**，要用 `EXPLAIN ANALYZE` 實際執行並看「**查詢計畫**」（Query Plan）。

**實驗二：兩萬筆資料，建索引前後對照。**

先產生兩萬筆測試資料：
```
INSERT INTO students (name, age)
SELECT 'Student_' || g, (g % 80) + 18
FROM generate_series(1, 20000) AS g;
ANALYZE students;   -- 更新統計資訊，讓最佳化器知道資料長怎樣
```

**建索引前：**
```
EXPLAIN ANALYZE SELECT * FROM students WHERE name = 'Student_15000';
```
結果顯示 `Seq Scan on students`（循序掃描），`Rows Removed by Filter: 19999`（看了兩萬筆、丟掉 19999 筆），約 **3.8 毫秒**。

**建索引後：**
```
CREATE INDEX students_name_idx ON students(name);
EXPLAIN ANALYZE SELECT * FROM students WHERE name = 'Student_15000';
```
結果變成 `Index Scan using students_name_idx`（索引掃描），直接找到那 1 筆，約 **0.08 毫秒**。快了將近 50 倍！資料量越大，差距越驚人。

**一個危險的提醒：**`EXPLAIN ANALYZE` 會**真的執行**那條 SQL。如果你拿它去量測 `DELETE`，資料就**真的被刪了**。量測寫入語句時，一定要包在交易裡再回滾：
```
BEGIN;
EXPLAIN ANALYZE DELETE FROM students WHERE age > 90;
ROLLBACK;
```

這和第 29 課 LLMOps 的精神一樣：**不量測，就不知道改動到底有沒有效。**

@section 常見陷阱
**陷阱一：在交易裡呼叫外部服務。**
```
BEGIN
  寫入一筆訂單
  呼叫 LLM API 產生摘要（要等 10 秒）
  更新訂單摘要
COMMIT
```
這 10 秒裡，交易一直**占著一條資料庫連線**，還**鎖住**相關的資料列。只要同時來 20 個這種請求，資料庫連線就被占光，其他所有請求都在排隊，整個網站卡死，這叫做**雪崩**。

**正確做法：先在交易外完成慢的外部呼叫（LLM、寄信、上傳檔案），最後只開一個幾毫秒的短交易寫入結果。交易越短越好。**

**陷阱二：吞掉錯誤後繼續用同一個交易。**
在 PostgreSQL 中，交易裡**任何一條 SQL 失敗**，整個交易就被標記為「已中止」。之後在這個交易裡執行的任何 SQL，都會得到這個錯誤：
```
current transaction is aborted, commands ignored until end of transaction block
```
如果你用 `try...except` 把第一個錯誤吞掉（第 45 課說過別這樣做），然後繼續執行下一條 SQL，就會一直看到這個莫名其妙的錯誤。**出錯就 ROLLBACK，重新開始。**

**陷阱三：讓索引失效的寫法。**
索引建在 `name` 上，但查詢寫成：
- `WHERE lower(name) = 'alice'`：對欄位套了函式，索引裡存的是原始值，對不上；
- `WHERE name LIKE '%Alice%'`：開頭是萬用字元，不知道從哪裡開始找。

**比喻：**字典依開頭字母排序。找「apple」很快；找「中間有 ppl 的字」，字典的排序就幫不上忙，只能一頁頁翻。

解法：如果真的常用 `lower(name)` 查詢，可以建「**運算式索引**」：`CREATE INDEX ON students (lower(name));`。至於模糊搜尋，需要專門的全文檢索工具。

**陷阱四：只在小資料上測效能。**
10 筆資料上什麼都很快，量不出差別。效能測試要在**接近真實資料量和分佈**的環境進行。

@section 常見疑問
**問：我怎麼知道哪些欄位該建索引？**
答：從「實際的查詢」出發，而不是從「表的欄位」出發。列出系統最常執行、最慢的那幾條 SQL，看它們的 `WHERE`、`JOIN`、`ORDER BY` 用了哪些欄位。PostgreSQL 有個統計外掛 `pg_stat_statements`，會告訴你哪些查詢累計耗時最多，從那裡下手最有效。外鍵欄位（例如 `enrollments.course_id`）也常常需要索引，因為「查某門課的所有選課紀錄」是很常見的查詢，而 PostgreSQL **不會**自動幫外鍵建索引。

**問：多個欄位一起查，要建幾個索引？**
答：可以建「**複合索引**」，例如 `CREATE INDEX ON enrollments (course_id, enrolled_at);`，適合「某門課、某段時間內加選的學生」這類查詢。順序很重要：它像電話簿先依「姓」排、再依「名」排。只知道姓可以查；只知道名，這本電話簿就幫不上忙了。所以最常單獨出現的欄位要放前面。

**問：交易一定要手寫 BEGIN 嗎？**
答：在 Python 中通常不用。`with psycopg.connect() as conn:` 已經幫你包好了；之後學的 ORM（例如 SQLAlchemy）也有類似的 `session` 機制。重點不是語法，而是**你要清楚知道交易的邊界在哪裡**：哪些操作在同一個交易裡、什麼時候提交。

**問：隔離等級要怎麼選？**
答：初學階段用 PostgreSQL 預設的「讀已提交」（Read Committed）即可，它能避免讀到別人還沒提交的資料。真正需要防止並行衝突的地方（扣款、扣庫存、搶座位），再針對那幾段使用 `SELECT ... FOR UPDATE`，或用資料庫約束（第 53 課的組合唯一）直接擋住重複。與其全域調高隔離等級，不如精準保護關鍵的幾個地方。

@section 動動腦：判斷看看
**題一**：轉帳交易中，入帳成功、扣款卻違反 `CHECK` 失敗，ROLLBACK 後兩個帳戶的餘額是多少？
→ 都回到原本的值。原子性保證已成功的入帳也會一併撤銷。

**題二**：表上沒有 `CHECK (balance >= 0)`，程式也沒檢查，把餘額扣成負數的交易會成功嗎？
→ 會。資料庫的一致性只守你定義的規則，不會自動猜出業務規則。

**題三**：一張每秒寫入上千筆、幾乎不查詢的日誌表，要不要每個欄位都建索引？
→ 不要。每個索引都會拖慢寫入，應只為真正常用的查詢條件建索引。

**題四**：為什麼不該在交易裡呼叫 LLM API？
→ 等待期間持續占用連線與鎖住資料列，並行一多就會塞爆連線池，造成全站卡死。

@section 本課重點整理
- **交易**：`BEGIN` 開始、`COMMIT` 生效、`ROLLBACK` 全部撤銷。
- **ACID**：原子性（全有或全無）、一致性（符合你定義的約束）、隔離性（並行互不干擾）、持久性（提交後不遺失）。
- **一致性的前提**：資料庫不會猜業務規則，必須用約束或程式明確定義。
- **遺失更新**：重要扣款用 `SELECT ... FOR UPDATE` 鎖住資料列。
- **索引**：像書的目錄，B-Tree 讓查找從 N 步降到約 log N 步。
- **索引的代價**：占空間、拖慢寫入；只為常用查詢條件建。
- **EXPLAIN ANALYZE**：實際量測查詢計畫；它會真的執行 SQL，量測寫入要包在交易中回滾。
- **交易要短**：不要在交易裡呼叫 LLM 或其他慢速外部服務。
- **索引失效**：對欄位套函式、開頭萬用字元都會讓 B-Tree 用不上。

@term 索引
幫助資料庫快速找到資料的額外資料結構，類似書的目錄（Index）。
@term 循序掃描
從第一筆讀到最後一筆、逐一檢查的查詢方式（Sequential Scan）。
@term B-Tree
PostgreSQL 預設的索引結構，排序存放資料，查找約需 log N 步。
@term ACID
交易的四項保證：原子性、一致性、隔離性、持久性。
@term 原子性
交易中的操作要嘛全部成功、要嘛全部撤銷（Atomicity）。
@term 一致性
交易前後資料都符合所定義的約束（Consistency）。
@term 隔離性
同時進行的交易彼此不互相干擾（Isolation）。
@term 持久性
交易提交成功後，即使斷電也不會遺失（Durability）。
@term 預寫式日誌
修改真正寫入前先記錄在日誌，以便出錯時撤銷或重做（WAL）。
@term 遺失更新
兩個並行交易讀到同一舊值後各自寫回，導致其中一次修改被覆蓋（Lost Update）。
@term SELECT FOR UPDATE
讀取資料時同時鎖住該列，讓其他交易必須等待。
@term 查詢最佳化器
根據資料量與分佈估算、選擇最快查詢方式的資料庫元件（Query Optimizer）。
@term 查詢計畫
資料庫實際執行查詢的步驟，例如用循序掃描還是索引掃描（Query Plan）。
@term EXPLAIN ANALYZE
實際執行 SQL 並顯示查詢計畫與耗時的指令。
@term 運算式索引
對欄位運算結果（如 lower(name)）建立的索引（Expression Index）。
