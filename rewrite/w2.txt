@section 開場：五個地方，兩個忘了檢查
上一課我們把程式拆成一個個乾淨的函式。但隨著系統越長越大，又會出現新的問題。

假設學生的資料用字典表示：`{"name": "Alice", "scores": [85, 95]}`。專案裡有五個不同的檔案都會新增成績：
```
student["scores"].append(x)
```
其中三個地方記得先檢查分數是否在 0 到 100 之間，**兩個地方忘了**。結果一筆 -999 的錯誤資料，直接進入了資料庫，甚至變成 AI 模型的訓練資料。

要修這個問題，你得找出所有修改成績的地方，一個一個補上檢查。這種「改一個規則，要改散落在各處的很多地方」的狀況，叫做「**散彈槍式修改**」（Shotgun Surgery）：像散彈槍一樣，一個需求打出去，要在一大片地方修補。

這一課要學三個工具，解決這類問題：
1. **類別**（Class）：把資料和「修改它的唯一合法方式」綁在一起；
2. **例外**（Exception）：發現錯誤時，清楚地喊停，交給懂得處理的人；
3. **模組**（Module）：把程式拆成多個檔案，彼此有清楚的依賴方向。

@section 類別：資料加上它的守門員
**類別**是一張「藍圖」，描述某種東西**有哪些資料**、**能做哪些事**。照著藍圖做出來的具體東西，叫做「**實例**」（Instance）或「**物件**」（Object）。

```
class Student:
    def __init__(self, student_id, name):
        self.student_id = student_id
        self.name = name
        self.scores = []

    def add_score(self, score):
        if isinstance(score, bool) or not isinstance(score, (int, float)):
            raise InvalidScoreError("分數必須是數字")
        if not (0 <= score <= 100):
            raise InvalidScoreError("分數必須介於 0～100")
        self.scores.append(float(score))
```

幾個名詞：
- `__init__` 叫做「**建構子**」（Constructor）：建立新實例時自動執行，負責設定初始資料；
- `self` 代表「**這個實例自己**」。`self.scores` 就是「這位學生自己的成績清單」；
- `add_score` 是一個「**方法**」（Method）：屬於類別的函式。

**類別的真正價值不是語法，而是守護規則。**
現在，系統裡所有地方要新增成績，都**只能**呼叫 `alice.add_score(85)`。驗證規則只寫在一個地方。要改規則（例如滿分改成 150），只改一處，所有地方自動生效。

這種「無論何時都必須成立」的規則（例如「成績一定在 0 到 100 之間」），叫做「**不變量**」（Invariant），第 45 課規格書中也出現過。類別就是不變量的**守門員**。

**比喻：**字典像一個沒上鎖的抽屜，誰都能往裡面丟東西；類別像銀行櫃台，所有存提款都必須經過櫃員檢查，金庫不對外開放。

@section 陷阱：大家共用了同一份清單
上一課說過「可變預設參數」的陷阱。類別也有一個非常類似的陷阱。

**錯誤的寫法：**
```
class Student:
    scores = []          # 寫在 __init__ 外面！

    def __init__(self, name):
        self.name = name
```

寫在類別最上層（`__init__` 外面）的變數，叫做「**類別屬性**」（Class Attribute）：它屬於**整張藍圖**，所有實例**共用同一份**。

```
alice = Student("Alice")
bob = Student("Bob")
alice.scores.append(85)
print(bob.scores)   # [85]  ← Bob 也有了 Alice 的成績！
```

為什麼？因為 `alice` 自己沒有 `scores`，Python 就往上去藍圖找，找到了那份共用的清單，然後修改它。

**正確的寫法：**在 `__init__` 裡面用 `self.scores = []` 建立。這樣每個實例都有**自己專屬**的清單，叫做「**實例屬性**」（Instance Attribute）。

**比喻：**類別屬性像全班共用的一本筆記本，誰寫了大家都看得到；實例屬性像每人發一本自己的筆記本。

**原則：清單、字典這類可變的資料，一律在 `__init__` 裡用 `self.xxx = ...` 建立。**

@section 例外：發現錯誤時，大聲喊停
當程式發現不能繼續的情況（例如分數是 -10），該怎麼辦？上一課提過：不要回傳錯誤文字，而是「**拋出例外**」。

**例外**（Exception）就是程式在執行中遇到問題時發出的「**警報**」。用 `raise` 發出：
```
raise InvalidScoreError("分數必須介於 0～100")
```

**例外發生時會怎樣？**
1. Python **立刻停止**目前函式剩下的程式碼；
2. 沿著「**誰呼叫了我**」的路線，一層一層往外找，有沒有人準備好處理這種警報；
3. 找到 `try...except` 區塊，就交給它處理；
4. 一直找到最外層都沒人處理，程式就停止，並印出錯誤訊息。

這條「誰呼叫了誰」的路線，叫做「**呼叫堆疊**」（Call Stack）。

**捕捉例外：**
```
try:
    alice.add_score(-10)
except InvalidScoreError as e:
    print(f"輸入錯誤：{e}，請重新輸入")
```

**「立刻停止」帶來一個重要的好處。**
看前面 `add_score` 的寫法：檢查在前，`append` 在後。分數不合法時，`raise` 讓函式**立刻停止**，`append` 根本不會執行。所以 Alice 的成績清單**完全不會被改到**。

**錯誤的順序：**
```
def add_score(self, score):
    self.scores.append(score)       # 先寫進去了
    if not (0 <= score <= 100):
        raise InvalidScoreError(...) # 才發現不對
```
例外雖然拋出了，但 -10 已經留在清單裡了！

**原則：先完成所有檢查，最後一步才修改資料。**這樣出錯時，物件會維持原本的樣子，不會留下「做了一半」的髒狀態。

@section 自訂例外：讓錯誤有名字
Python 內建了很多例外，例如 `ValueError`（值不對）、`TypeError`（型別不對）、`KeyError`（字典裡找不到）。

但在業務系統中，建議**自己定義**有意義的例外：
```
class InvalidScoreError(ValueError):
    pass

class DuplicateStudentError(Exception):
    pass
```
`class InvalidScoreError(ValueError)` 的意思是：「`InvalidScoreError` 是一種 `ValueError`」，這叫做「**繼承**」。

**為什麼要自訂？**
- **名字本身就是說明**：看到 `DuplicateStudentError`，馬上知道是「學號重複」；
- **可以精準捕捉**：外層可以只處理「業務上的錯誤」，而不會意外地把真正的程式錯誤（例如打錯變數名稱造成的 `NameError`）也一起攔下來、隱藏起來。

@section 誰拋出，誰處理？
一個重要的分工原則：
- **底層**（例如 `Student`、`StudentManager`）：負責**發現**錯誤，並**拋出**有意義的例外；
- **最外層**（例如命令列介面 `main.py`，或第 54 課的網站 API）：負責**捕捉**例外，決定怎麼呈現給使用者。

**為什麼底層不自己處理？**因為底層**不知道**自己正在被誰使用：
- 被命令列程式呼叫時，應該印出紅字、請使用者重新輸入；
- 被網站 API 呼叫時，應該回傳「400 請求錯誤」或「409 衝突」的狀態碼（第 54 課）；
- 被自動化測試呼叫時，測試要檢查「有沒有正確拋出例外」。

如果底層自己 `print("錯誤")` 然後繼續，這三種用法就全都沒辦法正確運作了。

**比喻：**工廠的品管員發現瑕疵品時，責任是**按下警報、把產品攔下來**，而不是自己決定要退貨、打折賣還是送給員工。那是業務主管（最外層）根據情況做的決定。

@section 最危險的寫法：把錯誤吞掉
在程式碼審查中，最危險的一種寫法是：
```
try:
    do_something()
except:
    pass
```
或 `except Exception: return None`。意思是：「**不管發生什麼錯誤，都假裝沒事**。」

**為什麼危險？**
1. 它會把**所有**錯誤都吞掉：包括你打錯變數名稱、型別用錯這種程式本身的錯誤。程式明明有問題，卻沒有任何訊息，非常難除錯；
2. 光寫 `except:`（什麼都不寫）甚至會攔下使用者按 Ctrl+C 想停止程式的訊號；
3. 最嚴重的是：資料寫入失敗了，程式卻**繼續往下跑**，造成帳務或資料不一致。

第 46 課提過「默默吞掉錯誤」是 AI 寫的程式中最常見的深層漏洞之一，就是這個。

**原則：只捕捉你知道怎麼處理的、特定的例外。**不知道怎麼處理的，就讓它繼續往外傳。

@section 模組：拆成多個檔案
當程式越來越長，我們會把它拆成多個檔案。每個 `.py` 檔案就是一個「**模組**」（Module）。

以成績管理系統為例，拆成三層：
- `student.py`：定義 `Student` 類別和 `InvalidScoreError`（**領域層**：最核心的業務規則）；
- `manager.py`：定義 `StudentManager`，管理所有學生，並定義 `DuplicateStudentError`（**管理層**）；
- `main.py`：負責和使用者互動、捕捉例外、顯示訊息（**介面層**）。

在 `manager.py` 裡用別的檔案的東西：
```
from student import Student, InvalidScoreError
```
Python 執行到這行時，會去載入 `student.py`，並把它記在快取裡（之後再匯入就不會重新執行）。

**依賴方向只能單向。**
- `main.py` 依賴 `manager.py`；
- `manager.py` 依賴 `student.py`；
- `student.py` **絕不**反過來匯入 `manager.py` 或 `main.py`。

如果 `student.py` 匯入 `manager.py`，而 `manager.py` 又匯入 `student.py`，就會發生「**循環匯入**」（Circular Import）：Python 載入到一半，發現需要的東西還沒準備好，就會出錯（`ImportError: cannot import name`）。

**比喻：**公司的組織圖：總經理指揮經理，經理指揮員工。如果員工也能指揮總經理，命令就會繞圈圈，沒人知道該聽誰的。

**原則：越核心、越底層的模組，越不應該依賴別人。**這樣核心規則可以被任何外層重複使用。

@section 走一遍：三層系統的運作
操作順序如下：

**第一步：新增 Alice（學號 S01）。**
`StudentManager.add_student("S01", "Alice")` 檢查內部字典裡有沒有 S01，沒有，就建立 `Student("S01", "Alice")` 存進去。

**第二步：再新增一次 S01。**
`StudentManager` 發現 S01 已存在，立刻 `raise DuplicateStudentError("學號 S01 已存在")`。原本的 Alice 完全不受影響。`main.py` 捕捉到例外，顯示「此學號已被使用」。

**第三步：替 Alice 登錄 85 分、95 分，接著誤輸入 -10 分。**
`add_score(-10)` 在檢查時就拋出 `InvalidScoreError`。這時檢查 `alice.scores`，仍然是 `[85.0, 95.0]`，沒有留下任何髒資料。

**第四步：新增 Bob（學號 S02）。**
`bob.scores` 是全新的 `[]`。證明兩位學生的清單完全分開，沒有共用的陷阱。

@section 什麼時候用字典，什麼時候用類別？
不是所有資料都需要寫成類別。判斷的準則是：

**用字典（或之後會學的 dataclass、Pydantic 模型）就好：**
資料只是單純地「**被傳來傳去**」，沒有複雜的規則。例如從網路收到的一筆請求內容、要存進檔案的設定值。這類資料叫做「**資料傳輸物件**」（DTO，Data Transfer Object）。

**應該寫成類別：**
只要符合以下任一條件：
- 有**必須永遠成立的規則**（餘額不能是負數、成績要在 0 到 100）；
- 有**和資料緊密相關的行為**（計算平均 `average()`、判斷能否畢業 `can_graduate()`）；
- 需要**防止外部繞過檢查**直接修改資料。

**比喻：**快遞的紙箱（字典）只需要裝東西、寫地址；但保險箱（類別）有密碼鎖和規則，誰能開、怎麼開都有規定。

@section 和 AI 一起做：設計類別與例外
類別和例外的設計，牽涉到「這個物件必須永遠成立的規則」（不變量）。AI 很會寫出語法正確的類別，但常常**漏掉不變量的保護**。

**適合請 AI 做的事**
- 把一堆散落的函式和字典，整理成一個類別的草稿；
- 為你的領域設計一組自訂例外的階層（例如 `GradingError` 底下再分幾種）；
- 把單一大檔案拆成幾個模組，並畫出誰匯入誰。

**一段好的請求範例**
```
請幫我設計一個 Assignment 類別。
不變量（任何時候都必須成立）：
1. max_score 必須大於 0
2. 已繳交的作業不能再修改截止時間
3. score 不能超過 max_score
違反時丟出自訂例外，不要用 print 或回傳 False。
請在程式碼旁邊註明每個不變量在哪一行被保護。
```
要求 AI「**註明每條規則在哪一行被保護**」是一個很好用的技巧：它沒辦法指出來的規則，通常就是沒做到的規則。

**怎麼檢查 AI 的產出**
- 試著直接改屬性（例如 `a.score = 999`），看會不會繞過檢查。AI 常常只在建構子檢查，忘了之後的修改；
- 看例外的名稱和訊息，是不是讓呼叫者看得懂發生什麼事；
- 確認沒有「抓到所有例外然後默默忽略」的程式碼（`except: pass`）。

**不要交給 AI 的事**
哪些規則是真正的不變量，來自你對業務的理解。AI 只能從你的描述裡推測，推測錯了，它也會很有自信地寫下去。

@section 動動腦：找出問題
**題一**：把 `scores = []` 寫在類別最上層，建立 Alice 和 Bob 後，`alice.scores.append(85)` 會發生什麼事？
→ `scores` 是所有實例共用的類別屬性，Bob 的成績也會出現 85。

**題二**：`Student.add_score()` 發現分數是 -20，最好的處理方式是什麼？
→ 在 `append` 之前就拋出 `InvalidScoreError`，讓資料保持不變，由外層（`main.py` 或 API）決定怎麼回應使用者。

**題三**：`try: save_to_db(data) except: pass` 有什麼問題？
→ 所有錯誤都被吞掉，包括程式錯誤；資料沒存成功，程式卻繼續執行，造成不一致，而且很難除錯。

**題四**：`student.py` 和 `manager.py` 互相匯入，會發生什麼事？怎麼修正？
→ 循環匯入錯誤。保持單向依賴：`manager.py` 匯入 `student.py`，反過來不行。

@section 本課重點整理
- **散彈槍式修改**：同一個規則散落各處，改一次要改很多地方，容易漏改。
- **類別**：把資料和修改它的唯一合法方式綁在一起，集中守護不變量。
- **實例屬性 vs. 類別屬性**：可變的資料一律在 `__init__` 裡用 `self.xxx` 建立，避免所有實例共用。
- **例外**：`raise` 讓函式立刻停止並沿呼叫堆疊往外找處理者。先檢查、最後才修改資料，出錯時狀態不變。
- **自訂例外**：有意義的名字、能精準捕捉。底層負責拋出，最外層負責處理和呈現。
- **不要吞錯誤**：禁止 `except: pass`，只捕捉知道怎麼處理的特定例外。
- **模組**：拆成多個檔案，依賴方向單向，避免循環匯入。
- **字典還是類別**：單純傳資料用字典；有規則和行為就寫類別。
