@section 開場：「在我的電腦明明可以跑」
這是軟體工程中**最經典**的一句話。

你的電腦裝了 Python 3.12.2、某個特定版本的系統函式庫、某個你早就忘了自己裝過的套件。伺服器卻是不同的作業系統、不同的版本。程式在你這裡好好的，一上伺服器就壞了。

專案越大越嚴重。一個典型的 AI 應用可能包含：FastAPI 後端、PostgreSQL 資料庫、Redis 快取、背景工作程式。靠一份 README 寫著「請依序安裝以下 15 樣東西」，新同事要花一整天設定環境，而且幾乎一定會在某一步出錯。

**Docker** 解決的就是這個問題：把**程式碼、Python 執行環境、系統套件、啟動指令**全部打包成一個「**映像檔**」（Image）。不管在你的筆電、同事的電腦、CI 測試環境（第 69 課）還是雲端伺服器，只要啟動同一個映像檔，就得到**一模一樣**的執行環境。

**比喻：**貨櫃。在貨櫃發明之前，貨船裝貨要一件一件搬，每種貨物的形狀、包裝都不同，裝卸又慢又容易出錯。貨櫃發明後，不管裡面裝的是汽車零件還是香蕉，外面都是**標準規格的箱子**，起重機、貨船、卡車都能直接處理。Docker 的 logo 就是一隻載著貨櫃的鯨魚。

這一課要學：
1. 三個核心概念：**映像檔、容器、資料卷**；
2. 寫 Dockerfile，以及怎麼利用快取加速建置；
3. 用 **Docker Compose** 同時管理多個服務；
4. 容器之間怎麼連線（`localhost` 的陷阱）；
5. 一個會讓資料全部消失的指令。

@section 容器 vs. 虛擬機
在 Docker 之前，常見的做法是**虛擬機**（Virtual Machine）：在一台電腦上模擬出**另一整台電腦**，包含完整的作業系統。隔離得很徹底，但很笨重，每台虛擬機都要好幾 GB、開機要好幾分鐘。

**容器**（Container）比較輕巧：它**共用主機的作業系統核心**，只是用 Linux 的隔離機制，讓每個容器以為自己有獨立的檔案系統、網路和行程（第 51 課）。啟動只要幾秒，大小常常只要幾百 MB。

**比喻：**
- 虛擬機像**獨棟透天厝**：每棟有自己的地基、水電、屋頂，很獨立但成本高；
- 容器像**公寓大樓的單位**：共用地基和主要管線，但每戶有自己的門鎖、隔間，彼此看不到對方家裡。

@section 三個核心概念：映像檔、容器、資料卷
**一、映像檔（Image）：唯讀的範本。**
映像檔是一份**唯讀的**打包結果，包含執行程式需要的一切。它由 `Dockerfile` 裡的每一行指令**一層一層疊起來**。

**比喻：**映像檔像**食譜加上預先備好的料理包**，本身不會變。

**二、容器（Container）：從映像檔啟動的執行個體。**
容器是映像檔「**跑起來**」的樣子。同一個映像檔可以啟動很多個容器。

每個容器在唯讀的映像檔上面，加了一層薄薄的「**可寫層**」。程式在執行中寫的檔案，就存在這一層。

**關鍵：可寫層的生命和容器綁在一起。**容器一刪除（例如部署新版本時），可寫層裡的**所有檔案都會消失**。

**比喻：**映像檔是食譜，容器是照著食譜煮出來的那一鍋菜。你可以在這鍋菜裡加點鹽，但倒掉之後，下一鍋又是照原本的食譜重新煮，那撮鹽不會留下來。

**三、資料卷（Volume）：容器之外的持久儲存。**
資料庫的檔案、使用者上傳的附件，這些**必須長期保存**的資料，不能放在容器的可寫層。要掛載到 **Volume**：一塊獨立於容器生命週期的儲存空間。容器刪了、換新版了，Volume 裡的資料還在。

**比喻：**Volume 像**外接硬碟**。電腦重灌（容器重建）時，外接硬碟裡的檔案不受影響，接上新電腦就能繼續用。

@section 寫一個 Dockerfile
```
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

RUN useradd --create-home appuser
USER appuser

CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```
逐行說明：
- `FROM python:3.12-slim`：以官方的 Python 3.12 精簡版映像檔為基礎；
- `WORKDIR /app`：之後的指令都在容器裡的 `/app` 資料夾執行；
- `COPY requirements.txt .`：**先只複製**套件清單；
- `RUN pip install ...`：安裝套件；
- `COPY . .`：**再複製**其餘的程式碼；
- `USER appuser`：切換成**一般使用者**執行，而不是最高權限的 root；
- `CMD [...]`：容器啟動時執行的指令。注意 `--host 0.0.0.0`：容器內的程式要監聽所有網路介面，外面才連得進來（第 53 課提過 127.0.0.1 只接受本機連線）。

**為什麼先複製 requirements.txt，再複製程式碼？——善用快取。**
Docker 會**快取**每一層的建置結果。只要某一層的輸入沒變，就直接用快取，不用重做。但**一旦某一層變了，它之後的所有層都要重做**。

- 程式碼**經常改**；套件清單**很少改**；
- 先複製套件清單並安裝，這一層通常不變，可以用快取；
- 程式碼放在最後，改了程式碼只需要重做最後幾層。

建置時間可以從**五分鐘縮短到幾秒鐘**。

**反面例子：**一開頭就 `COPY . .` 再 `pip install`。你只改了 README 的一個字，Docker 也認為那一層變了，後面的 `pip install` 全部重跑。

**比喻：**做千層蛋糕。如果最上面那層奶油要常常換口味，就應該把它放在最上面。放在最底層的話，每次換口味都要把整個蛋糕重做。

**為什麼不用 root 執行？**
萬一程式有漏洞被攻破，攻擊者拿到的是容器內的**最高權限**，能做的事情多很多。用一般使用者執行，可以縮小「**爆炸半徑**」。這是第 28 課最小權限原則的又一次應用。

**`.dockerignore`：不要什麼都打包進去。**
和 `.gitignore`（第 52 課）類似，列出**不該**複製進映像檔的東西：
```
.git
.venv
__pycache__
node_modules
.env
```
特別是 `.env`：裡面有密碼和金鑰（第 68 課），打包進映像檔，任何拿到映像檔的人都能看到。

**鎖定版本：不要用 `latest`。**
`FROM python:latest` 或 `postgres:latest` 的「最新版」會**隨時改變**。某天官方發布新的主要版本，你的建置結果就悄悄變了。例如資料庫的主要版本升級，舊的資料檔格式可能不相容，資料庫直接啟動失敗。正式環境要寫明確版本，例如 `python:3.12-slim`、`postgres:16`。

這和第 10 課的可重現性是同一個道理。

@section Docker Compose：一次管理多個服務
真實的應用通常有好幾個服務。**Docker Compose** 用一個 YAML 檔描述所有服務，一個指令全部啟動：
```
services:
  api:
    build: .
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: postgresql://app:secret@db:5432/app
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD", "pg_isready", "-U", "app"]
      interval: 5s
      retries: 10

volumes:
  pgdata:
```
執行 `docker compose up -d`，API 和資料庫就一起啟動了。新同事加入團隊，只要裝好 Docker，一個指令就有完整的開發環境。

（範例中直接寫了密碼是為了簡化說明；第 68 課會講正確的秘密管理。）

**`ports: "8000:8000"`**：把主機的 8000 埠，接到容器的 8000 埠。這樣你在瀏覽器打開 `localhost:8000` 才連得到容器裡的 API。

@section 容器之間怎麼連線：localhost 的陷阱
注意上面的連線字串：`@db:5432`，而**不是** `@localhost:5432`。

**每個容器都有自己獨立的網路空間。**在 `api` 容器裡，`localhost` 指的是「**api 容器自己**」，不是你的電腦，也不是資料庫容器。所以寫 `localhost:5432` 會得到「連線被拒絕」：api 容器自己身上並沒有跑資料庫。

Compose 會把同一個檔案裡的服務放在同一個虛擬網路中，並且讓**服務名稱就是主機名稱**。所以在 api 容器裡，用 `db` 就能連到資料庫容器。這叫做「**服務發現**」。

**比喻：**公寓大樓裡，每戶都說「我家」。你在 3 樓說「我家」，指的是 3 樓；要找 5 樓的鄰居，得說「5 樓」，而不是「我家」。

@section 先啟動 ≠ 已經準備好
`depends_on: db` 只保證 Docker **先啟動** db 容器，**不保證**資料庫已經完成初始化、可以接受連線。PostgreSQL 第一次啟動時，可能需要好幾秒鐘準備。api 如果一啟動就馬上連資料庫，可能會失敗。

**解法：**
- 替 db 加上 **健康檢查**（`healthcheck`）：定期執行 `pg_isready` 確認資料庫準備好了；
- api 的 `depends_on` 加上 `condition: service_healthy`：等 db **健康**了才啟動；
- 應用程式本身也要有**連線重試**的機制，因為正式環境中，資料庫也可能短暫重啟。

**比喻：**餐廳開門營業，不代表廚房已經備好料。服務生要等廚房說「可以出餐了」，才開始接單。

@section 一個會讓資料消失的指令
假設工程師用 Compose 啟動了服務，新增了 50 筆課程資料。為了更新程式，他執行：
```
docker compose down -v
docker compose up -d
```
結果：**所有課程資料都不見了！**

**原因：**
- `docker compose down`：停止並移除容器。如果資料庫有掛載 Volume，資料還在 Volume 裡，沒事；
- **`-v`（`--volumes`）**：**連同 Volume 一起刪除**。資料就永久消失了。

而如果一開始**根本沒有**把資料庫目錄掛載到 Volume，那連 `-v` 都不用，只要容器一重建，資料就沒了。

**日常更新服務的正確指令：**
```
docker compose up -d --build
```
重新建置映像檔並替換容器，Volume 保持不動。

**`down -v` 只用在你「確定要清空所有資料、從頭開始」的時候**，例如重置測試環境。正式環境絕對不要隨手用。

@section 常見陷阱
**陷阱一：把容器的可寫層當成永久儲存。**
用 SQLite 存資料、上傳的圖片直接存在容器裡。容器隨時可能因為擴充、健康檢查失敗、版本更新而被**銷毀重建**。需要保存的資料，必須放在外部資料庫、物件儲存（例如雲端的 S3），或掛載的 Volume。

**陷阱二：一開頭就 `COPY . .`。**每次改程式碼都要重新安裝所有套件，還可能把 `.env` 打包進去。

**陷阱三：用 `latest` 標籤。**版本隨時改變，破壞可重現性。

**陷阱四：把秘密寫進 Dockerfile。**`ENV API_KEY=sk-...` 會永久留在映像檔的層裡，就算後面再刪掉也查得到。秘密要在**執行時**用環境變數注入（第 68 課）。

**陷阱五：容器內用 `localhost` 連其他容器。**要用服務名稱。

@section 常見疑問
**問：多階段建置（multi-stage build）是什麼？**
答：有些套件安裝時需要編譯工具（例如 gcc），但程式**執行時**並不需要它們。多階段建置把 Dockerfile 分成兩段：第一段「建置階段」裝好編譯工具、把套件裝進虛擬環境；第二段「執行階段」從乾淨的精簡映像檔開始，**只複製**建置好的虛擬環境和程式碼過來。最後的映像檔不含編譯工具，體積更小，被攻擊時可利用的工具也更少。**比喻：**蓋房子時要搭鷹架，但交屋時鷹架要拆掉，不會跟著房子一起賣給屋主。

**問：容器裡的日誌要寫到哪裡？**
答：寫到**標準輸出**（stdout，第 51 課），不要寫到容器內的檔案。容器一刪除，檔案就沒了；而標準輸出會被 Docker 收集，用 `docker compose logs api` 就能查看，正式環境也能統一轉送到日誌平台（第 66 課）。

**問：我改了程式碼，每次都要重新建置映像檔嗎？開發時很慢。**
答：開發時可以把本機的程式碼資料夾**掛載**進容器，搭配 Uvicorn 的 `--reload`，存檔後容器內立刻生效，不用重新建置。但這只是開發時的便利；部署到正式環境時，仍要用建置好的、固定不變的映像檔，才能保證「測試過的就是上線的」。

**問：AI 模型檔案那麼大，也要打包進映像檔嗎？**
答：通常不要。幾 GB 的模型權重打包進去，映像檔會非常肥大，每次部署都要搬運一次。常見做法是把模型放在物件儲存或掛載的 Volume，容器啟動時再載入；或者乾脆呼叫外部的模型 API（第 16、18 課）。

@section 動動腦：判斷看看
**題一**：api 容器的連線字串寫 `@localhost:5432` 連不上資料庫，為什麼？
→ 容器內的 localhost 指的是容器自己；要用 Compose 的服務名稱 `db`。

**題二**：為什麼 Dockerfile 要先複製 requirements.txt 安裝套件，再複製程式碼？
→ 利用層快取：程式碼常改、套件清單少改，這樣改程式碼時不必重新安裝套件。

**題三**：`docker compose down -v` 會發生什麼事？
→ 停止並移除容器，連同具名 Volume 一起刪除，資料庫資料會永久消失。

**題四**：設了 `depends_on: db`，api 啟動時仍然連不上資料庫，可能原因是什麼？
→ depends_on 只保證啟動順序，不保證資料庫已就緒；要加健康檢查與 `service_healthy` 條件，並在程式中實作重試。

@section 本課重點整理
- **Docker** 把程式和執行環境打包成標準化的映像檔，解決「在我電腦可以跑」的問題。
- **容器 vs. 虛擬機**：容器共用主機核心，輕巧快速。
- **映像檔**是唯讀範本；**容器**是執行個體，可寫層隨容器刪除而消失；**Volume** 讓資料獨立於容器存活。
- **Dockerfile**：先裝套件再複製程式碼以善用快取；用一般使用者執行；`.dockerignore` 排除 `.env` 等；鎖定版本不用 `latest`。
- **Docker Compose**：一個檔案描述多個服務，一個指令啟動。
- **容器間連線**用服務名稱，不是 localhost。
- **depends_on 不等於就緒**：搭配健康檢查與重試。
- **`down -v` 會刪除資料**；日常更新用 `up -d --build`。

@term Docker
把應用程式與執行環境打包成標準化容器的工具。
@term 映像檔
包含程式碼、執行環境與設定的唯讀打包結果（Image）。
@term 容器
從映像檔啟動、彼此隔離的執行個體（Container）。
@term 虛擬機
模擬一整台電腦、含完整作業系統的隔離環境（Virtual Machine）。
@term Dockerfile
描述如何一層層建置映像檔的指令檔。
@term 層快取
Docker 重用未改變之建置層的機制，可大幅加速建置（Layer Cache）。
@term 可寫層
容器在映像檔之上的寫入空間，容器刪除時一併消失。
@term Volume
獨立於容器生命週期的持久儲存空間。
@term Docker Compose
用一個 YAML 檔定義並同時管理多個容器服務的工具。
@term 服務發現
在同一網路中用服務名稱找到其他服務的機制（Service Discovery）。
@term 健康檢查
定期確認服務是否已就緒並正常運作的機制（Health Check）。
@term .dockerignore
列出不應複製進映像檔之檔案的清單。
@term 爆炸半徑
系統被攻破或故障時，影響所及的範圍（Blast Radius）。
