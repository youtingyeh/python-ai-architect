@section 開場：從「懂原理」到「做應用」
前面 15 課，我們把 AI 拆到最底層：梯度、損失、注意力、GPT。從這一課開始，視角換了：**我們不再自己訓練模型，而是使用別人訓練好的大型模型，來打造實用的應用程式。**

這一段跟著 Microsoft 的開源課程《Generative AI for Beginners》（生成式 AI 入門，有繁體中文版）。它共 21 課，從怎麼寫提示詞、怎麼做聊天機器人、怎麼讓 AI 查資料，一路到 AI 代理人和安全部署。

**這一課是第 00 課：在寫第一行程式之前，先學會保護你的「鑰匙」。**

為什麼第一課不是教你怎麼叫 AI 回答問題，而是講安全？因為使用 OpenAI、Azure、Anthropic（Claude）、Google 這些公司的 AI 服務，都需要一把「**API 金鑰**」（API Key）。

**API 是什麼？**API（Application Programming Interface，應用程式介面）是讓程式跟程式溝通的窗口。就像餐廳的點餐櫃台：你不用進廚房，只要照菜單點餐，廚房就會送出料理。你的程式透過 API 送出問題，AI 公司的伺服器把回答傳回來。

**API 金鑰是什麼？**它是一長串像 `sk-proj-aB3x...` 的文字，代表「你的身分」，**而且綁定你的信用卡**。每次呼叫 API 都會依使用量扣錢。換句話說，**API 金鑰 = 你的信用卡**。誰拿到它，誰就能用你的錢去呼叫 AI。

真實世界裡，金鑰外洩的故事屢見不鮮：有人不小心把金鑰傳上 GitHub，幾分鐘內就被自動掃描程式偷走，一個週末刷掉幾千美元。這一課要教你一套完整的防護觀念，避免這種事發生在你身上。

@section 三層架構：使用者、你的伺服器、AI 供應商
一個正式上線的 AI 應用，**絕對不能**讓使用者的瀏覽器或手機 App 直接連到 OpenAI。正確的結構是**三層**：

**第一層：使用者介面（前端，Frontend）。**
使用者看到、點擊的網頁或 App。它跑在使用者的電腦或手機上。

**第二層：你自己的後端伺服器（Backend）。**
你控制的程式，跑在雲端或公司機房。它負責保管金鑰、檢查使用者身分、決定能不能呼叫 AI。

**第三層：AI 供應商的 API。**
OpenAI、Azure、Anthropic 等公司的伺服器。

資料的流向是：使用者 → 你的後端 → AI 供應商 → 你的後端 → 使用者。

**為什麼中間一定要夾一層？**

用銀行來比喻。你去銀行領錢，不會自己走進金庫，而是在櫃台跟行員說。行員確認你的身分、查你的帳戶餘額、確認金額合理，才進金庫拿錢給你。金庫的鑰匙永遠在行員手上，不會交給客人。

- 使用者介面 = 客人
- 你的後端 = 櫃台行員
- API 金鑰 = 金庫鑰匙
- AI 供應商 = 金庫

在資訊安全的觀念裡，**任何送到使用者電腦上的東西，都要假設會被看光**。網頁的程式碼、App 的安裝檔，使用者都能拆開來看。只有跑在你自己伺服器上的程式，才是安全的地方，才能放機密。

這條「前後端職責分離」的原則，是所有 AI 應用的第一道鐵律。

@section 為什麼金鑰絕對不能放在網頁或 App 裡？
很多初學者做作品集時，為了省掉架後端的麻煩，直接在網頁的 JavaScript 裡呼叫 OpenAI，把金鑰寫在程式碼中。這是會造成財務災難的漏洞。

**常見的錯誤想法一：「我把金鑰放進環境變數，就不會出現在程式碼裡了。」**

前端開發工具（例如 Vite、Next.js）有一種設定：名稱以 `VITE_` 或 `NEXT_PUBLIC_` 開頭的變數，可以在網頁程式裡使用。但這些工具在「打包」網站時，會**直接把變數的值，以明文寫進公開的 .js 檔案**。這些前綴的意思本來就是「這個值可以公開」，所以放金鑰等於把它貼在網站上。

**常見的錯誤想法二：「我把金鑰加密、編碼、混淆一下就安全了。」**

不管你怎麼藏，瀏覽器在真正送出請求的那一刻，都**必須把明文金鑰放進請求標頭裡**，否則 OpenAI 不認得你。任何人只要按 **F12** 打開瀏覽器的「開發者工具」，切到「Network（網路）」分頁，就能在請求內容裡直接看到完整的金鑰，前後只要幾秒鐘。

這就像把家裡鑰匙放進一個上了鎖的盒子，再把盒子的鑰匙黏在盒子上。

**更可怕的是自動化攻擊。**網路上有大量的「機密掃描程式」（Secret Scanner），24 小時不停地掃描公開網站和 GitHub，專門找 `sk-` 開頭的字串。你的金鑰一旦公開，可能**幾分鐘內**就被抓走。攻擊者會用程式大量呼叫最貴的模型，把你的額度刷爆；或者用你的帳號產生違規內容，導致帳號被永久封鎖。

**結論：金鑰只能放在後端伺服器。沒有例外。**

如果你只是想做一個純前端的練習作品，正確的做法是：要求使用者**自己輸入他們的金鑰**（只存在他們自己的瀏覽器裡），而不是放你的金鑰。

@section 就算在後端，也不能直接寫在程式碼裡
金鑰放在後端，那在 Python 程式裡直接寫 `api_key = "sk-proj-12345..."` 可以嗎？

**也不行。**這叫做「**硬編碼**」（Hardcoding），把機密直接寫死在程式碼裡。問題是：你的程式碼會用 **Git** 做版本管理，然後推送到 **GitHub**。

**Git 和 GitHub 是什麼？**Git 是一種「版本控制」工具，會記錄程式碼每一次修改的完整歷史，像一個超強的「上一步」功能，可以回到任何一個過去的版本。GitHub 是一個放 Git 專案的網站，可以公開分享或團隊協作。

只要程式碼裡出現過一次金鑰，任何能看到這個專案的人都能看到它。

**正確做法：把設定和程式碼分開。**

這是軟體工程界有名的「**12 因子應用**」（12-Factor App）原則之一：程式碼可以公開，但設定（特別是密碼和金鑰）要放在程式碼之外。

具體做法：
1. 在專案資料夾建立一個叫 **`.env`** 的檔案（檔名開頭的點代表它是隱藏檔），內容寫：
   ```
   OPENAI_API_KEY=sk-proj-你的真實金鑰
   ```
2. Python 程式用 `python-dotenv` 套件讀取：
   ```
   from dotenv import load_dotenv
   import os
   load_dotenv()
   api_key = os.environ["OPENAI_API_KEY"]
   ```
   程式碼裡只有「變數名稱」，沒有真實的金鑰。

**環境變數是什麼？**作業系統為每個執行中的程式準備的一組「設定值」，像是一個公告欄。程式啟動時可以去讀上面的值。`.env` 檔案只是方便在本機開發時，把這些值一次載入到公告欄上。

@section .gitignore 與範本檔：讓 Git 永遠不碰你的金鑰
有了 `.env`，還要確保它**永遠不會被推上 GitHub**。

**第一步：寫 `.gitignore`。**
`.gitignore` 是一個告訴 Git「這些檔案不要管」的清單。在建立專案的**第一時間**就要加上：
```
.env
*.env
.env.*
!.env.example
```
最後一行開頭的 `!` 代表「例外」：範本檔 `.env.example` 要保留（等一下解釋）。

**為什麼要「第一時間」？**因為 `.gitignore` 只對「還沒被 Git 追蹤的檔案」有效。如果 `.env` 已經被提交過一次，後來才加進 `.gitignore`，它的歷史紀錄還是在。

**第二步：提供範本檔 `.env.example`。**
團隊其他人下載你的專案後，要怎麼知道需要設定哪些變數？答案是提交一份**不含真實值**的範本：
```
OPENAI_API_KEY=your_api_key_here
OPENAI_API_BASE=https://api.openai.com/v1
```
新成員只要複製一份改名成 `.env`，填入自己的金鑰就能執行。

**第三步：正式上線時，連 .env 都不用。**
在正式環境（Production，給真實使用者用的版本），通常連 `.env` 檔案都不放在伺服器上，而是使用雲端平台的「**機密管理服務**」，例如 GitHub Actions Secrets、Azure Key Vault、AWS Secrets Manager。它們把金鑰加密保存，只在程式啟動時注入到環境變數中，而且會記錄誰在什麼時候讀取過。

@section 萬一金鑰外洩了，怎麼辦？
假設你不小心把含有金鑰的檔案推上了 GitHub。最常見的**錯誤**反應是：「趕快把金鑰從檔案刪掉，再推一次就好了。」

**這完全無效。**Git 的本質就是保存**完整歷史**。只要有人打開 GitHub 的提交紀錄（Commit History），或在電腦上執行 `git log -p`，被刪掉的金鑰在舊版本裡依然清清楚楚。而且前面說過，掃描程式可能在你推送後**幾秒鐘內**就已經抓到了。

**正確的緊急處理步驟：**

1. **立刻撤銷金鑰**（最重要、最優先）。到 AI 供應商的管理後台（例如 OpenAI 的 Dashboard 或 Azure Portal），找到這把金鑰，按下撤銷（Revoke）或刪除。這樣就算別人拿到了，也已經是一把廢鑰匙。
2. **檢查帳單和使用紀錄**，看有沒有異常的大量呼叫。
3. **產生一把新金鑰**，放進安全的環境變數。
4. **清理 Git 歷史**：用 `git-filter-repo` 或 BFG Repo-Cleaner 這類工具，把金鑰從所有歷史版本中徹底抹除。

記住順序：**先撤銷，再清理**。清理歷史很花時間，但撤銷只要幾秒，而且一撤銷就安全了。

**定期換鑰匙：金鑰輪替。**
大公司會定期更換金鑰（例如每 90 天），就算某把鑰匙不知不覺外洩了，有效期也有限。這叫做「**金鑰輪替**」（Key Rotation）。

為了換鑰匙時服務不中斷，通常會準備**主、副兩把金鑰**：先讓程式改用副金鑰，再重新產生主金鑰，下次輪替時再反過來。整個過程服務完全不停機。

GitHub 現在也有「**推送保護**」（Push Protection）功能：在你推送時自動偵測常見格式的金鑰，直接擋下來。建議開啟。

@section 後端不能只是「傳話筒」：四道防線
金鑰安全地藏在後端了，是不是就沒事了？還沒有。

假設你的後端寫了一個 API，原封不動地把前端傳來的內容轉給 OpenAI：

```
@app.post("/api/generate")
def generate(request):
    return client.chat.completions.create(**request.json())
```

攻擊者雖然拿不到你的金鑰，但他可以**直接呼叫你的後端**，而且自己指定要用最貴的模型、要求最長的回答。你的後端就變成了一個「**開放代理**」（Open Proxy），任何人都能免費用你的錢呼叫 AI。

這就像銀行櫃台行員不查身分、不看餘額，誰來說要領多少就給多少。

一個合格的後端，必須做好**四道防線**：

**① 身分驗證（Authentication）。**
確認請求來自你網站上已登入的使用者，而不是陌生人寫的程式。常用方式是登入後發給使用者一個「通行證」（例如 JWT Token 或 Session Cookie），每次請求都要帶上。

**② 參數鎖定（Parameter Locking）。**
**不要讓前端決定要用哪個模型、回答能多長。**後端應該寫死：「只能用 gpt-4o-mini」、「回答最多 500 個 Token」、「輸入不能超過 2,000 字」。前端傳什麼都不重要，後端自己決定。

**③ 速率限制（Rate Limiting）。**
限制每個使用者（或每個 IP 位址）在一段時間內的請求次數，例如每分鐘最多 10 次。超過就拒絕。常見的演算法叫「**令牌桶**」（Token Bucket）：每個使用者有一個桶子，以固定速度補充令牌，每次請求消耗一個，桶子空了就要等。

**④ 稽核與個資遮罩（Audit & PII Redaction）。**
記錄「誰、什麼時候、用了多少 Token」，出事時能追查。另外，在把內容送給外部 AI 公司之前，先把敏感個人資料（PII，Personally Identifiable Information，例如身分證字號、信用卡號、電話）遮掉或替換，避免使用者的隱私外流到第三方。

@section 成本斷路器：讓帳單永遠不會失控
傳統的網站，多處理一萬次請求，幾乎不會多花錢（伺服器本來就開著）。但 AI API 是「**按 Token 計費**」的：每一次呼叫，輸入和輸出的每一個 Token 都要付錢。

這代表：如果遇到惡意攻擊、程式有無窮迴圈的錯誤、或某篇貼文突然爆紅，**一個週末就可能燒掉幾千美元**。

所以正式上線的 AI 服務，一定要裝「**成本斷路器**」（Cost Circuit Breaker）。名字來自家裡的電路斷路器：電流太大時自動跳電，保護整棟房子不會燒起來。

**第一重保護：在 AI 供應商後台設上限。**
- **硬上限**（Hard Limit）：例如每月 50 美元，到了就直接停止服務。這是最後一道保險，確保最壞情況下的損失有上限。
- **軟上限**（Soft Limit）：例如到 30 美元時寄信警告你，讓你有時間處理。

**第二重保護：在你的後端自己算錢。**
每次 AI 回應時，回應裡會附上這次用了多少 Token（`usage.prompt_tokens` 輸入、`usage.completion_tokens` 輸出）。後端把它乘上單價，即時累加起來。

**算一個例子**：假設某模型輸入每百萬 Token 0.15 美元、輸出每百萬 Token 0.60 美元。一次呼叫用了 1,000 個輸入 Token、500 個輸出 Token：
- 輸入：$1000 \times 0.15 / 1{,}000{,}000 = 0.00015$ 美元
- 輸出：$500 \times 0.60 / 1{,}000{,}000 = 0.0003$ 美元
- 合計 0.00045 美元，約台幣 0.015 元。

單次很便宜，但如果被攻擊者每秒打 100 次、持續一整天：$0.00045 \times 100 \times 86{,}400 \approx 3{,}900$ 美元。這就是為什麼需要斷路器。

後端可以設定：「全站每天最多花 5 美元」、「每個免費使用者每天最多 20 次」。一旦觸及門檻，斷路器跳脫，後續請求直接回傳「**HTTP 429 請求太多**」的錯誤，或改用快取的回答、改用更便宜的小模型。這叫做「**優雅降級**」（Graceful Degradation）：服務變差一點，但不會整個掛掉，也不會讓帳單爆炸。

@section 動動腦：抓出三個安全漏洞
**情境一**：小美做了一個 React 聊天網頁，把金鑰放在 `.env` 檔裡，命名為 `VITE_OPENAI_API_KEY`，也確認 `.env` 已經加進 `.gitignore`，然後把網站部署到 GitHub Pages。安全嗎？

**不安全。**`VITE_` 開頭的變數會在打包時被寫進公開的 .js 檔。`.gitignore` 只是讓 `.env` 不進 Git，但打包後的網站裡已經有明文金鑰了。而且 GitHub Pages 只能放靜態網頁，沒有後端，金鑰無處可藏。

**情境二**：小明不小心把金鑰推上 GitHub，馬上把那行刪掉、再推一次。還安全嗎？

**不安全。**舊的提交紀錄裡還有金鑰，掃描程式可能已經抓走了。第一件事是**立刻到後台撤銷金鑰**，再換新的。

**情境三**：一家新創公司把金鑰放在後端，後端直接把前端的 JSON 轉發給 OpenAI。還缺什麼？

**缺四道防線。**任何人都能指定最貴的模型和最長的輸出，無限次呼叫。需要補上：身分驗證、參數鎖定、速率限制，以及成本斷路器。

@section 本課重點整理
- **API 金鑰 = 你的信用卡**：誰拿到誰就能花你的錢。
- **三層架構**：使用者介面 → 你的後端 → AI 供應商。金鑰只能放在後端。
- **前端藏不住秘密**：`VITE_`、`NEXT_PUBLIC_` 變數會被寫進公開檔案；加密混淆也沒用，按 F12 就看得到。
- **不要硬編碼**：金鑰放 `.env`，用環境變數讀取。`.gitignore` 第一時間就要加上 `.env`，另外提交一份 `.env.example` 範本。
- **外洩時先撤銷**：刪掉再推送沒用，Git 有完整歷史。立刻到後台撤銷、換新，再清理歷史。
- **金鑰輪替**：定期更換，用主副兩把金鑰達成零停機。
- **後端四道防線**：身分驗證、參數鎖定、速率限制、稽核與個資遮罩。
- **成本斷路器**：供應商後台設硬上限，後端自己計算花費，超過門檻就優雅降級。

可識別個人身分的資料（Personally Identifiable Information），例如身分證字號、電話、信用卡號。
@term 成本斷路器
花費達到門檻時自動停止或降級服務的保護機制，避免帳單失控。
@term 優雅降級
系統遇到問題時改用較簡單的方式繼續服務（Graceful Degradation），而不是整個掛掉。
@term HTTP 429
伺服器回應「請求太多」的狀態碼，常用於速率限制。
