@section 開場：一個看似聰明、其實會爆炸的設計
上一課，我們有了一張學生表。現在系統要長大：學生要**選課**，老師要**開課**、**出作業**，學生要**繳交作業**。

很多初學者會看著畫面想：「學生選了哪些課？那就在學生表加一個欄位吧。」
```
students
id | name  | course_ids
1  | Alice | '101,102,205'
```
把選了的課程編號，用逗號串成一個字串塞進去。看起來簡單直覺，但這個設計（業界稱為「**亂穿馬路反模式**」，Jaywalking）上線不久就會出問題：

**一、幽靈資料。**205 號課早就被刪除了，字串裡還留著 `'205'`。資料庫只看到一段文字，**完全不知道**這是課程編號，更無法檢查它存不存在。

**二、沒地方放額外資訊。**老師問：「哪些學生是**本週**加選 101 的？」選課時間要記在哪？字串裡沒有位置。

**三、查詢又慢又容易錯。**要找「選了 1 號課的學生」，只能做文字比對，結果 `'101'`、`'210'` 裡都有「1」，一不小心就誤判。

**四、無法防止重複。**沒有任何機制阻止 `'101,101'`。

這一課要學的，是從「看畫面寫功能」升級為「**資料建模**」（Data Modeling）：先想清楚**世界上有哪些東西、彼此是什麼關係**，再用正確的表格結構表達。我們會學：
1. 實體與關係，以及畫成 **ER 圖**；
2. 三種關係：一對一、一對多、多對多；
3. **外鍵**如何守住「參照完整性」；
4. 多對多的解法：**交集表**；
5. 組合唯一約束：防止重複選課、重複繳交；
6. 刪除時的連帶行為：`RESTRICT` vs. `CASCADE`。

@section 實體與關係：先畫地圖再蓋房子
**實體**（Entity）是系統中「值得記錄的東西」，通常是名詞：使用者、課程、作業、繳交紀錄。每個實體通常對應一張資料表。

**關係**（Relationship）是實體之間的連結，通常是動詞：老師「開設」課程、學生「選修」課程、學生「繳交」作業。

**ER 圖**（Entity-Relationship Diagram，實體關係圖）就是把這些實體畫成方框、關係畫成連線的圖。它是資料庫的**設計藍圖**：在寫任何 SQL 之前，先在紙上（或白板上）畫出來，和團隊討論。

**比喻：**蓋房子前要先畫平面圖，確認有幾個房間、哪個門通哪裡。直接開始砌磚，蓋到一半才發現廚房沒有門，代價就很大。資料庫也一樣：上線後才改表結構，要搬移大量資料，非常痛苦。

**怎麼開始？**先**離開 UI 畫面**，問自己：
- 這個系統裡有哪些「東西」需要被記錄？
- 每個東西靠什麼唯一識別（主鍵，第 52 課）？
- 這些東西之間，是「一個對一個」、「一個對很多個」，還是「很多個對很多個」？

@section 三種關係：數一數兩邊各有幾個
描述關係時，最重要的是「**基數**」（Cardinality）：兩邊各可以有幾個。

**一對多（1:N）：最常見的關係。**
「一位老師可以開很多門課，但每門課只有一位主責老師。」

**做法：在「多」的那一邊，放一個欄位指向「一」的那一邊。**
```
courses
id  | title     | teacher_id
101 | Python    | 7
102 | 資料庫    | 7
205 | 網頁開發  | 9
```
每門課記下「我的老師是誰」。老師表不需要記「我開了哪些課」，要查的話，就去課程表找 `teacher_id = 7` 的課。

**比喻：**一位媽媽可以有很多個孩子，但每個孩子只有一位生母。與其在媽媽的資料上列出所有孩子（列表會越來越長），不如在每個孩子的資料上寫「母親：某某某」。

**一對一（1:1）：比較少見。**
例如「每位使用者有一份個人設定」。通常做法是：在其中一邊放外鍵，再加上 `UNIQUE` 約束，保證不會有兩份設定指向同一位使用者。

**多對多（N:M）：最需要小心的關係。**
「一位學生可以選很多門課，一門課也可以被很多學生選。」

這種關係**沒辦法**只在其中一邊放一個欄位解決：學生表放一個課程欄位？一位學生選了很多課，放不下（就變回開場的逗號字串了）。課程表放一個學生欄位？同樣放不下。

解法在下面的「交集表」。

@section 外鍵：守住「指向的東西一定存在」
上面 `courses.teacher_id` 這種「指向另一張表主鍵」的欄位，叫做**外鍵**（Foreign Key，FK）。在 SQL 中這樣宣告：
```
CREATE TABLE courses (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title text NOT NULL,
    teacher_id bigint NOT NULL REFERENCES users(id)
);
```
`REFERENCES users(id)` 告訴資料庫：「這個欄位的值，**必須**是 users 表中真實存在的某個 id。」

宣告了之後，資料庫會強制守住「**參照完整性**」（Referential Integrity）：
- 想新增一門課，`teacher_id = 999`，但沒有 999 號使用者 → **拒絕**；
- 想刪除 7 號老師，但還有課程指向他 → 預設**拒絕**（下面會講細節）。

**比喻：**外鍵像圖書館的借書卡。借書卡上的書號必須是館藏裡真實存在的書；而書還沒還回來之前，圖書館不能把這本書報廢。

這就解決了開場的「幽靈資料」問題：用外鍵關聯，資料庫**保證**不會指向不存在的東西。

@section 交集表：多對多的標準解法
多對多的解法是：**另外建一張表，專門記錄「誰和誰有關係」**。這張表叫做**交集表**（Junction Table），也叫連結表。

選課的交集表 `enrollments`：
```
CREATE TABLE enrollments (
    student_id  bigint NOT NULL REFERENCES users(id),
    course_id   bigint NOT NULL REFERENCES courses(id),
    enrolled_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (student_id, course_id)
);
```
資料看起來像這樣：
```
student_id | course_id | enrolled_at
1          | 101       | 2026-09-01
1          | 102       | 2026-09-03
2          | 101       | 2026-09-02
```
每一列代表「某位學生選了某門課」。Alice（1 號）選了 101 和 102，Bob（2 號）選了 101。

**神奇之處：**一個難搞的「多對多」，被拆成了兩個乾淨的「一對多」：
- 一位學生 → 多筆選課紀錄；
- 一門課程 → 多筆選課紀錄。

開場的四個問題全部解決了：
- **幽靈資料**：兩個欄位都是外鍵，資料庫保證學生和課程都存在；
- **額外資訊**：`enrolled_at`（加選時間）有地方放了，日後還可以加 `final_grade`（學期成績）；
- **查詢**：`WHERE course_id = 101` 精準比對，不會誤判，還能建索引（第 54 課）加速；
- **重複**：`PRIMARY KEY (student_id, course_id)` 擋住，見下一節。

**重要觀念：交集表不只是「連線」，它本身也是一個業務實體。**「選課」這件事有自己的時間、狀態、成績。把它當成正式的實體來設計，系統會好擴充很多。

**比喻：**婚姻登記。一個人一生可能有多段婚姻，一段婚姻有兩個人。戶政事務所不會在每個人的身分證上列一長串配偶，而是另外有「婚姻登記簿」，每一筆記錄兩個人、結婚日期、登記地點。這本登記簿就是交集表。

@section 組合唯一約束：防止重複
`PRIMARY KEY (student_id, course_id)` 是「**組合主鍵**」：兩個欄位**合起來**必須唯一。

意思是：
- `(1, 101)` 和 `(1, 102)`：可以，同一位學生選不同課；
- `(1, 101)` 和 `(2, 101)`：可以，不同學生選同一門課；
- `(1, 101)` 和 `(1, 101)`：**拒絕**，同一位學生不能重複選同一門課。

**為什麼一定要加？**想像學生在網頁上**連點兩下**「加選」按鈕，或網路不穩自動重送（第 45 課的重試）。如果沒有這個約束，資料庫會多出兩筆一模一樣的選課紀錄。之後程式查詢「Alice 有沒有選 101」，預期拿到一筆，結果拿到兩筆，就會出錯；統計選課人數時也會多算。

**不要只靠程式檢查。**「先查有沒有選過，沒有才新增」看起來可行，但兩個請求**同時**進來時，兩個都查到「沒選過」，然後兩個都新增了（第 52 課的競態條件）。**只有資料庫約束能在並行時百分之百守住。**

另一種寫法是：交集表有自己獨立的 `id` 主鍵，再加上 `UNIQUE (student_id, course_id)`。效果一樣，都能防重複。

@section 刪除時怎麼辦：RESTRICT vs. CASCADE
外鍵還要決定一件事：**被指向的資料要刪除時，指向它的資料怎麼辦？**

例如要刪除 101 號課程，但選課表裡還有 30 筆紀錄指向它。有幾種策略：

**`ON DELETE RESTRICT`（或預設的 `NO ACTION`）：禁止刪除。**
只要還有東西指向它，就不准刪。要刪課程，必須先處理掉相關的選課和作業。

**`ON DELETE CASCADE`：連帶刪除。**
刪除課程時，**自動把所有指向它的資料一起刪掉**：選課紀錄、作業、繳交、成績……全部消失。

**`ON DELETE SET NULL`：設為空值。**
指向它的欄位改成 `NULL`，資料本身保留。

**`CASCADE` 是一個重大的業務決策，絕對不能為了方便亂加。**常見的慘劇是：開發時為了方便清測試資料，到處加 `CASCADE`；上線後有人誤刪一門課，全班一學期的作業和成績**瞬間永久消失**。

**實務建議：**
- 重要的主資料（使用者、課程、訂單），通常用 `RESTRICT`；
- 真的要「刪除」使用者時，多半改用「**軟刪除**」：不真的刪，而是加一個欄位 `is_active = false` 標記停用，資料保留下來供稽核；
- `CASCADE` 只用在「子資料離開父資料就毫無意義」的情況，例如一則貼文底下的按讚紀錄。

**比喻：**`RESTRICT` 像「房子裡還住著人，不准拆」；`CASCADE` 像「拆房子時，連裡面的人和家具一起拆掉」。後者一旦搞錯，就無法挽回。

@section 走一遍：迷你線上學習平台
把以上觀念組起來，設計一個迷你學習平台的五張表：

**一、`users`（使用者）：**`id` 主鍵、`email` 唯一、`name`、`system_role`（學生或老師）。

**二、`courses`（課程）：**`id` 主鍵、`title`、`teacher_id` 外鍵指向 users，`ON DELETE RESTRICT`。
→ 老師對課程是 1:N；開了課的老師不能被直接刪除。

**三、`enrollments`（選課）：**`student_id` 和 `course_id` 兩個外鍵，`enrolled_at`，組合主鍵。
→ 學生與課程的 N:M 交集表。

**四、`assignments`（作業）：**`id` 主鍵、`course_id` 外鍵、`title`、`due_at`（截止時間）。
→ 課程對作業是 1:N。

**五、`submissions`（繳交）：**`id` 主鍵、`assignment_id` 外鍵、`student_id` 外鍵、`content`、`score`，加上 `UNIQUE (assignment_id, student_id)`。
→ 每位學生對每份作業，**只會有一份目前有效的繳交**。

**重新繳交怎麼辦？**Alice 第一次交作業 10，成功寫入。截止前她想改內容再交一次。如果直接 `INSERT`，會違反唯一約束而失敗。這時可以用 PostgreSQL 的「**有就更新，沒有就新增**」語法：
```
INSERT INTO submissions (assignment_id, student_id, content)
VALUES (10, 1, '新的內容')
ON CONFLICT (assignment_id, student_id)
DO UPDATE SET content = EXCLUDED.content, updated_at = now();
```
`ON CONFLICT` 的意思是：「如果撞到唯一約束（已經交過），就改成更新那一筆。」`EXCLUDED` 指的是「這次想新增、但被擋下的那筆資料」。一句 SQL 就完成，而且在並行時也安全。這種「有就更新、沒有就新增」的操作，叫做 **upsert**。

**想保留每次繳交的歷史？**那就再建一張 `submission_versions` 表，用 `(submission_id, version_no)` 唯一。主表永遠只有「目前這份」，歷史表記錄每一版。**不要**為了保留歷史就把主表的唯一約束拿掉，否則查詢時就不知道哪一筆才是最新的。

@section 外鍵擋不住的事
外鍵保證「指向的東西存在」，但**不保證關係合理**。

例子：Bob 沒有選 Python 課，卻繳交了 Python 課的作業。外鍵檢查：作業 10 存在 ✓、Bob 存在 ✓，於是通過了。但業務上這不合理：沒選課的人不該能交作業。

這種「跨多張表的業務規則」，需要**後端邏輯額外檢查**（先確認 Bob 在 enrollments 中有這門課），或用更進階的資料庫設計。這也呼應第 51 課的觀念：每一層防線都有它看不到的地方。

@section 動動腦：判斷看看
**題一**：要表達「學生選課」的多對多關係，標準做法是什麼？
→ 建立交集表（如 `enrollments`），兩個外鍵分別指向學生與課程，並設組合主鍵或唯一約束。

**題二**：`submissions` 表加上 `UNIQUE (assignment_id, student_id)`，保證了什麼？
→ 同一位學生對同一份作業最多只有一筆目前的繳交，連點兩下或並行請求都不會產生重複。

**題三**：為了測試時刪資料方便，在所有外鍵加上 `ON DELETE CASCADE`，好不好？
→ 不好。誤刪一門課就會連帶清空所有作業與成績；重要資料應預設 `RESTRICT`，必要時用軟刪除。

**題四**：「一位老師開多門課，每門課一位老師」，外鍵該放在哪張表？
→ 放在「多」的那一邊：課程表的 `teacher_id`。

@section 本課重點整理
- **反模式**：用逗號字串存關聯，會有幽靈資料、無處放屬性、查詢不準、無法防重複等問題。
- **ER 圖**：先找出實體（名詞）與關係（動詞），畫出藍圖再寫 SQL。
- **三種關係**：1:N 在「多」的一方放外鍵；1:1 用外鍵加 UNIQUE；N:M 用交集表。
- **外鍵**：`REFERENCES` 保證參照完整性，指向的資料一定存在。
- **交集表**：把 N:M 拆成兩個 1:N，本身也是業務實體，可存時間、成績等屬性。
- **組合唯一約束**：防止重複選課、重複繳交；並行時只有資料庫約束靠得住。
- **刪除策略**：重要資料用 `RESTRICT`；`CASCADE` 是重大決策；常以軟刪除取代真刪除。
- **upsert**：`INSERT ... ON CONFLICT DO UPDATE`，有就更新、沒有就新增。
- **外鍵的極限**：跨表的業務規則（沒選課不能交作業）仍需額外檢查。

@term 資料建模
在寫程式前，先規劃系統有哪些實體、彼此關係與表格結構的過程（Data Modeling）。
@term 實體
系統中值得記錄的事物，通常對應一張資料表（Entity）。
@term ER 圖
用方框表示實體、連線表示關係的資料庫設計藍圖（Entity-Relationship Diagram）。
@term 基數
描述兩個實體關係中，各邊可以有幾筆資料，如 1:1、1:N、N:M（Cardinality）。
@term 一對多
一筆資料對應多筆另一種資料，外鍵放在「多」的一方（1:N）。
@term 多對多
雙方都可以對應多筆，需要用交集表表達（N:M）。
@term 外鍵
指向另一張表主鍵的欄位，保證指向的資料存在（Foreign Key）。
@term 參照完整性
保證外鍵所指向的資料一定真實存在的規則（Referential Integrity）。
@term 交集表
專門記錄兩個實體多對多關係的資料表（Junction Table）。
@term 組合主鍵
由多個欄位共同組成、合起來必須唯一的主鍵（Composite Primary Key）。
@term ON DELETE CASCADE
刪除父資料時，自動連帶刪除所有指向它的子資料。
@term ON DELETE RESTRICT
只要還有子資料指向它，就禁止刪除父資料。
@term 軟刪除
不真正刪除資料，而是用欄位標記為停用，以保留紀錄（Soft Delete）。
@term upsert
有就更新、沒有就新增的操作，PostgreSQL 用 INSERT ... ON CONFLICT 實現。
